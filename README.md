# sf-tools — Salesforce 開発自動化ツールキット

> **この README は概要です。** 詳しい使い方・管理者向けの手順・コマンドの説明は、**[文書サイト](https://tama-create.github.io/sf-tools/)** にあります（手元では、`site/index.html` をブラウザで開いても読めます）。

---

## 1. sf-tools とは

Salesforce の変更を、**安全に、決まった手順で、本番に届ける**ための道具です。

「変更を作る → 確かめる → 本番に反映する」という毎日のくり返しを、コマンドと自動の仕組みに任せられます。変更は、本番に出る前に、自動でチェックされます。うっかりミスや、反映のし忘れを防げます。

- 🔑 **最初の準備**は、プロジェクト管理者（セットアップ担当の方）が、1 回だけ行います。
- 💻 **毎日の作業**で使うのは、おもに開発者です。
- 👀 業務担当の方が、コマンドを使う必要は、ほとんどありません。Slack に届く結果の通知を見る形で、関わります。

しくみは、シェルスクリプト（コマンド）の集まりです。パソコンの `~/sf-tools` に置いて、各プロジェクト（`force-*` フォルダ）から呼び出します。変更の検証とリリースは、GitHub Actions（GitHub 上の自動処理）が行います。

---

## 2. できること

- **プロジェクトの立ち上げ（管理者）:** `sf-init.sh` が、必要な準備をまとめて行います。対話しながら進めます。GitHub のリポジトリ（ファイルの保管場所）の作成、Salesforce の組織への接続、ブランチ（変更を分けて進めるための枝）の構成、認証情報の登録、本番ブランチの保護までを行います。
- **毎日の開発（開発者）:** `sf-job.sh` で作業を始めます（ブランチの作成から VS Code の起動まで自動です）。`sf-push.sh` で変更を GitHub に送り、`sf-next.sh` で、次に PR（変更を取り込む依頼）を出す先を確認します。
- **安全なリリース:** まず dry-run（実際には反映せず、「反映できるか」だけを確かめること）が基本です。git のフックと GitHub Actions が、次の 3 つを自動で行います。ターゲットファイル（何を反映するかを書いたファイル）の確認、マージの順序の確認、保護ブランチへの直接の変更の防止です。
- **メタデータの同期:** Salesforce の組織の最新の状態を、定期的に、Git の `main` に取り込みます。
- **Windows と Mac で動きます。** 追加のインストールは、要りません（Windows は Git Bash、Mac は標準のターミナルを使います）。

言葉が分からないときは、文書サイトの「用語集」を見てください。

## 3. 前提条件

次のコマンドが使えることが前提です。入れ方は、文書サイトの「前提条件とインストール」にあります。

| ツール | 確認コマンド | 用途 |
|---|---|---|
| Git（Windows は Git Bash） | `git --version` | 変更の履歴の管理・フック |
| Salesforce CLI（**npm 版**） | `sf --version` | 組織への接続・反映・取得 |
| GitHub CLI | `gh --version` | PR の作成・認証情報の登録 |
| Visual Studio Code | `code --version` | エディタの起動 |
| Slack | — | リリース結果の通知を受け取る |

> ⚠️ **Salesforce CLI は npm 版**（`npm install -g @salesforce/cli`）を使ってください。Windows の Git Bash で、公式インストーラー版を使うと、`sf` は成功しても終了コード 1 を返します。そのため、sf-tools の処理が、失敗として扱われます。Windows は、Git Bash で実行します（PowerShell・コマンドプロンプトは使えません）。

### 3.1 動作環境

実際に動かして確かめた環境だけを書いています。

| 環境 | 使う場面 | 確認した内容 |
|---|---|---|
| **Windows**（Git Bash） | 手元のパソコン（開発者・管理者） | ✅ 自動テストに合格。さらに、実際の GitHub と Salesforce で、初期セットアップから、リリースと削除まで、通しで動かして確認しました |
| **Mac**（macOS） | 手元のパソコン | ✅ 同じ確認を、Mac mini の実機で行いました |
| **WSL**（Windows の中で動く Ubuntu） | 手元のパソコン | ✅ 同じ確認を行いました |
| **Linux**（GitHub Actions のサーバー） | 自動で動く部分（人は触りません）: 変更の検証・Salesforce へのリリース・メタデータの同期 | ✅ 実際の Salesforce に対して、検証・リリース・同期が成功することを確認しました |

- 確認に使った Salesforce は、**Developer Edition**（開発者向けの無料の組織）です。ほかのエディション（Enterprise など）や Sandbox では、確認していません。
- 自動テストは、GitHub 上で、変更のたびに自動で実行されます。Linux・Mac・Windows の 3 つの環境で、合格しています。
- Linux のパソコンを、手元で使うことは、想定していません（Linux は、自動で動くサーバーとしてだけ使います）。WSL は、Windows の中で動くので、手元で使えます。
- Mac は、標準のターミナル（zsh）と標準の Bash のままで動きます（Bash の入れ直しは要りません）。
- いつ、どの環境で確認したかの記録は、開発者向けの資料（`doc/dev-reference.md` の 9.7）にあります。

## 4. はじめかた

```bash
# 1. sf-tools を置く
git clone https://github.com/tama-create/sf-tools.git ~/sf-tools

# 2. PATH を通す（どこからでも、コマンド名だけで呼べるようにする）
#    Windows（Git Bash）・Linux は ~/.bashrc、Mac（zsh）は ~/.zshrc に、次の 1 行を追加
export PATH="$HOME/sf-tools/bin:$PATH"
```

- **管理者**は、作業フォルダで `sf-init.sh` を実行して、プロジェクト（`force-XXXX`）を作ります。
- **開発者**は、作業フォルダで `sf-job.sh` を実行して、作業を始めます。ブランチの名前を入力すると、作業用のコピーの準備から、VS Code の起動までが進みます。

詳しい手順は、文書サイトの「使い方ガイド」（開発者向け）と「管理者ガイド」にあります。

## 5. コマンド早見表

どのコマンドも `--help` を付けると、概要・オプション・処理の流れを表示できます。🔑 は**管理者専用**のコマンドです（実行すると、警告と確認が出ます）。⚠️ は、使うときに注意が必要なコマンドです。

| 対象 | コマンド | 用途 |
|---|---|---|
| 開発者 | `sf-job.sh` | 新しい作業を始める（ブランチの作成から VS Code の起動まで） |
| 開発者 | `sf-start.sh` | 開発環境を起動する（作業の再開） |
| 開発者 | `sf-push.sh` | 変更をコミットして、GitHub に送る |
| 開発者 | `sf-next.sh` | 次に PR を出す先を確認する |
| 開発者 | `sf-check.sh` | ターゲットファイル（`deploy-target.txt` など）の書き方を確認する |
| 開発者 | `sf-dryrun.sh` / `sf-release.sh` | 反映できるかを確かめる（dry-run）/ 確かめて、反映する |
| 開発者 | `sf-deploy.sh` | ⚠️ 自分用の組織へ、強制的に反映する（共有環境には、使えません） |
| 開発者 | `sf-restart.sh` | 接続先の組織を切り替える |
| 開発者 | `sfl`（`sf-launcher.sh`） | 上のコマンドを、メニューから選んで実行する |
| 開発者 | `sf-hook.sh` / `sf-unhook.sh` | 手元のクローンの検証フックを、有効にする / 削除する |
| 管理者 | 🔑 `sf-init.sh` | 新しいプロジェクトを作る。段階の追加（`--add-tier`）・診断（`--status`）・接続先の付け替え（`--reconnect`）・動作の確認（`--verify`）も |
| 管理者 | 🔑 `sf-update-secret.sh` | GitHub の認証情報（Secrets / Variables）を登録し直す |
| 管理者 | 🔑 `sf-sync-wf.sh` | 作成済みのワークフローを、最新の雛形に合わせて更新する |
| 管理者 | 🔑 `sf-typecheck.sh` | 個人用の組織で、メタデータの種類ごとに、リリースと削除ができるかを確かめる |
| 自動 | `sf-install.sh` / `sf-upgrade.sh` / `sf-prepush.sh` / `sf-precommit.sh` / `sf-metasync.sh` | ほかのコマンド・git のフック・GitHub Actions から、自動で動く |

## 7. 設計方針

- シンプルなコマンドで、毎日の作業を自動化する。
- 失敗したときは、ログで原因を追いやすくする。
- 追加の依存を減らし、Git Bash（Windows）・macOS（標準の Bash 3.2）・Linux（GitHub Actions の Ubuntu）で、同じように動く構成を保つ。
- まず dry-run を基本にし、必要なときだけ本番に反映する。
- Bash 3.2 以上で動かす（macOS 標準の `/bin/bash` のまま、追加のインストールなしで使えるようにするため。Bash 4 以降の機能は使わない）。
