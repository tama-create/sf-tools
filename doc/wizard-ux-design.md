# ウィザード形式への全面見直し（設計書）

> **ステータス: 設計（外部レビュー反映済み）。段階 S1 は実装済み（共通部品 `lib/wizard.sh`・開始画面・ステップの見出し・完了画面・sf-tools の自動更新）。S2 以降は未実装**
> 対象: `sf-init.sh`（最優先）、続いて他のコマンド（sf-start / sf-job / sf-next / sf-deploy / sf-release / sf-metasync / sf-update-secret / sf-sync-wf）
> 外部レビュー（Codex）の指摘と、その対応は、10 章。

---

## 1. 目的と判断基準

### 1.1 目的

**指示のとおりに操作すれば、迷わず、最後まで設定が完了する**こと。利用者がポチポチと選んでいくだけで終わる、ウィザード形式にする。

### 1.2 合否の基準（これが満たせなければ不合格）

利用者が、使っている最中に、次のどれかを思ったら、それは**設計の不具合**である。

| 利用者の疑問 | 設計が満たすべきこと |
|---|---|
| 「いま、どこ？」 | すべての画面に、現在地（全体のうち、いくつ目か）を出す |
| 「これは、何？」 | 画面の先頭に、このステップが何のためかを、1 文で出す |
| 「次は、何をすればいい？」 | 利用者の操作を、1 画面に 1 つだけ、はっきり書く |
| 「このあと、どうなる？」 | 操作のあとに起きることを、先に書く |
| 「どれを選べばいい？」 | 推奨を先頭に示し、迷う選択肢は、そもそも出さない |
| 「固まった？」 | 待ち時間は、「何を待っているか・最大どのくらいか」を出す |
| 「失敗した。どうすれば？」 | 何が起きたか／どう直すか／どこから再開されるか、を出す |
| 「終わった？次は？」 | 完了画面に、できたことと、次にやることを出す |

## 2. 現状の問題（洗い出し）

`sf-init.sh` の、利用者の操作・待ち時間の箇所を、コードで確認した結果。「状態」は、この設計書の時点のもの。

| # | 場所（根拠） | 問題 | 状態 |
|---|---|---|---|

## 3. 設計原則

| # | 原則 | 具体的なルール |
|---|---|---|
| R1 | **全体像を最初に** | ステップの一覧・所要時間の目安・事前に用意するもの（必要な権限・組織の数も）を、最初に出す。準備ができてから、始める |
| R2 | **現在地を常に** | すべての画面の先頭に `ステップ 3 / 8: ○○` と、完了済みを出す |
| R3 | **1 画面に 1 つの操作** | 利用者の操作は、1 画面に 1 つ。「やること」と「そのあと起きること」を、書く。複数の操作が要るときは、画面を分ける |
| R4 | **利用者に判断させない** | 検出できるもの・既定が決まるものは、聞かない。判断が必要なときは、推奨を先頭にして、Enter で推奨を選べるようにする |
| R5 | **言葉を平易に** | 専門用語は、はじめに 1 度だけ説明する。内部の呼び名（Phase・ECA・JWT）は、画面に出さない |
| R6 | **操作の語彙を統一** | `Enter` = 次へ／`番号` = 選択／`q` = 中断。画面の下に、毎回、操作のヒントを出す |
| R7 | **待ち状態を明示** | ブラウザで作業するときは、「何の画面が出ていれば合っているか」「何をするか」「終わったら何を押すか」を書く。**時間制限があれば、先に書く**（P15） |
| R8 | **待ち時間を明示** | 数十秒以上かかる処理は、「何を待っているか・最大どのくらいか・いま何回目か」を出す（P16） |
| R9 | **失敗の三点セット** | 何が起きたか／どう直すか／**どこから再開されるか（再開の単位を、正確に）**。（`die` は、既存規約どおり事実のみ。案内は、直前の `log` で出す） |
| R10 | **完了画面** | できたこと／次にやること（具体的なコマンド・URL）を出す。実際に設定できたものだけを書く |
| R11 | **やり直せる** | 中断しても、再実行で、続きから再開できる。各ステップは、冪等にする |
| R12 | **機密を見せない** | Token 等は、画面・ログに出さない（既存規約） |

## 4. sf-init のウィザード設計

### 4.1 ステップ一覧（内部の Phase との対応。表示と実行順は一致させる）

利用者に見せるステップは **8 つ**。ただし、ステップ 8（Salesforce の接続）は、組織の数だけ、画面（小ステップ）に分ける（4.4 (6)）。内部の Phase 番号は、画面に出さない。

| 表示 | 内部 Phase | 利用者の操作 |
|---|---|---|
| 1 / 8 準備の確認 | 1 | 自動 |
| 2 / 8 プロジェクトの確認 | 2 | Enter |
| 3 / 8 リポジトリの作成 | 3・4 | 自動（完了を 1 行で表示） |
| 4 / 8 ブランチの構成 | 5 | 番号選択（推奨が既定） |
| 5 / 8 GitHub の Token | 6 | ブラウザで 1 クリック → 貼り付け |
| 6 / 8 Slack の通知 | 7 | ブラウザ操作 → 貼り付け ×2 → 招待（画面を 3 つに分ける） |
| 7 / 8 リポジトリの設定 | 8・9 | 自動 |
| 8 / 8 Salesforce の接続 | 10 | 組織ごとに、ブラウザでログイン（本番／Sandbox は、既定を提示） |

### 4.2 開始画面（R1）

```
══════════════════════════════════════════════
  新しい Salesforce プロジェクトを作ります
══════════════════════════════════════════════

  作るもの   : tamashimon-org/force-yamada（GitHub のリポジトリ）
  かかる時間 : 30〜60 分ほど（ブラウザでの作業・Salesforce の反映待ちを含みます）
               ※ 仮の値。実機で測って、確定します

  【先に、用意してください】
    □ GitHub : tamashimon-org の管理者としてログインしたブラウザ
    □ Slack  : 通知用の「共有チャンネル」（全員が参加するもの）
               まだなければ、いま Slack で作ってください
    □ Salesforce : 接続する組織の、システム管理者のアカウント
               ブランチの構成で選ぶ数（1〜3 組織）だけ、必要です

  【これから行うこと】
    1. 準備の確認   2. プロジェクトの確認   3. リポジトリの作成
    4. ブランチの構成   5. GitHub の Token   6. Slack の通知
    7. リポジトリの設定   8. Salesforce の接続

  ▶ 用意ができたら Enter を押してください（q で中断）
```

- 管理者向けの警告（既存の赤いボックス）と、「続行しますか？」は、**この画面に統合**する（P13）。
- 前回の途中までの状態が残っている場合は、この画面の前に、「続きをやる／最初からやり直す」を出す（実装済み）。
- sf-tools が古い場合は、管理者向けの警告のあと、確認の前に、**確認のうえ更新し、自動で、もう一度、はじめから実行する**（P14）。実行しなおしたあとも、警告と確認は、毎回出す（確認を飛ばさない）。

### 4.3 各ステップの共通の見た目（R2・R3・R6）

```
──────────────────────────────────────────────
  ステップ 5 / 8: GitHub の Token を作ります
  （完了: 準備の確認・プロジェクト・リポジトリ・ブランチ）
──────────────────────────────────────────────

  ○○のために、必要です。（1 文）

  ▶ あなたがやること
      1. …
      2. …

  ▶ そのあと
      この画面に戻って、貼り付けて、Enter を押してください

  [Enter] 次へ   [q] 中断
```

- 自動のステップは、「ステップ n / 8: ○○ ... ✔ 完了」の 1 行に集約する（画面を埋めない）。
- ブラウザを使うステップは、R7 に従い、「ブラウザに、○○の画面が出ます。**そこで、やること**」を、箇条書きにする。

### 4.4 主要な画面の設計

**(1) ステップ 2（プロジェクトの確認）**: Y/N を聞かず、内容を見せて Enter のみ。誤りの原因は、フォルダ名であることを書く。

```
  次の内容で、作ります。
    GitHub のリポジトリ : tamashimon-org/force-yamada
    作る場所             : ~/home/tamashimon-org/yamada/init/force-yamada

  フォルダの名前から決めています。違う場合は q で中断して、
  正しいフォルダに移動してから、もう一度、実行してください。

  [Enter] この内容で進む   [q] 中断
```

**(2) 環境種別（本番／検証）（P4）**: 一般の利用者には**聞かない**。既定は「本番環境」。sf-tools の開発者が検証環境を使うときだけ、環境変数 `SF_TOOLS_BRANCH=development` で指定する（既存の仕組み）。検証環境のときだけ、開始画面に「検証環境（開発者用）で実行します」と表示する。

**(3) ステップ 4（ブランチの構成）（P5）**: 推奨を先頭に、言葉をやさしく。選んだあとに、**必要な Salesforce の組織の数**を、はっきり出す。

```
  ブランチの構成（コードを、段階的に確認してから、本番に出す流れ）

    [1] 3 段階（開発 → 検証 → 本番）   ← おすすめ
         Salesforce の組織が 3 つ（本番・検証用 Sandbox・開発用 Sandbox）
    [2] 2 段階（検証 → 本番）
         Salesforce の組織が 2 つ（本番・検証用 Sandbox）
    [3] 1 段階（本番のみ）
         Salesforce の組織が 1 つ。少人数・1 人で開発する場合

  迷ったら 1 を選んでください。後から、増やすこともできます。
  [Enter] 1 を選ぶ   [2] [3] 他を選ぶ   [q] 中断
```

**(4) ステップ 5（Token）**: 実装済みの内容（ブラウザをすぐ開く・Note と Scopes を入力済みの作成ページ・貼り付けても表示されない旨・失敗の理由と直し方）を、共通の見た目に入れる。

**(5) ステップ 6（Slack）（P3・P9）**: 開始画面で、チャンネルの事前準備を案内済み。画面を 3 つに分ける（Bot Token の取得 → チャンネル ID → Bot の招待）。各画面に、「いま、Slack のどの画面を開いているか」の目印を書く。

**(6) ステップ 8（Salesforce の接続）（P6・P7・P15・P16）**: **組織ごとに、画面（小ステップ）を分ける**（「8 / 8 の 1: 本番の組織」「2: 検証用の組織」「3: 開発用の組織」）。

- アプリ種別は、**聞かない**（既定は「外部クライアントアプリ」）。従来の接続アプリは、オプション `--legacy-connected-app` を付けた場合のみ（仕様は 4.6）。
- 本番／Sandbox は、**ブランチの階層から既定を決めて、提示する**（1 つ目＝本番、2 つ目以降＝Sandbox）。Enter で、既定を使う。

```
  ステップ 8 / 8 の 2: 検証用の Salesforce 組織につなぎます

  ▶ この組織は、どちらですか？
      [1] Sandbox（テスト用の組織）   ← 一般的です
      [2] 本番（業務で使っている組織）
  [Enter] 1 を選ぶ

  ▶ あなたがやること
      1. ブラウザに、Salesforce のログイン画面が出ます
      2. この組織の、システム管理者のユーザーで、ログインして、「許可」を押す
         ※ 2 分以内に、ログインしてください（時間切れになります）
  ▶ そのあと
      自動で、接続の設定を行います（反映待ちを含めて、数分かかります）
```

  - 反映待ちの間は、「Salesforce の反映を待っています（3 / 20 回目・最大 約 10 分）」のように、進み具合を出す（R8）。
  - ログイン後、実際の組織の種類（Sandbox／本番）を、`sf org display --json` で確認し、**選択と食い違っていれば警告して、確認する**（ログイン先 URL は、ログイン前に決める必要があるため、判定は、事後の検証にのみ使う）。

**(7) 完了画面（R10）**:

```
══════════════════════════════════════════════
  できました: tamashimon-org/force-yamada
══════════════════════════════════════════════

  設定したもの : GitHub リポジトリ / Token / Slack 通知 / Salesforce 接続（3 組織）

  【次にやること】
    1. 開発する人に、次のコマンドを伝えてください
         sf-start.sh        （作業フォルダ: ~/home/tamashimon-org/yamada/）
    2. リポジトリを見る:
         https://github.com/tamashimon-org/force-yamada

  詳しい使い方: README.md の 4. を見てください
```

### 4.5 失敗の画面（R9・R11）

再開の単位は、**内部の Phase の先頭**（表示のステップの先頭）である。画面は、そのとおりに書く。

```
  ✖ うまくいきませんでした（ステップ 5 / 8: GitHub の Token）
     原因 : この Token には「workflow」の権限がありません

  【直し方】 作成ページで、workflow にチェックが入っていることを確認して、
             作り直してください。
  【やり直し】 もう一度 sf-init.sh を実行し、「続きをやる」を選ぶと、
               ステップ 5 / 8 の最初から、再開します。
               （ここまでの内容は、保存されています）
```

- ステップ 6（Slack）の途中で失敗した場合は、「ステップ 6 / 8 の最初から」と書く（途中の小画面からは、再開しない。登録は、上書きできるため、問題ない）。
- Token は、再開のために、`init/.sf-init.env`（権限 600）に、ステップ 5 からステップ 7 の完了まで残る。完了時に削除する（既存の仕様）。「最初からやり直す」を選ぶと、状態ごと消える。再入力を求めると、利用者の手間が増えるため、再入力は求めない。

### 4.6 `--legacy-connected-app` の仕様

| 項目 | 内容 |
|---|---|
| 指定方法 | `sf-init.sh --legacy-connected-app`（新規実行・`--resume N` のどちらでも指定できる） |
| 動作 | Phase 10 のアプリ種別を、「接続アプリケーション（1）」にする。従来の手動手順（Connected App の作成案内・コンシューマー鍵とユーザー名の入力）に、そのまま入る |
| 保存 | 選んだ種別は、`APP_TYPE` として `.sf-init.env` に保存する（既存の仕組み）。続きから再開するときは、保存した種別を使い、オプションの再指定は要らない |
| 既定 | 指定がなければ、外部クライアントアプリ（2）。`APP_TYPE` が保存されていれば、その値 |
| 無効な組み合わせ | `--legacy-connected-app` と、保存済みの `APP_TYPE=2` が食い違うとき（途中まで ECA で進めたあと）は、中断して、事実を表示する |
| ヘルプ | `--help` と、不明なオプションのメッセージに、追記する |
| テスト | 既定の経路（ECA）と、`--legacy-connected-app` の経路を、別々のシナリオにする |

## 5. 共通部品（lib の設計）

画面の見た目を、コマンドごとに作らず、**共通の部品**で出す。

| 関数（案） | 役割 |
|---|---|
| `wizard_begin <タイトル> <ステップ名…>` | 開始画面（全体像・事前準備・ステップ一覧）を出し、Enter を待つ |
| `wizard_step <番号> <タイトル> <目的の 1 文>` | ステップの見出し（現在地・完了済み）を出す |
| `wizard_do <手順…>` | 「あなたがやること」を、番号付きで出す |
| `wizard_next <説明>` | 「そのあと」を出す |
| `wizard_choose <変数> <推奨> <選択肢…>` | 推奨つきの選択（Enter で推奨） |
| `wizard_wait_browser <URL> <確認する目印> [制限時間]` | ブラウザを開き、目印・制限時間を出す。ブラウザが開かないときのために、URL も出す |
| `wizard_progress <説明> <n> <最大>` | 待ち時間の進み具合（R8） |
| `wizard_auto <説明>` | 自動のステップの 1 行表示（完了を `✔`） |
| `wizard_fail <原因> <直し方> <再開の方法>` | 失敗の三点セット |
| `wizard_done <できたこと> <次にやること…>` | 完了画面 |

- 既存の `read_key` / `press_enter` / `read_secret` などの入力関数を、中で使う（独自実装はしない）。操作の語彙と、画面の下のヒントは、この部品だけが決める。
- 表示は標準エラー出力（既存の `log` と同じ）。ログファイルには、色・記号を除いて記録する（既存の仕組み）。
- **Windows の Git Bash を、最優先の動作環境にする**: 新しい外部コマンドを増やさない。ブラウザ起動は、既存の `open_browser`（失敗しても、URL を表示するため、止まらない）。色は、既存の `CLR_*` 変数（端末でないときは空）。罫線・記号は、既存の警告ボックスと同じ種類の文字のみ使う。EOF（標準入力の終了）は、既存の入力関数と同じく中断として扱う。

## 6. 他のコマンドへの展開

優先順位は、「誤操作の影響（危険度）」「利用頻度」「入力の複雑さ」の 3 軸で決める。

| 順 | コマンド | 理由 | 見直す内容 |
|---|---|---|---|
| 1 | sf-init | 初見の利用者が、必ず通る。入力が最も多い | 本設計の全面適用 |
| 2 | sf-deploy / sf-release / sf-metasync | **本番に影響する**。確認の不足は、安全性に直結する | 確認の直前に、「何が起きるか」（影響）を、定型で出す。確認の語彙を統一する |
| 3 | sf-start | 毎日使う。初回に迷う | 組織のエイリアスを、一覧（`sf org list`）から選べるようにする。接続済みの組織の自動検出。初回の説明 |
| 4 | sf-job | 毎日使う | ジョブ名の書式と例を、入力の直前に出す。作ったあとの「次にやること」を出す |
| 5 | sf-next / sf-push / sf-sync-wf | 実行後の案内 | 「次にやること」を、定型で出す |
| 6 | sf-update-secret | 利用頻度が低い。入力が多い | 全体像と現在地を出す |

> 全コマンド共通の最低ライン: **終了時に、「できたこと」と「次にやること」を 1 行以上出す**。

## 7. 検証計画

| # | 検証 | 方法 |
|---|---|---|
| V1 | 画面の必須要素 | 各ステップの出力に、現在地・目的・やること・次、が含まれるかを、自動テストで確認する。比較の前に、色・記号・改行コードを正規化する |
| V2 | 入力の流れ | 台本（標準入力）を、**シナリオごとに分けて**管理する（通常・途中で失敗・再開・q で中断・1/2/3 階層・`--legacy-connected-app`）。各シナリオで、期待するステップの見出しが、順に出ることを確認する（入力の位置だけを見る検証にしない） |
| V3 | 失敗・再開 | 各ステップで失敗させ、三点セットが出ること、続きから再開できることを確認する |
| V4 | 外部レビュー | 本設計書（済）と、各段階の実装後のコード・画面を、Codex にレビューさせ、指摘を反映する |
| V5 | 実機 | **Windows の Git Bash**（最優先）で、検証環境（`SF_TOOLS_BRANCH=development`）の `sf-init` を、初見の操作として、通しで実行する（利用者による確認）。ブラウザが開かない場合の表示も確認する |
| V6 | 「迷い」の確認 | 利用者が、1.2 の疑問を持たずに、最後まで進めたか。持った箇所は、設計の不具合として、直す |
| V7 | 所要時間の測定 | 1・2・3 階層ごとに、実機で測り、開始画面の値を確定する |

## 10. 外部レビュー（Codex）の指摘と対応

レビュー実施: 2026-10-11。設計書（初版）を、コードと照らして評価させた。

| # | 指摘の要約 | 判断 | 対応 |
|---|---|---|---|
| 1 | Phase 10 は、組織ごとに、複数の入力・ログインがあり、「1 画面 1 操作」「8 ステップ」と、矛盾する | **採用** | ステップ 8 を、組織ごとの小ステップに分けた（4.1・4.4 (6)）。本番／Sandbox の既定、ログイン先、時間制限を、明示した |
| 2 | `--legacy-connected-app` は、実装に存在せず、仕様が未定義 | **採用** | 仕様を定義した（4.6）。既存のコードに、このオプションは無く、実装時に追加する旨を、明記した |
| 3 | Sandbox の自動判定は、ログイン先を決めるために、ログイン前の情報が要る | **採用** | 事後の判定に、役割を限定し、ログイン前は、階層からの既定を使う（Q3・4.4 (6)） |
| 4 | 再開の単位は Phase の先頭で、表示のステップ・小画面とは、一致しない。Token の残存期間も長い | **一部採用** | 再開の単位を、正確に書くことにした（4.5）。Token の**再入力は不採用**（Q7）。利用者の手間が増え、R4 に反する。権限 600・完了時に削除（既存の仕様）を、明記した |
| 5 | 開始画面の事前準備が、実際の必要条件を網羅していない | **採用** | 権限・組織の数を追加した（4.2）。階層を選んだ後に、必要な組織の数を、再度出す（4.4 (3)） |
