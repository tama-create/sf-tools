🔐 認証情報（Secrets / Variables）

GitHub 上の自動処理が、Salesforce や Slack に接続するときに使う、認証情報（パスワードの代わりになる情報）のページです。sf-init.sh が登録するものの一覧と、あとから登録し直す sf-update-secret.sh の使い方を説明します。

使い分け

認証情報は、隠すべきかどうかで、2 種類に分けて登録します。Secret は、GitHub が暗号化して、人にも見えないように保管します。Variable は、見えても問題のない設定です。

項目種別説明
SF_PRIVATE_KEYSecretJWT 署名用の RSA 秘密鍵
SF_CONSUMER_KEY_*Secret外部クライアントアプリ（従来の接続アプリケーション）のコンシューマーキー。アプリを見分けるための ID のようなものです
PAT_TOKENSecretGitHub の Personal Access Token（Classic。repo・workflow）。force-* のリポジトリの、オーナー（組織の管理者）のもの。sf-tools（公開リポジトリ）とは、関係ありません
SLACK_BOT_TOKENSecretSlack Bot のアクセストークン
SF_USERNAME_*VariableSalesforce のユーザー名（平文で問題ありません）
SF_INSTANCE_URL_*VariableSalesforce のインスタンス URL（平文で問題ありません）
SF_ORG_ID_* / SF_ORG_NAME_* / SF_ORG_KIND_* / SF_ORG_CHECKED_*Variable接続した組織の ID・名前・種類（本番 / Sandbox など）・確認した日時。接続のテストで組織の ID を読み取れたときに、自動で保存します（--status の一覧に使います）
SLACK_CHANNEL_IDVariable通知先の Slack チャンネル ID（平文で問題ありません）
SF_TOOLS_BRANCHVariableActions が clone する sf-tools のブランチ。検証環境で sf-init.sh を、環境変数 SF_TOOLS_BRANCH=development 付きで実行したときだけ、development を登録します。未設定なら main

* の部分は、段階（組織）ごとに変わります。main は PROD、staging は STG、develop は DEV です（例: SF_USERNAME_PROD）。

SF_TOOLS_TOKEN は不要です

sf-tools は公開リポジトリのため、wf-metasync / wf-validate / wf-release は、Token なしで sf-tools を clone します。以前のバージョンにあった、Token（SF_TOOLS_TOKEN）の作成・登録は、ありません。

以前のバージョンで作ったプロジェクトに、SF_TOOLS_TOKEN が登録されていても、そのままで構いません。ただし、そのプロジェクトのワークフローが Token 付きで clone している間は、その Token を無効にしないでください（無効な Token では、公開リポジトリでも clone に失敗します）。ワークフローを新しい雛形（Token なし）に更新したあとなら、Token と Secret を削除して構いません（ワークフローの更新）。

再登録する（sf-update-secret.sh）

sf-update-secret.sh

GitHub の JWT 認証情報を、まとめて登録し直します。JWT の秘密鍵を更新するときなどに使います。force-* フォルダの中で実行してください。

管理者専用

実行の前に、赤い警告ボックスと確認が表示されます。

機密情報（Secret）と、平文の設定値（Variable）を、それぞれ適切な方法で登録します。

  • Secret: SF_PRIVATE_KEY / SF_CONSUMER_KEY_*（gh secret set）
  • Variable: SF_USERNAME_* / SF_INSTANCE_URL_*（gh variable set）

主な処理

  1. git remote から、対象のリポジトリ（OWNER/REPO）を、自動で取得する

  2. gh の認証ユーザーと、リポジトリのオーナーが、一致するかを確認する

  3. メインメニューで、操作を選ぶ（秘密鍵の更新 / コンシューマーキーの更新 / ユーザー名の更新 / すべて更新）

  4. 組織の選択は、branches.txt の構成（PROD / STG / DEV）に合わせて、変わる

  5. gh secret set / gh variable set で、それぞれ更新する

補足

  • ユーザー名（SF_USERNAME_*）は、現在の登録値を、自動で取得して表示します。
  • メニューは、1 秘密鍵 / 2 コンシューマーキー / 3 ユーザー名 / 4 すべて（q で中断）です。選べる組織は、branches.txt の行数で決まります（1 行: PROD / 2 行: ＋STG / 3 行以上: ＋DEV）。
  • 接続のテストを行うもの・行わないもの: 秘密鍵（メニュー 1）は、接続のテストなしで登録します。メニュー 4 も、最初に秘密鍵を登録します（接続のテストより前です）。コンシューマーキーとユーザー名は、接続のテストに成功してから登録します。テストに失敗したら中断します。それより前に登録した値は、そのまま残ります。
  • ログイン先は、login.salesforce.com / test.salesforce.com（Enter の既定）/ 組織の URL（My Domain）から選びます。メニュー 4 では、選んだ URL を SF_INSTANCE_URL_* として登録します。メニュー 2・3 では、接続のテストにだけ使い、登録しません。
  • 本番組織のガード: STG・DEV に、本番組織、または種類を判定できない組織を接続しようとすると、登録する前に中断します。
  • 確認で N と答えて、何も登録しなかったときも、「更新が完了しました」と表示されます。
  • JWT の接続テストは、一時的なホームフォルダの中で実行します。あなたの sf に、エイリアス（prod など）が増えたり、同じユーザーの既存のログインが置き換わったりしません（sf-init.sh の接続テストも同じです）。
PAT_TOKEN は、このコマンドでは更新できません

sf-update-secret.sh は、JWT の認証情報のためのコマンドです。PAT_TOKEN は、扱えません。Token を無効にしたり、有効期限が切れたりしたときは、新しい Token を発行します。そして、リポジトリの Secrets の PAT_TOKEN を登録し直してください（トラブルシューティング）。
