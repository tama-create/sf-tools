🤖 自動実行コマンド

ほかのコマンドや、git のフック、GitHub Actions が、自動で呼び出すコマンドです。自分で実行することは、ほとんどありません。「裏で何が動いているのか」を知りたいときに、読んでください。全体の一覧は、コマンド一覧にあります。

sf-install.sh

sf-install.sh

sf-tools 自体の更新と、プロジェクト側の準備（Git フック・リリース用フォルダなど）を行います。通常は、sf-start.sh がバックグラウンドで、sf-init.sh が Phase 4 で、自動で実行します。force-* フォルダの中で、単独でも実行できます。

主な処理（この順序）

  1. sf が動くかを確認する（動かなくても、警告だけで、続けます）
  2. ~/sf-tools の現在のブランチを、git pull で最新にする（失敗しても続行。sf-init.sh から呼ばれたときは行わない）
  3. 設定ファイル（sf-tools/config/metadata.txt と branches.txt）を確認する。通常の実行で、どちらかがなければ中断します（プロジェクトの破損として扱い、作りません）。sf-init.sh から呼ばれたときだけ、雛形からコピーします
  4. Git フック（pre-commit と pre-push）を、sf-hook.sh でインストールする
  5. release/<ブランチ名>/ を準備する（main ブランチでは、作りません）
  6. （sf-init.sh から呼ばれたときだけ）コミットメッセージの雛形（.gitmessage）を置く
  7. npm install（package.json があるとき。node_modules が package-lock.json 以降に更新済みなら省略）
  8. 前回から 24 時間以上たっていれば、sf-upgrade.sh をバックグラウンドで実行する

手順 3 以外の失敗は、警告を表示して続行します。ワークフロー（.github/workflows/）は、扱いません。作成済みのプロジェクトへの反映は、sf-sync-wf.sh（管理者が手動で実行）が行います。

sf-upgrade.sh

sf-upgrade.sh

npm と Salesforce CLI（sf）を、最新版に更新します。Git は、Windows の Git Bash でだけ更新します（macOS・Linux・WSL では実行せず、パッケージマネージャーで更新するよう案内します）。sf-install.sh から、前回から 24 時間以上たっているときに、バックグラウンドで自動で実行されます。手動でも実行できます。

  • どの手順が失敗しても、警告を表示して続行し、最後に「すべてのアップデートが完了しました」と表示します。
  • sf は、npm 版なら npm install -g @salesforce/cli@latest、それ以外（公式インストーラー版など）なら sf update で更新します。

sf-prepush.sh

git push の前に自動で実行される、チェックのスクリプトです（pre-push フックの本体）。

主な処理

  1. 次のどちらかなら、プッシュを拒否する（保護ブランチ = sf-tools/config/branches.txt に書かれたブランチ。ファイルがない・空のときは main）。
    • 現在のブランチが、保護ブランチ
    • プッシュ先が、保護ブランチ（git push origin feature:main や、保護ブランチの削除も、拒否します）
  2. sf-check.sh で、ターゲットファイルの構文を検証する（エラーなら中断）
  3. リモートの最新を取得する（現在のブランチと、branches.txt のブランチ）。origin にまだないブランチや、使えない名前は、警告を表示して飛ばします。プッシュは止めません
  4. origin/<現在のブランチ> に未取り込みのコミットがあれば、表示して、git merge で取り込む（失敗したら git merge --abort して中断）
  5. origin/main に未取り込みのコミットがあれば、同じように、git merge で取り込む

補足

  • 取り込みは merge で行います（rebase ではありません）。
  • 構文の検証は、取り込みより前に行います。手順 4・5 で取り込んだ変更は、検証されません。
  • 取り込みをしたとき（merge のコミットを作ったとき）は、そのプッシュを中止します。git は、フックを呼ぶ前に、送るコミットを決めているため、そのままでは、取り込みが含まれないまま、プッシュが成功と表示されるからです。取り込み後に、もう一度プッシュすると、取り込みは済んでいるため、通ります。
  • 中断したときは、終了コード 1 で終わり、プッシュも中止されます。

sf-precommit.sh

git commit のときに自動で実行される、pre-commit フックの本体です。直接実行することはありません。

主な処理

  • sf-check.sh で、ターゲットファイルの構文を確認する
  • エラーがあれば、コミットを中止する

補足

  • 確認するのは、sf-tools/release/branch_name.txt に書かれたブランチのターゲットファイルです。このファイルがないときは、確認せずに成功となり、コミットは続行されます。
  • 確認するのは、作業フォルダにあるファイルです（ステージした内容ではありません）。

sf-metasync.sh

sf-metasync.sh

sf-init で登録した prod エイリアスの組織（本番・Sandbox のどちらでも）から、メタデータを取得して、main にコミットしてプッシュします。Salesforce 組織の内容を正とします。どのブランチから実行しても、main に切り替えて処理し、終わると元のブランチに戻ります。主に、GitHub Actions からの定期実行を想定しています。

管理者専用

実行の前に、赤い警告ボックスと確認が表示されます。GITHUB_ACTIONS=true のときは、確認をスキップして自動で実行します。

役割

  • 組織の最新のメタデータを取得する
  • Git へ反映する
  • 変更があるときだけ、コミットしてプッシュする
  • 変更がなくても、前回のプッシュが失敗して、送れていないコミットが残っているときは、確認のうえで、プッシュだけ行う
  • main へのプッシュは、pre-push フックを通さない（--no-verify。このコマンド専用です。GitHub の保護の設定は、そのまま効きます）
  • プッシュしたときは、branches.txt の main 以外の各ブランチ（staging・develop など）に、main をマージしてプッシュする（こちらのプッシュは、フックを通ります）

処理の流れ

  1. sf の確認。prod エイリアスの組織と、sf-tools/config/metadata.txt があるかを確認する（なければ中断）
  2. 警告を表示して、続行の確認（Y/N）を取る（GitHub Actions の上では、表示も確認もしません）
  3. main に切り替える。追跡中のファイルに未コミットの変更があれば、いったん退避（git stash）する
  4. リモートの最新を取り込む（git pull origin main --rebase）。main に未コミットの変更が残っているときは、中断する
  5. 差分を解析する（sfdx-git-delta のプラグインが必要）
  6. 組織からメタデータを取得する（差分の分と、metadata.txt の全種類）
  7. 変更があれば、一覧を表示して確認を取り、コミットしてプッシュする。変更がなく、前回のプッシュが残っていれば、プッシュだけ行う。どちらもなければ、「変更はありませんでした」と表示して終わる
  8. プッシュしたときだけ、ほかのブランチへ伝える。リモートにないブランチは、警告を出して飛ばします。伝えるのに失敗したブランチも、警告を出して飛ばし、次へ進みます
  9. 終了時（中断したときも）、元のブランチに戻り、退避した変更を戻す

補足

  • 終了コードは、成功（同期した・変更がなかった）が 0、中断が 1 です。
  • 未コミットの変更の判定と退避は、追跡中のファイルだけが対象です。手元で実行したときは、追跡していない（新しい）ファイル（.gitignore の対象を除く）があると、同期のコミットに無関係なファイルが含まれてしまうため、処理の途中で中断します。GitHub Actions 上では、確認しません。
  • 完了のメッセージには、実際に伝播できたブランチだけが表示されます。リモートにない・失敗したなどでスキップしたブランチは、警告で一覧されます（終了コードは 0 のままです）。

取得するメタデータの種類（sf-tools/config/metadata.txt）

取得する種類は、各プロジェクトの sf-tools/config/metadata.txt で決まります（sf-init が、雛形から作ります）。設定ファイルだけで調整でき、コードの変更は要りません。

前提

雛形の標準セットは、Developer Edition（Sales・Service の標準機能つき）でのみ、リリースと削除を確認しています。ほかのエディション・製品（Service Cloud・Experience Cloud・業種クラウドなど）で使う場合は、必要な種類を足してください。

区分既定内容
1. 標準セット有効Developer Edition で、リリース・削除を確認済み（Apex・LWC・オブジェクト・項目・Layout・権限・レポート・ワークフローなど）
2. 標準だが制限あり有効更新のみ・権限による・一部未確認（StandardValueSet・Flow・Settings など。理由は、ファイル内のコメント）
3. 機能が必要なものコメントアウトService Cloud 系（Entitlement・Omni-Channel・Knowledge）・Experience Cloud 系。使う組織だけ、コメントを外す
4. 未確認コメントアウト確認できていない種類。使う場合は、外して、リリースを確かめる
5. 参考コメントアウトそのほかの種類の候補（業種クラウド・AI・分析など）
  • 取得の対象に、その組織にない種類があっても、警告になるだけで、取得は続きます。
  • 種類ごとの確認の状況は、sf-typecheck.sh --coverage で見られます（変更セットで扱える種類のうち、確認済み・未確認の数）。
  • リリース・削除できないと確認済みの種類は、ターゲットファイルに書くと、sf-check.sh が止めます（警告だけの種類もあります）。
  • すでに作成済みのプロジェクトの metadata.txt は、雛形が更新されても、変わりません。
