# AI 向けの手順書（sf-tools のコマンドの使い方と、デバッグログを読みながら直す開発のサイクル）

> この手順書は、force-* のプロジェクトで Salesforce の開発を手伝う AI（Claude Code・Codex など）が読む。
> force-* の `CLAUDE.md`・`AGENTS.md` は、この文書を指す行だけを持つ（sf-tools の `templates/` から入る。その行は消さない）。
> 手順を直すと、各利用者の `~/sf-tools` の `git pull` で届く。デバッグログの設計の正本は `~/sf-tools/doc/sf-log-design.md`（11 章）。

## 1. 前提

- 作業の場所は force-* のプロジェクトのルート（`sfdx-project.json` があるフォルダ）。コマンドは `bash ~/sf-tools/bin/<名前>.sh` で呼ぶ。どのコマンドも `--help` で、使い方と処理の流れを表示できる
- 人は `sf-start.sh` で作業を始める（組織への接続・VS Code・ランチャー）。sf-start は、デバッグログ（`ApexLog`。Apex だけでなく、フロー・入力規則・重複ルールなど、1 回の処理の動きの記録）を、裏で自動で取り始める。ランチャーの見出しの下に、状態の 1 行（取得中・準備中・取っていません など）が出る
- 取るのは、接続中の組織の、**自分のユーザー**のログだけ。一人用の開発組織（Developer Edition・Sandbox・スクラッチ組織）で、ダミーデータで使う
- **sf-start と同じ環境で実行する**（sf-start を WSL で起動したなら、AI のコマンドも WSL で。Windows の Git Bash と WSL を、同じプロジェクトで混ぜない）。別の環境から `sf-log.sh pull` を実行すると、「別の環境（wsl）で、デバッグログを取っています」と出て止まる（`status` だけは答える）。そのときは、表示された環境で実行し直す（人に、どの環境で sf-start したかを聞く）

## 2. コマンドの使い分け（会話で動かす）

人は、ランチャーの番号の代わりに、言葉（「チェックして」「反映して」「PR を出して」）で頼める。AI は、ランチャーを使わず、コマンド（`bash ~/sf-tools/bin/<名前>.sh`）を直接動かす。設計の正本は `~/sf-tools/doc/ai-operation-design.md`。

- **書き込むコマンド（2.1 の B）を動かすときは、必ず環境変数 `SF_TOOLS_AI=1` を付ける。** 付けると、コマンドの確認（Y/N）は、標準入力を読まず、`SF_TOOLS_ANSWERS` の答えだけを使い、答えがなければ止まる（2.3）。付けないで動かすと、人の端末の入力を待って止まる・意図しない答えを読むことがある
- `printf 'y' |` のように、標準入力に答えを流し込まない（どの質問に使われるか分からない。人が見ていない質問にも答えてしまう）
- **言葉で頼まれてコマンドを動かすときは、必ず、人が見られるターミナル（タブ・画面）で動かし、そのターミナルを自動で人の画面に出す**（読むだけの短いコマンドも同じ）。裏で動かして結果だけを伝えると、人には、何をしているのか・動いているのかが分からない（2026-11-26 の利用者の指示）。ターミナルを画面に出せない AI のときは、動かすコマンドと、途中の出力を、こまめに会話に書く

### 2.1 区分

| 区分 | コマンド | AI の扱い |
|---|---|---|
| A 読むだけ | `sf-check.sh`・`sf-dryrun.sh -n`（`-r` は付けない。付けると実際の反映）・`sf-next.sh`（`SF_TOOLS_ANSWERS="next.pr=n"` で、状況の表示だけ）・`sf-log.sh status` / `pull` | 言われたら、確認なしで動かす |
| B 書き込む（自分の組織・Git・GitHub） | `sf-deploy.sh -n`（自分用の組織への反映）・`sf-push.sh -m <ファイル>`（コミットと push）・`sf-next.sh`（`next.pr=y` で、PR の作成画面を開く） | 2.2 のとおり、内容を示して、人の「はい」をもらってから動かす |
| C 人が動かす | `sf-start.sh`・`sf-restart.sh`・`sf-job.sh`（作業の開始・組織の切り替え・新しい作業。VS Code・ブラウザでのログインがある） | 人に頼む（ランチャーの [6] Start・[7] Restart） |
| D 動かさない | `sf-log.sh start` / `stop` / `auto`（組織に書き込む）・管理者向け（`sf-init.sh`・`sf-update-secret.sh`・`sf-sync-wf.sh`・`sf-typecheck.sh`）・自動で動くもの（`sf-install.sh`・`sf-metasync.sh` など） | 動かさない（人に頼む） |

- 共有の環境の組織（エイリアス `develop`・`staging`・`main`・`prod`）と本番には、手元から反映できない（コマンドが拒否する。AI 操作の印があっても変わらない）。頼まれても動かさず、理由（GitHub の PR とワークフローで反映する）を伝える

### 2.2 書き込む操作の進め方（B）

1. 動かす前に、会話で次を示し、人の「はい」をもらう
   - `sf-deploy.sh`: 反映先の組織（エイリアス）・ターゲットファイルの要点（反映する数・削除するもの）・直前の `sf-dryrun.sh -n` の結果
   - `sf-push.sh`: `origin/main` を取り込むこと・変更の一覧（`git status` の要点）・未プッシュのコミット・コミットのメッセージの案
   - `sf-next.sh`（PR）: PR の先（例: develop）と、`next.pr=n` で動かしたときの状況の表示
2. 「はい」をもらった質問だけに、答えを渡して動かす
   - `SF_TOOLS_AI=1 SF_TOOLS_ANSWERS="deploy.force=y" bash ~/sf-tools/bin/sf-deploy.sh -n`
   - `SF_TOOLS_AI=1 bash ~/sf-tools/bin/sf-push.sh -m <メッセージのファイル>`（メッセージは、案を人に見せて決めたものを、ファイルに書いて渡す。`#` で始まる行・前後の空行は除かれる）
   - `SF_TOOLS_AI=1 SF_TOOLS_ANSWERS="next.pr=y" bash ~/sf-tools/bin/sf-next.sh`（ブラウザで、PR の作成画面が開く。作成のボタンは、人が押す）
3. 「はい」は、**その 1 回の実行・その質問にだけ**使う。前の「はい」を、別の実行・別の質問に使わない
4. 終わったら、結果（成功・失敗・作られたもの）を報告する。失敗は、表示されたエラーをそのまま添える

質問の名前（`SF_TOOLS_ANSWERS` の名前）:

| 名前 | コマンド | 質問 |
|---|---|---|
| `deploy.force` | `sf-deploy.sh` | 強制デプロイ（--force）を実行します。続行しますか？ |
| `next.pr` | `sf-next.sh` | 〜にPRを出しますか？（staging・main へは、前の段階の組織で確かめたかも聞く） |
| `update.sftools` | （どのコマンドでも。sf-tools が古いとき） | sf-tools を更新しますか？ |

- 形は `名前=y` / `名前=n` を空白区切り。形が違う・同じ名前が 2 つあると、コマンドは中断する

### 2.3 確認待ち（終了コード 20）

- 答えのない質問に来ると、コマンドは入力を待たずに、`[確認待ち] <名前>: <質問の文>` を出して、終了コード 20 で終わる
- 20 のときは、質問の文を**そのまま**人に聞く（言い換えて、意味を変えない）。「はい」なら、その名前の答えを `SF_TOOLS_ANSWERS` に足して、同じコマンドを最初から動かし直す
- 名前が `(名前なし)` の確認待ちは、AI からは答えられない質問（テキストの入力・秘密の値・名前のない確認）。人に、ランチャーかコマンドで実行してもらう
- `sf-push.sh` で `[確認待ち] push.message` が出たら、`-m <ファイル>` を付け忘れている（取り込み・ステージの前に止まっている）
- 20 以外の失敗を、やり直しの合図にしない

### 2.4 言葉とコマンドの対応

人は、**ランチャーの名前**（Check・Dryrun・Deploy・Push・Next）を、そのまま言って頼める（「Check して」「Dryrun」「Deploy お願い」「Push して」「Next」）。ふつうの言葉で頼んでもよい。

| ランチャーの名前 | ふつうの言葉（例） | コマンド | 区分 |
|---|---|---|---|
| Check | 「チェックして」「ターゲットファイルを確かめて」 | `sf-check.sh` | A |
| Dryrun | 「反映できるか試して」「dry-run して」 | `sf-dryrun.sh -n` | A |
| Deploy | 「反映して」「デプロイして」 | `sf-deploy.sh -n`（自分用の組織） | B |
| Push | 「コミットして」「プッシュして」 | `sf-push.sh -m <ファイル>` | B |
| Next | 「次はどこに PR？」「状況を見て」 | `sf-next.sh`（`next.pr=n`。状況の表示だけ） | A |
| Next（PR を出す） | 「PR を出して」 | `sf-next.sh`（`next.pr=y`） | B |
| （なし） | 「ログを見て」 | `sf-log.sh pull` → `logs/apex/latest.md` | A |
| Start・Restart | 「作業を始めて」「組織を切り替えて」 | （C: 人に頼む。ランチャーの [6]・[7]） | C |

- 「Next」だけと言われたら、まず状況の表示（`next.pr=n`）を見せ、PR を出すかは、あらためて聞く（PR の作成画面を開くのは B のため）
- 番号（「3 番」など）で頼まれたら、ランチャーの名前に直して確かめる（「3 は Deploy です。反映してよいですか？」）。番号の並びは、ランチャーの版で変わることがあるため、番号だけで動かさない
- 合うものがないとき・どちらとも取れるときは、聞き返す（推測で、書き込む操作をしない）

## 3. 開発のサイクル

### 3.1 始める前に

- `bash ~/sf-tools/bin/sf-log.sh status` で、取得役が動いているか・TraceFlag の期限を確かめる
- 動いていなければ、理由を人に伝える（取らない組織・答えが「取らない」・ほかの TraceFlag と重なっている など。`status` とランチャーの 1 行に出る）。取り始めるのは人（`sf-start.sh` のやり直しか `sf-log.sh start`）

### 3.2 直して、反映できるか確かめる

- コードを直す
- 反映するメタデータを、ターゲットファイル `sf-tools/release/<ブランチ>/deploy-target.txt`（削除は `remove-target.txt`）に書く。ブランチは `sf-tools/release/branch_name.txt` に書かれている。書き方は `sf-check.sh --help` と、文書サイトの「ターゲットファイルの書き方」
- `sf-check.sh` で書き方を確かめ、`sf-dryrun.sh -n` で反映できるかを確かめる。失敗したら、表示されたエラーを直して繰り返す

### 3.3 反映して、確かめる操作を、人に頼む

- 反映は、2.2 のとおり、人の「はい」をもらってから、AI が `sf-deploy.sh -n` で行う（自分用の組織の内容を上書きする）。人がランチャーの [3] Deploy で行ってもよい
- 反映できたら、画面での操作を、具体的に伝える（どの画面で、どのレコードに、何をするか）。終わったら知らせてもらう
- デバッグログには、画面のクリックそのものは残らない（サーバーで動いた処理だけ）。人に、操作の内容を一言添えてもらうと、ログと結び付けやすい

### 3.4 ログを読む

- `bash ~/sf-tools/bin/sf-log.sh pull` を実行し、`logs/apex/latest.md` を読む（組織には書き込まない。何度呼んでもよい）
  - 取得役が動いていれば、取得役に「今すぐ取って」と頼んでから要約する。動いていなければ、自分で組織から取る
  - 要約には、前回の `pull` のあとに手元に保存したログが入る（開始時刻ではなく、保存した順。遅れて取れた長い処理のログも漏れない）
- 要約の節（上から順）:
  1. エラー（保存を止めたもの: 例外・致命的なエラー・フローのエラー・フローのカスタムエラー・入力規則の停止。場所 `[ファイル:行]` つき）
     - フローのカスタムエラーと入力規則の停止は、ログに文言が出ない。要素・規則の名前を手がかりに、フロー・入力規則の定義を読む
     - ログの `状態` は、入力規則やフローで保存が止まっても「成功」になる。状態ではなく、この 1 を見る
  2. ログの一覧（操作・状態・長さ・所要・SOQL・DML。操作の括弧に、最初の処理と、フロー・入力規則・重複ルールの名前）
     - 所要は Salesforce の値のまま。`※` の付いたものは、ログの中の経過より 1 時間以上長い不自然な値（実際の所要ではない可能性）
  3. `System.debug` の出力（新しい順）
  4. フロー・入力規則・重複ルール（どのフローが動き、どの要素を実行したか・入力規則の評価と停止・重複ルールの保存の中と後の回数・見つかった重複・動作）
  5. 制限の使用量（上限の 50% を超えたものだけ）
  6. 切り詰め・出なかった区分・読み取れなかった行
- 詳しく見たいときだけ、要約に書かれた `[ファイル:行]` の本文を開く（本文の全部を読まない。長い）
- 要約の先頭の注意（「入れなかった古いログ」「拾い直しに失敗」「要約のロックを取れませんでした」など）を、必ず読む。古い分は `pull --since <分>`（必要なら `--max <本数>`）で入れ直せる

### 3.5 直して、3.2 に戻る

- 原因が分からないときは、人に `sf-log.sh start --level detail` を頼む（詳しいログに切り替える。項目の値・条件の結果・制限の使用量などが出る。ログが大きくなる）
- 直し終わったら、変更を送るか（`sf-push.sh`）・PR を出すか（`sf-next.sh`）を、人に聞く。頼まれたら、2.2 のとおり動かす

## 4. Apex を試しに動かすとき

- **動かす前に、毎回、人の了承を取る**（読み取りだけのコードも）。了承を求めるときは、接続先の組織（エイリアス・組織 ID）と、動かす Apex の全文を見せる。組織でコードを動かすことは、データの書き換え（DML）・非同期の処理の登録・外部への通信になりうるため
- `sf apex run` ではなく、Tooling API の `executeAnonymous` を直接呼ぶ（`sf apex run` は、sf が自分の詳しさでログを出すため、SOQL・DML などの行が出ない）:
  `MSYS_NO_PATHCONV=1 sf api request rest "/services/data/v68.0/tooling/executeAnonymous/?anonymousBody=<URL エンコードしたコード>" --target-org <エイリアス>`
  - Windows の Git Bash では、`/` で始まる引数が Windows のパスに書き換えられることがあるため、`MSYS_NO_PATHCONV=1` を付ける
  - コードは URL の引数（GET）でしか渡せない。長いコード（URL エンコード後に約 16KB を超えるもの）は失敗しうる。長いコードは、クラスにしてデプロイしてから呼ぶ
- データを残さずに試すときは、セーブポイントで巻き戻す（`Savepoint sp = Database.setSavepoint(); … Database.rollback(sp);`）

## 5. AI がしないこと

- 2.1 の C（人が動かす）・D（動かさない）のコマンドを、自分で実行しない。B を、人の「はい」なしに動かさない
- 組織のログや、手元のログ（`logs/apex/`）を消さない
- 了承なしに、組織のデータを書き換えない（4 章）。共有の環境・本番の組織には、つながない

## 6. ログで取れないもの・注意

- **長い処理のログ**: ログは、処理が終わってから組織の一覧に現れる。取得役と `pull` は、直近 30 分に始まった自分のログを確かめ直して拾う。目安として、処理の時間と取得の間隔（既定 3 分）を足して 30 分を超えるログは、取れないことがある
- **LWC・Aura の画面側のエラー**（ブラウザのコンソール）は、デバッグログに残らない。人に、ブラウザの開発者ツールのコンソールの内容を貼ってもらう
- **別のユーザーで動く処理**: プラットフォームイベントのトリガー（Automated Process ユーザー）・スケジュールで動くフロー・プラットフォームイベントで動くフロー・他の人がスケジュールしたジョブは、自分のユーザーの TraceFlag では取れない
- **画面フロー**: 正常に終わっても、ログに完了の行が出ない。要約の 4 では「完了 0」と並んで「画面待ち N」「続き N」と出る（止まったのではない）。画面ごとにログが分かれ、「次へ」で動いた要素（更新など）は、続きのログに出る（要約では、開始したフローの要素に入れている）。画面でエラーが出たかは、1 のエラーと、人の画面で見る
- **非同期の処理**（Queueable・Batch・future）は、実行の時刻がずれる。`pull` を少し待ってから呼ぶ
- **重複ルール**: 動作が「許可（警告）」のルールでも、Apex・API の保存は、`DuplicateRuleHeader.allowSave` がなければ止められる（`DUPLICATES_DETECTED`）。部分保存（`Database.insert(…, false)`）は、ログに失敗の行が出ない。要約の 4 の「重複あり」で見る
- 取得中に人が Developer Console を開くと、別の種類（DEVELOPER_LOG）の TraceFlag が作られる。ログの詳しさがどうなるかは未確認。ログの行が足りないと感じたら、`status` で確かめる
