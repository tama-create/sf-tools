🩺 トラブルシューティング

うまく動かないときの、原因と直し方です。落ち着いて、当てはまるものを探してください。ほとんどは、やり直せば元に戻ります。

最初に試すこと
  • エラーの文章を、最後まで読んでみてください。直し方が、書いてあることが多いです。
  • ログは、force-* フォルダの中の sf-tools/logs/<コマンド名>.log に残っています（sf-init.sh だけは、~/sf-tools/logs/sf-init.log です）。
  • 管理者は、sf-init.sh --status で、足りないものを調べられます。

開発者の方へ（毎日の作業で困ったとき）

sf-job.sh が動かない

sf-job.sh は、管理者用のフォルダ（admin）や、force-* フォルダの中では、動きません。作業フォルダ（作業用のフォルダを、まとめて置いている場所）に移動して、もう一度実行してください。

sf-push.sh が、コミットする前に止まる

次のどちらかのときに、止まります。変更が、手元に半端に残らないようにするための仕組みです。

  • ブランチの上にいない（detached HEAD）
  • 保護ブランチ（main など）の上にいる

sf-job.sh で作った、作業用のブランチに移ってから、もう一度実行してください。

git push が止められる

main / staging / develop の上にいるとき、または、これらへプッシュしようとしたとき（git push origin feature:main など）は、プッシュを止める仕組みです。作業用のブランチに移って、PR（取り込みの依頼）を出して、反映してください（sf-next.sh が、出し先を案内します）。ターゲットファイルの書き方にエラーがあるときも、止まります（画面に、エラーの行が出ます）。

「リモートの変更を、現在のブランチに取り込みました。このプッシュには、取り込みが含まれないため、中止しました」と表示されたときは、故障ではありません。main などの新しい変更を取り込んだので、もう一度 git push を実行してください（今度は通ります）。

この仕組みを、避けて通る方法は、案内していません。どうしても必要なときは、管理者に相談してください。

dry-run（sf-dryrun.sh）が失敗する

画面に、エラーの内容が出ています。多くは、ターゲットファイルの書き方や、変更の内容が原因です。直して、もう一度実行してください。書き方は、ターゲットファイルの書き方にあります。

sf-deploy.sh が、実行前に断られる

接続先の組織が、共有の環境（エイリアスが prod / staging / develop の組織）だからです。sf-deploy.sh は、自分専用の組織（Sandbox・Developer Edition・Scratch Org）にだけ、使えます。sf-restart.sh で、接続先を、自分用の組織に切り替えてください。

sf は成功しているのに、失敗と表示される

Salesforce CLI が、公式インストーラー版のときに起こります。npm 版に入れ替えると、直ります（Salesforce CLI は npm 版を使う）。

管理者の方へ（セットアップや自動処理で困ったとき）

sf-init.sh が、途中でエラーで止まった

まず、ログを見ます。

cat ~/sf-tools/logs/sf-init.log

「どこで間違えたか分からない」ときは、管理者用の admin フォルダの中の force-* で、sf-init.sh --status を実行します。リポジトリ・ブランチ・ワークフロー・Secrets・Variables が、そろっているかを、✓（できている）と ✗（足りない。直し方も表示）で教えてくれます（何も変更しません。診断の説明）。

原因を直したら、同じフォルダで、もう一度 sf-init.sh を実行してください。途中まで進んでいたときは、続きから再開する選択肢が出ます（途中で止まったとき）。

wf-metasync（[metasync] メタ同期）が「push declined due to repository rule violations」で失敗する

PAT_TOKEN が登録されていないか、権限が足りないのが原因です。sf-init.sh は、登録のときに、権限を確かめます。そのあとで、Token を無効にしたり、有効期限が切れたりすると、この状態になります。

新しい Token を発行して、リポジトリの Secrets の PAT_TOKEN を、登録し直してください。sf-update-secret.sh では、PAT_TOKEN は更新できません。

wf-validate（[validate] デプロイ前検証）や wf-sequence（[sequence] マージ順序チェック）が動かない

ワークフローのファイルが、.github/workflows/ の中にあるかを、確かめてください。

ファイルがないときは、sf-sync-wf.sh で、最新の雛形から作り直せます。

CRLF の警告が出る

Windows と、ほかの環境の、改行コードの違いを知らせる警告です。動作には影響しないので、そのままで大丈夫です。

wf-metasync / wf-validate / wf-release が「自動化ツール（sf-tools）を取得」で失敗する

sf-tools は公開リポジトリなので、新しいワークフローは、Token なしで取得します。このエラーは、以前のバージョンの雛形で作ったプロジェクトで起こります。ワークフローが SF_TOOLS_TOKEN 付きで取得していて、その Token が使えないときに起こります（登録されていない・期限が切れた・無効になった、のどれかです）。

プロジェクトの wf-metasync.yml / wf-validate.yml / wf-release.yml にある、取得の行を、新しい雛形と同じ、Token なしの形に直してください。

git clone -b ${{ vars.SF_TOOLS_BRANCH || 'main' }} https://github.com/tama-create/sf-tools.git ...

配布済みのプロジェクトには、自動では反映されません。sf-sync-wf.sh で、雛形に合わせて更新できます。

「差分抽出ツール（Salesforce Git Delta）をインストール」で TypeError が出て失敗する

エラーの例: TypeError: webidl.util.markAsUncloneable is not a function

ワークフローで使っている Node.js が、古いのが原因です（@salesforce/cli の最新版は、Node 22 以上が必要です）。各ワークフローの node-version を、22 以上に直してください。雛形を直しても、配布済みのプロジェクトには、自動では反映されません。プロジェクト側のワークフローも、sf-sync-wf.sh で更新します。
