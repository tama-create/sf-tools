🤖 自動実行コマンド

ほかのコマンドや、git のフック、GitHub Actions が、自動で呼び出すコマンドです。自分で実行することは、ほとんどありません。「裏で何が動いているのか」を知りたいときに、読んでください。全体の一覧は、コマンド一覧にあります。

このページの要点
  • ここにあるコマンドは、人が打つ必要は、ほとんどありません。ほかのコマンド・git のフック・GitHub Actions が、自動で動かします。
  • 動くきっかけ: sf-install.sh は sf-start.sh から、sf-upgrade.sh は sf-install.sh から 24 時間おきに、sf-prepush.sh は git push のとき、sf-precommit.sh は git commit のとき、sf-metasync.sh は GitHub Actions からです。
  • どれも、force-* フォルダ（フォルダの名前が force- で始まる）で動きます。

sf-install.sh

sf-install.sh [-v]

~/sf-tools 自体の更新と、プロジェクト側の準備（Git フック・リリース用フォルダなど）を行います。通常は、sf-start.sh がバックグラウンドで、sf-init.sh が Phase 4（ステップとの対応） で、自動で実行します。force-* フォルダの中で、単独でも実行できます。

-v（--verbose）は、コマンドの応答をコンソールにも表示します（sf-hook.sh にも渡し、sf-upgrade.sh には渡しません）。-h（--help。1 つ目の引数のときだけ）以外の、ほかの引数は、「不明なオプションです」で中断します。

主な処理（この順序）

  1. sf が動くかを確認する（sf --version の終了コードが 0 以外なら、エラーの案内を表示しますが、中断はしません。中断すると、sf-tools 自身の更新まで止まるためです）。sf が未インストールのとき・GitHub Actions 上では、確認しません。続けて、Java のバージョンを確認します。17 未満のとき・見つからないとき・バージョンを読み取れないときは、警告で案内を表示しますが、中断はしません（VS Code の Apex 拡張が、Java 17 以上を必要とするためです。調べるのは、JAVA_HOME/bin/java（あれば）、なければ PATH の java です（VS Code の設定は読みません。見る場所は JAVA_HOME に一本化しています。案内は、Windows・macOS・Linux 別です）。成功は 24 時間、確認を省きます。GitHub Actions 上・環境変数 SF_TOOLS_SKIP_JAVA_CHECK=1 のときは、確認しません。対処は、困ったときの節）
  2. ~/sf-tools の現在のブランチ（取得できなければ main）を、git pull で最新にする（失敗しても続行。sf-init.sh から呼ばれたときは行わない）
  3. 設定ファイル（sf-tools/config/metadata.txt と branches.txt）を確認する。通常の実行で、どちらかがなければ中断します（プロジェクトの破損として扱い、作りません）。sf-init.sh から呼ばれたときだけ、ないものを雛形からコピーします（失敗したら中断）
  4. Git フック（pre-commit と pre-push）を、sf-hook.sh でインストールする
  5. リリース用のフォルダを準備する
    • 現在のブランチ名を取得できない（detached HEAD など）ときは、警告を表示して、何もしません
    • sf-tools/release/ と sf-tools/release/.gitkeep を作ります
    • main ブランチでは、ここで終わります（release/<ブランチ名>/ と branch_name.txt は、作成も更新もしません）
    • それ以外のブランチでは、release/<ブランチ名>/ を作り、deploy-target.txt・remove-target.txt がなければ雛形からコピーし、release/branch_name.txt にブランチ名を書き込みます
  6. （sf-init.sh から呼ばれたときだけ）コミットメッセージの雛形（.gitmessage）を置き、git config commit.template を設定する
  7. npm install を実行する（package.json があるとき）。node_modules/.package-lock.json が package-lock.json 以降に更新済みのとき（package-lock.json がないときは、省略しない）と、sf-init.sh から呼ばれたときは、省略します
  8. ~/.sf-tools-last-update がない、またはその更新時刻から 24 時間以上たっていれば、sf-upgrade.sh をバックグラウンドで実行する（画面への表示（標準エラー）は、sf-install.log に追記）。起動を確認できたら、~/.sf-tools-last-update の時刻を更新します（完了の時点ではなく、起動の時点です）

補足

  • 手順 3 以外の失敗は、警告を表示して続行します。終了コードは 0 で、手順 3 で中断したとき・不明なオプションのときだけ 1 です。
  • branch_name.txt は、Git の管理外の、手元のファイルです。main では書き換えないため、作業用のブランチのあとで main に切り替えると、前のブランチの値が残ります（sf-check.sh は、その値で検証します）。
  • 前提: ~/sf-tools が初回のインストール済み（git clone https://github.com/tama-create/sf-tools.git ~/sf-tools）で、Salesforce CLI（sf）が npm 版であること。Java 17 以上があり、環境変数 JAVA_HOME が、それを指していること（VS Code の Apex 拡張の要件。確認は警告のみ）。
  • ワークフロー（.github/workflows/）は、扱いません。新しいプロジェクトには sf-init.sh（Phase 3）が雛形からコピーし、作成済みのプロジェクトへの反映は、sf-sync-wf.sh（管理者が手動で実行）が行います。
  • ログは ./sf-tools/logs/sf-install.log です（実行のたびに作り直します）。

sf-upgrade.sh

sf-upgrade.sh [-v]

npm・Salesforce CLI（sf）・Git（Windows の Git Bash だけ）を、最新版に更新します。sf-install.sh から、前回から 24 時間以上たっているときに、バックグラウンドで自動で実行されます（引数なし）。force-* フォルダの中で、手動でも実行できます。-v（--verbose）・-h（--help。1 つ目の引数のときだけ）以外の引数は、「不明なオプションです」で中断します。

  1. npm を確認する（npm がなければ、警告を表示して飛ばす）。今の版と最新の版が同じなら、何もしません。違うときは、npm install -g npm@latest で更新します。Node が対応していないときは、npm が何も変えずに止まるので、Node の更新を案内するだけです（npm は Node に同梱されていて、最新の npm は、Node が新しくないと入らないことがあります）。Windows の Git Bash では winget upgrade --id OpenJS.NodeJS.LTS を示します（Node は自動では更新しません）。そのほかの理由で失敗したときは、警告に、npm の出力の末尾 5 行（理由）を表示します。なお、事前の確認に --dry-run は使いません（npm 12 は、--dry-run のときだけ、誤って失敗するため）
  2. sf を更新する（sf がなければ、警告を表示して飛ばす）。npm 版（npm ls -g @salesforce/cli が成功する）なら npm install -g @salesforce/cli@latest、それ以外（公式インストーラー版など）なら sf update。失敗したとき、npm の置き場所（npm config get prefix）に書き込めなければ、その旨を警告します（C:\Program Files\nodejs だと、Windows では管理者権限が要ります。自分のフォルダに npm config set prefix で変えると、権限なしで更新できます）
  3. Git を更新する（最後に実行）。Windows の Git Bash では git update-git-for-windows --yes。macOS・Linux・WSL では実行せず、パッケージマネージャーで更新するよう案内する
  • どの手順が失敗しても、警告を表示して続行します。最後に、更新できなかったもの（npm・Salesforce CLI・Git）があれば、その名前を「更新できなかったものがあります: 〇〇」と並べ、なければ「すべてのアップデートが完了しました」と表示します。終了コードは、失敗があっても 0 です。
  • 自動で動いたときの表示は、sf-install.log にだけ残ります。Node の更新の案内などを画面で見るには、手動で実行してください。
  • ログは ./sf-tools/logs/sf-upgrade.log です（実行のたびに作り直します）。

sf-prepush.sh

git push のときに自動で実行される、チェックのスクリプトです（pre-push フックの本体。フックは -v を付けて呼びます）。-v・-h 以外の引数は、エラーで終了します。

主な処理

  1. 次のどれかなら、プッシュを拒否する（保護ブランチ = sf-tools/config/branches.txt に書かれたブランチ。ファイルがない・空のときは main）。
    • ブランチの上にいない（detached HEAD）
    • 現在のブランチが、保護ブランチ
    • プッシュ先が、保護ブランチ（git push origin feature:main や、保護ブランチの削除（:main）も、拒否します。プッシュ先は、git がフックに渡す内容から読みます。端末から手動で実行したときは、読みません）
  2. sf-check.sh で、ターゲットファイルを検証する（エラーなら中断）
  3. リモートの最新を取得する（origin にある現在のブランチと、保護ブランチ）。origin にまだないブランチや、使えない名前の保護ブランチは、警告を表示して飛ばします。取得に失敗したときは、中断します
  4. origin/<現在のブランチ> に未取り込みのコミットがあれば、表示して、git merge で取り込む（失敗したら git merge --abort して中断）
  5. origin/main に未取り込みのコミットがあれば、同じように、git merge で取り込む（手順 3 で取得したかにかかわらず、手元の origin/main を見ます）

補足

  • 取り込みは merge で行います（rebase ではありません）。
  • 検証は、取り込みより前に行います。手順 4・5 で取り込んだ変更は、検証されません。
  • 未取り込みのコミットの確認が失敗したとき（手元に origin/main がないなど）は、取り込みを試みずに中断します。
  • 取り込みをしたとき（早送り（fast-forward）を含む）は、そのプッシュを中止します。git は、フックを呼ぶ前に、送るコミットを決めているため、そのままでは、取り込みが含まれないまま、プッシュが成功と表示されるからです。取り込み後に、もう一度プッシュすると、取り込みは済んでいるため、通ります。
  • 中断したときは、終了コード 1 で終わり、プッシュも中止されます。
  • ログは ./sf-tools/logs/sf-prepush.log です（実行のたびに追記します）。

sf-precommit.sh

git commit のときに自動で実行される、pre-commit フックの本体です。直接実行することはありません。

主な処理

  • sf-check.sh を引数なしで実行して、ターゲットファイルを検証する
  • エラーがあれば、コミットを中止する（終了コード 1）

補足

  • 検証するのは、sf-tools/release/branch_name.txt に書かれたブランチのターゲットファイルです。このファイルがないときは、検証せずに成功となり、コミットは続行されます。
  • 検証するのは、作業フォルダにあるファイルです（ステージした内容ではありません）。
  • ログは ./sf-tools/logs/sf-precommit.log です（実行のたびに作り直します）。

sf-metasync.sh

sf-metasync.sh [-n] [-y] [--full] [--allow-mass-delete] [-j] [-v]

main の組織（sf-init で 1 番目に登録した組織。本番・Sandbox・Developer Edition のどれでも）から、メタデータを取得して、main にコミットしてプッシュします。Salesforce 組織の内容を正とします。どのブランチから実行しても、main に切り替えて処理し、終わると元のブランチに戻ります。主に、GitHub Actions（wf-metasync）からの定期実行を想定しています。

管理者専用

実行の前に、赤い警告ボックスと確認（Y/N）が表示されます。GITHUB_ACTIONS=true のときは、警告も確認もスキップして、自動で実行します。

-n（--dry-run）は、組織から取得して、計画（追加・変更・削除・保留の件数と一覧）を表示するだけで終わります（作業ツリーの変更・コミット・プッシュ・伝播は行いません）。-y（--yes）は、--dry-run のときだけ、最初の確認を省きます。--full は、変更の検知（下の補足）が「変更なし」でも、取得を省かずに、全件取得します。--allow-mass-delete は、削除の保留のうち、消えたフォルダと削除が多いものを解きます（手元で実行したときだけ。GitHub Actions 上では指定できません）。-j（--json）は、組織からの取得の応答（JSON）の先頭を、ログにも記録します。-v（--verbose）は、コマンドの応答をコンソールにも表示します。これと -h（--help）以外の引数は、中断します（終了コード 1）。

役割

  • 組織の最新のメタデータを取得する
  • main の「同期の対象のフォルダ」を、取得した内容と同じにする（追加・変更・削除）。削除には安全の守りがあり、当たったものは保留にする
  • 変更があるときだけ、コミットしてプッシュする
  • 変更がなくても、前回のプッシュが失敗して、送れていないコミットが残っているときは、確認のうえで、プッシュだけ行う
  • プッシュしたときは、branches.txt の main 以外の各ブランチ（staging・develop など）に、main をマージしてプッシュする
  • main へのプッシュも、ほかのブランチへのプッシュも、pre-push フックを通さない（--no-verify）。pre-push フックは、保護ブランチの上から・保護ブランチへのプッシュを必ず拒否するため、通すと失敗するからです。GitHub の保護の設定（Ruleset）は、そのまま効きます

処理の流れ

  1. sf の確認（sf --version の終了コードが 0 以外なら中断。成功は 24 時間、確認を省く）。引数の解析は、このあとに行う
  2. 事前の確認（満たされなければ、何も変更せずに中断する）。接続先の組織（main の組織）を決めます。手元で実行するときは、エイリアスの名前ではなく、組織の ID で決めます: GitHub の Variable SF_ORG_ID_PROD（sf-init が記録した、1 番目の組織の ID）を読み、この PC の sf にログイン済みの組織から、ID が一致するものを探して使います。origin から GitHub のリポジトリを特定できない・SF_ORG_ID_PROD を読めない・一致する組織がログインされていない、のどれかなら、推測せずに中断します（別のプロジェクトの組織で main を書き換えるのを防ぐためです）。GitHub Actions 上では、ワークフローが作る prod エイリアスの組織を使います。続けて、その組織の情報を取得できること（確認の出力は、アクセストークンを含むため、表示もログへの記録もしない）・ブランチの上にいること（detached HEAD では中断）・sf-tools/config/metadata.txt があること
  3. 警告を表示して、続行の確認（Y/N）を取る（GitHub Actions 上では、表示も確認もしない）
  4. main に切り替える。追跡中のファイルに未コミットの変更があれば、いったん退避（git stash）する
  5. リモートの最新を取り込む（git fetch origin（失敗しても続行）→ git pull origin main --rebase。失敗したら git rebase --abort して中断）。その前に、main に未コミットの変更が残っているとき・手元の実行で、追跡していないファイルがあるときは、中断する（下の補足）
  6. 取得先の一時プロジェクトを準備する（sfdx-project.json の packageDirectories が 1 つでなければ中断）。作業ツリーには、まだ何も書かない。続けて、環境変数 SF_METASYNC_DETECT が shadow または on のときは、変更の検知を行う（読み取りのみ）。on で「変更なし」なら、次以降を行わずに終了する（コミット・プッシュ・伝播もしない）。検知の失敗・不明・変更ありは、すべて、次の全件取得に進む
  7. 組織からメタデータを、一時プロジェクトへ取得する（metadata.txt の全種類。--ignore-conflicts・--json）。一時的なエラー（MetadataTransferError・ERROR_HTTP_404・接続の切断など）なら、60 秒待って 1 回だけやり直す。それでも失敗したら中断する（作業ツリーは変わらない）
  8. 直近 24 時間に、同期以外のコミット（PR のマージなど）で変わったファイルの一覧を作る（削除の守り S5 に使う）
  9. 計画を作る: 同期の対象のフォルダごとに、手元と取得結果を比べて、追加・変更・削除を決める。次に当たる削除は保留にして、ファイルを残す。S2 取得の応答に問題の報告がある ／ S3 手元に 1 件以上あったフォルダが、取得結果で 0 件 ／ S4 削除が max(100 件, 手元の対象の 10%) を超える ／ S5 直近にマージされたファイル。取得の応答が失敗（S1）なら、中断する。計画の要約を表示し、手元では、変更があるときに確認（Y/N）を取る。--dry-run は、ここで終了する
  10. 計画を作業ツリーに反映する
  11. （検知が「変更あり」「不明」だったときは、検知の状態を sf-tools/metasync/state.json に書く。）同期の対象のパッケージのフォルダ（と、書いたときは状態ファイル）をステージし（sf-tools/release/ は含めない）、変更があれば、「定期更新: Salesforce変更の自動反映 (YYYY-MM-DD)」でコミットしてプッシュする（本文に件数）。変更がなく、origin/main より先のコミットが残っていれば、一覧を表示して確認を取り、プッシュだけ行う。どちらもなければ、「完了: Salesforce 組織側に変更はありませんでした。」と表示して終わる（コミット・プッシュの失敗は、中断）
  12. プッシュしたときだけ、ほかのブランチへ伝える（各ブランチで、git pull --rebase → git merge main → git push --no-verify）。リモートにないブランチは、警告を出して飛ばします。伝えるのに失敗したブランチも、取り消して（--abort）、警告を出して飛ばし、次へ進みます
  13. 終了時（事前の確認より後に中断したときも）、計画を反映したあと、コミットの前に中断したときは、同期の対象のパッケージのフォルダを元に戻す。そのあと、元のブランチに戻り、退避した変更を戻し、一時プロジェクトを削除する

補足

  • 終了コードは、成功（同期した・変更がなかった）が 0、中断が 1、削除の保留（S2・S3・S4）があるときが 3 です。3 のときも、追加・変更のコミット・プッシュと、ほかのブランチへの伝播は済んでいます（GitHub Actions では、ジョブが失敗として表示されます）。S5（直近にマージされたファイル）の保留だけのときは 0 です。
  • 同期の対象のフォルダは、force-app/main/default の下の、metadata.txt の種類に当たるフォルダ（種類とフォルダ名の対応は、sf-tools の config/metadata-dirs.txt）と、取得結果にあるフォルダです。それ以外（metadata.txt にない種類のフォルダなど）は触りません。objects のように、複数の種類が共有するフォルダは、フォルダ単位で同じにします。
  • 削除しないファイル: .gitkeep と、.forceignore の行に当たるファイル。
  • 変更の検知（環境変数 SF_METASYNC_DETECT。off が既定）: 組織に変更があるかを、全件取得の前に調べて、変更がなければ取得を省きます。off = 行わない（従来どおり、毎回、全件取得）／ shadow = 検知はするが、取得は常に行う（検知が「変更なし」なのに、実際は変更があったときは、警告で一覧を出す。運用の前の確かめ用）／ on = 「変更なし」なら取得を省く。種類ごとに、設定変更の履歴（A）か、更新日時の一覧（B）で調べます（sf-tools の config/metasync-detect.txt）。表にない種類は、検知できないため、毎日 1 回の全件取得（--full）でだけ反映されます（最大約 1 日の遅れ）。検知の状態は sf-tools/metasync/state.json に持ち、変更あり・不明の回にだけ更新します（状態だけが変わるコミットは、ほかのブランチへ伝えません）。検知は取得を省く手がかりで、失敗や不明のときは、必ず全件取得します。接続ユーザーに「設定・定義の参照」の権限がないと、履歴の問い合わせが失敗し、毎回、全件取得になります。
  • 以前の動作との違い: 以前は、組織で削除されたものが main に残り続け、差分の解析に sfdx-git-delta（公式サポート外のプラグイン）を使っていました。今は、削除が反映され、プラグインは使いません。初回は、たまっていた古いファイルが一度に削除の対象になり、保留（終了コード 3）になることがあります。手元で --dry-run で確かめてから --allow-mass-delete で実行してください。
  • 未コミットの変更の判定と退避は、追跡中のファイルだけが対象です。手元で実行したときは、追跡していない（新しい）ファイル（.gitignore の対象と、sf-tools/release/ を除く）があると、同期のコミットに無関係なファイルが含まれてしまうため、手順 5 で中断します。GitHub Actions 上では、確認しません。sf-tools/release/（作業用のブランチの作業ファイル）は、確認の対象外で、同期のコミットにも含めません。
  • branches.txt がない・ブランチの定義がないときは、警告を表示し、main だけとして扱います（ほかのブランチへは伝えません）。
  • 完了のメッセージには、実際に伝播できたブランチだけが表示されます。リモートにない・失敗したなどでスキップしたブランチは、警告で一覧されます（終了コードは 0 のままです）。
  • ログは ./sf-tools/logs/sf-metasync.log です（実行のたびに作り直します）。

取得するメタデータの種類（sf-tools/config/metadata.txt）

取得する種類は、各プロジェクトの sf-tools/config/metadata.txt で決まります（sf-init が、雛形から作ります）。コメント行・空行を除いた各行が、取得する種類です。設定ファイルだけで調整でき、コードの変更は要りません。

前提

雛形の標準セットは、Developer Edition（Sales・Service の標準機能つき）でのみ、リリースと削除を確認しています。ほかのエディション・製品（Service Cloud・Experience Cloud・業種クラウドなど）で使う場合は、必要な種類を足してください。

区分既定内容
1. 標準セット有効Developer Edition で、リリース・削除を確認済み（Apex・LWC・オブジェクト・項目・Layout・権限・レポート・ワークフローなど）
2. 標準だが制限あり有効更新のみ・権限による・一部未確認（StandardValueSet・Flow・Settings など。理由は、ファイル内のコメント）
3. 機能が必要なものコメントアウトService Cloud 系（Entitlement・Omni-Channel・Knowledge）・Experience Cloud 系。使う組織だけ、コメントを外す
4. 未確認コメントアウト確認できていない種類。使う場合は、外して、リリースを確かめる
5. 参考コメントアウトそのほかの種類の候補（業種クラウド・AI・分析など）
  • 取得の対象に、その組織にない種類があっても、警告になるだけで、取得は続きます。
  • 種類ごとの確認の状況は、sf-typecheck.sh --coverage で見られます（変更セットで扱える種類のうち、確認済み・未確認の数）。
  • リリース・削除できないと確認済みの種類は、ターゲットファイルに書くと、sf-check.sh が止めます（警告だけの種類もあります）。
  • すでに作成済みのプロジェクトの metadata.txt は、雛形が更新されても、変わりません。
