🔐 認証情報（Secrets / Variables）

GitHub 上の自動処理が、Salesforce や Slack に接続するときに使う、認証情報（パスワードの代わりになる情報）のページです。sf-init.sh が登録するものの一覧と、あとから登録し直す sf-update-secret.sh の使い方を説明します。

このページの要点
  • Secret は、隠すもの（秘密鍵・コンシューマーキー・Token）。Variable は、見えてよいもの（ユーザー名・URL・チャンネル ID）です。
  • どれも、sf-init.sh が、最初に登録します。
  • Salesforce の接続（JWT 認証）の情報を、あとから登録し直すときは、sf-update-secret.sh（管理者専用）を使います。接続先の組織そのものを変えるときは、sf-init.sh --reconnect を使います。
  • PAT_TOKEN と Slack の情報（SLACK_BOT_TOKEN・SLACK_CHANNEL_ID）は、sf-update-secret.sh では更新できません（そのほかの情報の登録し直し）。

使い分け

認証情報は、隠すべきかどうかで、2 種類に分けて登録します。Secret は、GitHub が暗号化して、人にも見えないように保管します。Variable は、見えても問題のない設定です。

項目種別説明
SF_PRIVATE_KEYSecretJWT 認証の署名に使う、RSA の秘密鍵（すべての段階で共通）。鍵のファイルを、1 行の Base64 の文字列にして登録します。元のファイルは、sf-init.sh を実行した PC の ~/.sf-jwt/force-XXXX/server.key にあります
SF_CONSUMER_KEY_*Secret外部クライアントアプリ（または、従来の接続アプリケーション）のコンシューマーキー。アプリを見分けるための ID のようなものです
PAT_TOKENSecretGitHub の Personal Access Token（Classic。repo・workflow）。force-* のリポジトリの、オーナー（組織の場合は、その組織の管理者）のもの。sf-tools（公開リポジトリ）とは、関係ありません
SLACK_BOT_TOKENSecretSlack Bot のアクセストークン（xoxb- で始まる文字列）
SF_USERNAME_*Variable接続に使う、Salesforce のユーザー名（平文で問題ありません）
SF_INSTANCE_URL_*Variableログイン先の URL（login.salesforce.com・test.salesforce.com・組織の URL のどれか。平文で問題ありません）
SF_ORG_ID_* / SF_ORG_NAME_* / SF_ORG_KIND_* / SF_ORG_CHECKED_*Variable接続した組織の ID・名前・種類（本番 / Sandbox など）・確認した日時。組織の情報を読み取れたときに、自動で保存します（--status の一覧に使います）
SLACK_CHANNEL_IDVariable通知先の Slack チャンネル ID（平文で問題ありません）
SF_TOOLS_BRANCHVariableGitHub Actions が使う sf-tools のブランチ。sf-init.sh のステップ 2 で「開発版（development）」を選んだときだけ、development を登録します（sf-tools の開発者用）。ふつうは登録されず、未設定なら main（配布版）を使います

* の部分は、段階（組織）ごとに変わります。main は PROD、staging は STG、develop は DEV です（例: SF_USERNAME_PROD）。

SF_TOOLS_TOKEN は不要です

sf-tools は公開リポジトリのため、wf-metasync / wf-validate / wf-release は、Token なしで sf-tools を clone します。以前のバージョンにあった、Token（SF_TOOLS_TOKEN）の作成・登録は、ありません。

以前のバージョンで作ったプロジェクトに、SF_TOOLS_TOKEN が登録されていても、そのままで構いません。ただし、そのプロジェクトのワークフローが Token 付きで clone している間は、その Token を無効にしないでください（無効な Token では、公開リポジトリでも clone に失敗します）。ワークフローを新しい雛形（Token なし）に更新したあとなら、Token と Secret を削除して構いません（ワークフローの更新）。

再登録する（sf-update-secret.sh）

sf-update-secret.sh
sf-update-secret.sh -v    # 実行したコマンドの応答も、画面に表示する

Salesforce の接続（JWT 認証）に使う GitHub の Secrets / Variables を、項目を選んで登録し直します。JWT の秘密鍵を作り直したとき、コンシューマーキーや接続ユーザーが変わったときなどに使います。force-* フォルダの中（管理者用の admin/force-XXXX など）で実行してください。対象のリポジトリは、そのフォルダの Git の設定（origin）から、自動で決まります。

管理者専用

実行の前に、赤い警告ボックスと、確認（「続行しますか？」Y/N/q。N / q で中断）が表示されます。続けて、gh にログインしているユーザーが、リポジトリのオーナー本人か、その組織の有効な管理者かを確かめます（違えば、止まります）。GitHub Actions の上では、警告と確認を出さずに実行します。

接続先の組織そのものを変える（別の組織につなぎ直す）ときは、このコマンドではなく、sf-init.sh --reconnect を使います。外部クライアントアプリの作成から、まとめてやり直せます。

こんなときは、どのメニューか

メニューは、1 秘密鍵 / 2 コンシューマーキー / 3 ユーザー名 / 4 すべて です（番号のキーを 1 つ押します。q で中断）。

こんなとき選ぶメニュー登録するもの
JWT の秘密鍵を、作り直した1 秘密鍵Secret SF_PRIVATE_KEY（接続のテストは、しません）
外部クライアントアプリ（コンシューマーキー）を、作り直した2 コンシューマーキーSecret SF_CONSUMER_KEY_*（接続のテストに成功したら）
接続するユーザーを、変えた3 ユーザー名Variable SF_USERNAME_*（接続のテストに成功したら）
まとめて、全部やり直したい4 すべて上の 3 つと、Variable SF_INSTANCE_URL_*（段階ごとに、接続のテストに成功したら）
接続先の組織を、別の組織に変えたいこのコマンドではなく --reconnect—
PAT_TOKEN の期限が切れた・Slack の設定を変えたいこのコマンドでは更新できませんそのほかの情報の登録し直し

どのメニューでも、接続のテストで組織の情報を読み取れたときは、Variable SF_ORG_*（組織の ID・名前・種類・確認日時）も保存します（保存に失敗しても、警告を出して続けます）。

画面の流れ

  1. 必要なツール（sf・gh・git・openssl）があるかを確かめます。

  2. 管理者向けの警告と確認が出ます（上の「管理者専用」）。

  3. Git の設定（origin）から、対象のリポジトリ（オーナー/リポジトリ名）を決めます。gh のユーザーが、オーナー本人か、その組織の管理者かを確かめます。

  4. Salesforce CLI（sf）が、正しく動くかを確かめます（npm 版が必要です。確認に成功すると、24 時間は省略します）。

  5. メニューで、更新する項目を選びます。

  6. メニュー 2・3 は、段階（組織）を選びます。選べる段階は、branches.txt の段階の数で決まります（1 つ: PROD / 2 つ: ＋STG / 3 つ以上: ＋DEV）。メニュー 4 は、すべての段階を、順に行います。

  7. 項目に応じて、秘密鍵のファイル・コンシューマーキー・接続ユーザー名を入力し、ログイン先を選びます。接続のテストに成功したら、登録します。

  8. 最後に「JWT Secrets の更新が完了しました。」と表示されます。確認で N と答えて、何も登録しなかったときも、この表示になります。

補足

  • 秘密鍵のファイル: メニュー 1 は、いつも、ファイルの場所を入力します（例: ~/.sf-jwt/force-XXXX/server.key。先頭の ~ は、ホームフォルダとして扱います）。メニュー 2〜4 は、~/.sf-jwt/force-XXXX/server.key があれば、それを使い、なければ、場所を入力します。ファイルがなければ、止まります。
  • 確認: メニュー 1・4 は、秘密鍵を登録する前に、確認（Y/N）が出ます。メニュー 4 で Y と答えると、接続のテストより前に、秘密鍵を登録します（N なら、秘密鍵は登録しません）。メニュー 2 は、ユーザー名が登録済みなら、「このユーザー名で接続テストを実行しますか？」と聞かれます（N なら、ユーザー名を入力します）。
  • ユーザー名: メニュー 3 では、いまの登録値を、自動で取得して表示します。コンシューマーキーも入力しますが、接続のテストに使うだけで、登録しません。
  • ログイン先: login.salesforce.com / test.salesforce.com（Enter の既定）/ 組織の URL（My Domain）から選びます（ログイン先の選び方）。メニュー 4 では、選んだ URL を SF_INSTANCE_URL_* として登録します。メニュー 2・3 では、接続のテストにだけ使い、登録しません。
  • 接続のテストに失敗したとき: そこで止まります。それより前に登録した値（メニュー 4 の秘密鍵など）は、そのまま残ります。
  • 本番組織のガード: STG・DEV に、本番組織、または種類を判定できない組織を接続しようとすると、登録する前に止まります。PROD で種類を判定できないときは、警告を出して続けます。
  • JWT の接続テストは、一時的なホームフォルダの中で実行します。あなたの sf に、エイリアス（prod など）が増えたり、同じユーザーの既存のログインが置き換わったりしません（sf-init.sh の接続テストも同じです）。
  • 入力の途中で q を押すと、止まります。登録に失敗したときも、止まります。
  • 記録（ログ）は、実行した force-* フォルダの中の sf-tools/logs/sf-update-secret.log に残ります（実行のたびに作り直します）。知らないオプションを付けると、「不明なオプションです」と表示して止まります。

そのほかの情報の登録し直し

sf-update-secret.sh は、Salesforce の接続（JWT 認証）のためのコマンドです。次のものは、扱えません。

PAT_TOKEN は、このコマンドでは更新できません

Token を無効にしたり、有効期限が切れたりしたときは、リポジトリのオーナー（組織の場合は、その組織の管理者）のアカウントで、新しい Token（Classic。repo・workflow）を発行します（作り方は、GitHub の Token（PAT）と同じです）。そして、リポジトリの Secrets の PAT_TOKEN を登録し直してください（トラブルシューティング）。force-* フォルダの中なら、次のコマンドでも登録できます（実行すると、Token の入力を求められます）。

gh secret set PAT_TOKEN

Slack の Bot Token（SLACK_BOT_TOKEN）と、通知先のチャンネル ID（SLACK_CHANNEL_ID）も、同じように、force-* フォルダの中で登録し直せます。

gh secret set SLACK_BOT_TOKEN       # Token の入力を求められます
gh variable set SLACK_CHANNEL_ID    # チャンネル ID の入力を求められます

どれも、sf-init.sh --status の診断で足りないと表示されたときに、同じ直し方が表示されます。
