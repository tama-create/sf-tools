💻 開発者向けコマンド

開発者が毎日使うコマンドの、詳しい説明です。全体の一覧は、コマンド一覧にあります。使い方の流れを知りたいときは、先に日々の開発の流れを読むと、分かりやすくなります。

sf-job.sh

sf-job.sh

新しい作業（ブランチ）を始めるときの、オールインワンのスクリプトです。作業フォルダ（作業単位のフォルダを置く場所）で実行します。

主な処理

  • ジョブ名（例: JOB-20260323）を入力して、GitHub 上に、main の最新から作業用のブランチを作る
  • git clone で、そのブランチを ./ジョブ名/force-XXXX に取り出す
  • そのフォルダで sf-start.sh を自動で起動する（組織への接続・VS Code の起動。続けて、ランチャーも起動します）

補足

  • ブランチの作成から VS Code の起動まで、すべて自動です。新しい作業は、必ずここから始めます。
  • ジョブ名は、英数字で始まり、英数字・-・_ だけの 1〜50 文字です。環境ブランチと管理者用のブランチの名前（main / staging / develop / admin）は、使えません。同じ名前のフォルダ（./ジョブ名/force-XXXX）がすでにあるときも、入力し直しになります。
  • GitHub 上に同じ名前のブランチがすでにあるときは、最後のコミットの作者と日時を表示して、確認します。
    • Y: そのブランチを使って続ける（ブランチを作ったあとに clone が失敗した、前回のジョブの続き）
    • N: 別のジョブ名にする。ほかの人のジョブのブランチなら、N にしてください
  • --project だけを指定して、同じプロジェクト名のクローンが複数のオーナーにあるときは、最初のものを黙って使わず、オーナーを選ばせます。
  • 実行するフォルダの名前が admin のとき、または force- で始まるときは、実行できません（フォルダの名前だけで判定します）。
  • 途中で中断・失敗しても、それまでに作ったブランチ・フォルダ・クローンは、削除しません。ブランチを作ったあとに clone が失敗したときは、同じジョブ名でもう一度実行し、既存のブランチを使う（Y）と、続きから進められます。
  • sf-start.sh が失敗で終わると、sf-job.sh も中断します（クローンは残ります）。sf-job.sh は、ランチャーを終了するまで終わりません。

プロジェクトの決まり方

どのプロジェクト（オーナーと XXXX）を使うかは、フォルダの名前では決まりません。次の順で決めます（上にあるものが優先です）。

  1. 引数の --owner / --project
  2. 作業フォルダの下にあるクローンの git remote。クローンしたときに、Git が記録した住所から、オーナーとリポジトリの名前を読み取ります（1 種類だけなら自動、複数なら番号で選びます）
  3. 対話で入力

sf-start.sh

sf-start.sh

既存のブランチで、開発環境を起動し直します。force-* フォルダの中で実行します。

役割

  • 組織への接続を確認し、必要なときだけログインする
  • .sf/config.json と .sfdx/sfdx-config.json を更新する
  • code . を実行する（code コマンドがなければ、警告だけで先へ進みます）
  • sf-install.sh を、バックグラウンドで実行する（~/sf-tools の更新・Git フックの設置・リリース用フォルダの準備・npm install など）
  • 最後に、ランチャー（sf-launcher.sh）を前面で起動する

補足

  • sf-job.sh が内部で自動で呼ぶので、新しい作業のときは、直接実行する必要はありません。
  • 前日の続きなど、既存のブランチに戻るときに使います。
  • 接続済みかどうかは、.sf/config.json の組織を sf org display で確かめて判断します。接続済みなら、ログインを省略します。
  • ログインに失敗したら、エラーで終了します（設定ファイルの書き込み・VS Code の起動・ランチャーの起動は、行いません）。
  • 終了コードは、ランチャーの結果によらず 0 です。バックグラウンドの sf-install.sh が失敗しても、影響しません。
  • 接続済みの組織を切り替えるときは、sf-restart.sh を使います。

sf-launcher.sh（ランチャー）

sfl          # メニュー形式で選択
sflf         # fzf でインクリメンタル検索
sfl 4        # 番号を直接指定して、すぐ実行

sf-tools の主なコマンドを、メニューから選んで実行できます。force-* フォルダの中で使います。

  ──────────────────────────────────────────────────
  >> Launcher <<
  ──────────────────────────────────────────────────
  [1] Check      ターゲットファイルの構文チェック
  [2] Push       変更をコミット & プッシュ
  [3] Next       次の PR 先ブランチを確認
  [4] Dryrun     現在接続中の組織へリリース検証
  [5] Deploy     現在接続中の組織へリリース
  [6] Start      開発環境を起動（Salesforce ログイン・VSCode 起動）
  [7] Restart    接続組織を切り替えて Start 実行
  ──────────────────────────────────────────────────
  番号を入力 (1-7 / q で終了):

VS Code の中では、start と restart は表示されません（二重に起動しないため）。

  • メニューでは、番号を 1 文字入力すると（Enter 不要）実行し、終わるとメニューに戻ります。q で終了します。範囲外の数字や、数字と q 以外の入力は、無視されます。
  • 番号を直接指定したとき（sfl 4 など）は、そのコマンドを 1 回だけ実行して終わります。選んだコマンドは、引数なしで実行されます。
  • sflf（--fzf）には、fzf が必要です。なければ、警告を表示して終了します。
  • メニューの中では、実行したコマンドが失敗しても、ランチャーは終了しません。

sf-check.sh

sf-check.sh [deploy-target.txt] [remove-target.txt]

ターゲットファイルの構文を確認します。通常は、sf-release.sh や sf-prepush.sh から自動で実行されます。

確認する内容

  • [files] セクション: 書いたパスが、リポジトリの中にあるか。絶対パスや .. を含むパスなど、リポジトリの外を指すパスは、存在していてもエラーです。
  • [members] セクション: 種別名:メンバー名 の書式になっているか。
  • 種類の可否: config/metadata-capability.txt（sf-typecheck.sh が、実際の組織で確かめた表）で、API ではリリース・削除できないと確認済み（ng）の種類を書くと、エラーにします。条件によってできないことがある種類（limited。権限・使用中・標準のものなど）は、警告にします。組織の権限でできる場合は、環境変数 SF_CHECK_IGNORE_CAPABILITY=1 で、この確認を省略できます。
  • テストクラスの不足: Apex クラス（通常のクラス）に対応するテストクラスがローカルにあるのに、deploy-target.txt に含まれていないときは、警告を出します（エラーにはなりません）。
    • 手順 A: 命名規則（MyClassTest.cls / MyClass_Test.cls）で、同じフォルダを探す
    • 手順 B: A で見つからなければ、@isTest を含む .cls ファイルを、内容で探す（クラス名を単語として含む、最初のファイル）
    • 本番や Sandbox にすでにあるテストクラスは、含めなくてよいため、警告にとどめています。テストクラスが見つからないときは、何も表示しません。

補足

  • 引数を省略すると、sf-tools/release/branch_name.txt（sf-start.sh / sf-install.sh が保存するファイル）に書かれたブランチ名で、release/<ブランチ名>/ の下を探します。今の Git のブランチではなく、このファイルの内容を使います。ファイルがないときは、何も検証せず、警告を表示して、正常（終了コード 0）で終わります（main など、リリース用のフォルダを作らないブランチでは、このファイルがないため、コミットは止めません）。
  • 引数が 2 つ以上のときは、1 つ目を deploy-target.txt、2 つ目を remove-target.txt として検証します。1 つのときは、deploy-target.txt だけです。
  • ターゲットファイルがないときは、そのファイルの検証を飛ばします（エラーにはしません）。-v / --verbose 以外の - で始まる引数は、「不明なオプションです」で中断します。
  • 終了コードは、0 が正常（警告があっても 0）、1 がエラー（書式・パス・種類の可否が ng）です。

sf-dryrun.sh

sf-dryrun.sh

sf-release.sh のラッパーで、dry-run（検証だけ）専用のコマンドです。ランチャーの [4] Dryrun から呼ばれます。

  • sf-release.sh の既定が dry-run なので、オプションなしで呼ぶだけで、検証が実行されます。
  • 直接 sf-release.sh を実行しても、同じ動作になります。
  • 受け取った引数は、すべてそのまま sf-release.sh に渡します（-n・-t・-v など）。
-r / --release を付けると、実際にリリースします

検証だけのつもりで sf-dryrun.sh -r と実行すると、リリースモードになります（GitHub Actions の外では、確認（Y/N/q）が表示されます）。検証だけが目的なら、付けないでください。

sf-release.sh

sf-release.sh [オプション]

ターゲットファイルの内容を、接続中の組織へ検証またはリリースします。既定は dry-run です。

オプション内容
（指定なし）, --validate, --dry-run検証だけを行う（sf project deploy start --dry-run）。--validate と --dry-run は、指定なしと同じ
--release, -rデプロイを実行する（dry-run を解除）
--no-open, -nブラウザを開かない
--force, -f--ignore-conflicts を付ける
--target, -t対象の組織のエイリアスを指定する（-t ALIAS / --target ALIAS の形。--target=ALIAS は使えません）
--json, -jsf コマンドの出力を、JSON 形式で表示する
--verbose, -vコマンドの出力を、コンソールにも表示する
テストクラスは自動で指定されます

deploy-target.txt に書いた .cls ファイルに @isTest があれば、自動で検出し、--test-level RunSpecifiedTests --tests <クラス名> を設定します。手動で指定する必要はありません。検出されなければ、--test-level は付けません。

処理の流れ

  1. 接続先の組織を決める。優先順位は、-t の値 → 環境変数 SF_TARGET_ORG → sf org display のエイリアス。決まらなければ中断する
  2. 接続先が予約名（prod / staging / develop / main）なら、検証モードでも中断する（共有環境には、ローカルから実行できません）
  3. GitHub Actions の外で --release を付けたときは、確認（Y/N/q）を表示する。-f も付けたときは、確認の前に、上書きの警告を表示する
  4. sf-tools/release/branch_name.txt のブランチ名で、release/<ブランチ名>/ を対象にし、sf-check.sh で構文を検査する（エラーなら中断）
  5. マニフェスト（package.xml / destructiveChanges.xml）を作り直す。対象が 1 件もなければ、何もせず正常（終了コード 0）で終わる
  6. （-n がなければ）組織のデプロイ状況の画面を、ブラウザで開く
  7. sf project deploy start を実行する。削除対象があれば、デプロイより先に削除される（--pre-destructive-changes）

補足

  • deploy-target.txt が空で、remove-target.txt にだけ対象があるときは、メンバーのない package.xml を作り、削除だけを行います。
  • 組織にない削除対象をエラーにしたくないとき（後始末など）は、remove-target.txt に # @ignore-missing で始まるコメント行を書きます。sf project deploy start に --ignore-warnings が付き、削除以外の警告も、エラーになりません。通常のリリース・削除では、付けないでください（綴りの誤りを、見落とさないためです）。
  • 終了コードは、成功（対象なしを含む）が 0、中断・失敗が 1 です。ログは ./sf-tools/logs/sf-release.log に、毎回上書きされます。

sf-deploy.sh

sf-deploy.sh [オプション]

sf-release.sh --release --force を簡単に呼ぶラッパーです。Sandbox の乗り換えなどで、現在の開発物を、接続中の組織へ強制的にリリースする用途で使います。追加で使えるオプションは、--no-open（-n）・--target（-t）・--verbose（-v）です。

個人用の Sandbox / Developer Edition / Scratch Org 専用です

共有環境（本番・staging・develop）には、ローカルの PC からリリースできません。GitHub にコミットして、レビューを通し、GitHub Actions で行います。

sf-tools は、組織のエイリアスの名前 prod / staging / develop（と、互換のための main）を、共有環境として予約しています。この名前の組織を接続先にすると、確認（Y/N/q）の前に、拒否されます。sf-init は、この名前で組織を登録します（sf-start.sh も、prod を本番として扱います）。

予約名以外の名前に付け替えた場合は、動作を保証しません。名前で判断しているため、共有環境の組織を別の名前で接続すると、この保護は働きません。共有環境の組織は、予約名のまま使ってください。

実行の前に、--force の警告と確認（Y/N/q）が表示されます。N または q で中断できます。

  • 環境ブランチの上では、実行できません。現在のブランチが、sf-tools/config/branches.txt に書かれたブランチ（ファイルがない・空のときは main）なら、中断します。作業用のブランチで実行してください。
  • 接続先は、-t の値 → 環境変数 SF_TARGET_ORG → sf org display のエイリアスの順に決まります。
  • 使えないオプション（2 番目以降の -h を含む）は、確認（Y/N/q）の前に、「不明なオプションです」で中断します。
  • 終了コードは、中断が 1、それ以外は sf-release.sh の終了コードです。

sf-push.sh

sf-push.sh

カレントフォルダの下の変更を、コミットしてプッシュします。

主な処理

  1. origin/main を fetch して、現在のブランチにマージする（コンフリクトしたら、エラーで中止）
  2. カレントの下を git add --all する
  3. sf-check.sh で、構文を確認する
  4. VS Code を別のウィンドウで開いて、コミットメッセージを入力する
  5. git commit → git push

補足

  • コミットメッセージが未入力なら、何もせずに終了します。
  • 変更がなくても、未プッシュのコミットがあれば、コミットせず、プッシュだけ行います。コミットは成功してプッシュが失敗したあとに、もう一度 sf-push.sh を実行すれば、取り残されません。
  • ブランチの上にいないとき（detached HEAD）と、保護ブランチ（sf-tools/config/branches.txt に書かれたブランチ。ファイルがない・空のときは main）の上にいるときは、何もコミットせずに、エラーで終了します。
  • 手順 1 の取り込みで、コンフリクトなどにより失敗したときは、git merge --abort で取り消して、エラーで終了します。
  • ステージするのは、カレントフォルダの下だけです。ただし、コミットでは、パスを指定しません。カレントの外で、前からステージ済みだった変更も、一緒にコミットされます。
  • コミットメッセージを未入力で閉じたときは、コミットもプッシュもしません。手順 1 の取り込みと、ステージは、元に戻らず、そのまま残ります。
  • コミットとプッシュのときは、インストール済みの pre-commit / pre-push フックも動きます。
  • 終了コードは、正常終了（何もせず終わった場合を含む）が 0、エラーが 1 です。

sf-next.sh

sf-next.sh

現在の feature ブランチが、develop / staging / main のどこまでマージ済みかを確認し、次に出すべき PR 先のブランチを案内します。

表示されるステータス

記号ステータス説明
✓マージ済み直接 PR をマージ済み（デプロイのワークフローも実行済み）
✓マージ済み（ブランチ同期）直接の PR はないが、上位のブランチ経由でコードが伝わっている。デプロイのワークフローは未実行
⚠マージ済み（順序外）前のブランチの直接 PR が完了する前に、マージ済み。前のブランチのデプロイは未実行
→PR 発行中PR を出してあり、マージを待っている
▶次の PR 先次に PR を出すべきブランチ
✗未着手まだ PR を出していない

判定の方法

  1. gh pr list --state merged で、現在のブランチ → 対象ブランチの直接 PR を確認する → 「マージ済み」
  2. git merge-base --is-ancestor で、上位ブランチ経由の伝わり方（間接）を確認する → 「マージ済み（ブランチ同期）」
  3. gh pr list --state open で、PR 発行中かを確認する → 「PR 発行中」
  4. どれにも当てはまらなければ → 「次の PR 先」または「未着手」

順序外のマージの制約

develop → staging → main の順番を守らずにマージすると、飛ばしたブランチへのデプロイは、できなくなります
  • 上位のブランチ（例: main）にマージすると、コードが下位のブランチ（例: staging）に伝わります。
  • 伝わったあとは「差分なし」になり、feature → staging の直接 PR を作れなくなります。
  • デプロイのワークフローは、直接 PR のマージで起動するため、伝わっただけでは動きません。

飛ばしたブランチにデプロイしたいときは、新しいブランチを切って、順序どおりに PR を出し直します。

順序外の PR を、レビュアーが見つける仕組み（wf-sequence）

sf-next.sh を使う限り、PR の先は「次の段階」だけです。ランチャーを使わず、GitHub 上で直接 PR を作って段階を飛び越したときは、PR を作った時点で、次のようにレビュアーに知らせます。

通知先内容
PR の会話欄「⚠️ マージ順序の確認が必要です。意図的でなければ、この PR は却下してください」というコメント（同じ PR では、既存のコメントを更新します）
Slack通知

マージは止めません（緊急の Hotfix を妨げないため。Free プランの Private リポジトリでは、GitHub がそもそも止められません）。気づいたレビュアーが、PR を却下します。

補足

  • 保護ブランチ（sf-tools/config/branches.txt に書かれたブランチ。ファイルがない・空のときは main）の上と、ブランチの上にいないとき（detached HEAD）は、エラーで終了します。
  • 次の PR 先があるときは、「PR を出しますか？」と確認します（Y/N/q）。Y で、その PR 作成画面を、ブラウザで開きます（PR そのものは、作りません）。N は何もせず終了、q は中断（終了コード 1）です。
  • PR の一覧は、マージ済み・オープンとも、最新の 50 件だけを取得します。gh が使えないなど、取得に失敗したときは、警告を出さずに「PR なし」として判定します。
  • リモートの最新を取得できなかったときは、警告を出して続行し、手元の origin/* で判定します。
  • 次の PR 先がないときは、「PR 発行中」が残っていれば「マージ完了を待ってください」、なければ「全ブランチへのマージが完了しています」と表示して終わります。

sf-restart.sh

sf-restart.sh

接続先の組織を切り替えたいときに使います。force-* フォルダの中で実行します。

主な処理

  1. 接続の設定ファイル（.sf/config.json と .sfdx/sfdx-config.json）を、一時フォルダに退避してから、確認なしで削除する
  2. 接続済みでも、組織のエイリアスの入力とログインからやり直す形で、sf-start.sh を実行する

補足

  • sf-start.sh が失敗したとき（ログインの失敗・入力の中断など）は、新しい設定ファイルが書かれていなければ、退避しておいた元の設定ファイルを戻します（戻したときは、警告を表示します）。成功したときは、新しい設定ファイルに置き換わります。

sf-hook.sh / sf-unhook.sh

sf-hook.sh
sf-unhook.sh
  • sf-hook.sh: ~/sf-tools/hooks/ の pre-commit と pre-push を、.git/hooks/ にコピーして、実行権限を付けます。既存のファイルは、確認もバックアップもなしに上書きします。git config core.hooksPath に husky が含まれていれば、確認なしに設定を削除します（元には戻しません）。
  • sf-unhook.sh: .git/hooks/pre-push を削除します。pre-commit は残ります。sf-tools が置いたフック（目印の文字列がある）だけを削除し、それ以外のフックなら、警告を表示して、削除しません。

どちらも、force-* フォルダの、Git リポジトリのルート（.git がある場所）で実行します。-v / --verbose 以外の引数は、「不明なオプションです」で中断します。

フックの動きは、sf-prepush.sh と sf-precommit.sh にあります。
