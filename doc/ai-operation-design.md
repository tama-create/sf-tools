# 会話で sf-tools を動かす（AI 操作）の設計

> 状態: 実装済み（2026-11-26。Codex のレビュー 4 回で条件つき承認（10 章）。条件の `run` の 20 は、`tests/test_common.sh` の `test_ai_mode_input` で確かめる）。9 章の未決 3 件は、2026-11-27 に決めた（11 章。PR の作成・`sf-job.sh` の追加の設計。11 章も実装済み（2026-11-27。Codex の実装レビューで承認））
> 目的: 開発者が、ランチャーの番号ではなく、Claude Code・Codex への言葉（「チェックして」「反映して」「PR を出して」）で、sf-tools を動かせるようにする。
> 正本の手順書は `doc/ai-dev-loop.md`（force-* の `CLAUDE.md`・`AGENTS.md` が指す）。この文書は、その変更と、コマンド側に足す仕組みの設計。

## 1. 背景

- 今は、人がランチャーを開いて、番号で操作している。AI は、確認（Y/N）に答えられないため、`sf-deploy.sh`・`sf-next.sh` は「人に頼む」決まり（`ai-dev-loop.md` の 2 章）
- 2026-11-26 の force-test-win の実証で、人の指示で AI が `sf-deploy.sh` を動かした。確認には `printf 'y' |` で答えた。動いたが、次の弱さがある
  - 標準入力に流した答えが、どの質問に使われるか分からない（質問が 2 つあるコマンドでは、人が見ていない 2 つ目にも答えてしまう）
  - 質問の文を、AI が前もって知る方法がない（人に何を聞けばよいか分からない）
- `sf-push.sh` は、コミットのメッセージを VS Code で入力させるため、AI からは使えない（同じ実証で、意図しないメッセージ「P4 の確認: 段階 1」のコミットができた）

## 2. 方針

1. **ルールの置き場所は `doc/ai-dev-loop.md`**（Claude Code・Codex の両方が読む。`git pull` で全員に届く）。force-* ごとの `CLAUDE.md` には書かない。Claude Code のスキルは、必要になったら、呼び出しの近道として薄く足す（ルールの正本にしない）
2. **AI はランチャーを使わず、コマンド（`bin/sf-*.sh`）を直接動かす**（番号の並びに左右されない）
3. **「全部はい」にする設定は作らない。** 書き込む操作は、AI が会話で内容を示し、人の「はい」をもらってから、その質問だけに答えを渡す（質問ごとに名前を付けて渡す。4）
4. **AI のときの動きは、明示の印（環境変数 `SF_TOOLS_AI=1`）があるときだけ変える。** 人の操作・テスト・GitHub Actions の動きは、今のまま
5. 安全の決まり（管理者向けの警告と確認のセット・共有の組織と本番の拒否）は、緩めない

## 3. コマンドの区分

| 区分 | コマンド | AI の扱い |
|---|---|---|
| A 読むだけ | `sf-check.sh`・`sf-dryrun.sh -n`・`sf-next.sh`（`next.pr=n` で、状況の表示だけ。PR の作成画面は開かない）・`sf-log.sh status` / `pull` | 言われたら、確認なしで動かす（今と同じ）。`git fetch`・`gh pr list`・組織の問い合わせなど、読むだけの通信はする |
| B 書き込む（自分の組織・Git・GitHub） | `sf-deploy.sh`（自分用の組織）・`sf-push.sh`・`sf-next.sh`（`next.pr=y` で、PR の作成画面を開く。`--create` なら PR を作る。11.2）・`sf-job.sh --name`（新しい作業のブランチとクローン。AI のときは sf-start を動かさない。11.3） | 会話で内容を示し、人の「はい」をもらってから、答えを渡して動かす（5 章） |
| C 人が動かす | `sf-start.sh`・`sf-restart.sh`（VS Code・ブラウザでのログイン。`sf-job.sh` のあとの sf-start も） | 人に頼む（今と同じ。11.1） |
| D 動かさない | 管理者向け（`sf-init.sh` など）・`sf-log.sh start` / `stop` / `auto`・自動で動くもの | 動かさない（今と同じ） |

- 共有の環境の組織（予約名 `develop`・`staging`・`main`・`prod`）と本番には、コマンド側が手元からの反映を拒否する。AI の印があっても変わらない

## 4. 確認の仕組み（コマンド側に足すもの）

### 4.1 質問の名前

- B のコマンドの `ask_yn` に、質問の名前（英小文字・数字・`.`・`-`）を付ける。例: `ask_yn "強制デプロイ（--force）を実行します。続行しますか？" deploy.force`
- 名前は、コマンドの冒頭コメントの【補足】に一覧で書く（AI が前もって知れるように）

| 名前 | コマンド | 質問 |
|---|---|---|
| `deploy.force` | `sf-deploy.sh` | 強制デプロイ（--force）を実行します。続行しますか？ |
| `next.pr` | `sf-next.sh` | 〜にPRを出しますか？（2 つ目以降の段階では、前の段階で確かめたかも聞く） |
| `update.sftools` | `lib/project.sh`（sf-tools が古いとき） | sf-tools を更新しますか？ |
| `job.existing` | `sf-job.sh` | （GitHub に同じ名前のブランチがあるとき）このブランチを使って、続けますか？（11.3） |
| `job.create` | `sf-job.sh` | ▶ よろしいですか？（ジョブ名・ブランチ・クローン先の確認。11.3） |
| `push.message` | `sf-push.sh` | （質問ではなく、確認待ちの名前だけ）AI のとき `-m` がない。答えでは渡せない（`-m` で渡す。4.5） |

### 4.2 答えの渡し方

- 環境変数 `SF_TOOLS_ANSWERS` に、`名前=y` / `名前=n` を空白区切りで渡す。例: `SF_TOOLS_AI=1 SF_TOOLS_ANSWERS="deploy.force=y" bash ~/sf-tools/bin/sf-deploy.sh -n`
- 形式は厳密にする（Bash 3.2 で、連想配列・`mapfile` を使わずに読む）
  - 名前は `^[a-z][a-z0-9-]*(\.[a-z0-9-]+)+$`（`<コマンド>.<質問>`。コマンドの名前を先頭に付けて、ほかのコマンドの質問と重ねない）。値は `y` か `n` だけ
  - 形が違う項目・同じ名前が 2 つある・値が `y` / `n` でない → その場で中断する（推測で読まない）
  - 質問されなかった名前の答え（例: 次の PR 先がなく、`next.pr` が聞かれなかった）は、中断しない。受け取った答えは、起動のときに「（AI 経由の答えを受け取りました: …）」と出し、使った答えは「（AI 経由の回答: 名前=値）」と出す（使わなかったものは、この 2 つの差で分かる。終わりに WARNING を出すには、各コマンドの `trap … EXIT` と重ねる必要があり、壊しやすいため、出さない）
- `SF_TOOLS_AI=1` のときだけ、`SF_TOOLS_ANSWERS` を見る。自分の名前の答えがあれば、それを使い、画面とログに「（AI 経由の回答: deploy.force=y）」と残す
- **答えは、1 回の実行の中で 1 回だけ使う。** 同じ名前の質問が、同じ実行の中でもう一度出たら、答えがないものとして 4.3 で止まる（2 回目は、人が見ていないため）
  - 「使った」の記録は、そのプロセスの中の普通の変数（使った名前を空白区切りで足していく文字列）に持つ。`SF_TOOLS_ANSWERS` 自体は書き換えない（入力専用）
  - 子・孫のプロセスとの受け渡しは、4.6 の決まり（自分の答えを受け取ったら、子には渡さない）で閉じる。使った記録を、プロセスの間で受け渡すことはしない
  - `$( )` の中（サブシェル）で入力の関数を呼ぶと、使った記録も、20 での終了も、外に伝わらない。そのため、**入力の関数は `$( )` の中で呼ばない**（4.3）
- 名前のない質問・答えのない質問は、4.3 で止まる（ほかの名前の答えを流用しない）

### 4.3 確認待ちで止まる

- `SF_TOOLS_AI=1` で、答えがない質問に来たら、`need_answer <名前> <質問の文>`（`lib/input.sh` に新しく足す。`die` とは別）が、次の 1 行を標準エラーに出し、**終了コード 20**（`RET_NEED_ANSWER`。`lib/common.sh` で定義）で終わる。入力は待たない
  - `[確認待ち] <名前>: <質問の文>`
- 20 は、今のコマンドの終了コード（0・1・2・`sf-log.sh` の 10）と重ならない。親のコマンドは、子の 20 を、そのまま返す（ほかのエラーに変えない）。AI は、20 のときだけ「人に聞いて、やり直す」。20 以外の失敗を、やり直しの合図にしない
- AI は、この行を見たら、質問の文をそのまま人に聞き、答えを `SF_TOOLS_ANSWERS` に足して、同じコマンドを最初から動かし直す
- **止める仕組みは、いちばん下の入力の関数（`read_key`・`read_input`・`read_secret`）に置く。** `ask_yn`・`press_enter`・`read_or_quit`・`wizard_confirm` も、これらを通るため、名前の付け忘れや、`read_key` を直接使う箇所（`sf-log.sh` の「自動で取りますか？」など）があっても、AI のときは必ず止まり、待ち続けない・標準入力を誤って読まない
  - 名前を付けられるのは `ask_yn` だけ（4.1）。名前のない入力は、`[確認待ち] (名前なし): <質問の文>` で止まる。これは「AI からは答えられない質問」として、人に頼む合図にする
- `read_secret` は、AI のときは必ず止まる（Token などを AI に扱わせない。答えも受け取らない）
- AI の判定と `need_answer` は、各関数の**入力のループより前**で 1 回だけ行う（ループの中で、何度も止めない。無効な入力での再入力のループにも入らない）。`need_answer` は `exit` で終わるため、`|| die` や `wizard_confirm` の中で、別のエラーに変わらない
- **入力の関数（`read_key`・`read_input`・`read_secret`・`ask_yn` など）は、`$( )` の中で呼ばない。** サブシェルの `exit 20` は外に伝わらず、`|| ans=""` などで続いてしまうため。今あるのは `bin/sf-log.sh` の「自動で取りますか？」（`ans=$(read_key …)`）だけ。ここは、標準入力が端末でないときは聞かずに「今回は取らない（答えは保存しない）」で返るため、AI のとき（端末でない）は `$( )` の中の `read_key` に届かない。そのため直さず、テストで、この 1 か所だけを理由つきで除外して、`$(read_key`・`$(ask_yn`・`$(read_input` などの書き方が、`bin/`・`lib/`・`phases/` にほかにないことを確かめる（8 章）

### 4.4 止まる位置と、その前の処理（コマンドごと）

確認待ちで止まったとき、それまでに行った処理が、やり直しで困らないかを、コマンドごとに決める。

| コマンド | 質問の前に行うこと | 止まったときの扱い |
|---|---|---|
| `sf-deploy.sh` | 組織の決定・共有の組織と本番の拒否・ログの表示（組織は変えない） | 困らない（反映の前に止まる） |
| `sf-next.sh` | `git fetch`・`gh pr list`（読むだけ。`git fetch` は手元の `origin/*` を新しくするだけ） | 困らない（ブラウザを開く前・`--create` では PR を作る前に止まる） |
| `sf-job.sh` | gh の認証の確認・リポジトリと同じ名前のブランチの確認（読むだけ） | 困らない（ブランチの作成・クローンの前に止まる。11.3） |
| `sf-push.sh` | `origin/main` の取り込み（`git merge`）・`git add --all` | **困る**（取り込みとステージが残る）→ 次の 4.5 で、質問そのものをなくす |

- 確認のない書き込み（`sf-push.sh` の、未プッシュのコミットだけを push する分岐）は、AI のときも確認を足さない。代わりに、AI が動かす前に、未プッシュのコミットを示して「はい」をもらう（5 章）。人の操作の `sf-push.sh` に確認を足すことはしない（Push の番号を押したこと自体が、人の了承のため。sf-push は管理者向けのコマンドではない。CLAUDE.md の 2.4）

### 4.5 テキストの入力と、sf-push のメッセージ

- テキストの値は、コマンドのオプションで渡す（環境変数で渡さない）。秘密の値は、AI に渡させない
- `sf-push.sh -m <ファイル>`: VS Code を開かず、そのファイルの内容をメッセージにする
  - 整形は、VS Code の経路と同じ（今の処理の流れの 7: 行末の CR・`#` で始まる行・先頭と末尾の空行を除く）。同じ関数を通す
  - 整形の結果が空なら、今と同じく、コミット・プッシュせずに終わる（終了コード 0）
  - ファイルがない・読めない → 処理の流れの 1 で中断する（取り込み・ステージの前）。ファイルは消さない（AI が作ったものは、AI が消す）
- **`SF_TOOLS_AI=1` で `-m` がないときは、処理の流れの 1（取り込み・ステージの前）で、確認待ち（`push.message`）で止まる。** 止まるのを、副作用のない位置に前倒しする（4.4）

### 4.6 子のコマンドと、最後の守り

**答えの受け渡しの決まり（親・子・孫で同じ）**

1. 名前の先頭は、その質問を出すスクリプトの短い名前（`sf-deploy.sh` → `deploy`、`sf-release.sh` → `release`、`sf-next.sh` → `next`、`sf-push.sh` → `push`、`lib/project.sh` の関数は呼んだスクリプトの名前ではなく `update`）。各スクリプトは、**自分の先頭の答えだけ**を使う
2. 各スクリプトは、起動の直後（ほかの処理の前）に、`SF_TOOLS_ANSWERS` から自分の先頭の答えを取り出して手元の変数に移し、**残り（自分の先頭の答えを除いたもの）を `SF_TOOLS_ANSWERS` として export し直す**。これより後に起動する子・孫は、親の答えを見られない（同じスクリプトが子・孫として、もう一度動いても、使えない）
3. 子・孫に渡るのは、ほかのスクリプトの先頭の答えだけ。子は、その中から自分の先頭の答えを取り出し、同じく残りを次へ渡す
4. 同じ名前の答えが `SF_TOOLS_ANSWERS` に 2 つあれば、その場で中断する（4.2。出現の順では選ばない）
- この決まりで、使った記録をプロセスの間で受け渡さなくても、1 つの答えが、親・子・孫を通して 2 回使われることはない

**終了コード 20 の伝わり方**

- `need_answer` は、そのプロセスを `exit 20` で終わらせる（同じプロセスで `source` した関数の中から呼んでも、プロセスごと終わる）
- 子のコマンドを動かす `run`（`lib/common.sh`）は、`SF_TOOLS_AI=1` のとき、子の終了コードが 20 なら、ログに「確認待ちで止まりました」と残して、自分も `exit 20` で終わる（呼び出し側の `|| die`・`|| return` で、別のエラーに変わらない）
- `exec` で子に置き換える箇所（`sf-deploy.sh` → `sf-release.sh`）は、子の終了コードが、そのまま親の終了コードになる
- 子のコマンドを、`$( )` の中・パイプの途中で動かさない（質問を出しうる子に限る。今の B のコマンドには、ない。足すときは、テストで確かめる）。このプロジェクトは `set -e` を使わない（変わらない）
- `sf-deploy.sh` は、確認のあと `SF_DEPLOY_CONFIRMED=1` を渡して、`sf-release.sh` の確認を省く（今と同じ）。`sf-release.sh` に別の質問を足すときは、`release.<質問>` の名前を付ける（`SF_DEPLOY_CONFIRMED` で省かない限り、AI のときは止まる）
- **共有の組織（予約名）と本番の拒否は、`sf-release.sh` 自身が、確認より前に行う最後の守りのまま。** `SF_TOOLS_AI`・`SF_TOOLS_ANSWERS`・`SF_DEPLOY_CONFIRMED` のどれがあっても、省かない（テストで確かめる。8）

## 5. AI の振る舞い（`ai-dev-loop.md` に書く決まり）

1. 人の言葉を、6 章の表でコマンドに置き換える。合うものがなければ、聞き返す（推測で書き込む操作をしない）
2. B のコマンドは、動かす前に、会話で次を示し、「はい」をもらう
   - `sf-deploy.sh`: 反映先の組織（エイリアス）・ターゲットファイルの中身の要点（反映する数・削除するもの）・直前の dry-run の結果
   - `sf-push.sh`: `origin/main` を取り込むこと・変更の一覧（`git status` の要点）・未プッシュのコミット・コミットのメッセージの案
   - `sf-next.sh`: PR の先（例: develop）・sf-next が出した状況の表示（`--create` では、ブランチ・題名・本文も。11.2）
   - `sf-job.sh`: プロジェクト・ジョブ名・作るブランチ・クローン先（11.3）
3. 「はい」は、**その 1 回の実行・その質問にだけ**使う。前の「はい」を、別の実行や別の質問に使わない
4. 確認待ち（終了コード 20）で止まったら、質問の文をそのまま人に聞く。言い換えて、意味を変えない
5. 終わったら、結果（成功・失敗・作られたもの）を報告する。失敗は、表示されたエラーをそのまま添える
6. 共有の組織・本番・管理者向けの操作を頼まれたら、動かさず、理由を伝える

## 6. 言葉とコマンドの対応（例）

- 人は、ランチャーの名前（Check・Dryrun・Deploy・Push・PullRequest。2026-11-27 に Next から改名。PR・Next と言われても同じに扱う）を、そのまま言って頼める（2026-11-26 に TAMAさんの希望で追加。対応の表の正本は `doc/ai-dev-loop.md` の 2.4）。番号（「3 番」）で頼まれたら、名前に直して確かめる（番号の並びは、ランチャーの版で変わるため）

| 人の言葉（例） | コマンド | 区分 |
|---|---|---|
| 「チェックして」「ターゲットファイルを確かめて」 | `sf-check.sh` | A |
| 「反映できるか試して」「dry-run して」 | `sf-dryrun.sh -n` | A |
| 「反映して」「デプロイして」 | `sf-deploy.sh -n`（自分用の組織） | B |
| 「コミットして」「プッシュして」 | `sf-push.sh -m <ファイル>` | B |
| 「次はどこに PR？」「状況を見て」 | `sf-next.sh`（`next.pr=n` で、表示だけ） | A |
| 「PR を出して」 | `sf-next.sh --create --title <題名> --body-file <ファイル>`（`next.pr=y`。AI が PR を作る。11.2） | B |
| 「新しい作業を始めて」「ジョブを作って」 | `sf-job.sh --project XXXX --owner OWNER --name <ジョブ名>`（作業フォルダで。`job.create=y`。11.3） | B |
| 「ログを見て」 | `sf-log.sh pull` → `logs/apex/latest.md` | A |

## 7. 変える場所

| ファイル | 変更 |
|---|---|
| `lib/input.sh` | `ask_yn` に名前の引数（省略可）・`SF_TOOLS_ANSWERS` の読み取り（形の検査・1 回だけ使う・受け取った答えと使った答えの表示）・`need_answer`。`read_key`・`read_input`・`read_secret` は、AI のとき `need_answer` で止まる（4.3） |
| `lib/common.sh` | 終了コード `RET_NEED_ANSWER=20` の定義。`run` は、今は 0 以外をすべて `RET_NG`（1）に変えて返すため、`SF_TOOLS_AI=1` で子の終了コードが 20 のときだけ、変えずに `exit 20` で終わるようにする（4.6。テストで確かめる） |

## 11. 未決の結論と、追加の設計（2026-11-27）

### 11.1 決めたこと

1. **PR は、AI が作る**（`sf-next.sh --create`。11.2）。人がランチャーから使うときは、今のまま、ブラウザで作成画面を開く（`--create` を付けたときだけ変わる）。理由: AI の操作では、ブラウザを開いても、作成のボタンを人が押す手間が残る。PR の作成にも、通知・CI の起動・人に見える記録という副作用があるが、マージよりは軽い（組織へ出るのはマージのあとで、検証と、一方通行の確認（`doc/one-way-promotion-design.md`）が守る）。そのため、作る前に、人の「はい」は今のとおり要る
2. **`sf-job.sh` を B に入れる**（`--name`。11.3）。理由: 2026-11-27 の force-test-win の作業で、同じ手順（main からブランチを作ってクローン）を、AI が git で 3 回、手で再現した。`sf-restart.sh`・`sf-start.sh` は C のまま。理由: ブラウザでのログインと組織の選択は人の操作で、AI が起動しても手間が減らない（`sf-job.sh` の AI の操作でも、続きの sf-start は人が動かす）
3. **Claude Code のスキルは、配らない。** 理由: force-* の `CLAUDE.md`・`AGENTS.md` の 1 行（`templates/`）が、`doc/ai-dev-loop.md` を指している（Claude Code・Codex が、それらのファイルを毎回読む、という今の環境の動きが前提。設計で保証するものではない）。スキルは、その写しになり、2 か所の手入れが要る。Codex では使えない（両方の AI で同じ動きにする方針。2 章の 1）

### 11.2 PR の作成（`sf-next.sh --create`）

- オプション: `--create`・`--title <題名>`・`--body-file <ファイル>`
  - `--create` には、`--title` と `--body-file` の両方が要る。`--title`・`--body-file` だけ（`--create` なし）も、中断する
  - 題名: 空でない 1 行（CR・LF を含まない）。合わなければ中断する。長さは数えない（GitHub が確かめ、長すぎれば `gh pr create` の失敗になる。Bash の `${#…}` は、ロケールが C だとバイトで数え、日本語の題名を誤って弾くため）
  - 本文のファイル: あって、読めること（中身は空でもよい。整形しない。`gh pr create --body-file` にそのまま渡す）。なければ中断する。ファイル名に空白があってもよい
  - 題名・本文のファイル名は、`gh` に、それぞれ独立した 1 つの引数として、`--title=<題名>`・`--body-file=<ファイル>` の形で渡す（シェルの文字列の連結・`eval` を使わない。`=` の形なので、題名が `-` で始まっても、別のオプションとして読まれない）
  - これらの検査は、処理の流れの 1 より前に行う（`git fetch` などをする前）。値は、画面とログに出してよい（秘密の値ではない）
- 処理: 今の 1〜5（状況の判断・表示・対象が空・全段階済み・発行済みの PR）は同じ。6 の確認（`next.pr`）で Y のとき、ブラウザを開く代わりに、`gh pr create --repo <OWNER/REPO> --base <next_tier> --head <現在のブランチ> --title <題名> --body-file <ファイル>` で PR を作り、作られた PR の URL を表示する
  - `<OWNER/REPO>` は、今の origin の URL の直し（認証情報を除き、`https://github.com/` に直し、末尾の `.git` を除く）の結果が、`^https://github\.com/[A-Za-z0-9][A-Za-z0-9-]*/[A-Za-z0-9._-]+$` に一致するときだけ取る（ほかのホスト・余分なパス・`?`・`#` は不可。`<REPO>` が `.` `..` も不可）。合わなければ、PR を作らずに中断する
  - `gh pr create` が失敗したら、その出力（失敗の理由）を表示して、中断する（終了コード 1）
  - 同じ PR を二重に作らない: 開いている PR があれば、今の 5 で「発行済み」と表示して終わる（確認まで進まない）。確かめてから作るまでの間に、ほかで同じ head・base の PR が作られたときは、GitHub が 2 つ目の作成を拒む（開いている PR は、同じ head・base で 1 つだけ）。そのときは、上の失敗として、gh の理由を表示して中断する
- 人の「はい」は、AI の振る舞いの決まり（5 章・`doc/ai-dev-loop.md`）で守る。コマンドは、渡された答えが人のものかを確かめられない（`deploy.force` と同じ。2 章の 3）。技術で破れない守りは、共有の組織・本番の拒否と、マージの検証・一方通行の確認のほう
- AI の操作: 動かす前に、会話で、出し先（next_tier）・ブランチ・題名・本文・sf-next の状況の表示を示し、「はい」をもらう。そのあと `SF_TOOLS_AI=1 SF_TOOLS_ANSWERS="next.pr=y" bash ~/sf-tools/bin/sf-next.sh --create --title "<題名>" --body-file <ファイル>`。本文のファイルは、AI が一時ファイルに作り、終わったら消す
  - 状況だけを見たいときは、今のまま `next.pr=n`（`--create` を付けても、`n` なら何も作らない）

### 11.3 新しい作業（`sf-job.sh --name` と、AI のとき）

- オプション: `--name <ジョブ名>`。手順 5 の入力の代わりに、この値を 1 回だけ確かめる（今の検査と同じ: 形・予約名・同じ名前のフォルダ）。合わなければ、入力し直さずに中断する
  - 検査は 1 つの関数にまとめ、入力のループと `--name` の両方から呼ぶ（複製して、差が出ないようにする）
  - GitHub に同じ名前のブランチがあるときは、今と同じく、最後のコミットの作者・日時を表示して確かめる（`job.existing`）。N なら、入力し直さずに中断する（`--name` のときは、別の名前を聞かない）
  - 最後の確認（ジョブ名・ブランチ・クローン先）は、今と同じ（`job.create`）。人の操作で `--name` を付けたときも、確認は残す
- AI のとき（`SF_TOOLS_AI=1`）だけ、次を変える
  - `gh auth status` が失敗したら、`gh auth login` を動かさず、終了コード 1 で中断する（ブラウザでのログインは、人の操作）。中断は手順 3 で起きるため、ブランチの作成・クローンは行わない
  - 手順 8（`sf-start.sh`）を動かさない。クローンまで終えたら、`cd` せずに、クローン先と「sf-start.sh は、人がそのフォルダで動かす」を表示して、終了コード 0 で終わる（sf-start は、VS Code・ランチャーを開き、ランチャーを閉じるまで終わらないため。C）。クローンの失敗は、今と同じく中断（1）
  - `--name` がないとき・プロジェクトの特定で番号の選択や入力になったときは、4.3 のとおり、確認待ち（名前なし）で止まる。AI は、`--project`・`--owner`・`--name` を必ず付ける（今の force-* の `git remote` から、オーナーとプロジェクトを取る）
- 実行場所: 作業フォルダ（ジョブフォルダの親。今の force-* のフォルダの 2 つ上）。今と同じく、`admin`・`force-*` のフォルダでは中断する
- AI の操作: 動かす前に、会話で、プロジェクト（`OWNER/force-XXXX`）・ジョブ名・作るブランチ（main の最新から）・クローン先を示し、「はい」をもらう。そのあと `cd <作業フォルダ> && SF_TOOLS_AI=1 SF_TOOLS_ANSWERS="job.create=y" bash ~/sf-tools/bin/sf-job.sh --project XXXX --owner OWNER --name <ジョブ名>`。同じ名前のブランチがあって `job.existing` で止まったら、表示された作者・日時を、そのまま人に聞く。やり直すときに渡す答えは、その回に人がもらったものだけ（前の回の答えを、残して足さない。5 章の 3）
- 人の操作（`SF_TOOLS_AI` なし）は、`--name` を付けない限り、今のまま
