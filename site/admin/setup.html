🏗️ 新規プロジェクトの作成（sf-init）

新しい Salesforce プロジェクトを、一から立ち上げます。sf-init.sh が、画面の案内に沿って、必要な準備をまとめて行います。GitHub のリポジトリの作成、Salesforce 組織への接続、ブランチの構成、認証情報の登録、ブランチ保護の設定です。あなたが行うのは、画面に出る質問に答えることと、ブラウザでの数回の操作だけです。

この作業が、全員の出発点です。開発者は、これが終わるまで、何もできません

sf-tools は、この手順で作る、決まった形のリポジトリ（force-XXXX）の上でしか動きません。開発者は、リポジトリができて、あなたから連絡を受けるまで、始められません。管理者の作業と、開発者の作業は、同時には進められません。終わったら、開発者に、リポジトリの名前（force-XXXX）と、「使い始めてよい」ことを知らせてください。

管理者専用です

実行すると、赤い警告ボックスが表示され、続けてよいかを確認されます。続けて、GitHub CLI（gh）にログインしているユーザーが、リポジトリのオーナー本人か、オーナーの組織の有効な管理者かを確かめます（違えば、そこで止まります）。Windows では、Git Bash で実行してください（PowerShell やコマンドプロンプトでは動きません）。

かかる時間と、途中で止まったとき
  • ⏱️ 目安は、30〜60 分です（ブラウザでの作業と、Salesforce の反映待ちを含みます）。
  • 途中で止まっても大丈夫です。もう一度、同じように実行すれば、続きから再開できます（途中で止まったとき）。
  • セットアップ中は、Ctrl+C が効きません。やめたいときは、入力を求められたところで q を押します。どうしても止めたいときは、ターミナルを閉じます（画面にも、そう表示されます）。どちらの場合も、あとで、続きから再開できます。

始める前に、用意するもの

実行すると、最初の画面にも、同じ一覧が出ます。

用意するもの内容
ツールGit（Git Bash）・GitHub CLI・Node.js / npm・Salesforce CLI（npm 版）・VS Code・Slack。入れ方は、前提条件とインストールにあります。VS Code で開発する場合の拡張機能は、開発者の前提です（同じページに書いています）。
GitHubリポジトリのオーナー（個人のアカウント、または GitHub の組織）を決めておきます。GitHub CLI には、オーナー本人か、その組織の管理者のアカウントでログインしておきます（gh auth login。ログインしていなければ、ステップ 1 で、ログインの画面が出ます）。ブラウザでも、同じアカウントでログインしておきます（Token の作成で使います）
Salesforceつなげる組織（本番・Sandbox・Developer Edition など）と、その組織のシステム管理者のアカウント。組織の数は、選ぶブランチの構成で決まります（1〜3 組織。ブランチの構成）
Slack通知先にする、このプロジェクトを使う全員が参加している共有チャンネル。sf-init は、チャンネルを作りません。Slack で、先に作っておいてください（既存のチャンネルでも構いません）

実行する

リポジトリの名前は、force-XXXX の形です（force- は固定で、XXXX は管理者が決めます）。作業フォルダ（置く場所は自由です。おすすめは、~/sf のような短い名前）で、実行します。

cd {作業フォルダ}
sf-init.sh                                          # 対話: オーナーを選び、XXXX を入力
sf-init.sh --owner my-org --project acme            # オーナーと XXXX を引数で指定 → my-org/force-acme

引数で指定すると、オーナーと XXXX の質問が出ません（開始画面や、各ステップの質問は、同じように出ます）。対話では、次のように聞かれます。

  GitHub のオーナー: my-org（gh のログインから取得）

  リポジトリ名は「force-XXXX」の形です。
  「force-」は自動で付きます。XXXX の部分だけを入力してください。
     例: acme と入力 → force-acme

  my-org に、すでにあるプロジェクト（XXXX）:
     acme / beta

  XXXX（force- の後ろ）を入力してください: yamada

  XXXX = yamada
  → 作るリポジトリ         : my-org/force-yamada
  → 管理者用の作業フォルダ : /c/Users/you/sf/admin/force-yamada
  これでよいですか？ [Y/N/q]:
  • オーナーの候補は、gh にログインしているアカウントから作ります（あなたが管理者の GitHub 組織と、あなた自身のアカウント）。候補が 1 つなら自動で決まり、複数なら番号で選びます。候補がなければ、入力します。
  • 入力するのは、XXXX の部分だけです（force-yamada と書いても、yamada として扱います）。すでにある名前を入れると、警告が出て、聞き直されます（大文字と小文字は、区別しません）。ただし、この作業フォルダに、そのプロジェクトの途中の状態や、管理者用のクローンが残っているときは、受け付けて、続きから・完了済みの画面に進みます。
  • 「これでよいですか？」で N を押すと、XXXX を入力し直せます。
  • XXXX に使える文字: 英数字と、区切り（- _ .）です。区切りは、英数字の間に 1 つだけ置けます（a--b や、先頭・末尾の - は使えません）。50 文字までで、末尾を .git にはできません。Salesforce に自動で作るアプリの名前に、この XXXX が入るための決まりです（合わない名前は、入力した時点で断られます）。
  • --project で指定したときは、すでにある名前かどうかを、ここでは確かめません。--owner は、英数字とハイフンだけ（39 文字まで）です。
  • 同じ作業フォルダでは、同じ XXXX で、別のオーナーのプロジェクトは作れません。
  • 管理者用のフォルダ（admin）や、force-* の中では、実行できません。作業フォルダで実行してください。
  • できあがる管理者用のフォルダは、{作業フォルダ}/admin/force-XXXX です。admin は、いつもこの名前になります。複数のプロジェクトを、同じ admin に作っても構いません。

画面の流れ（全 9 ステップ）

実行すると、はじめに、作るもの・かかる時間の目安・管理者向けの赤い警告・先に用意するもの・全 9 ステップの一覧が表示されます。用意ができたら、Enter を押します（N か q で中断できます。ほかのキーでは進みません）。各ステップの先頭には、「ステップ n / 9」と、これまでに終わったステップ、そのステップの目的が表示されます。

ステップ何をするかあなたの操作
1. 準備の確認必要なツール（git・gh・node・npm・sf・code）があるかと、GitHub CLI へのログインを確かめます。1 つでもなければ、止まります。GitHub CLI にログインしていなければ、ログインの画面を出しますなし（ログインしていなければ、ログイン）
2. プロジェクトの確認作るリポジトリの名前と、管理者用のクローンの場所を表示して、確認します（Y/N/q。N か q で中断します）。使う sf-tools の版（配布版か開発版か）を選びます確認と選択
3. リポジトリの作成GitHub に、非公開（Private）のリポジトリを作って、管理者用フォルダにクローンします。sf-tools の雛形（設定ファイル・ワークフロー）をコピーして、Git のフック（コミット・プッシュの前に動くチェック）を入れますなし
4. ブランチの構成変更を、段階的に確かめて、最後の段階（main）に出す流れ（ブランチの構成）を選びます。GitHub のブランチは、ステップ 7 で作ります選択
5. GitHub の Token自動で動くワークフローが、リポジトリを更新するための Token（PAT）を確かめて、Secret PAT_TOKEN に登録しますブラウザで発行して、貼り付ける
6. Slack の通知ワークフローの結果を、Slack に通知するための設定をします（Secret SLACK_BOT_TOKEN・Variable SLACK_CHANNEL_ID）ブラウザと Slack での操作
7. リポジトリの設定ここまでの内容を、最初のコミットとして、GitHub に送ります（main と、選んだ段階のブランチを作ります）。続けて、リポジトリの設定と、ブランチ保護（保護のルール）を設定しますなし
8. Salesforce の接続Salesforce の各組織と、GitHub をつなげます。続けて、最初のメタデータの同期も行いますブラウザで、組織にログインする
9. 動作の確認（任意）作ったものが、実際に動くことを確かめます（動作の確認）。目安の時間（段階の数 × 6 + 3 分）が表示されますEnter で確認する／s であとにする

終わると、完了の画面に、次の 5 つが表示されます。

  1. 開発を始めるときに実行するコマンド（作業フォルダで sf-job.sh）
  2. リポジトリの URL
  3. 管理者用フォルダの場所と、ブランチ（admin フォルダと admin ブランチ）
  4. 動作の確認の結果（あとにしたときは、あとで確かめる方法）
  5. 最初のメタデータの同期の結果（最初のメタデータの同期）
sf-tools が古いときは、自動でやり直します

開始画面で、~/sf-tools が GitHub の最新より遅れていないかを確かめます。古いときは、「sf-tools を更新しますか？」（Y/N/q）と聞かれます。Y で更新すると、更新した sf-tools で、自動的に、はじめから（警告と確認から）実行し直します。もう一度実行する必要は、ありません。N なら、更新せずに続けます。~/sf-tools に、まだ送っていない変更があるときは、更新せずに続けます。

入力する項目

sf-tools の版（通常は「1. 配布版」）

ステップ 2 で、2 つの選択肢が出ます。これは、Salesforce の組織の話ではなく、「どの版の sf-tools を、このプロジェクトの自動処理に使うか」の選択です。（用語集の「段階」「環境」（develop / staging / main）とは、別のものです。）

  • 1. 配布版（main）（通常は、こちら）: GitHub Actions が、sf-tools の main（リリース済みの版）を使います。
  • 2. 開発版（development）: sf-tools の開発者だけが使います。リリース前の、未検証のコード（development）が使われます。選ぶと、警告と確認（Y/N/q）が出ます（N で選び直し）。開発版を選んだときだけ、GitHub の Variable SF_TOOLS_BRANCH（development）を登録します。

選んだ版と、手元の ~/sf-tools のブランチが違うときは、警告が出て、続けるかを聞かれます（Y/N/q。N か q で中断）。

ブランチの構成（3 / 2 / 1 階層）

ステップ 4 で、段階の数を、番号で選びます（q で中断）。段階ごとに、ブランチと Salesforce の組織が 1 つずつ対応するので、選んだ数だけ、ステップ 8 で組織に接続します。

番号ブランチ向いている場合
1main / staging / develop標準の構成です。3 段階で確かめてから出します
2main / staging2 段階です。開発用の組織を使わない場合
3main小さなプロジェクトや、1 人での開発

あとから、段階を足すこともできます（段階を足す）。減らす操作は、自動化していません。段階の考え方は、CI/CD の仕組みにあります。

GitHub の Token（PAT）

PAT（Personal Access Token）は、GitHub の「合鍵」のようなものです。自動で動くワークフローが、あなたの代わりに、リポジトリを更新するために使います（メタデータの同期で main に送るときなど。main は保護されていますが、リポジトリの管理者の Token なら、保護のルールを越えて送れます）。この Token は、作る force-XXXX のためのもので、sf-tools のリポジトリとは関係ありません。

  • どのアカウントで作るか: force-* のリポジトリのオーナーのアカウントです（組織のリポジトリなら、その組織の管理者）。作るアカウントは、実行の最初に表示されます。ブラウザで、別のアカウントにログインしているときは、切り替えてください。sf-tools の開発者のアカウントは、関係ありません。
  • 作り方: ブラウザで、Token の作成ページが、自動で開きます（Note と Scopes は、入力済みです）。ページの一番下の「Generate token」を押して、表示された Token をコピーし、ターミナルに貼り付けます。「発行済みの Token があるか」は聞きません（Token の値は、作成した直後の 1 回しか表示されないためです）。保存してある Token があれば、それを貼り付けてもかまいません。
  • 設定の内容: Note は sf-metasync-{プロジェクト名}（自動で表示）、Expiration は No expiration（期限なし）、Scopes は repo（全選択）と workflow です。
  • 貼り付けるとき: 文字の数だけ * が並びます（Token の中身は、画面に出ません）。Git Bash では、右クリック（または Shift+Insert）で貼り付けます。Enter を押すと、「N 文字を受け取りました（先頭: ghp_…）」と表示されるので、コピーできたかを確かめられます。
  • 確認: Token が有効か、Classic の Token か、スコープ（repo・workflow）があるか、リポジトリの管理者の Token か、を GitHub に問い合わせて確かめます。違っていれば、理由と直し方が表示され、貼り直せます。貼り付けは、合計 3 回までです（3 回とも使えなければ、止まります。もう一度実行すると、このステップから再開できます）。Fine-grained の Token は、スコープを確かめられないので、使えません。
  • やめたいとき: q だけを入力して Enter を押すと、中断します。

Slack の通知

3 つの作業があります。画面にも、同じ手順が表示されます。

  1. Bot Token を取る（ブラウザで Slack の API ページが開きます）

    1. 「Create New App」→「From scratch」をクリックします。
    2. App Name に sf-notify-{プロジェクト名} を入れ、通知先のワークスペースを選んで、「Create App」をクリックします。
    3. 左のメニューの「OAuth & Permissions」をクリックします。
    4. 「ボットトークンのスコープ」→「OAuth スコープを追加する」で、chat:write を追加します。
    5. 左のメニューの「Install App」→「Install to ワークスペース名」をクリックして、「許可する」をクリックします。
    6. 表示されたページの「Bot User OAuth Token」（xoxb- で始まる文字列）をコピーします。
    7. ターミナルに戻って Enter を押し、続けて、コピーした Token を貼り付けて Enter を押します。貼り付けた文字は、* で表示されます（Token は画面に出ません）。xoxb- で始まらないときは、入力し直しになります。Token は、Secret SLACK_BOT_TOKEN に登録されます。

  2. チャンネル ID を入れる（C で始まる文字列。G で始まるものも受け付けます）

    Slack で、通知先のチャンネルを開き、チャンネル名をクリックすると、いちばん下に「チャンネル ID」が出ます。DM（D…）やユーザー（U…）の ID は、本人にしか通知が届かないので、受け付けられません（入力し直しになります）。チャンネル ID は、Variable SLACK_CHANNEL_ID に登録されます。

  3. Bot をチャンネルに招待する（Slack で、手動で行います）

    通知先のチャンネルで、次のコマンドを実行してから、ターミナルで Enter を押します。Bot がチャンネルにいないと、通知が届きません。sf-init は、招待されたかどうかを確かめないので、忘れずに行ってください。

    /invite @sf-notify-<プロジェクト名>

どの入力でも、q で中断できます。

最初のコミットと、保護のルール（自動）

ステップ 7 は、自動で進みます。入力はありません。

  • 最初のコミット: ここまでに用意したファイルを、コミットして、main に送ります。ステップ 4 で選んだ段階のブランチ（staging・develop）も、main から作って送ります。送るときは、ステップ 5 の Token を使い、送ったあとで、手元に保存していた Token の値を消します。
  • リポジトリの設定: 既定のブランチを main にし、PR のマージの方法（マージコミット・スカッシュ・リベース）をすべて許可し、マージしたあとのブランチの自動削除を、しない設定にします。
  • ブランチ保護（Ruleset）: main と staging に、ルール（protect-main・protect-staging）を設定します。ブランチの構成に関係なく、両方を作ります。中身は、次のとおりです。
    • ブランチの削除と、強制プッシュ（履歴の書き換え）を禁止します。
    • PR をマージする前に、3 つのチェックが通ることを必須にします。名前は、ワークフローのジョブの名前の 対象ファイル確認・デプロイ検証・順序チェック です（ワークフローの名前は含めません。含めると、チェックが永久に満たされず、PR をマージできなくなります。以前の sf-init で作ったプロジェクトは、トラブルシューティングを見てください）。
    • リポジトリの管理者（Admin）は、このルールを越えられます（メタデータの同期などで、ワークフローが、管理者の Token で main に送るためです）。
  • 無料プランの非公開リポジトリなどでは、ブランチ保護を設定できないことがあります。その場合は、警告が出て、先へ進みます（セットアップは止まりません）。ブランチ保護がないと、チェックに失敗した PR も、マージできてしまいます。--status で、設定されているかを確かめられます。

Salesforce の接続（JWT 認証）

JWT 認証は、パスワードの入力なしで、秘密鍵を使って Salesforce にログインする方法です。GitHub 上のワークフローが、自動でログインするために使います。

既定は、外部クライアントアプリ（Salesforce の側に作る、「このツールからのログインを許可する」という登録。Salesforce の推奨）です。アプリの作成は、sf-init が自動で行います（アプリの種類は、聞かれません）。

はじめに、JWT 認証に使う秘密鍵と証明書を、この PC の ~/.sf-jwt/force-XXXX/（server.key・server.crt）に作ります。前回の実行で作ったものが残っているときは、使い続けるかを聞かれます（Y/N/q）。

  • Y: そのまま使います（ふつうは、こちら）。
  • N: 消して、新しく作り直します。秘密鍵が変わるので、接続が済んでいる段階も、すべて接続し直します（ブラウザでのログインも、やり直します）。

続けて、段階ごとに（main → staging → develop の順。選んだ構成にある段階だけ）、次のように進みます。

  1. ログイン先を選びます。組織の種類ではなく、ログインする URL で選びます。

          [1] https://login.salesforce.com   本番・Developer Edition・Trial など
      [2] https://test.salesforce.com    Sandbox   ← 安全なおすすめ（本番に影響しません）
      [3] 組織の URL を入力する   My Domain（例: https://会社名.my.salesforce.com）

    Enter だけなら 2 番です。main 以外の段階では、1 番の説明が「Developer Edition・Trial など（※ Salesforce の本番は、main のみ）」になります。

  2. ブラウザで、Salesforce にログインします。接続するユーザーは、システム管理者のユーザーです。ブラウザでのログインは、約 2 分で時間切れになります。ブラウザが開いたら、すぐにログインしてください（時間切れ・ブラウザを閉じたときは、止まります。もう一度実行すると、このステップから再開できます）。あなたの操作は、ここまでです。

  3. 組織の種類を確かめます（自動）。組織から、ID・名前・種類（本番 / Sandbox / Developer Edition / Trial）を読み取ります。本番の組織は、main にしかつなげません。種類を判定できない組織も、main 以外にはつなげません。staging や develop に、本番の組織でログインすると、アプリを作る前に止まります。

  4. アプリを作って、接続を確かめます（自動）。外部クライアントアプリ（名前は SF_TOOLS_ で始まります）の作成・証明書の登録・ポリシーとプロファイルの設定・コンシューマー鍵の取得を行います。組織に設定が反映されるまで時間がかかるので、JWT での接続のテストを、30 秒おきに、最大 20 回（約 10 分）くり返します。それでも成功しないときは、「接続テストをスキップして、登録だけ行いますか？」と聞かれます（Y で登録して先へ、N / q で中断。アプリは、組織に作られたまま残ります）。

  5. GitHub に登録します（自動）。

登録先名前内容
Secret（隠す）SF_PRIVATE_KEY秘密鍵（すべての段階で共通。毎回、上書きします）
Secret（隠す）SF_CONSUMER_KEY_PROD / _STG / _DEV段階ごとの、アプリのコンシューマー鍵
Variable（見えてよい）SF_USERNAME_* / SF_INSTANCE_URL_*段階ごとの、接続ユーザー名と、組織の URL

名前の末尾の PROD / STG / DEV は、段階の main / staging / develop を表します。くわしくは、認証情報にあります。段階と組織の種類の関係は、構成の変更と診断でも説明しています。

従来の接続アプリケーション（--legacy-connected-app）
  • --legacy-connected-app を付けると、従来の接続アプリケーション（今後、廃止の予定）を使います。Salesforce の画面での設定（画面に手順が出ます）と、段階ごとの、コンシューマーキー・接続ユーザー名の手入力が必要です。証明書（server.crt）も、自分で各組織にアップロードします。
  • 一度決まったアプリの種類は、続きから再開しても変わりません。外部クライアントアプリで始めたプロジェクトに、あとから --legacy-connected-app を付けると、止まります。
  • 作った接続アプリケーションを、Salesforce の画面で「外部クライアントアプリへの移行」や「削除」をしないでください。接続ができなくなります（client_identifier_invalid のエラー）。問題が起きたときは、同じアプリを直さずに、別の名前で作り直します。
  • Developer Edition の組織では、事前承認の反映が遅れる、または失敗することがあります。本番・Sandbox での利用をおすすめします。

最初のメタデータの同期（自動）

Salesforce の接続のあとで、wf-metasync（組織の最新の状態を、Git に取り込むワークフロー）を GitHub で実行し、終わるのを待ちます。待っている間は、30 秒おきに経過が表示されます。続けて、同期した内容を、管理者用のクローン（admin/force-XXXX）に取り込みます。数分かかります（組織の大きさで、長くなります）。

  • セットアップが終わると、Salesforce のメタデータが、すべて入った状態になります。GitHub の main にも、手元のクローンにも入ります（最初のコミットの force-app は、空のひな型です）。
  • 待つのは、最長 20 分です。時間切れのときは、実行を取り消します（あとの同期と重ならないようにするためです）。
  • 同期に失敗しても（時間切れを含みます）、セットアップ自体は、成功のままです。完了の画面に、すぐ同期するためのコマンド（gh workflow run wf-metasync.yml -R オーナー/force-XXXX。終わったら、管理者用フォルダで git pull origin main）が出ます。何もしなくても、定期の同期（平日の 3 時間おき）で入ります。

途中で止まったとき（続きから）

どこまで進んだかを、覚えておく必要はありません

止まったら、同じ作業フォルダで、もう一度 sf-init.sh を実行してください（同じオーナー・XXXX を選びます）。前回の状態が残っていれば、開始画面の確認のあとに、続きから再開する選択肢が出ます。

止まったときは、画面に「うまくいきませんでした」と、原因と、やり直しの方法が表示されます。ステップ 3 以降で止まったときは、止まったところ（内部の処理の単位の最初）から再開できます。ステップ 1・2 で止まったときは、保存された状態がないので、最初から始まります。

前回のセットアップは、「ブランチの構成」まで完了しています（2026-10-11 14:32）。（owner/force-xxx）

    [1] 「GitHub の Token」から、続きをやる   ← おすすめ
    [2] 最初からやり直す（作成済みのリポジトリ・admin フォルダは、そのまま使います）
    [q] 中断
  • [1] 続きをやる: 保存してある入力内容（sf-tools の版・ブランチの構成など）を使って、失敗した所から再開します（最初の準備の確認は、毎回行います）。表示される名前（「GitHub の Token」など）は、内部の処理の単位の名前で、画面のステップの名前と少し違うことがあります（「設定ファイルの作成」「初回のコミット」など）。
  • [2] 最初からやり直す: 保存した状態を消して、最初から始めます。作成済みのリポジトリと admin フォルダは、削除せず、そのまま使います。設定は、上書きします（管理者用のクローンで、sf-tools の雛形と同じ名前のファイルを変えていたときは、雛形の内容に戻ります）。
  • [q] 中断: 何もせずに終わります。
  • Salesforce の接続は、段階ごとに、終わったことを記録します。途中（たとえば staging）で失敗しても、「続きをやる」では、終わった段階（main など）は飛ばして、残りの段階だけを実行します。ブラウザでのログインを、やり直さなくて済みます（登録した Secret が、いまもあるときだけ、飛ばします。秘密鍵を作り直したときは、すべての段階をやり直します）。
  • GitHub に main を送ったと記録されているのに、GitHub に main が見つからないときは、続けずに止まります（記録と実際が食い違っているためです）。
  • 前回が最後まで終わっているときは、「セットアップが、すでに完了しています」と表示されます。次の 4 つから選べます。
    • [1] いまの Salesforce の接続を見る（何も変更しません。--status と同じ表示です）
    • [2] 動作を確認する（--verify。Hello World を各段階にリリースして、削除します。約 20 分。確認が出ます）
    • [3] 最初からやり直す（作成済みのリポジトリは、そのまま使い、設定を上書きします）
    • [q] 終了
    別のリポジトリの状態が残っているときは、選択肢は出ず、最初から始まります。
  • 同じ作業フォルダ・同じ XXXX の sf-init.sh を、同時に 2 つ動かすことはできません（あとから実行したほうは、「すでに実行中です」で止まります）。
  • 完了済みのプロジェクトでは、--resume N と --only N は使えません（接続の処理などを、確認なしで、やり直さないためです）。
  • 進み具合は、admin/.sf-init-XXXX.progress（入力内容は .sf-init-XXXX.env）に記録されます。この 2 つのファイルは、最後まで終わると削除されます（途中で止まったときだけ、残ります）。終わっているかどうかは、クローンの git config sf-tools.setup-complete で判断します。
  • リポジトリそのものを作り直したいときは、GitHub 上のリポジトリと admin フォルダを、手動で削除してから、実行します。

終わったあと

admin フォルダと admin ブランチ

  • admin フォルダは、削除せず、残してください。ワークフローの更新（sf-sync-wf）・接続の確認（--status）・接続先の付け替え（--reconnect）など、管理者のメンテナンスに使います。日々の開発には使いません（開発は、sf-job.sh の作業フォルダで行います）。
  • 管理者用のクローンは、セットアップの最後に、admin ブランチになります。main から作って、GitHub にも git push -u origin admin で作ります（強制プッシュは、しません）。main は保護されたブランチなので、その上で作業しなくて済むようにするためです（sf-sync-wf.sh も、保護ブランチの上では、実行を断ります）。
  • 管理者の変更は、「main を取り込む → 変更する → プッシュ → PR」の順で、GitHub に反映します。admin は、時間がたつと、main から遅れます。使う前に、git pull origin main で取り込んでください。
  • admin ブランチがすでにあるときは、作り直さずに、切り替えるだけです（作業が消えることは、ありません）。ブランチを作れなかったとき、またはプッシュできなかったときは、完了の画面に案内が出ます。その案内どおりに、管理者用フォルダで、次のコマンドを実行してください。セットアップ自体は、成功のままです。
    • 作れなかったとき: git switch -c admin
    • プッシュできなかったとき: git push -u origin admin

開発者を迎える（セットアップが終わったら）

リポジトリができただけでは、開発者は使い始められません。次の 4 つを、順に行って、開発者に連絡してください。

  1. GitHub で、開発者に、リポジトリの権限を付けます。リポジトリ（オーナー/force-XXXX）の Settings → Collaborators and teams で、開発者を追加します。ブランチを作って、変更を送って、PR を出すので、書き込みの権限（Write）が必要です。リポジトリが非公開のときは、権限がないと、リポジトリが見つからないと表示されます。

  2. Slack の共有チャンネルに、開発者が参加していることを確かめます。リリースや検証の結果は、そのチャンネルに届きます（Slack の通知）。

  3. 開発者に、自分用の Salesforce 組織があることを確かめます。開発者は、自分専用の組織（Sandbox・Developer Edition など）に接続して作業します。共有の環境（本番・staging・develop）には、GitHub を通して反映されるので、開発者が、共有の環境の認証情報を持つ必要は、ありません。

  4. 開発者に、次の 3 つを知らせます。オーナーとリポジトリの名前（force-XXXX）、前提条件とインストールのページ、「ツールを入れたら、自分の作業フォルダで sf-job.sh から始める」こと。作業を始めると、ランチャー（sf-launcher.sh。毎日のコマンドを、メニューの番号で選んで実行する画面）が自動で開きます。開発者には、ランチャーで進めることを勧めてください（ランチャーの使い方）。

動作を確認する

設定がそろっているかは、管理者用フォルダで sf-init.sh --status を実行すると、何も変更せずに確かめられます。実際に動くかは、次の 2 つで確かめられます。

  1. メタデータの同期: セットアップの最後に、1 回、自動で実行済みです（最初のメタデータの同期）。あとで確かめたいときは、GitHub → Actions → 「[metasync] メタ同期」→「Run workflow」で、手動で実行します。正常に終われば、組織のメタデータが main に同期されます。

  2. PR のワークフロー: 作業フォルダで sf-job.sh を実行すると、sf-start.sh が自動で動きます。sf-install.sh が、sf-tools/release/<ブランチ名>/ の下に、空のターゲットファイル（説明のコメントだけのもの）を作ります。これがそのまま差分になるので、ほかの変更は要りません。続けて、ランチャーで、次の番号を押します（コマンドで打つなら、かっこの中）。

    [2] Push   （sf-push.sh）  # 自動で作られたファイルを、コミットして送る
[3] Next   （sf-next.sh）  # 次の PR 先を確認 → ブラウザで PR の作成画面を開く → PR を作って、マージ

    ブランチが 3 階層なら、develop → staging → main の順に、[3] Next をくり返します。PR を作ると、次の処理が、自動で動きます。

    • [validate] デプロイ前の検証 — すべての PR で動く
    • [sequence] マージ順序の確認 — main と staging への PR で動く
    • [release] デプロイ → Slack に通知 — main・staging・develop への PR をマージしたあとで動く
    • [propagate] ブランチの伝播 — main への PR をマージしたあとで、main の内容を staging・develop に反映する

    ターゲットファイルが空なので、検証とリリースの本体は「デプロイ対象なし」で飛ばされます（組織には、何も反映しません）。ここで確かめられるのは、ワークフローが動くことと、PR をマージできることです。組織へのリリースと削除（と、その通知）まで確かめるときは、次の --verify を使います。

もっとしっかり確かめたいときは、動作の確認（--verify）を使います。実際のリポジトリと組織で、リリースと削除まで、通しで確かめます。セットアップの最後（ステップ 9）に、「動作を確認しますか？」と聞かれます（任意です）。
