> **ステータス: 設計（外部レビュー 2 回反映済み）。段階 S1 は実装済み（共通部品 `lib/wizard.sh`・開始画面・ステップの見出し・完了画面・sf-tools の自動更新）。S2 以降は未実装。4.7（段階と組織の種類の独立）は、実装済み（S3: ログイン先の 3 択・種類の読み取り・本番は main のみのガード・`--reconnect`・`--status`・`--legacy-connected-app`・sf-start の修正・add_tier の PR 化）。S2（各ステップの画面の刷新）は未実装**
> 対象: `sf-init.sh`（最優先）、続いて他のコマンド（sf-start / sf-job / sf-next / sf-deploy / sf-release / sf-metasync / sf-update-secret / sf-sync-wf）

## 1. 目的と判断基準

### 1.1 目的

**指示のとおりに操作すれば、迷わず、最後まで設定が完了する**こと。利用者がポチポチと選んでいくだけで終わる、ウィザード形式にする。

### 1.2 合否の基準（これが満たせなければ不合格）

利用者が、使っている最中に、次のどれかを思ったら、それは**設計の不具合**である。

| 利用者の疑問 | 設計が満たすべきこと |
|---|---|
| 「いま、どこ？」 | すべての画面に、現在地（全体のうち、いくつ目か）を出す |
| 「これは、何？」 | 画面の先頭に、このステップが何のためかを、1 文で出す |
| 「次は、何をすればいい？」 | 利用者の操作を、1 画面に 1 つだけ、はっきり書く |
| 「このあと、どうなる？」 | 操作のあとに起きることを、先に書く |
| 「どれを選べばいい？」 | 推奨を先頭に示し、迷う選択肢は、そもそも出さない |
| 「固まった？」 | 待ち時間は、「何を待っているか・最大どのくらいか」を出す |
| 「失敗した。どうすれば？」 | 何が起きたか／どう直すか／どこから再開されるか、を出す |
| 「終わった？次は？」 | 完了画面に、できたことと、次にやることを出す |

## 3. 設計原則

| # | 原則 | 具体的なルール |
|---|---|---|
| R1 | **全体像を最初に** | ステップの一覧・所要時間の目安・事前に用意するもの（必要な権限・組織の数も）を、最初に出す。準備ができてから、始める |
| R2 | **現在地を常に** | すべての画面の先頭に `ステップ 3 / 8: ○○` と、完了済みを出す |
| R3 | **1 画面に 1 つの操作** | 利用者の操作は、1 画面に 1 つ。「やること」と「そのあと起きること」を、書く。複数の操作が要るときは、画面を分ける |
| R4 | **利用者に判断させない** | 検出できるもの・既定が決まるものは、聞かない。判断が必要なときは、推奨を先頭にして、Enter で推奨を選べるようにする |
| R5 | **言葉を平易に** | 専門用語は、はじめに 1 度だけ説明する。内部の呼び名（Phase・ECA・JWT）は、画面に出さない |
| R6 | **操作の語彙を統一** | `Enter` = 次へ／`番号` = 選択／`q` = 中断。画面の下に、毎回、操作のヒントを出す |
| R7 | **待ち状態を明示** | ブラウザで作業するときは、「何の画面が出ていれば合っているか」「何をするか」「終わったら何を押すか」を書く。**時間制限があれば、先に書く**（P15） |
| R8 | **待ち時間を明示** | 数十秒以上かかる処理は、「何を待っているか・最大どのくらいか・いま何回目か」を出す（P16） |
| R9 | **失敗の三点セット** | 何が起きたか／どう直すか／**どこから再開されるか（再開の単位を、正確に）**。（`die` は、既存規約どおり事実のみ。案内は、直前の `log` で出す） |
| R10 | **完了画面** | できたこと／次にやること（具体的なコマンド・URL）を出す。実際に設定できたものだけを書く |
| R11 | **やり直せる** | 中断しても、再実行で、続きから再開できる。各ステップは、冪等にする |
| R12 | **機密を見せない** | Token 等は、画面・ログに出さない（既存規約） |

## 4. sf-init のウィザード設計

### 4.1 ステップ一覧（内部の Phase との対応。表示と実行順は一致させる）

利用者に見せるステップは **8 つ**。ただし、ステップ 8（Salesforce の接続）は、組織の数だけ、画面（小ステップ）に分ける（4.4 (6)）。内部の Phase 番号は、画面に出さない。

| 表示 | 内部 Phase | 利用者の操作 |
|---|---|---|
| 1 / 8 準備の確認 | 1 | 自動 |
| 2 / 8 プロジェクトの確認 | 2 | Enter |
| 3 / 8 リポジトリの作成 | 3・4 | 自動（完了を 1 行で表示） |
| 4 / 8 ブランチの構成 | 5 | 番号選択（推奨が既定） |
| 5 / 8 GitHub の Token | 6 | ブラウザで 1 クリック → 貼り付け |
| 6 / 8 Slack の通知 | 7 | ブラウザ操作 → 貼り付け ×2 → 招待（画面を 3 つに分ける） |
| 7 / 8 リポジトリの設定 | 8・9 | 自動 |
| 8 / 8 Salesforce の接続 | 10 | 段階ごとに、ログイン先（URL）を選び、ブラウザでログイン（4.7。種類は、ログイン後に、組織から読み取る） |

### 4.2 開始画面（R1）

```
══════════════════════════════════════════════
  新しい Salesforce プロジェクトを作ります
══════════════════════════════════════════════

  作るもの   : tamashimon-org/force-yamada（GitHub のリポジトリ）
  かかる時間 : 30〜60 分ほど（ブラウザでの作業・Salesforce の反映待ちを含みます）
               ※ 仮の値。実機で測って、確定します

  【先に、用意してください】
    □ GitHub : tamashimon-org の管理者としてログインしたブラウザ
    □ Slack  : 通知用の「共有チャンネル」（全員が参加するもの）
               まだなければ、いま Slack で作ってください
    □ Salesforce : 接続する組織の、システム管理者のアカウント
               ブランチの構成で選ぶ数（1〜3 組織）だけ、必要です

  【これから行うこと】
    1. 準備の確認   2. プロジェクトの確認   3. リポジトリの作成
    4. ブランチの構成   5. GitHub の Token   6. Slack の通知
    7. リポジトリの設定   8. Salesforce の接続

  ▶ 用意ができたら Enter を押してください（q で中断）
```

- 管理者向けの警告（既存の赤いボックス）と、「続行しますか？」は、**この画面に統合**する（P13）。
- 前回の途中までの状態が残っている場合は、この画面の前に、「続きをやる／最初からやり直す」を出す（実装済み）。
- sf-tools が古い場合は、管理者向けの警告のあと、確認の前に、**確認のうえ更新し、自動で、もう一度、はじめから実行する**（P14）。実行しなおしたあとも、警告と確認は、毎回出す（確認を飛ばさない）。

### 4.3 各ステップの共通の見た目（R2・R3・R6）

```
──────────────────────────────────────────────
  ステップ 5 / 8: GitHub の Token を作ります
  （完了: 準備の確認・プロジェクト・リポジトリ・ブランチ）
──────────────────────────────────────────────

  ○○のために、必要です。（1 文）

  ▶ あなたがやること
      1. …
      2. …

  ▶ そのあと
      この画面に戻って、貼り付けて、Enter を押してください

  [Enter] 次へ   [q] 中断
```

- 自動のステップは、「ステップ n / 8: ○○ ... ✔ 完了」の 1 行に集約する（画面を埋めない）。
- ブラウザを使うステップは、R7 に従い、「ブラウザに、○○の画面が出ます。**そこで、やること**」を、箇条書きにする。

### 4.4 主要な画面の設計

**(1) ステップ 2（プロジェクトの確認）**: Y/N を聞かず、内容を見せて Enter のみ。誤りの原因は、フォルダ名であることを書く。

```
  次の内容で、作ります。
    GitHub のリポジトリ : tamashimon-org/force-yamada
    作る場所             : ~/home/tamashimon-org/yamada/init/force-yamada

  フォルダの名前から決めています。違う場合は q で中断して、
  正しいフォルダに移動してから、もう一度、実行してください。

  [Enter] この内容で進む   [q] 中断
```

**(2) 環境種別（本番／検証）（P4）**: 一般の利用者には**聞かない**。既定は「本番環境」。sf-tools の開発者が検証環境を使うときだけ、環境変数 `SF_TOOLS_BRANCH=development` で指定する（既存の仕組み）。検証環境のときだけ、開始画面に「検証環境（開発者用）で実行します」と表示する。

**(3) ステップ 4（ブランチの構成）（P5）**: 段階の数だけを選ぶ。**どの段階に、どの種類の組織をつなぐかは、ここでは決めない**（4.7。段階と、組織の種類は、独立）。選んだあとに、**必要な Salesforce の組織の数**を、はっきり出す。

```
  ブランチの構成（コードを、何段階で確認してから、最後の環境に出すか）

    [1] 3 段階（main / staging / develop）   ← おすすめ
         開発 → 検証 → 最後の環境。Salesforce の組織が 3 つ必要です
    [2] 2 段階（main / staging）
         検証 → 最後の環境。Salesforce の組織が 2 つ必要です
    [3] 1 段階（main）
         Salesforce の組織が 1 つ。少人数・1 人で開発する場合

  どの段階にも、本番・Sandbox・Developer Edition の、どれでもつなげます
  （つなぐ組織は、このあと、段階ごとに選びます）。後から、増やすこともできます。
  [Enter] 1 を選ぶ   [2] [3] 他を選ぶ   [q] 中断
```

**(4) ステップ 5（Token）**: 実装済みの内容（ブラウザをすぐ開く・Note と Scopes を入力済みの作成ページ・貼り付けた文字を `*` で表示する・Enter のあとに「N 文字を受け取りました」を表示する・空 Enter は貼り付け方を案内する・失敗の理由と直し方）を、共通の見た目に入れる。

**(5) ステップ 6（Slack）（P3・P9）**: 開始画面で、チャンネルの事前準備を案内済み。画面を 3 つに分ける（Bot Token の取得 → チャンネル ID → Bot の招待）。各画面に、「いま、Slack のどの画面を開いているか」の目印を書く。

**(6) ステップ 8（Salesforce の接続）（P6・P7・P15・P16・P17）**: **段階ごとに、画面（小ステップ）を分ける**（「8 / 8 の 1: main」「2: staging」「3: develop」）。呼び名は、**段階の名前（main / staging / develop）と、実際の組織名**で出す。「本番」「検証」を、段階に当てはめない（4.7）。

- アプリ種別は、**聞かない**（既定は「外部クライアントアプリ」）。従来の接続アプリは、オプション `--legacy-connected-app` を付けた場合のみ（仕様は 4.6）。
- ログイン先は、組織の「種類」ではなく、**ログイン先の URL** で選ぶ（種類の名前は、利用者が迷うため）。段階ごとに、3 つから選ぶ。

```
  ステップ 8 / 8 の 2: staging に、つなぐ Salesforce の組織を選びます

  ▶ この組織には、どこからログインしますか？
      [1] https://login.salesforce.com   Developer Edition・Trial など（※ 本番は、main のみ）
      [2] https://test.salesforce.com    Sandbox   ← 安全なおすすめ（本番に影響しません）
      [3] 組織の URL を入力する          My Domain（例: https://会社名.my.salesforce.com）
  [Enter] 2 を選ぶ   [1] [3] 他を選ぶ   [q] 中断

  ▶ あなたがやること
      1. ブラウザに、Salesforce のログイン画面が出ます
      2. この組織の、システム管理者のユーザーで、ログインして、「許可」を押す
         ※ 2 分以内に、ログインしてください（時間切れになります）
  ▶ そのあと
      自動で、接続の設定を行います（反映待ちを含めて、数分かかります）
```

- 画面の [1] の説明は、**段階によって変わる**: main では「本番・Developer Edition・Trial など」。staging・develop では「Developer Edition・Trial など（※ 本番は、main のみ）」（F8）。
- 「安全なおすすめ」は、段階に依存しない。**どの段階でも、同じ**（最初の接続は、Sandbox が安全、という理由のみ）。本番を選ぶときは、[1] を選ぶ。
- ログイン後、**組織の種類を、組織自身から読み取って**、表示・保存する（`Organization.IsSandbox`・`OrganizationType`）。例: 「ログインした組織: Developer Edition（組織名: ○○）」。利用者が、種類を、覚えている必要はない。選んだログイン先と、実際の種類が、食い違うとき（例: [2] を選んだのに、Sandbox ではない）は、警告して確認する。
- 反映待ちの間は、「Salesforce の反映を待っています（3 / 20 回目・最大 約 10 分）」のように、進み具合を出す（R8）。

**(7) 完了画面（R10）**:

```
══════════════════════════════════════════════
  できました: tamashimon-org/force-yamada
══════════════════════════════════════════════

  設定したもの : GitHub リポジトリ / Token / Slack 通知 / Salesforce 接続（3 組織）

  【次にやること】
    1. 開発する人に、次のコマンドを伝えてください
         sf-start.sh        （作業フォルダ: ~/home/tamashimon-org/yamada/）
    2. リポジトリを見る:
         https://github.com/tamashimon-org/force-yamada

  詳しい使い方: README.md の 4. を見てください
```

### 4.5 失敗の画面（R9・R11）

再開の単位は、**内部の Phase の先頭**（表示のステップの先頭）である。画面は、そのとおりに書く。

```
  ✖ うまくいきませんでした（ステップ 5 / 8: GitHub の Token）
     原因 : この Token には「workflow」の権限がありません

  【直し方】 作成ページで、workflow にチェックが入っていることを確認して、
             作り直してください。
  【やり直し】 もう一度 sf-init.sh を実行し、「続きをやる」を選ぶと、
               ステップ 5 / 8 の最初から、再開します。
               （ここまでの内容は、保存されています）
```

- ステップ 6（Slack）の途中で失敗した場合は、「ステップ 6 / 8 の最初から」と書く（途中の小画面からは、再開しない。登録は、上書きできるため、問題ない）。
- Token は、再開のために、`init/.sf-init.env`（権限 600）に、ステップ 5 からステップ 7 の完了まで残る。完了時に削除する（既存の仕様）。「最初からやり直す」を選ぶと、状態ごと消える。再入力を求めると、利用者の手間が増えるため、再入力は求めない。

### 4.6 `--legacy-connected-app` の仕様

| 項目 | 内容 |
|---|---|
| 指定方法 | `sf-init.sh --legacy-connected-app`（新規実行・`--resume N` のどちらでも指定できる） |
| 動作 | Phase 10 のアプリ種別を、「接続アプリケーション（1）」にする。従来の手動手順（Connected App の作成案内・コンシューマー鍵とユーザー名の入力）に、そのまま入る |
| 保存 | 選んだ種別は、`APP_TYPE` として `.sf-init.env` に保存する（既存の仕組み）。続きから再開するときは、保存した種別を使い、オプションの再指定は要らない |
| 既定 | 指定がなければ、外部クライアントアプリ（2）。`APP_TYPE` が保存されていれば、その値 |
| 無効な組み合わせ | `--legacy-connected-app` と、保存済みの `APP_TYPE=2` が食い違うとき（途中まで ECA で進めたあと）は、中断して、事実を表示する |
| ヘルプ | `--help` と、不明なオプションのメッセージに、追記する |
| テスト | 既定の経路（ECA）と、`--legacy-connected-app` の経路を、別々のシナリオにする |

### 4.7 段階と、組織の種類の独立（柔軟性の設計）

> 利用者（設計者・導入する人）は、**開発の時期・テストの時期・本番への代行**など、さまざまな場面で使う。導入する側も、**お試しで Sandbox に入れる → 本番に入れる**と、**段階的に**進める。どの段階（main / staging / develop）にも、**どの種類の Salesforce 組織（本番・Sandbox・Developer Edition）が来るかは、不定**である。この前提で、設計する。

#### 4.7.1 独立した 3 つの軸

| 軸 | 内容 | 制約 | あとから変えられるか |
|---|---|---|---|
| A. 段階の数 | main / staging / develop（何段階か） | なし | 増やせる（`--add-tier`・実装済み） |
| B. 各段階の接続先 | 段階ごとに、**ログイン先の URL**（本番・Developer Edition 等 / Sandbox / 組織の URL）と、接続するユーザー | **Salesforce の本番組織は、main にしか、つなげない**（staging・develop には、つなげない。4.7.2 の F8）。Sandbox・Developer Edition などは、**どの段階にも、つなげる**（main にも） | **付け替えられる（新規: `--reconnect`）** |
| C. sf-tools の版 | 配布版（main）・検証版（development） | 開発者向け | 環境変数 `SF_TOOLS_BRANCH` |

#### 4.7.2 ルール

| # | ルール |
|---|---|
| F1 | **段階の名前（main / staging / develop）と、組織の種類は、基本的に、結びつけない。** 「main = 本番」「staging = Sandbox」を、前提にしない（画面・文言・既定値・判定）。**唯一の制約は F8（本番は main のみ）** |
| F2 | ログイン先は、**URL で決める**（`login.salesforce.com` / `test.salesforce.com` / 組織の URL）。「種類」を聞いて、URL に変換することは、しない |
| F3 | 組織の種類は、**ログイン後に、組織自身から読み取る**（`IsSandbox`・`OrganizationType`）。表示と保存（状況の確認用）に使う。ログイン先の決定には、使わない（ログイン前に決める必要があるため） |
| F4 | 画面の呼び名は、**段階の名前**と、**実際の組織名・種類**にする。「本番」「検証」を、段階に当てはめない |
| F5 | 接続先は、**あとから付け替えられる**。段階ごとに、1 つずつ、同じ画面の流れで、やり直せる |
| F6 | 日々のコマンド（sf-start 等）も、**エイリアスの名前**で、ログイン先を決めない（P17）。認証済みの組織の一覧から選ぶ。新しくつなぐときは、F2 の 3 択 |
| F7 | 安全のための既定（Sandbox）は、**段階に依存しない**。どの段階でも、同じ。本番に接続するときだけ、利用者が、明示的に選ぶ |
| F8 | **Salesforce の本番組織は、main にしか、つなげない**（ソースの流れは、develop → staging → main で、本番に出るのは、main のみ。staging・develop が本番に接続されると、意図しない本番への反映になるため）。**ガード**: ① staging・develop のログイン先の選択肢 [1] には、「本番は、main のみ」と添える。② **ログイン後**、組織から種類を読み取り（F3）、**本番と判定されたら、staging・develop には、接続しない**（中断して、事実を表示する）。③ **判定できないとき（種類を読み取れない・矛盾する）は、main 以外には、つなげない**（利用者の確認では、通さない。本番かどうか、確かめられないため。外部レビューの指摘で、確認で通す案から変更）。main は、どの種類でも可（判定できなくても、続行する）。④ `--reconnect` でも、同じガードを通す |

#### 4.7.3 段階的な導入の流れ

| 場面 | やること | 使うもの |
|---|---|---|
| お試し（Sandbox 1 つ） | 1 段階（main）にして、ログイン先に Sandbox を選ぶ | `sf-init.sh` |
| 本番にも入れる | main の接続先を、本番に付け替える。または、段階を増やして、本番を後ろに置く | `sf-init.sh --reconnect main` / `--add-tier` |
| 開発用・検証用の組織を増やす | 段階を増やす | `sf-init.sh --add-tier staging` / `--add-tier develop` |
| 本番作業の代行 | 利用者の管理者として、ブラウザでログインして、接続する | `sf-init.sh`（F2 の [1]） |
| いまの接続を見る | 段階ごとの、ログイン先・組織名・種類・ユーザーを、一覧にする | `sf-init.sh --status`（新規） |

#### 4.7.6 接続情報のモデル（共通）

`sf-init.sh`・`--reconnect`・`--status`・`sf-start.sh`・`sf-update-secret.sh` が、**同じ接続情報モデル**を使う（実装を、共通の関数に集約する）。段階ごとに、次を持つ。

| 項目 | 内容 | 保存先 |
|---|---|---|
| ログイン入口 | `login.salesforce.com` / `test.salesforce.com` / 組織固有の URL | GitHub Variables `SF_INSTANCE_URL_*`（既存） |
| 接続ユーザー | 管理者権限のユーザー名 | GitHub Variables `SF_USERNAME_*`（既存） |
| コンシューマー鍵 | 外部クライアントアプリのキー | GitHub Secrets `SF_CONSUMER_KEY_*`（既存） |
| 組織 ID・組織名 | ログイン後に、組織から読み取る | GitHub Variables（新規。機密ではない） |
| 組織の種類 | `IsSandbox`・`OrganizationType`・（Trial の場合）期限 | 同上（新規。表示用） |
| 最終確認日時 | 実際にログインして、確認した日時 | 同上（新規） |

- **用語**: 「ログイン入口」（`login.salesforce.com` など。組織そのものの URL ではない）と、「組織固有の URL」（My Domain）を、区別して書く。
- **種類の読み取り**: ログイン後に、`sf data query` で、`Organization`（`Id`・`Name`・`IsSandbox`・`OrganizationType`・`TrialExpirationDate`）を取得する。**取得できない・矛盾する場合は、「判定不能」と表示し、推測しない。main 以外には、接続しない**（main は、続行する）。項目名・値は、実機の応答を記録してから、仕様にする（Q10）。
- **取り違えの防止**: 段階ごとに、**組織 ID を必須の状態**として保存する。`--status` と `--reconnect` は、組織 ID・組織名・ユーザー・ログイン入口・最終確認日時を表示する。
- **同じ組織を、複数の段階に使う**: 禁止はしない。**強い警告**を出す（デプロイが、同じ組織の中で、循環するため）。`--status` で、重複を明示する。
- **スクラッチ組織**: 対象外（寿命のある、別の仕組みのため）。Trial は、期限が近い・切れたとき、`--status` で警告する。

#### 4.7.7 `--reconnect` の安全設計

1 つの段階の接続先を、付け替えるときの手順と、守ること。

1. **現在の接続を表示**する（段階・組織 ID・組織名・種類・ユーザー・ログイン入口）。
2. ログイン先を選ぶ（4.4 (6)）。ログインしたあと、**新しい組織の ID・名前・種類を表示**し、「この段階（main など）に、この組織をつなぎます」と、**明示的に確認**する。
3. F8 のガード（本番は main のみ）を通す。
4. **一括で更新する**: `SF_USERNAME_*`・`SF_INSTANCE_URL_*`・`SF_CONSUMER_KEY_*`・組織情報。途中で失敗したときは、**どこまで更新されたかを、表示する**（古い接続と、新しい接続が、混ざったままにしない）。
5. **古い組織に残るもの**（外部クライアントアプリなど）は、自動では削除しない。**残っていることと、片付け方を、表示する**。削除は、明示の確認つきの、別の操作にする。
6. `--add-tier` と、`sf-update-secret.sh` との**役割**: `--add-tier` = 段階（ブランチ・ワークフロー）の追加。接続は、共通の接続の流れを使う。`sf-update-secret.sh` = 鍵・ユーザー名の部分的な更新（鍵の入れ替えなど）。付け替えは、`--reconnect`。いずれも、4.7.6 の共通の関数を使う。

## 5. 共通部品（lib の設計）

画面の見た目を、コマンドごとに作らず、**共通の部品**で出す。

| 関数（案） | 役割 |
|---|---|
| `wizard_begin <タイトル> <ステップ名…>` | 開始画面（全体像・事前準備・ステップ一覧）を出し、Enter を待つ |
| `wizard_step <番号> <タイトル> <目的の 1 文>` | ステップの見出し（現在地・完了済み）を出す |
| `wizard_do <手順…>` | 「あなたがやること」を、番号付きで出す |
| `wizard_next <説明>` | 「そのあと」を出す |
| `wizard_choose <変数> <推奨> <選択肢…>` | 推奨つきの選択（Enter で推奨） |
| `wizard_wait_browser <URL> <確認する目印> [制限時間]` | ブラウザを開き、目印・制限時間を出す。ブラウザが開かないときのために、URL も出す |
| `wizard_progress <説明> <n> <最大>` | 待ち時間の進み具合（R8） |
| `wizard_auto <説明>` | 自動のステップの 1 行表示（完了を `✔`） |
| `wizard_fail <原因> <直し方> <再開の方法>` | 失敗の三点セット |
| `wizard_done <できたこと> <次にやること…>` | 完了画面 |

- 既存の `read_key` / `press_enter` / `read_secret` などの入力関数を、中で使う（独自実装はしない）。操作の語彙と、画面の下のヒントは、この部品だけが決める。
- 表示は標準エラー出力（既存の `log` と同じ）。ログファイルには、色・記号を除いて記録する（既存の仕組み）。
- **Windows の Git Bash を、最優先の動作環境にする**: 新しい外部コマンドを増やさない。ブラウザ起動は、既存の `open_browser`（失敗しても、URL を表示するため、止まらない）。色は、既存の `CLR_*` 変数（端末でないときは空）。罫線・記号は、既存の警告ボックスと同じ種類の文字のみ使う。EOF（標準入力の終了）は、既存の入力関数と同じく中断として扱う。

## 6. 他のコマンドへの展開

優先順位は、「誤操作の影響（危険度）」「利用頻度」「入力の複雑さ」の 3 軸で決める。

| 順 | コマンド | 理由 | 見直す内容 |
|---|---|---|---|
| 1 | sf-init | 初見の利用者が、必ず通る。入力が最も多い | 本設計の全面適用 |

| 3 | sf-start | 毎日使う。**エイリアス名でログイン先を決めている不具合（P17）** | 認証済みの組織の一覧（`sf org list`）から選ぶ。新規は、ログイン先の 3 択（4.7）。初回の説明 |

| 5 | sf-next / sf-push / sf-sync-wf | 実行後の案内 | 「次にやること」を、定型で出す |
| 6 | sf-update-secret | 利用頻度が低い。入力が多い | 全体像と現在地を出す |

> 全コマンド共通の最低ライン: **終了時に、「できたこと」と「次にやること」を 1 行以上出す**。
