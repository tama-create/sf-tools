日々の開発の流れ

変更を書いて、検証して、デプロイして、送る。毎日くり返す一連の操作です。すべて force-* フォルダの中で実行します。

全体の流れ

ターゲットファイルを書く → sf-release.sh（検証）→ sf-deploy.sh（デプロイ）→ sf-push.sh（送る）→ sf-next.sh（次の PR 先を確認）

1. ターゲットファイルを記述する

ターゲットファイルとは、デプロイ対象・削除対象のメタデータを列挙するファイルです。release/<ブランチ名>/ の下に置きます。

ファイル役割
deploy-target.txtデプロイするメタデータを列挙する
remove-target.txt削除するメタデータを列挙する

書き方は、ターゲットファイルの書き方 を見てください。

2. dry-run で検証する

sf-release.sh

実際には変更せずに、接続中の組織へ、リリースできるかを確かめます。

3. デプロイを実行する

sf-deploy.sh

4. 変更をコミットして送る（sf-push）

sf-push.sh

カレントフォルダの下の変更を、まとめてコミットしてプッシュします。

  • コミットメッセージは、VS Code で入力します。
  • main との差分も、自動で取り込みます。
  • プッシュだけ失敗したときは、もう一度実行すれば、未プッシュのコミットが送られます。
コミットする前に止まる場合

ブランチの上にいないとき（detached HEAD）と、保護ブランチ（branches.txt のブランチ。main など）の上にいるときは、コミットする前にエラーで終了します。コミットだけが手元に残り、プッシュは通らない状態を作らないためです。

5. PR の状況を確認する（sf-next）

sf-next.sh

現在のブランチが、develop / staging / main のどこまでマージ済みかを一覧で表示し、次に出すべき PR の先を案内します。

6. git フックによる自動チェック

コミットとプッシュのときに、次のチェックが自動で動きます。

フックいつ内容
pre-commitgit commit のときターゲットファイルの構文を確認します。エラーがあれば、コミットを中止します
pre-pushgit push のときmain との同期を確認します。main / staging / develop への直接のプッシュは、ブロックされます

7. ランチャーから実行する

ここまでのコマンドは、すべて sfl（sf-launcher.sh）から、メニュー形式でも実行できます。sf-job / sf-start を実行すると自動で起動するので、個別に呼び出す必要はありません。

sfl
  ──────────────────────────────────────────────────
  >> Launcher <<
  ──────────────────────────────────────────────────
  [1] Check      ターゲットファイルの構文チェック
  [2] Push       変更をコミット & プッシュ
  [3] Next       次の PR 先ブランチを確認
  [4] Dryrun     現在接続中の組織へリリース検証
  [5] Deploy     現在接続中の組織へリリース
  [6] Start      開発環境を起動（Salesforce ログイン・VSCode 起動）
  [7] Restart    接続組織を切り替えて Start 実行
  ──────────────────────────────────────────────────
  番号を入力 (1-7 / q で終了):
