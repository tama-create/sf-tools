🔧 構成の変更と診断

セットアップが済んだあとの、管理者のメンテナンスです。段階（ブランチの階層）を足す、接続先の組織を付け替える、いまの状態を診断する、の 3 つを説明します。どれも、force-* フォルダの中（管理者用の admin/force-XXXX）で実行します。

まず困ったら、診断から

「どこで間違えたか分からない」というときは、sf-init.sh --status から始めてください。何も変更せずに、足りないものと、直し方を教えてくれます。

どのコマンドを使うか

管理者のメンテナンスのコマンドを、「やりたいこと」から探せます。

やりたいことコマンド説明
いまの状態を調べたい（何も変えない）sf-init.sh --statusセットアップを診断する
段階（staging・develop）を足したいsf-init.sh --add-tier段階を足す
接続先の Salesforce 組織を、付け替えたいsf-init.sh --reconnect接続先を付け替える
秘密鍵・ユーザー名などを、登録し直したいsf-update-secret.sh再登録する
ワークフローを、最新の雛形に合わせたいsf-sync-wf.sh雛形に合わせて更新する
実際に動くことを、確かめたいsf-init.sh --verify動作の確認

Salesforce 組織の接続の考え方

段階（main / staging / develop）と、組織の種類は、結びつけていません。どの段階にも、Sandbox・Developer Edition などを、自由につなげられます（main に Sandbox や Developer Edition をつないでも構いません）。ただし、本番の組織だけは、次のルールがあります。

本番の組織は、main にだけつなげます

staging や develop に、本番の組織をつなごうとすると、ログインのあとで組織の種類を確かめて、そこで止まります（既定の方式では、外部クライアントアプリを作る前に止まります）。種類を判定できない組織も、同じように、main 以外にはつなげません。本番を、うっかり、開発用の段階につなげないための仕組みです。最初のセットアップ・段階の追加・付け替えの、どれでも同じです。

ログイン先の選び方

段階ごとに、ログイン先を、次の 3 つから選びます（Enter だけなら 2 番です。q で中断）。組織の種類ではなく、ログインする URL で選びます。

  1. https://login.salesforce.com — 本番・Developer Edition・Trial など（main 以外の段階では、「Developer Edition・Trial など（※ Salesforce の本番は、main のみ）」と表示されます）
  2. https://test.salesforce.com — Sandbox（安全なおすすめ。本番に影響しません）
  3. 組織の URL を入力（My Domain。例: https://会社名.my.salesforce.com）。https:// で始まり、salesforce.com か force.com のドメインでないと、入力し直しになります

選んだあと、ブラウザで Salesforce にログインします（システム管理者のユーザーで。約 2 分で時間切れになります）。ログインすると、組織の ID・名前・種類（本番 / Sandbox / Developer Edition / Trial）を、組織から読み取ります。読み取った内容は、GitHub の Variable（SF_ORG_*）に保存され、--status で見られます。

そのあとの、外部クライアントアプリの自動作成・接続のテスト（最大 約 10 分くり返します）・GitHub への登録は、最初のセットアップと同じです（Salesforce の接続）。--legacy-connected-app を付けると、従来の接続アプリケーション（手動の入力）を使います。

段階を足す（--add-tier）

セットアップのあとで、main だけの構成から、staging・develop へ、段階を足せます。

# force-* フォルダの中で実行
sf-init.sh --add-tier staging    # main のみ → main + staging
sf-init.sh --add-tier develop    # main + staging → main + staging + develop

実行すると、次の順に進みます。

  1. 足せるかを確かめます。GitHub の最新の main の branches.txt（段階の一覧のファイル）を読んで、すでにある段階を、もう一度足そうとしていないか、develop を足すときに staging があるかを確かめます（手元のファイルではなく、GitHub の main で確かめます）。
  2. 管理者向けの警告と確認が出ます。gh にログインしているユーザーが、オーナー本人か、その組織の管理者かを確かめてから、「続行しますか？」（Y/N/q）と聞かれます。GITHUB_ACTIONS=true でも、省略しません。
  3. 足す段階の組織に接続して、認証情報を登録します。ログイン先を選んで、ブラウザでログインします（ログイン先の選び方）。staging なら STG、develop なら DEV の名前で、Secret SF_CONSUMER_KEY_* と、Variable SF_USERNAME_*・SF_INSTANCE_URL_*・SF_ORG_* を登録します。
  4. GitHub に、新しいブランチ（staging または develop）を作ります（すでにあれば、作りません）。
  5. 作業用のブランチ（system-add-tier-段階-日時）を作り、branches.txt に段階を足して、コミットとプッシュをします。
  6. main に向けて、PR を作ります（main には直接プッシュしません）。
  7. 実行する前のブランチ（管理者用のクローンでは admin）に戻ります。
PR をマージすると、段階として有効になります

作られた PR を、GitHub でマージしてください。マージするまでは、段階として使われません。マージする前に、もう一度 --add-tier を実行すると、PR が 2 本できます（GitHub の main には、まだ段階が入っていないため、重複として止まりません）。staging のブランチ保護（protect-staging）は、最初のセットアップで作ってあるので、足す必要はありません。

  • staging を飛ばして、main から develop を足すことは、できません（エラーになります）。すでに足してある段階を、もう一度足すこともできません。
  • 最初のセットアップとは、順序が逆です。段階を足すときは、先に Salesforce に接続して、成功してから、ブランチと PR を作ります。接続に失敗したときに、GitHub 側を、変更しないためです。ただし、外部クライアントアプリは、接続のテストの前に組織に作るので、失敗しても組織に残ります（自動では消えません）。
  • 接続のテストに失敗したときに、テストを飛ばして登録する（Y）と答えると、認証情報は登録されます。
  • 接続のあと（ブランチ・PR を作る途中）で失敗したときは、そこまでに作ったブランチが残り、admin に戻らないことがあります（自動では元に戻しません）。もう一度 --add-tier を実行すると、GitHub に段階のブランチがあれば作らずに進み、新しい作業用のブランチで PR を作ります（Salesforce への接続も、もう一度行います。前の実行で PR まで作れていたときは、PR が 2 本になります）。ただし、作業ツリーに未コミットの変更が残っていると、止まります。
実行する前に
  • 未コミットの変更があると、エラーで止まります。先にコミットするか、取り除いてください。
  • JWT の鍵（~/.sf-jwt/force-XXXX/server.key。既定の方式では server.crt も）が、この PC に必要です。sf-init.sh を実行した PC で行ってください。
  • 新しいブランチ（staging / develop と、branches.txt を更新する作業用のブランチ）は、リモートの最新の main（origin/main）から作ります。手元の main が古くても、古い内容からは派生しません（手元の main は、更新しません）。

段階を減らすとき（手動）

段階を減らす操作は、自動化していません
  • ブランチの削除・Ruleset の変更・Secrets / Variables の削除など、影響が広い操作だからです。
  • まちがえて削除すると、元に戻せないおそれがあります。
  • 必要になる機会が少なく、1 回で済む手作業と判断しました。

次の順番で、手作業で行います。

  1. GitHub の Repository Ruleset を更新します（減らす段階のブランチを、対象から外します）。Ruleset の設定によっては、先に外さないと、ブランチを削除できません。

  2. branches.txt から、減らす段階を削除して、コミットしてプッシュします。

  3. GitHub で、ブランチ（staging / develop）を削除します。

  4. GitHub の Secrets / Variables から、その段階の SF_CONSUMER_KEY_*（Secret）と、SF_USERNAME_* / SF_INSTANCE_URL_* / SF_ORG_*（Variable）を削除します。

接続先を付け替える（--reconnect）

sf-init.sh --reconnect <段階>      # 段階: main / staging / develop

1 つの段階について、接続先の Salesforce 組織を、別の組織に付け替えます（「お試しで Sandbox につないだが、本番につなぎたい」「組織を作り直した」ときなど）。最初のセットアップと同じ画面の流れで、外部クライアントアプリの自動作成まで行います。ログイン先の選び方と、本番は main にだけつなげるというルールは、最初の章のとおりです。段階は増やしません（増やすときは --add-tier）。鍵やユーザー名の部分的な更新は、sf-update-secret.sh で行います。

  1. いまの接続（ログイン先・組織の種類・ユーザー・組織名・組織の ID）を表示します。
  2. 管理者向けの警告が出て、gh にログインしているユーザーが、オーナー本人か、その組織の管理者かを確かめてから、「付け替えますか？」（Y/N/q）と聞かれます（N / q で中止）。
  3. ログイン先を選んで、ブラウザで、新しい組織にログインします。組織の種類を確かめて、外部クライアントアプリを作り、接続をテストします。
  4. Secret SF_CONSUMER_KEY_* と、Variable SF_USERNAME_*・SF_INSTANCE_URL_*・SF_ORG_* を、新しい組織の値に更新します。
  5. 以前の組織と新しい組織が違うときは、以前の組織に、以前の接続に使ったアプリが残っていることと、削除する場所を表示します。以前の接続の方式は記録していないので、両方を表示します: sf-init が作った外部クライアントアプリ（SF_TOOLS_ で始まる名前。外部クライアントアプリマネージャ）と、--legacy-connected-app で手動で作った接続アプリケーション（アプリケーションマネージャ）。自動では削除しません。以前の組織の ID が記録されていなかったときは、確かめるよう案内が出ます。
  • 段階は、main（prod も main として受け付けます）・staging・develop のいずれかです。staging と develop は、branches.txt にその段階があるときだけ指定できます。
  • JWT の鍵と証明書（~/.sf-jwt/force-XXXX/ の server.key と server.crt）が、この PC に必要です（--legacy-connected-app のときも、両方が必要です）。
途中で止まったとき
  • 外部クライアントアプリは、接続のテストの前に、新しい組織に作ります。そのあとで止まると、新しい組織にアプリが残ります（自動では消えません）。
  • 接続のテストに失敗しても、テストを飛ばして登録する（Y）と答えると、登録されます。
  • 登録は、SF_CONSUMER_KEY_* → SF_USERNAME_* → SF_INSTANCE_URL_* の順に 1 つずつ行います。途中で止まると、新しい組織の値と、以前の組織の値が混ざった状態になります。もう一度 --reconnect を実行して、そろえてください。

セットアップを診断する（--status）

sf-init.sh --status

🔍 読み取りのみ 何も変更せずに、いまの状態を調べます。「どこで間違えたか分からない」ときの、最初の手がかりです。管理者向けの警告と確認は、出ません。セットアップが済んだプロジェクトで、オプションなしの sf-init.sh を実行して「[1] いまの Salesforce の接続を見る」を選んでも、同じ表示になります。

調べる段階は、main と、branches.txt にある staging / develop です。項目ごとに、次の記号で示します。

記号意味不足に数えるか
✓できている—
✗足りない。すぐ下に「直し方」（実行するコマンド）を表示します数える
！注意（直近のワークフローが成功していない、組織の種類が記録されていない、など）数えない
？確認できなかった（通信エラー・権限がない・プランが対応していない、まだ実行されていない、など）数えない

調べる項目

項目調べること
リポジトリGitHub にリポジトリがあるか。段階のブランチがあるか（なければ、直し方は --add-tier）。ワークフロー 5 本（wf-metasync・wf-propagate・wf-release・wf-sequence・wf-validate）があるか（なければ、sf-sync-wf.sh）
SecretsPAT_TOKEN・SLACK_BOT_TOKEN・SF_PRIVATE_KEY・段階ごとの SF_CONSUMER_KEY_* があるか（名前だけを調べます。値は、だれにも読めません）
VariablesSLACK_CHANNEL_ID・段階ごとの SF_USERNAME_*・SF_INSTANCE_URL_* があるか。組織の種類の記録（SF_ORG_ID_*）がないときは「！」（以前のバージョンで作ったプロジェクト。--reconnect で記録できます）。SF_TOOLS_BRANCH は、開発版のときだけ使うものなので、なくても不足にしません
ブランチ保護Ruleset（protect-main・protect-staging）の必須チェックの名前が、ワークフローのジョブの名前（対象ファイル確認・デプロイ検証・順序チェック）と、過不足なく合っているか（合っていないと、PR をマージできません）。Ruleset が無い（無料プランの非公開リポジトリなど）・読めないときは、「？」と表示するだけで、不足には数えません
直近の実行（参考）wf-metasync・wf-release・wf-validate・wf-propagate の、直近の 1 回の結果。成功は ✓、成功以外で終わったものは「！」、まだ実行されていない・実行中のものは「？」です（時刻は UTC）

最後に、「不足はありません」か「不足が N 件あります」と表示します。

段階ごとの接続先

  • 段階ごとに、ログイン先（URL）・組織の種類・接続ユーザー・組織名・組織の ID・最後に確かめた日時を表示します。接続の情報がない段階は「（未接続）」と表示します。
  • 同じ組織が、複数の段階につながっているときは、警告が出ます（段階を進めても、同じ組織にリリースすることになり、段階で確かめる意味がなくなります）。
  • 本番の組織が、main 以外につながっているときは、エラーが出ます。
  • 表示する接続先は、GitHub に保存された値です（いま実際にログインして確かめた値ではありません）。以前のバージョンで作ったプロジェクトなど、保存されていないものは、組織が「未確認」、種類が「種類を判定できません」と表示されます。
  • Salesforce 側（外部クライアントアプリ・JWT 接続）は、ログインが必要なので、調べません。直近の wf-metasync や wf-release が成功していれば、接続はできています。

足りないもの（✗）がある、または、本番の組織が main 以外につながっていると、終了コードは 1 になります（スクリプトから、問題を見つけられるようにするためです）。
