⚙️ ワークフローの更新（sf-sync-wf）

ワークフローは、GitHub の上で自動で動く処理です（検証・リリース・同期など。GitHub Actions という仕組みで動きます）。このページでは、sf-init が作る 5 つのワークフローが、いつ・何をするのかと、作成済みのプロジェクトのワークフローを、sf-tools の最新の雛形に合わせて更新する sf-sync-wf.sh の使い方を説明します。

このページの要点
  • ワークフローは、sf-init.sh が作る 5 つ（validate・sequence・release・propagate・metasync）です。
  • main / staging への PR は、3 つのチェック（対象ファイル確認・デプロイ検証・順序チェック）が通らないと、マージできません（ブランチ保護が効いているとき）。
  • リリースや同期の処理の中身は、ワークフローが動くたびに、sf-tools から取ってきます。sf-tools の更新は、すぐに届きます。
  • ただし、ワークフローのファイル自体の修正は、自動では届きません。sf-sync-wf.sh（管理者専用）で、作成済みのプロジェクトに反映します。
  • sf-sync-wf.sh --check は、差分があるかを調べるだけです（何も変更しません）。

自動で作られるワークフロー

sf-init.sh は、プロジェクトの .github/workflows/ に、次の 5 つを作ります（雛形は sf-tools/templates/.github/workflows/）。GitHub の Actions の画面には、2 列目の名前で表示されます。

ファイル画面での名前いつ動くか手動の実行
wf-validate.yml[validate] デプロイ前検証PR の作成・更新（ソースブランチへのプッシュ）・再オープンのとき。マージ先のブランチは問いませんできない
wf-sequence.yml[sequence] マージ順序チェックmain / staging への PR の作成・更新・再オープンのときできない
wf-release.yml[release] デプロイmain / staging / develop への PR をマージしたあとできる（main / staging / develop で実行したときだけ、リリースする）
wf-propagate.yml[propagate] ブランチ伝播main への PR をマージしたあとできる（main で実行したときだけ、伝える）
wf-metasync.yml[metasync] メタ同期平日（月〜金）の日本時間 9:00 / 12:00 / 15:00 / 18:00（3 時間おき）に自動で。GitHub の混雑で、開始が遅れることがありますできる（どのブランチで実行しても、main を同期する）
  • 「手動の実行」は、GitHub の Actions の画面の「Run workflow」ボタン（workflow_dispatch）のことです。sf-init のセットアップの最後と、sf-init.sh --verify は、wf-metasync を、この方法で起動します。
  • どのワークフローも、ブランチへの直接のプッシュでは動きません。PR のタイトル・本文の編集でも動きません。
  • コンフリクト（同じ場所を、別々に変更した衝突）のある PR では、wf-validate と wf-sequence は動きません（GitHub が、マージした結果を作れないためです）。コンフリクトを解消すると、動きます。

マージの前の必須チェック

必須チェックとは、「これが成功しないと、PR をマージできない」と、ブランチ保護（GitHub の Ruleset）に登録したチェックです。sf-init は、main と staging のブランチ保護（protect-main / protect-staging）に、次の 3 つを登録します。

必須チェックの名前どのワークフローのジョブか失敗するとき
対象ファイル確認wf-validate と wf-sequence の両方にあります（PR の画面には、同じ名前で 2 つ並びます）ふつうは失敗しません（デプロイの対象があるかを調べるだけです）
デプロイ検証wf-validatedry-run の検証が失敗したとき
順序チェックwf-sequence環境ブランチ（main / staging / develop など）から、直接 PR を出したとき
  • 必須チェックは、ジョブの名前だけで照合されます。ワークフローの名前を付けた形（以前の sf-init が登録していた「validate / 対象ファイル確認」など）は、永久に満たされず、PR をマージできなくなります。以前のバージョンで作ったプロジェクトは、トラブルシューティングを見てください（sf-init.sh --status が、食い違いを見つけます）。
  • デプロイの対象がない PR（ターゲットファイルが空）では、デプロイ検証 と 順序チェック は、スキップされます。スキップされたチェックは、GitHub の仕様で、成功として扱われるので、マージは止まりません。
  • develop などへの PR には、ブランチ保護がないため、検証が失敗しても、マージは止まりません（結果の表示だけです）。
  • ブランチ保護が作れなかったプロジェクト（無料プランの非公開リポジトリなど）では、どのチェックが失敗しても、マージは止まりません。また、リポジトリの Admin（管理者の権限を持つ人）は、ブランチ保護を迂回できます。
ジョブの名前を、変えないでください

ワークフローのジョブの名前（name:）を手で変えると、必須チェックが永久に満たされず、PR をマージできなくなります。wf-release の「リリース対象確認」は、必須チェックの「対象ファイル確認」と、わざと別の名前にしてあります（同じ名前だと、先の段階の PR で付いた成功が、次の段階の PR の必須チェックを、満たしてしまう恐れがあるためです）。

wf-validate（デプロイ前検証）

PR を作るたび・更新するたびに、sf-release.sh を、検証のモード（dry-run。組織には反映しない）で実行し、結果を PR にコメントします。

  • ジョブは 2 つです。対象ファイル確認 が、ターゲットファイル（sf-tools/release/<ソースブランチ名>/ の deploy-target.txt・remove-target.txt）に中身があるかを調べ、あれば デプロイ検証 が動きます。
  • 検証に使う組織は、マージ先で決まります。main への PR は main の組織、staging への PR は staging の組織、それ以外（develop や、作業用のブランチへの PR）は develop の組織です。develop の組織を登録していない構成（main のみ・main + staging）で、main / staging 以外への PR を出すと、ログインで失敗します。
  • PR へのコメントは、毎回、新しく追加します。見出しは「✅ 検証成功」「❌ 検証失敗（終了コード）」、途中の手順で止まった・取り消された・時間切れになったときは「⚠️ 検証が実行されませんでした」です。長いログは、末尾の 3000 文字だけを載せます。
  • Slack には通知しません。

wf-sequence（マージ順序チェック）

main / staging への PR で、マージの順序（develop → staging → main）が守られているかを確かめます。順序は、main ブランチの sf-tools/config/branches.txt の並びで決まります（PR の中身ではなく、常に main から読みます）。

PR の状態チェック知らせ方
順序どおり成功何もしません（以前に警告のコメントがあれば、「✅ 問題ありません」に書き換えます）
順序外（前の段階に、まだマージされていない）成功（マージは止めない）PR へのコメント「⚠️ マージ順序の確認が必要です」と、Slack
環境ブランチから直接出した PR失敗（マージできない）PR へのコメント「⛔ 環境ブランチからの PR は、許可されていません」と、Slack
  • 順序外でもマージを止めないのは、緊急の修正（Hotfix）を妨げないためです。気づいたレビュアーが、PR を却下します。
  • 開発者が sf-next.sh（ランチャーの「次の PR」）を使う限り、順序は守られます。このチェックは、GitHub の画面で直接 PR を作ったときの備えです。仕組みの詳細は、sf-next.sh の説明にあります。
  • Salesforce の組織には、接続しません。

wf-release（デプロイ）

PR を main / staging / develop にマージすると、マージ先に対応する組織へ、sf-release.sh --release でリリースし（組織に反映し）、結果を Slack に通知します。

  • ジョブは 2 つです。リリース対象確認 がターゲットファイルに中身があるかを調べ、あれば リリース実行 が動きます。中身がない・マージせずに閉じた PR では、リリースせず、Slack にも通知しません。
  • ログインするのは、マージ先の組織だけです（main → main の組織、staging → staging の組織、develop → develop の組織）。
  • Slack には、成功なら「リリース成功」、失敗・取り消しなら「リリース失敗」を、リリース先・ブランチ・PR・日時・ログの URL と一緒に送ります。
  • 続けてマージしても、同じマージ先へのリリースは、1 つずつ順に動きます（待っている実行は、取り消されません。ただし、待ちが 100 を超えると、GitHub の仕様で、それ以降は取り消されます）。マージ先が違うリリースは、並行して動きます。
  • wf-propagate や wf-metasync による伝播（PR を通さないプッシュ）では、動きません。staging / develop の組織にリリースするのは、その段階への PR をマージしたときだけです。
手動の実行（Run workflow）の注意
  • main / staging / develop 以外のブランチで実行すると、リリースしません（警告を表示するだけです）。
  • 3 つのブランチで実行すると、そのブランチの名前の sf-tools/release/<ブランチ名>/ を、ターゲットファイルとして使います。このフォルダに deploy-target.txt・remove-target.txt のどちらかがないと、失敗します。両方とも中身がないと、組織に何も反映せずに成功し、Slack には「リリース成功」と通知されます。

wf-propagate（ブランチ伝播）

main への PR をマージすると、main を staging と develop へ、PR を通さずに直接マージして、プッシュします。下の段階のブランチを、main に追いつかせるためです（Git のブランチだけで、Salesforce の組織には接続しません）。

  • staging / develop がない構成では、そのブランチへの伝播を飛ばします（失敗にはしません）。
  • コンフリクトしたときは、そのマージを取り消し、Slack に通知して、失敗で終わります。コンフリクトしたブランチは、手で解消します（main を、そのブランチにマージします）。
  • 伝播のプッシュには、Secret PAT_TOKEN を使います（下のSecrets と Variables）。PAT_TOKEN の期限切れ・権限不足では、失敗します。このときは Slack に通知しないので、Actions の画面で気づく必要があります。
  • 続けてマージしても、伝播は 1 つずつ動きます。待っている実行は、より新しい実行に置き換えられ、「取り消し」と表示されますが、新しい実行が最新の main を伝えるので、漏れはありません。

wf-metasync（メタ同期）

main の組織（prod の名前で接続した組織。本番とは限りません）から、最新のメタデータを取得し、変更があれば、main ブランチにコミットしてプッシュします（Salesforce の組織の内容を正とします）。処理の中身は sf-metasync.sh です。

  • プッシュしたときは、sf-metasync.sh 自身が、main を staging / develop へ伝えます（wf-propagate は動きません）。伝えるのに失敗したブランチは、警告を出して飛ばし、ジョブは成功で終わります（ログの警告で気づいて、補います）。
  • このプッシュは PR ではないので、wf-release は動かず、組織へのリリースは行われません。
  • 変更がなければ、何もせずに成功します。
  • Slack には、成功・失敗のどちらも通知しません。失敗に気づくには、Actions の画面か、sf-init.sh --status の「直近の実行」を見ます。
  • 定期の実行と手動の実行が重なっても、1 つずつ動きます（待っている実行は、新しい実行に置き換えられます）。手元で実行した sf-metasync.sh と重なってプッシュが拒まれたときは、失敗するので、もう一度実行してください。

Secrets と Variables

ワークフローは、GitHub に登録した Secret（隠しておく値）と Variable（見えてもよい値）を使います。登録は sf-init が行い、あとからの登録し直しは、秘密の情報の管理のページで説明しています。

使うもの使うワークフロー用途
SF_PRIVATE_KEY・SF_CONSUMER_KEY_*・SF_USERNAME_*・SF_INSTANCE_URL_*validate・release・metasyncSalesforce の組織に、JWT 認証でログインする
PAT_TOKENmetasync・propagate だけリポジトリの取得と、main / staging / develop へのプッシュ（ブランチ保護を迂回し、ワークフローのファイルの変更を含むプッシュもできるようにするため。PAT の持ち主が Admin であることが前提）
SLACK_BOT_TOKEN・SLACK_CHANNEL_IDrelease・sequence・propagateSlack への通知（release はリリースのたび、sequence は順序外・環境ブランチのとき、propagate はコンフリクトのとき）
SF_TOOLS_BRANCH（任意）validate・release・metasync取ってくる sf-tools のブランチ。ふつうは登録しません（未登録なら main）

PR へのコメント（validate・sequence）には、GitHub が自動で用意する Token を使うので、登録は要りません。

雛形に合わせて更新する（sf-sync-wf.sh）

sf-sync-wf.sh            # 雛形との差分を表示し、確認のうえ、上書きする
sf-sync-wf.sh --check    # 差分があるかだけを調べる（何も変更しない）
sf-sync-wf.sh --remove wf-old.yml   # 雛形から廃止されたワークフローを削除する

sf-init.sh で作成済みの force-* に、あとから、ワークフローの修正（不具合の修正・安全対策など）を反映するコマンドです。sf-tools の雛形と、プロジェクトのワークフローを比べて、違いを表示します。確認のうえで、雛形の内容に上書きします。

いつ必要になるか

validate・release・metasync は、動くたびに、公開されている sf-tools（ふつうは main ブランチ）を取ってきて、その中の sf-release.sh や sf-metasync.sh を使います。そのため、リリースや同期の処理の中身の修正は、sf-tools が更新されれば、すべてのプロジェクトに、すぐ届きます（sf-sync-wf.sh は要りません）。

sf-sync-wf.sh が必要なのは、ワークフローのファイル自体（起動の条件・ジョブの構成・使う Secret など）が、雛形で直ったときです。これは、作成済みのプロジェクトには、自動では届きません。届いていないかは、sf-sync-wf.sh --check で調べられます。

管理者専用

CI/CD（リリース・検証）の動作が変わるため、実行の冒頭に、赤い警告ボックスと確認（Y/N/q）が表示されます（--check を除く）。sf-install.sh などから、自動では実行されません（利用者の意思なく、ワークフローが書き換わるのを防ぐためです）。

更新の手順（おすすめ）

  1. sf-job.sh で、ジョブ名 system-日付（例: system-20261006）の作業用ブランチを作ります。ブランチは、GitHub の最新の main から作られます。ワークフローの更新の PR だと、名前で分かります。

  2. そのフォルダで sf-sync-wf.sh を実行し、差分を確認して Y を答えます。

  3. git diff .github/workflows/ で、内容を確認します。

  4. sf-push.sh で、コミットしてプッシュします（ワークフローのファイルをプッシュするには、workflow の権限（スコープ）のある GitHub の認証が必要です）。

  5. PR を出して、マージします。develop / staging がある構成では、通常の変更と同じ順序（develop → staging → main）で、PR を出します（次の PR 先は、sf-next.sh が案内します）。

動作

  • force-* フォルダの中で、作業用のブランチの上でしか、実行できません。環境ブランチ（sf-tools/config/branches.txt のブランチ。main / staging / develop など）の上や、ブランチの上にいないとき（detached HEAD）は、中断します。sf-tools に雛形のフォルダがないときも、中断します。
  • sf-tools（~/sf-tools）が最新であることが必須です。実行すると、まず、sf-tools が GitHub（origin）の同じブランチより遅れていないかを確かめます。遅れていれば、確認（Y/N/q）のうえで sf-tools を更新し、更新した sf-tools で、同じオプションのまま、もう一度、自動で実行します（古い雛形で、プロジェクトのワークフローを書き換えないためです）。
    • origin に接続できない・更新を断った（N / q）・更新に失敗した・sf-tools に未コミットの変更や未プッシュのコミットがある場合は、中断します。
    • もう一度実行したあとも、まだ遅れているときは、確認と更新は行いますが、3 回目の実行はせずに、中断します。
    • 最新かどうかを確かめられないとき（sf-tools が Git のリポジトリでない・ブランチの上にいない・origin に同じブランチがない）は、警告を出して、続行します。
    • --check は、何も変更しない（読み取り専用の）ため、sf-tools を更新せず、遅れていれば中断します。
  • 比べるとき、改行コード（CRLF / LF）だけの違いは、差分とみなしません。雛形にあってプロジェクトにないファイルは「新規」、内容が違うファイルは差分（diff -u）を表示します。
  • 差分を表示したあと、もう一度「雛形の内容で、上記のワークフローを上書きします。よろしいですか？」（Y/N/q）と聞かれます。N / q なら、何も変更しません。
  • 自動でコミット・プッシュはしません。
  • 雛形にないワークフローは、変更せず、名前を表示するだけです。--remove で、雛形から廃止されたものだけを削除できます（雛形にあるものは、削除できません）。
  • --remove が受け付けるのは、wf-old.yml のような、フォルダを含まないワークフローのファイル名（英数字で始まり、.yml / .yaml で終わるもの）だけです。.github/workflows/ にないファイルを指定したときは、中断します。確認は、冒頭の警告のあとと、削除の直前の、2 回あります。--remove のときは、比較・上書きはしません。
  • --check は、差分なしで終了コード 0、あれば 1 を返します。複数のリポジトリを見回るときに使えます。ただし、1 は「中断」（sf-tools が遅れている・環境ブランチの上、など）のときにも返るので、「差分あり」とは区別できません。
  • --check と --remove は、同時に指定できません（エラーで終了し、何も変更しません）。
  • -v（--verbose）は、コマンドの応答をコンソールにも表示します。ほかの引数は、「不明なオプションです」で中断します。
  • GITHUB_ACTIONS=true の環境でも、警告と確認は省略しません。
  • ログは ./sf-tools/logs/sf-sync-wf.log です（実行のたびに作り直します）。
ブランチ保護（Ruleset）は、変更しません

sf-sync-wf.sh が書き換えるのは、.github/workflows/ のファイルだけです。雛形で、必須チェックになっているジョブの名前が変わったときは、ブランチ保護の必須チェックも、合わせて直す必要があります。食い違いは、sf-init.sh --status が見つけます（直し方は、トラブルシューティング）。
