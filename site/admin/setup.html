新規プロジェクトの作成（sf-init）

sf-init.sh は、新しい Salesforce プロジェクト（force-XXXX）を、一から立ち上げるセットアップのコマンドです。GitHub リポジトリの作成から、Salesforce 組織への接続、ブランチ構成、Secrets の登録、ブランチ保護の設定までを、対話しながら、まとめて自動で行います。

管理者専用です

実行すると、赤い警告ボックスが表示され、続行の確認が求められます。Windows は Git Bash で実行してください（PowerShell・コマンドプロンプトは非対応です）。

1. 先に用意するもの

実行すると、はじめの画面にも同じ一覧が出ます。

用意するもの内容
ツールGit（Git Bash）・GitHub CLI・Node.js / npm・Salesforce CLI（npm 版）・VS Code・Slack。入れ方は 前提条件とインストール にあります。VS Code には、Salesforce Extension Pack (Expanded) を入れておきます
GitHubリポジトリを作れる権限のあるアカウントで、GitHub CLI にログインしておく（gh auth login）。ブラウザで、GitHub の管理者のアカウントにログインできること
Salesforce接続する組織（本番・Sandbox・Developer Edition など）と、その組織の管理者権限のユーザー
Slack通知先にする、このプロジェクトを使う全員が参加する共有チャンネル。sf-init はチャンネルを作らないので、Slack で、先に作っておきます（既存のチャンネルでも構いません）

2. 実行する

リポジトリ名は force-XXXX です（force- は固定、XXXX は管理者が決める名前）。フォルダの構成には、決まりがありません。作業フォルダ（どこでもよい。おすすめは ~/sf のような短い名前）で実行します。

cd {作業フォルダ}
sf-init.sh                                          # 対話: オーナーを選び、XXXX を入力
sf-init.sh --owner my-org --project acme            # 引数で指定（対話なし）→ my-org/force-acme

対話では、次のように聞かれます。

  GitHub のオーナー: my-org（gh のログインから取得。複数あれば、番号で選ぶ）

  リポジトリ名は「force-XXXX」の形です。
  「force-」は自動で付きます。XXXX の部分だけを入力してください。
     例: acme と入力 → force-acme

  my-org に、すでにあるプロジェクト（XXXX）:
     acme / beta

  XXXX（force- の後ろ）を入力してください: yamada
  • 入力するのは、XXXX の部分だけです（force-yamada と書いても、yamada として扱います）。すでにある名前は、警告して、聞き直します。
  • XXXX に使える文字: 英数字と、区切り（- _ .）。区切りは、英数字の間に 1 つだけ（a--b や、末尾の - は不可）で、50 文字までです（外部クライアントアプリの名前が、Salesforce の API 名の制約を満たすため）。
  • 同じ作業フォルダでは、同じ XXXX で、別のオーナーのプロジェクトは作れません（admin/force-XXXX が別のリポジトリのクローンだと、中断します）。
  • admin や force-* の中では、実行できません。
  • 管理者用の作業フォルダは、{作業フォルダ}/admin/force-XXXX になります（admin は固定。複数のプロジェクトを、同じ admin に作ってもよく、途中経過のファイルは、プロジェクトごとに分かれます）。

3. 画面の流れ

実行すると、はじめに、作るもの・かかる時間の目安・先に用意するもの・全 9 ステップの一覧が表示されます。用意ができたら Enter を押します（q で中断）。各ステップの先頭には、「ステップ n / 9」と、完了したステップ・そのステップの目的が表示されます。

終わると、できたことと、次にやること（sf-job.sh の実行など）と、管理者用フォルダ（admin）の場所が表示されます。

sf-tools が古いとき

~/sf-tools が古いときは、確認のうえ更新し、自動で、はじめから実行し直します（もう一度の実行は、要りません）。

自動で行われる内容は、次のとおりです。

  1. 環境チェック: 必要なツールと、GitHub CLI の認証を確認します。

  2. プロジェクト情報の確認と環境種別の選択: オーナーとプロジェクト名（XXXX）を確認します。

  3. リポジトリの作成: GitHub にリポジトリを作り、クローンして、sf-tools/templates/ からファイルをコピーします。

  4. ファイルの生成: ワークフローと設定ファイルを作ります。

  5. ブランチ構成: main / staging / develop の構成を選んで、作ります。

  6. PAT_TOKEN の設定: GitHub の Classic PAT を発行して、Secrets に登録します。

  7. Slack 連携の設定: Bot Token とチャンネル ID を登録します。

  8. 初回のコミットとプッシュ。

  9. リポジトリの設定と Ruleset: ブランチ保護のルールを自動で設定します。

  10. JWT 認証情報の設定: Salesforce の認証情報を、GitHub の Secrets / Variables に登録します。外部クライアントアプリは、ブラウザでログインするだけで、自動で作られます。

  11. 最初のメタデータの同期: 下の説明のとおりです。

4. 入力する項目

4.1 環境種別（通常は「1. 本番環境」）

  • 1. 本番環境: GitHub Actions は、sf-tools の main（リリース済みの配布版）を使います。
  • 2. 検証環境: sf-tools の開発者専用です。リリース前の未検証のコード（development）が使われます。選ぶと、確認（Y/N/q）が出ます。
  • 選んだ環境に合わせて、~/sf-tools が最新かも確認します。遅れていれば更新して中断するので、もう一度 sf-init.sh を実行してください。

4.2 ブランチ構成（3 / 2 / 1 階層）

最初は main だけの構成にして、あとから段階を足すこともできます（段階の追加）。

4.3 GitHub の Classic PAT

  • 作るアカウント: force-* のリポジトリのオーナー（組織のリポジトリなら、その組織の管理者）のアカウントです（実行の最初に表示されます）。ブラウザでログインしているアカウントが違うときは、切り替えてください。sf-tools の開発者のアカウントは、関係ありません。
  • ブラウザで、Token の作成ページが自動で開きます（Note と Scopes は入力済みです）。ページの一番下の「Generate token」を押し、表示された Token をコピーして、ターミナルに貼り付けます。
  • Note は sf-metasync-{プロジェクト名}（自動で表示）、Expiration は No expiration、Scopes は repo（全選択）と workflow です。
  • 発行済みの Token があれば、ブラウザは開かず、そのまま貼り付けられます。
  • 貼り付けると、文字の数だけ * が並びます（Token の中身は、画面に出ません）。Git Bash は、右クリック（または Shift+Insert）で貼り付けます。Enter を押すと、「N 文字を受け取りました（先頭: ghp_…）」と表示されるので、コピーできたかを確認できます。
  • スコープ（repo・workflow）と、リポジトリの管理者であることを、GitHub に問い合わせて確認します。違えば、理由が表示され、3 回まで貼り直せます（Fine-grained の Token は、スコープを確認できないため、使えません）。

4.4 Slack

  1. Slack Bot Token の取得（ブラウザで操作して、Token を貼り付けます）
  2. チャンネル ID の入力（C で始まる文字列）。DM（D…）やユーザー（U…）の ID は、本人にしか通知が届かないため、受け付けられず、入力し直しになります。
  3. Bot をチャンネルに招待（Slack で手動）。通知先のチャンネルで、次を実行します。Bot が参加していないと、通知が届きません。 
    /invite @sf-notify-<プロジェクト名>

4.5 Salesforce の接続（JWT 認証）

既定は、外部クライアントアプリケーション（Salesforce の推奨）です。アプリの作成は、sf-init が自動で行います（アプリの種類は、聞きません）。

  • 段階（main / staging / develop）ごとに、ログイン先を選び、ブラウザで Salesforce にログインします（接続ユーザーは、管理者権限のユーザー）。それだけです。
  • ブラウザでのログインは、約 2 分で時間切れになります。ブラウザが開いたら、すぐにログインしてください。
  • アプリの作成・証明書の登録・ポリシーとプロファイルの設定・コンシューマー鍵の取得は、自動です（反映を待つため、接続テストは、成功するまで、やり直します）。
  • 登録される内容は、SF_PRIVATE_KEY（秘密鍵。全組織で共通）と、組織ごとの SF_CONSUMER_KEY_*・SF_USERNAME_*・SF_INSTANCE_URL_* です（認証情報）。
  • --legacy-connected-app を付けると、従来の接続アプリケーション（廃止予定）になり、Salesforce の画面での設定と、コンシューマーキー・ユーザー名の手入力が必要です。

ログイン先の選び方と、段階と組織の種類の関係は、構成の変更と診断で説明しています。

4.6 最初のメタデータの同期（自動）

手順 10 のあとに、wf-metasync を実行して完了を待ち、同期した内容を、管理者用のクローン（admin/force-XXXX）に git pull します（数分。組織の大きさで伸びます）。

  • セットアップが終わった瞬間に、Salesforce のメタデータが、GitHub の main にも、手元のクローンにも、全部入っています（初期コミットの force-app は、空のひな型です）。
  • 同期に失敗しても、セットアップは成功のままです。完了画面に、すぐ同期する方法が出ます（定期実行は、平日 3 時間おきです）。

5. 途中で止まったとき（続きから）

どの Phase まで進んだかを、覚えておく必要はありません。止まったら、同じフォルダで、もう一度 sf-init.sh を実行してください。前回の状態が残っていれば、次の選択肢が表示されます。

前回のセットアップは、「ブランチの構成」まで完了しています（2026-10-11 14:32）。（owner/force-xxx）

    [1] 「GitHub の Token」から、続きをやる   ← おすすめ
    [2] 最初からやり直す（作成済みのリポジトリ・admin フォルダは、そのまま使います）
    [q] 中断
  • [1] 保存済みの入力内容（環境種別・ブランチ構成など）を使い、失敗した所から再開します（最初の環境チェックは、毎回行います）。
  • [2] 保存した状態を消して、Phase 1 から始めます。作成済みのリポジトリと admin フォルダは、削除せず、そのまま使います。
  • Salesforce の接続は、段階ごとに、完了を記録します。途中（例: staging）で失敗しても、「続きをやる」では、完了した段階（main など）はスキップし、残りの段階だけを実行します（ブラウザのログインを、やり直さなくて済みます。登録した Secret が、いまもあるときだけ、スキップします）。
  • 前回が最後まで完了しているときは、「セットアップが、すでに完了しています」と表示され、[1] いまの Salesforce の接続を見る（何も変更しません）／[2] 動作を確認する（--verify）／[3] 最初からやり直す／[q] 終了 を選べます。別のリポジトリの状態の場合は、選択肢は出ず、最初から始まります。
  • 完了済みのプロジェクトでは、--resume N は使えません（接続の処理を、確認なしで、やり直さないため）。
  • 進み具合は、admin/.sf-init-XXXX.progress（入力内容は .sf-init-XXXX.env）に記録されます。この 2 つのファイルは、最後まで終わると削除されます（途中で止まったときだけ残ります）。完了済みかどうかは、クローンの git config sf-tools.setup-complete で判定します。
  • リポジトリそのものを作り直したいときは、GitHub 上のリポジトリと admin フォルダを、手動で削除してから実行します。

6. 終わったあと

6.1 admin フォルダと admin ブランチ

  • admin フォルダは、削除せず、残します。ワークフローの更新（sf-sync-wf）・接続の確認（--status）・接続先の付け替え（--reconnect）など、管理者のメンテナンスに使います。日常の開発には使いません（開発は、sf-job.sh の作業フォルダで行います）。
  • 管理者用のクローンは、セットアップの最後に、admin ブランチになります。main から作り、GitHub にも git push -u origin admin で作ります（強制 push はしません）。main は保護ブランチのため、その上で作業しないようにするためです（sf-sync-wf.sh も、保護ブランチでは実行を断ります）。
  • 管理者の変更は、「main を取り込む → 変更する → push → PR」で、GitHub に反映します。admin は、main から古くなります。使う前に、git pull origin main で取り込んでください。
  • admin ブランチがすでにあるときは、作り直さず、そこへ切り替えます（作業を消しません）。作れなかったとき・push できなかったときは、完了画面の案内どおり、管理者用フォルダで git switch -c admin（作れなかったとき）・git push -u origin admin（push できなかったとき）を実行してください（セットアップ自体は、成功のままです）。

6.2 動作を確認する

セットアップが正しく終わったかは、次の 2 つで確かめられます。

  1. メタデータの同期: GitHub → Actions → 「[metasync] メタ同期」→「Run workflow」で、手動で実行します。正常に終われば、組織のメタデータが main に同期されます。

  2. PR のワークフロー: 作業フォルダで sf-job.sh を実行すると、sf-start.sh が自動で動き、sf-install.sh が sf-tools/release/<ブランチ名>/ の下に、空のターゲットファイルを作ります。これがそのまま差分になるので、追加の変更は要りません。続けて、次を実行します。

    sf-push.sh      # 自動生成されたファイルを、コミットしてプッシュ
sf-next.sh      # 次の PR 先を確認 → ブラウザで PR を作成 → マージ

    ブランチ構成が 3 階層なら、develop → staging → main の順に、くり返します。PR を作ると、次が自動で動きます。

    • [validate] デプロイ前検証 — すべての PR で
    • [sequence] マージ順序チェック — main / staging への PR で
    • [release] デプロイ → Slack 通知 — PR をマージしたあとで

もっと確実に確認したいときは、動作の確認（--verify）が、実際のリポジトリと組織で、リリースと削除まで、通しで確かめます。セットアップの最後（ステップ 9）に、「動作を確認しますか？」と聞かれます（任意）。

7. オプションの一覧

オプション内容
--owner / --projectオーナーとプロジェクト名（XXXX）を指定する（対話なし）
--resume NPhase N から、質問なしで再開する（通常は、指定不要です）。完了済みのプロジェクトでは、拒否されます。動作の確認（最後のステップ）は、聞きません
--only NPhase N だけを実行する（デバッグ用）。進み具合は更新しません。動作の確認は、聞きません
--add-tier staging|develop既存のプロジェクトに、段階を足す（構成の変更と診断）
--reconnect <段階>1 つの段階の、接続先の Salesforce 組織を付け替える（構成の変更と診断）
--statusセットアップの診断（構成の変更と診断）
--verify動作の確認（動作の確認）
--legacy-connected-app従来の接続アプリケーション（廃止予定。手動の入力）を使う。既定は、外部クライアントアプリ（自動で作成）
  • 通常の初期セットアップは、force-* フォルダの外で実行します。--add-tier・--reconnect・--status・--verify は、force-* フォルダの中で実行します。
  • Salesforce へのログイン、PAT の作成、Slack の設定など、一部は、対話での操作が必要です。
