🏗️ 新規プロジェクトの作成（sf-init）

新しい Salesforce プロジェクトを、一から立ち上げます。sf-init.sh が、画面の案内に沿って、必要な準備をまとめて行います。GitHub のリポジトリの作成、Salesforce 組織への接続、ブランチの構成、認証情報の登録、ブランチ保護の設定です。あなたが行うのは、画面に出る質問に答えることと、ブラウザでの数回の操作だけです。

管理者専用です

実行すると、赤い警告ボックスが表示され、続けてよいかを確認されます。Windows では、Git Bash で実行してください（PowerShell やコマンドプロンプトでは動きません）。

かかる時間と、途中で止まったとき
  • ⏱️ 目安は、30〜60 分です（ブラウザでの作業と、Salesforce の反映待ちを含みます）。
  • 途中で止まっても大丈夫です。もう一度、同じように実行すれば、続きから再開できます（途中で止まったとき）。

始める前に、用意するもの

実行すると、最初の画面にも、同じ一覧が出ます。

用意するもの内容
ツールGit（Git Bash）・GitHub CLI・Node.js / npm・Salesforce CLI（npm 版）・VS Code・Slack。入れ方は、前提条件とインストールにあります。VS Code には、Salesforce Extension Pack (Expanded) も入れておきます
GitHubリポジトリを作れる権限のあるアカウントで、GitHub CLI にログインしておきます（gh auth login）。ブラウザでも、GitHub の管理者のアカウントにログインできる状態にしておきます
Salesforceつなげる組織（本番・Sandbox・Developer Edition など）と、その組織の管理者権限を持つユーザー
Slack通知先にする、このプロジェクトを使う全員が参加している共有チャンネル。sf-init は、チャンネルを作りません。Slack で、先に作っておいてください（既存のチャンネルでも構いません）

実行する

リポジトリの名前は、force-XXXX の形です（force- は固定で、XXXX は管理者が決めます）。作業フォルダ（置く場所は自由です。おすすめは、~/sf のような短い名前）で、実行します。

cd {作業フォルダ}
sf-init.sh                                          # 対話: オーナーを選び、XXXX を入力
sf-init.sh --owner my-org --project acme            # 引数で指定（対話なし）→ my-org/force-acme

対話では、次のように聞かれます。

  GitHub のオーナー: my-org（gh のログインから取得。複数あれば、番号で選ぶ）

  リポジトリ名は「force-XXXX」の形です。
  「force-」は自動で付きます。XXXX の部分だけを入力してください。
     例: acme と入力 → force-acme

  my-org に、すでにあるプロジェクト（XXXX）:
     acme / beta

  XXXX（force- の後ろ）を入力してください: yamada
  • 入力するのは、XXXX の部分だけです（force-yamada と書いても、yamada として扱います）。すでにある名前を入れると、警告が出て、聞き直されます。
  • XXXX に使える文字: 英数字と、区切り（- _ .）です。区切りは、英数字の間に 1 つだけ置けます（a--b や、末尾の - は使えません）。50 文字までです。
  • 同じ作業フォルダでは、同じ XXXX で、別のオーナーのプロジェクトは作れません。
  • 管理者用のフォルダ（admin）や、force-* の中では、実行できません。作業フォルダで実行してください。
  • できあがる管理者用のフォルダは、{作業フォルダ}/admin/force-XXXX です。admin は、いつもこの名前になります。複数のプロジェクトを、同じ admin に作っても構いません。

画面の流れ（全 9 ステップ）

実行すると、はじめに、作るもの・かかる時間の目安・先に用意するもの・全 9 ステップの一覧が表示されます。用意ができたら、Enter を押します（q で中断できます）。各ステップの先頭には、「ステップ n / 9」と、これまでに終わったステップ、そのステップの目的が表示されます。終わると、できたことと、次にやること（sf-job.sh の実行など）、そして管理者用フォルダの場所が表示されます。

ステップ何をするかあなたの操作
1. 準備の確認必要なツールと、GitHub へのログインを確かめますなし
2. プロジェクトの確認作るリポジトリの名前と場所を確かめます。使う sf-tools の版（環境の種類）を選びます確認と選択
3. リポジトリの作成GitHub にリポジトリを作って、パソコンにコピーし、設定ファイルとワークフローを用意しますなし
4. ブランチの構成変更を、段階的に確かめて、本番に出す流れ（ブランチの構成）を選んで、作ります選択
5. GitHub の Token自動で動くワークフローが、リポジトリを更新するための Token（PAT）を登録しますブラウザで発行して、貼り付ける
6. Slack の通知ワークフローの結果を、Slack に通知するための設定をしますブラウザと Slack での操作
7. リポジトリの設定ここまでの内容を、リポジトリに反映して（最初のコミットとプッシュ）、ブランチ保護のルールを設定しますなし
8. Salesforce の接続Salesforce の各組織と、GitHub をつなげます。続けて、最初のメタデータの同期も行いますブラウザで、組織にログインする
9. 動作の確認（任意）作ったものが、実際に動くことを確かめます（動作の確認）Enter で確認する／s であとにする
sf-tools が古いときは、自動でやり直します

~/sf-tools が古いときは、確認のうえで更新します。そのあと、更新した sf-tools で、自動的に、はじめから実行し直します。もう一度実行する必要は、ありません。

入力する項目

環境の種類（通常は「1. 本番環境」）

ステップ 2 で、2 つの選択肢が出ます。これは、Salesforce の組織の話ではなく、「どの版の sf-tools を、このプロジェクトの自動処理に使うか」の選択です。

  • 1. 本番環境（通常は、こちら）: GitHub Actions が、sf-tools の main（リリース済みの、配布版）を使います。
  • 2. 検証環境: sf-tools の開発者だけが使います。リリース前の、未検証のコード（development）が使われます。選ぶと、確認（Y/N/q）が出ます。

ブランチの構成（3 / 2 / 1 階層）

ステップ 4 で、段階の数を選びます。標準は、3 階層（develop → staging → main）です。小さなプロジェクトは、main だけの 1 階層でも使えます。あとから、段階を足すこともできます（段階を足す）。段階の考え方は、CI/CD の仕組みにあります。

GitHub の Token（PAT）

PAT（Personal Access Token）は、GitHub の「合鍵」のようなものです。自動で動くワークフローが、あなたの代わりに、リポジトリを更新するために使います。

  • どのアカウントで作るか: force-* のリポジトリのオーナーのアカウントです（組織のリポジトリなら、その組織の管理者）。作るアカウントは、実行の最初に表示されます。ブラウザで、別のアカウントにログインしているときは、切り替えてください。sf-tools の開発者のアカウントは、関係ありません。
  • 作り方: ブラウザで、Token の作成ページが、自動で開きます（Note と Scopes は、入力済みです）。ページの一番下の「Generate token」を押して、表示された Token をコピーし、ターミナルに貼り付けます。「発行済みの Token があるか」は聞きません（Token の値は、作成した直後の 1 回しか表示されないためです）。保存してある Token があれば、それを貼り付けてもかまいません。
  • 設定の内容: Note は sf-metasync-{プロジェクト名}（自動で表示）、Expiration は No expiration（期限なし）、Scopes は repo（全選択）と workflow です。
  • 貼り付けるとき: 文字の数だけ * が並びます（Token の中身は、画面に出ません）。Git Bash では、右クリック（または Shift+Insert）で貼り付けます。Enter を押すと、「N 文字を受け取りました（先頭: ghp_…）」と表示されるので、コピーできたかを確かめられます。
  • 確認: スコープ（repo・workflow）と、リポジトリの管理者であることを、GitHub に問い合わせて確かめます。違っていれば、理由が表示されます。3 回まで、貼り直せます。（Fine-grained の Token は、スコープを確かめられないので、使えません。）

Slack の通知

3 つの作業があります。画面にも、同じ手順が表示されます。

  1. Bot Token を取る（ブラウザで Slack の API ページが開きます）

    1. 「Create New App」→「From scratch」をクリックします。
    2. App Name に sf-notify-{プロジェクト名} を入れ、通知先のワークスペースを選んで、「Create App」をクリックします。
    3. 左のメニューの「OAuth & Permissions」をクリックします。
    4. 「ボットトークンのスコープ」→「OAuth スコープを追加する」で、chat:write を追加します。
    5. 左のメニューの「Install App」→「Install to ワークスペース名」をクリックして、「許可する」をクリックします。
    6. 表示されたページの「Bot User OAuth Token」（xoxb- で始まる文字列）をコピーして、ターミナルに貼り付けます。貼り付けた文字は、* で表示されます（Token は画面に出ません）。xoxb- で始まらないときは、入力し直しになります。

  2. チャンネル ID を入れる（C で始まる文字列）

    Slack で、通知先のチャンネルを開き、チャンネル名をクリックすると、いちばん下に「チャンネル ID」が出ます。DM（D…）やユーザー（U…）の ID は、本人にしか通知が届かないので、受け付けられません（入力し直しになります）。

  3. Bot をチャンネルに招待する（Slack で、手動で行います）

    通知先のチャンネルで、次のコマンドを実行します。Bot がチャンネルにいないと、通知が届きません。

    /invite @sf-notify-<プロジェクト名>

Salesforce の接続（JWT 認証）

JWT 認証は、パスワードの入力なしで、秘密鍵を使って Salesforce にログインする方法です。GitHub 上のワークフローが、自動でログインするために使います。

既定は、外部クライアントアプリケーション（Salesforce の推奨）です。アプリの作成は、sf-init が自動で行います（アプリの種類は、聞かれません）。

  • 段階（main / staging / develop）ごとに、ログイン先を選んで、ブラウザで Salesforce にログインします（接続するユーザーは、管理者権限を持つユーザーです）。あなたの操作は、これだけです。
  • ブラウザでのログインは、約 2 分で時間切れになります。ブラウザが開いたら、すぐにログインしてください。
  • アプリの作成・証明書の登録・ポリシーとプロファイルの設定・コンシューマー鍵の取得は、自動です。設定が反映されるまで時間がかかるので、接続のテストは、成功するまで、くり返します。
  • 登録されるのは、SF_PRIVATE_KEY（秘密鍵。すべての組織で共通）と、組織ごとの SF_CONSUMER_KEY_*・SF_USERNAME_*・SF_INSTANCE_URL_* です。組織の情報を読み取れたときは、組織の ID・名前・種類・確認日時（SF_ORG_*）も保存します（認証情報）。
  • --legacy-connected-app を付けると、従来の接続アプリケーション（廃止の予定）になります。Salesforce の画面での設定と、コンシューマーキー・ユーザー名の手入力が、必要です。

ログイン先の選び方と、段階と組織の種類の関係は、構成の変更と診断で説明しています。

最初のメタデータの同期（自動）

Salesforce の接続のあとで、wf-metasync（組織の最新の状態を、Git に取り込む処理）を実行し、終わるのを待ちます。続けて、同期した内容を、管理者用のクローン（admin/force-XXXX）に取り込みます。数分かかります（組織の大きさで、長くなります）。

  • セットアップが終わると、Salesforce のメタデータが、すべて入った状態になります。GitHub の main にも、手元のクローンにも入ります（最初のコミットの force-app は、空のひな型です）。
  • 同期に失敗しても、セットアップ自体は、成功のままです。完了の画面に、すぐ同期するための方法が出ます（定期の同期は、平日の 3 時間おきに動きます）。

途中で止まったとき（続きから）

どこまで進んだかを、覚えておく必要はありません

止まったら、同じフォルダで、もう一度 sf-init.sh を実行してください。前回の状態が残っていれば、続きから再開する選択肢が出ます。

前回のセットアップは、「ブランチの構成」まで完了しています（2026-10-11 14:32）。（owner/force-xxx）

    [1] 「GitHub の Token」から、続きをやる   ← おすすめ
    [2] 最初からやり直す（作成済みのリポジトリ・admin フォルダは、そのまま使います）
    [q] 中断
  • [1] 続きをやる: 保存してある入力内容（環境の種類・ブランチの構成など）を使って、失敗した所から再開します（最初の環境チェックは、毎回行います）。
  • [2] 最初からやり直す: 保存した状態を消して、最初から始めます。作成済みのリポジトリと admin フォルダは、削除せず、そのまま使います。
  • Salesforce の接続は、段階ごとに、終わったことを記録します。途中（たとえば staging）で失敗しても、「続きをやる」では、終わった段階（main など）は飛ばして、残りの段階だけを実行します。ブラウザでのログインを、やり直さなくて済みます（登録した Secret が、いまもあるときだけ、飛ばします）。
  • 前回が最後まで終わっているときは、「セットアップは、すでに完了しています」と表示されます。次の 4 つから選べます。
    • [1] いまの Salesforce の接続を見る（何も変更しません）
    • [2] 動作を確認する（--verify）
    • [3] 最初からやり直す
    • [q] 終了
    別のリポジトリの状態が残っているときは、選択肢は出ず、最初から始まります。
  • 完了済みのプロジェクトでは、--resume N と --only N は使えません（接続の処理などを、確認なしで、やり直さないためです）。
  • 進み具合は、admin/.sf-init-XXXX.progress（入力内容は .sf-init-XXXX.env）に記録されます。この 2 つのファイルは、最後まで終わると削除されます（途中で止まったときだけ、残ります）。終わっているかどうかは、クローンの git config sf-tools.setup-complete で判断します。
  • リポジトリそのものを作り直したいときは、GitHub 上のリポジトリと admin フォルダを、手動で削除してから、実行します。

終わったあと

admin フォルダと admin ブランチ

  • admin フォルダは、削除せず、残してください。ワークフローの更新（sf-sync-wf）・接続の確認（--status）・接続先の付け替え（--reconnect）など、管理者のメンテナンスに使います。日々の開発には使いません（開発は、sf-job.sh の作業フォルダで行います）。
  • 管理者用のクローンは、セットアップの最後に、admin ブランチになります。main から作って、GitHub にも git push -u origin admin で作ります（強制プッシュは、しません）。main は保護されたブランチなので、その上で作業しなくて済むようにするためです（sf-sync-wf.sh も、保護ブランチの上では、実行を断ります）。
  • 管理者の変更は、「main を取り込む → 変更する → プッシュ → PR」の順で、GitHub に反映します。admin は、時間がたつと、main から遅れます。使う前に、git pull origin main で取り込んでください。
  • admin ブランチがすでにあるときは、作り直さずに、切り替えるだけです（作業が消えることは、ありません）。ブランチを作れなかったとき、またはプッシュできなかったときは、完了の画面に案内が出ます。その案内どおりに、管理者用フォルダで、次のコマンドを実行してください。セットアップ自体は、成功のままです。
    • 作れなかったとき: git switch -c admin
    • プッシュできなかったとき: git push -u origin admin

動作を確認する

セットアップが正しく終わったかは、次の 2 つで確かめられます。

  1. メタデータの同期: GitHub → Actions → 「[metasync] メタ同期」→「Run workflow」で、手動で実行します。正常に終われば、組織のメタデータが main に同期されます。

  2. PR のワークフロー: 作業フォルダで sf-job.sh を実行すると、sf-start.sh が自動で動きます。sf-install.sh が、sf-tools/release/<ブランチ名>/ の下に、空のターゲットファイルを作ります。これがそのまま差分になるので、ほかの変更は要りません。続けて、次を実行します。

    sf-push.sh      # 自動で作られたファイルを、コミットして送る
sf-next.sh      # 次の PR 先を確認 → ブラウザで PR を作成 → マージ

    ブランチが 3 階層なら、develop → staging → main の順に、くり返します。PR を作ると、次の処理が、自動で動きます。

    • [validate] デプロイ前の検証 — すべての PR で動く
    • [sequence] マージ順序の確認 — main と staging への PR で動く
    • [release] デプロイ → Slack に通知 — PR をマージしたあとで動く

もっとしっかり確かめたいときは、動作の確認（--verify）を使います。実際のリポジトリと組織で、リリースと削除まで、通しで確かめます。セットアップの最後（ステップ 9）に、「動作を確認しますか？」と聞かれます（任意です）。

オプションの一覧

オプション内容
--owner / --projectオーナーとプロジェクト名（XXXX）を指定します（対話なし）
--resume NN 番目の段階から、質問なしで再開します（通常は、指定する必要はありません）。N は 1〜10 の整数です（それ以外は、実行する前にエラーになります）。完了済みのプロジェクトでは、使えません。動作の確認（最後のステップ）は、聞きません
--only NN 番目の段階だけを実行します（デバッグ用）。N は 1〜10 の整数です。進み具合は更新しません。動作の確認は、聞きません。完了済みのプロジェクトでは、使えません。
--add-tier staging|develop既存のプロジェクトに、段階を足します（構成の変更と診断）
--reconnect <段階>1 つの段階の、接続先の Salesforce 組織を、付け替えます（構成の変更と診断）
--statusセットアップの診断をします。🔍 読み取りのみ（構成の変更と診断）
--verify動作の確認をします（動作の確認）
--legacy-connected-app従来の接続アプリケーション（廃止の予定。手動の入力）を使います。既定は、外部クライアントアプリ（自動で作成）
  • 通常の初期セットアップは、force-* フォルダの外で実行します。--add-tier・--reconnect・--status・--verify は、force-* フォルダの中で実行します。
  • Salesforce へのログイン、PAT の作成、Slack の設定などは、あなたの操作が必要です。
