💻 開発者向けコマンド

開発者が毎日使うコマンドの、詳しい説明です。全体の一覧は、コマンド一覧にあります。使い方の流れを知りたいときは、先に日々の開発の流れを読むと、分かりやすくなります。

このページの要点
  • 毎日の操作は、ランチャー（sf-launcher.sh）のメニューで足ります。このページは、コマンドを直接打つときや、動きを詳しく知りたいときの説明です。
  • 新しい作業は、sf-job.sh から始めます。始めたあとは、ランチャーが自動で開きます。
  • リリース・検証（sf-release.sh / sf-dryrun.sh / sf-deploy.sh）は、個人用の組織だけが対象です。共有環境の予約名の組織と、本番の組織には、ローカルから実行できません。

sf-job.sh

cd 作業フォルダ
sf-job.sh [--project XXXX] [--owner OWNER]

新しい作業（ブランチ）を始めるときの、オールインワンのスクリプトです。作業フォルダ（ジョブフォルダを置く場所。おすすめは ~/sf のような短い名前のフォルダ）で実行します。

オプション

オプション内容
--project XXXXプロジェクト名（リポジトリ force-XXXX の XXXX）。先頭の force-（大文字・小文字を問わない）は、除いて扱います。使える文字は、英数字・-・_・. です（記号は、英数字の間に 1 つずつ。50 文字まで。末尾の .git は不可）。不正なら中断します
--owner OWNERGitHub のオーナー（組織名またはユーザー名）。英数字とハイフンだけです（先頭・末尾は英数字。39 文字まで）。不正なら中断します
-h, --help説明を表示して終了する（1 つ目の引数のときだけ）

これ以外の引数は、「不明なオプション」で中断します（-v / --verbose も、受け付けません）。

主な処理

  1. 使うプロジェクト（オーナーと XXXX）を決める（下の「プロジェクトの決まり方」）
  2. 環境を確認する。実行するフォルダの名前が admin、または force- で始まるときは、中断する（フォルダの名前だけで判定します）。gh auth status が失敗したら、gh auth login を実行し、それも失敗したら中断する
  3. リポジトリ OWNER/force-XXXX があるかを確かめる。見つからなければ中断する
  4. ジョブ名（例: JOB-20260323）を入力する（q で中断）。最後に、ジョブ名・ブランチ・クローン先を表示して確認する（N / q で中断）
  5. GitHub 上に、main の最新のコミットから、作業用のブランチ（ジョブ名）を作る。main がなければ中断する（既存のブランチを使うと選んだときは、作らない）
  6. git clone で、そのブランチを ./ジョブ名/force-XXXX に取り出す（-c core.longpaths=true 付き。Windows のパスの長さの上限への対策で、クローン先の設定に残ります）
  7. そのフォルダで、sf-start.sh を引数なしで実行する（組織への接続・VS Code の起動。続けて、ランチャーも起動します）

補足

  • ブランチの作成から VS Code の起動まで、すべて自動です。新しい作業は、必ずここから始めます。
  • GitHub CLI（gh）が必要です。オーナーの権限は、確かめません（開発者が毎日使うコマンドのため）。gh でログインしたユーザーに、リポジトリを読み書きする権限があれば使えます（オーナーや管理者である必要は、ありません）。権限が足りなければ、GitHub が拒否し、リポジトリの確認（手順 3）か、ブランチの作成（手順 5）で中断します。
  • ジョブ名は、英数字で始まり、英数字・-・_ だけの 1〜50 文字です。環境ブランチと管理者用のフォルダの名前（main / staging / develop / admin）は、使えません。./ジョブ名/force-XXXX がすでにあるときも、入力し直しになります。
  • GitHub 上に同じ名前のブランチがすでにあるときは、最後のコミットの作者と日時を表示して、確認します。
    • Y: そのブランチを使って続ける（ブランチを作ったあとに clone が失敗した、前回のジョブの続き）
    • N: 別のジョブ名を入力し直す。ほかの人のジョブのブランチなら、N にしてください
    • q: 中断する
  • 途中で中断・失敗しても、それまでに作ったブランチ・フォルダ・クローンは、削除しません。ブランチを作ったあとに clone が失敗したときは、同じジョブ名でもう一度実行し、既存のブランチを使う（Y）と、続きから進められます。
  • sf-start.sh が失敗で終わると、sf-job.sh も中断します（クローンは残ります）。sf-job.sh は、ランチャーを終了するまで終わりません。
  • Ctrl+C は効きません。中断は、入力のときに q で行います。中断・失敗の終了コードは 1 です。Ctrl+C を無視する設定は、ここから起動する sf-start.sh・ランチャーと、ランチャーから実行するコマンドにも、引き継がれます。ただし、sf・npm など Node のコマンドは、実行中に Ctrl+C を押すと、そのコマンドだけが止まることがあります。
  • ログは ~/sf-tools/logs/sf-job.log です（実行のたびに作り直します）。

プロジェクトの決まり方

どのプロジェクト（オーナーと XXXX）を使うかは、フォルダの名前では決まりません。次の順で決めます（上にあるものが優先です）。

  1. 引数の --owner / --project
  2. 作業フォルダの直下にあるクローン（*/force-*/）の git remote（origin）。クローンしたときに、Git が記録した住所（URL）から、オーナーとリポジトリの名前を読み取ります。--owner を指定したときは、そのオーナーのクローンだけを対象にします。
    • --project なし: 1 種類だけなら自動、複数なら番号で選ぶ、なければ対話
    • --project だけ: 同じ force-XXXX のクローンのオーナーが 1 つなら自動、複数なら番号で選ぶ（最初のものを、黙って使いません）、なければ対話
  3. 対話で入力（決まっていない項目だけを聞きます）。オーナーは、gh でログインした自分のアカウントと、所属する組織を候補にします（候補がなければ入力、1 つなら自動、複数なら番号で選ぶ）。XXXX は、入力して、Y / N で確認します。

sf-start.sh

sf-start.sh [-v]

開発環境を起動します。force-* フォルダ（フォルダの名前が force- で始まる）の中で実行します。-v（--verbose）は、コマンドの応答をコンソールにも表示します（sf-install.sh にも渡します）。-h（--help。1 つ目の引数のときだけ）以外の、ほかの引数は、「不明なオプションです」で中断します。

処理の流れ

  1. Salesforce CLI（sf）を確認する。sf --version の終了コードが 0 以外なら、案内を表示して中断する（npm 版が前提のため）。成功したら、~/.sf-tools-sf-check に sf の場所を記録し、同じ場所の sf なら、24 時間は確認を省く（sf が未インストールのとき・GitHub Actions 上では、確認しない）
  2. 接続を確認する。.sf/config.json があれば、sf org display --json を実行し、エイリアスが取れて、組織 ID が 00D で始まれば、接続済みとして、ログインを省く。sf org display が失敗した・JSON を読み取れないときは、未接続として扱う
  3. 未接続のときは、ログインする
    • 接続する組織のエイリアスを入力する（空の Enter は、入力し直し。q で中断）
    • sf alias unset vscodeOrg を実行する（失敗しても続ける）
    • ログイン先を選ぶ: [1] https://login.salesforce.com / [2] https://test.salesforce.com（Enter は 2）/ [3] 組織の URL を入力（https で、salesforce.com または force.com の配下）。q で中断。環境変数 SF_INIT_LOGIN_URL_START（login / test / URL）があれば、質問せずに、それを使う
    • 同じエイリアスで sf org logout を実行してから（同じ名前のエイリアスの、既存の認証は消えます）、sf org login web --set-default で、ブラウザからログインする（WSL で wslview がないときは、powershell.exe でブラウザを開く仕組みを、一時的に用意します）
  4. .sf/config.json と .sfdx/sfdx-config.json を、そのエイリアスで上書きする（書き込めなければ中断）。code . で VS Code を起動する（code コマンドがなければ、警告だけで先へ進む）
  5. sf-install.sh を、バックグラウンドで実行する（出力は、sf-start.sh のログに追記）。内容は、~/sf-tools の git pull・設定ファイル（metadata.txt・branches.txt）の確認・Git フック（pre-commit / pre-push）の設置・リリース用フォルダの準備と branch_name.txt の更新（main ブランチでは行わない）・npm install（package.json があるとき。更新済みなら省略）・開発ツールの更新（sf-upgrade.sh。24 時間に 1 回）
  6. 最後に、ランチャー（sf-launcher.sh）を前面で起動する（ランチャーから呼ばれたときは、二重に起動しない）

補足

  • sf-job.sh が内部で自動で呼ぶので、新しい作業のときは、直接実行する必要はありません。前日の続きなど、既存のブランチに戻るときに使います。sf-job.sh から呼ばれたとき（環境変数 SF_INIT_MODE=1）は、force-* フォルダかどうかの確認を省きます。
  • 環境変数 FORCE_RELOGIN=1 のときは、接続済みかどうかを確かめず、ログインからやり直します（sf-restart.sh が使います）。
  • ログインに失敗したら、エラー（終了コード 1）で終了します（設定ファイルの書き込み・VS Code の起動・ランチャーの起動は、行いません）。
  • それ以外の終了コードは、ランチャーの結果によらず 0 です。バックグラウンドの sf-install.sh が失敗しても、影響しません。
  • Ctrl+C は、手順 1 の確認のあとから効きません。中断は、入力のときに q で行います。この設定は、ランチャーと、そこから実行するコマンドにも、引き継がれます（sf・npm など Node のコマンドは、実行中に Ctrl+C を押すと、そのコマンドだけが止まることがあります）。
  • 接続済みの組織を切り替えるときは、sf-restart.sh を使います。
  • ログは ./sf-tools/logs/sf-start.log です（実行のたびに作り直します）。

sf-launcher.sh（ランチャー）

開発者の毎日の操作は、このランチャーで足ります（おすすめ）。使い方は、日々の開発の流れにあります。

sf-launcher.sh           # メニュー形式で選択（ふだんは、これだけ）
sf-launcher.sh 4         # 番号を直接指定して、すぐ実行
sf-launcher.sh --fzf     # fzf でインクリメンタル検索

sf-tools の日常のコマンドを、メニューから選んで実行できます。sf-start.sh の最後に自動で起動します（手動でも実行できます）。force-* フォルダの中で使います。

  ──────────────────────────────────────────────────
  >> Launcher <<
  ──────────────────────────────────────────────────
  [1] Check      ターゲットファイルの構文チェック
  [2] Push       変更をコミット & プッシュ
  [3] Next       次の PR 先ブランチを確認
  [4] Dryrun     現在接続中の組織へリリース検証
  [5] Deploy     現在接続中の組織へリリース
  [6] Start      開発環境を起動（Salesforce ログイン・VSCode 起動）
  [7] Restart    接続組織を切り替えて Start 実行
  ──────────────────────────────────────────────────
  番号を入力 (1-7 / q で終了):

番号ごとに実行するのは、sf-check.sh・sf-push.sh・sf-next.sh・sf-dryrun.sh・sf-deploy.sh・sf-start.sh・sf-restart.sh です。VS Code のターミナル（環境変数 TERM_PROGRAM=vscode）では、[6] Start と [7] Restart は表示されません（二重に起動しないため。番号の 6・7 は、範囲外になります）。

  • メニューでは、番号を 1 文字入力すると（Enter 不要）実行し、終わるとメニューに戻ります。q で終了します。範囲外の数字や、数字と q 以外の入力は、無視されます。
  • 番号を直接指定したとき（sf-launcher.sh 4 など）は、そのコマンドを 1 回だけ実行して終わります。番号は、数字だけを受け付け、10 進数として扱います（08 は 8）。見るのは 1 つ目の引数だけで、数字以外の引数（-h / --help / --fzf 以外）は、エラー（終了コード 1）です。
  • 選んだコマンドは、ランチャーと同じフォルダのスクリプトを、引数なしで実行します。スクリプトがなければ、警告を表示します。
  • --fzf では、Enter で実行、Esc で終了です。実行のあとは、選択に戻ります。fzf がなければ、警告を表示して終了します（終了コード 1）。
  • フォルダの名前が force- で始まらなければ、警告を表示して終了します（終了コード 1。-h は、フォルダの外でも動きます）。
  • メニューと --fzf の中では、実行したコマンドが失敗しても、ランチャーは終了しません。
  • 終了コードは、メニューを q・EOF で終了したとき・--fzf を Esc で終了したときが 0、番号を指定したときは、実行したコマンドの終了コードです（番号が範囲外・スクリプトがないときは 1）。
  • ランチャーは、ログファイルを作りません（共通のライブラリを読み込まない、単独の設計です）。

sf-check.sh

sf-check.sh [deploy-target.txt のパス] [remove-target.txt のパス]

ターゲットファイル（deploy-target.txt / remove-target.txt）の内容を検証します。sf-release.sh・sf-push.sh・sf-precommit.sh・sf-prepush.sh・ランチャーの [1] Check から呼ばれます（単体でも実行できます）。force-* フォルダ（プロジェクトのルート）で実行します。書き方は、ターゲットファイルにあります。

確認する内容

ファイルを 1 行ずつ読みます（行末の CR と前後の空白を除き、空行と # で始まる行は、読み飛ばします）。最初のセクションの印より前の行は、[files] として扱います。

  • [files] セクション: 次のときはエラーです。
    • リポジトリの外を指すパス（/・C:/・C:\ で始まる絶対パスや、要素に .. を含むパス）。存在していてもエラーです
    • カレントフォルダからの相対パスで、ファイルまたはフォルダとして存在しない
    • フォルダのうち、LWC・Aura のコンポーネントと、オブジェクトのフォルダ（lwc/<名前>・aura/<名前>・objects/<名前>）以外。classes や . などは、対象が広がりすぎるため、書けません
  • [members] セクション: 種別名:メンバー名 の形でない（: がない・先頭か末尾が :）ときは、エラーです。
  • 種類の可否: 上の確認でエラーにならなかった行について、config/metadata-capability.txt（sf-typecheck.sh が、実際の組織で確かめた表）を見ます。deploy-target.txt はリリースの列、remove-target.txt は削除の列です。
    • ng（API ではできないと確認済み）はエラー、limited（権限・使用中・標準のものなど、条件によってできないことがある）は警告です。ok・unknown・表にない種類は、何もしません
    • 種類は、[members] では最初の : より前です。[files] では、パスから推定できる次の種類だけを確かめます: */flows/*.flow-meta.xml（Flow）・*/classes/*.cls（ApexClass）・*/triggers/*.trigger（ApexTrigger）・*/lwc/*（LightningComponentBundle）・*/aura/*（AuraDefinitionBundle）・*/servicePresenceStatuses/*（ServicePresenceStatus）・*/standardValueSets/*（StandardValueSet）
    • 組織の権限でできる場合は、環境変数 SF_CHECK_IGNORE_CAPABILITY=1 で、この確認を省略できます。表の場所は、環境変数 SF_CHECK_CAPABILITY_FILE で変えられます（表のファイルがないときは、確認しません）
  • テストクラスの不足: 上のエラーの有無にかかわらず確かめ、警告だけを出します（エラーにはなりません）。対象は、deploy-target.txt の [files] にある .cls のうち、存在し、@isTest（大文字・小文字を区別しない）を含まないものです。
    • 手順 A: 同じフォルダの <クラス名>Test.cls / <クラス名>_Test.cls を探す
    • 手順 B: A で見つからなければ、カレントフォルダ以下の、@isTest（大文字・小文字を区別する）を含む .cls のうち、クラス名を単語として含む、最初のファイルを探す
    • 見つかったテストクラスが deploy-target.txt の [files] にないときに、警告します（比べるときは、どちらも先頭の ./ を除きます）。本番や Sandbox にすでにあるテストクラスは、含めなくてよいため、警告にとどめています。テストクラスが見つからないときは、何も表示しません。

引数

  • 引数を省略すると、sf-tools/release/branch_name.txt（sf-install.sh が保存する、Git の管理外の手元のファイル）に書かれたブランチ名で、sf-tools/release/<ブランチ名>/ の 2 つのファイルを検証します。今の Git のブランチではなく、このファイルの内容を使います。
    • ファイルがないとき（一度も作られていない、新しいクローンの main など）は、何も検証せず、警告を表示して、正常（終了コード 0）で終わります（コミットは止めません）。
    • sf-install.sh は、main では、このファイルを書き込みも削除もしません。作業用のブランチのあとで main に切り替えると、前のブランチの値が残り、そのブランチのターゲットファイルを検証します。
  • 引数が 2 つ以上のときは、1 つ目を deploy-target.txt、2 つ目を remove-target.txt として検証します（3 つ目以降は無視）。1 つのときは、deploy-target.txt だけです。
  • -v / --verbose は、どの位置でも受け付けますが、表示は変わりません（引数の数にも数えません）。-h / --help は、1 つ目の引数のときだけ、説明を表示します。ほかの - で始まる引数（2 つ目以降の -h を含む）は、「不明なオプションです」で中断します。

補足

  • ターゲットファイルがないときは、そのファイルの検証を飛ばします（エラーにはしません）。何も書かれていないときは、警告だけです。
  • エラー・警告は、<ファイル名>:<行番号>: error|warning: <理由> と、その行の内容を表示します（ファイル名は、deploy-target.txt / remove-target.txt）。テストクラスの不足の警告は、行番号なしで、deploy-target.txt のパスと、見つかったテストクラスのパスを表示します。
  • 終了コードは、0 が正常（警告だけ・検証を飛ばしたときを含む）、1 がエラー（書式・パス・種類の可否が ng）・不明なオプション・force-* フォルダの外で実行したときです。
  • ログは ./sf-tools/logs/sf-check.log です（実行のたびに追記します）。

sf-dryrun.sh

sf-dryrun.sh [オプション]

sf-release.sh のラッパーで、dry-run（検証だけ）専用のコマンドです。ランチャーの [4] Dryrun から呼ばれます。

  • このスクリプト自身は、オプションを付け足しません。sf-release.sh の既定が dry-run なので、オプションなしで呼ぶだけで、検証が実行されます。直接 sf-release.sh を実行しても、同じ動作になります。
  • 受け取った引数は、すべてそのまま sf-release.sh に渡します（-n・-t・-v・-f・-j など）。このスクリプトは引数を検査しません。不明なオプションは、sf-release.sh が中断します。2 つ目以降の -h / --help も、sf-release.sh に渡ります。
  • 共有環境・本番の組織を拒否する確認も、sf-release.sh が行います（下記）。
  • 終了コードは、sf-release.sh がないときは 1、それ以外は sf-release.sh の終了コードです。ログは ./sf-tools/logs/sf-dryrun.log（実行のたびに作り直す）で、sf-release.sh の処理のログは ./sf-tools/logs/sf-release.log です。
-r / --release を付けると、実際にリリースします

検証だけのつもりで sf-dryrun.sh -r と実行すると、リリースモードになります（GitHub Actions の外では、環境変数 SF_DEPLOY_CONFIRMED が 1 でない限り、確認（Y/N/q）が表示されます）。検証だけが目的なら、付けないでください。

sf-release.sh

sf-release.sh [オプション]

ターゲットファイルから、マニフェスト（package.xml / destructiveChanges.xml）を作り、接続中の組織へ、検証またはリリースします。既定は dry-run です。force-* フォルダ（プロジェクトのルート）で実行します。

オプション内容
（指定なし）, --validate, --dry-run検証だけを行う（sf project deploy start --dry-run）。--validate と --dry-run は、指定なしと同じ
--release, -r実際に組織へリリースする（--dry-run を付けない）
--no-open, -n組織のデプロイ状況の画面を、ブラウザで開かない
--force, -f--ignore-conflicts を付け、コンフリクトの検知を無効にして、上書きする
--target, -t対象の組織のエイリアスを指定する（-t ALIAS / --target ALIAS の形。値がない・値が - で始まるときは中断。--target=ALIAS は使えません）
--json, -jこのスクリプトが実行する sf コマンド（マニフェストの生成・組織を開く・デプロイ）に、--json を付ける
--verbose, -vコマンドの応答を、コンソールにも表示する（既定は、ログファイルだけ）
--help, -h説明を表示して終了する

これ以外のオプション・引数は、エラーで中断します。

共有環境と本番の組織には、ローカルから実行できません（検証も含む）

GitHub Actions の外では、次の組織を、確認（Y/N/q）より前に拒否します。リリースは、GitHub にコミットして、レビューを通し、GitHub Actions で行います。個人用の Sandbox / Developer Edition / Scratch Org には、ローカルから実行できます。

  • エイリアスが予約名の組織: prod / staging / develop（と、互換のための main）。大文字・小文字を区別した、完全一致で判定します。sf-init は、共有環境の組織を、この名前で登録します。
  • 本番の組織（名前は問わない）: 名前だけでは、別の名前を付けた本番の組織を止められないため、sf data query で組織の種類を読み取ります。本番の組織と、種類を確認できない組織は、名前にかかわらず、実行できません。
テストクラスは自動で指定されます

deploy-target.txt の [files] に書いた .cls ファイルに @isTest（大文字・小文字を区別しない）があれば、テストクラスとして自動で検出し、--test-level RunSpecifiedTests と、クラスごとの --tests <クラス名> を付けます。手動で指定する必要はありません。検出されなければ、--test-level は付けません。

処理の流れ

  1. Salesforce CLI（sf）の終了コードを確認する（npm 版が前提。sf --version が 0 以外なら、案内を表示して中断。成功は 24 時間、確認を省く。GitHub Actions 上・sf が未インストールのときは、確認しない）
  2. 接続先の組織を決める。優先順位は、-t の値 → 環境変数 SF_TARGET_ORG → sf org display のエイリアス（最大 3 回試す）。決まらなければ中断する
  3. GitHub Actions の外で、接続先が予約名、または本番の組織（種類を確認できないときを含む）なら、検証モードでも中断する（上の囲み）
  4. GitHub Actions の外で、--release を付けたときは、確認（Y/N/q）を表示する（環境変数 SF_DEPLOY_CONFIRMED=1 のときは省く）。N / q なら中断する。-f も付けたときは、確認の前に、上書きの警告を表示する
  5. sf-tools/release/branch_name.txt のブランチ名で、sf-tools/release/<ブランチ名>/ を対象にする
  6. deploy-target.txt / remove-target.txt があるかを確かめ、sf-check.sh で検証する（branch_name.txt か、どちらかのファイルがないとき・エラーのときは、中断する）
  7. 既存の package.xml / destructiveChanges.xml を削除してから、マニフェストを作る。両方のファイルに対象が 1 件もなければ、「デプロイ対象なし。正常終了します。」と表示して、正常（終了コード 0）で終わる
  8. テストクラスを検出する（上の囲み）
  9. （-n がなければ）組織のデプロイ状況の画面（lightning/setup/DeployStatus/home）を、ブラウザで開き、5 秒待つ
  10. sf project deploy start --manifest package.xml を実行する。削除対象があれば、--pre-destructive-changes で渡す（削除は、デプロイより先に行われる）。検証モードなら --dry-run を付ける。失敗すれば中断する

補足

  • マニフェストは、[files] の行を --source-dir、[members] の行を --metadata として、別々に sf project generate manifest で作り、1 つの XML にまとめます（両方を同時に渡すと、sf は共通の部分だけを返すため）。まとめたあとにメンバーが 1 つもなければ、エラーで中断します（「変更なし」の成功として、見落とさないため）。
  • deploy-target.txt が空で、remove-target.txt にだけ対象があるときは、メンバーのない package.xml（version 60.0）を作り、削除だけを行います。
  • 組織にない削除対象をエラーにしたくないとき（後始末など）は、remove-target.txt に # @ignore-missing で始まるコメント行（行頭・# の後の空白は可）を書きます。sf project deploy start に --ignore-warnings が付き、削除以外の警告も、エラーになりません。通常のリリース・削除では、付けないでください（綴りの誤りを、見落とさないためです）。
  • sf-check.sh の出力（どの行が、なぜエラーか）は、-v がなくても画面に出ます（sf-release.log には残りません）。
  • -h / --help は、1 つ目の引数なら、ほかの処理の前に説明を表示します。2 つ目以降なら、手順 1 のあとの引数の解析で、そこに来た時点で表示します（それより前の引数がエラーなら、そのエラーで中断します）。
  • 終了コードは、成功（対象なしを含む）が 0、中断・失敗が 1 です。ログは ./sf-tools/logs/sf-release.log に、毎回上書きされます。

sf-deploy.sh

sf-deploy.sh [オプション]

sf-release.sh --release --force を簡単に呼ぶラッパーです。Sandbox の乗り換えなどで、現在の開発物を、接続中の組織へ強制的にリリースする用途で使います。受け取った引数は、その後ろに付けて sf-release.sh に渡します。

オプション内容
（固定）--release / --force常に付きます（リリースモード・コンフリクトの検知を無効にして上書き）。指定しても、受け付けるだけです
--no-open, -nブラウザを開かない（sf-release.sh へ渡す）
--target, -t接続先の組織のエイリアスを指定する（sf-release.sh へも渡す）。値がない・値が - で始まる・--target=ALIAS の形は、確認の前に中断します
--verbose, -vコマンドの応答を、コンソールにも表示する（このスクリプトと sf-release.sh の両方）
--json, -jsf-release.sh へ渡す（sf コマンドに --json を付ける）
--help, -h説明を表示して終了する（1 つ目の引数のときだけ）

これ以外のオプション・引数（2 つ目以降の -h を含む）は、確認（Y/N/q）の前に、「不明なオプションです」で中断します。

個人用の Sandbox / Developer Edition / Scratch Org 専用です

共有環境（本番・staging・develop）には、ローカルの PC からリリースできません。GitHub にコミットして、レビューを通し、GitHub Actions で行います。

GitHub Actions の外では、組織のエイリアスが予約名 prod / staging / develop（と、互換のための main）の組織を、確認（Y/N/q）の前に拒否します。sf-init は、共有環境の組織を、この名前で登録します。

さらに、組織の種類も確かめ、本番の組織と、種類を確認できない組織は、名前にかかわらず拒否します（別の名前を付けた本番の組織も、止まります）。ただし、staging・develop の組織（本番以外の組織）を別の名前で接続すると、名前でしか判断できないため、この保護は働きません。共有環境の組織は、予約名のまま使ってください。

処理の流れ

  1. 同じフォルダに sf-release.sh があるかを確かめる（なければ中断）
  2. 現在のブランチを確かめる。取得できない（detached HEAD・Git リポジトリの外など）とき、または sf-tools/config/branches.txt に書かれたブランチ（ファイルがない・空のときは main）なら、中断する。作業用のブランチで実行してください。
  3. 引数を調べる（不明なオプションなどは、ここで中断する）
  4. 接続先を決める。-t の値 → 環境変数 SF_TARGET_ORG → sf org display のエイリアス（最大 3 回試す）の順。決まらなければ中断する
  5. GitHub Actions の外で、予約名・本番の組織・種類を確認できない組織なら、中断する（上の囲み）
  6. 上書きの警告と、確認（Y/N/q）を表示する。N または q で中断する（GitHub Actions 上でも、確認は省きません）
  7. 環境変数 SF_DEPLOY_CONFIRMED=1 を設定して（sf-release.sh の確認を省く）、sf-release.sh --release --force を実行する

補足

  • 終了コードは、中断が 1、それ以外は sf-release.sh の終了コードです。
  • ログは ./sf-tools/logs/sf-deploy.log（実行のたびに作り直す）で、sf-release.sh の処理のログは ./sf-tools/logs/sf-release.log です。

sf-push.sh

sf-push.sh [-v]

カレントフォルダの下の変更を、VS Code で入力したコミットメッセージで、コミットしてプッシュします。force-* フォルダの中で実行します（git と code（VS Code のコマンド）が必要です）。-v（--verbose）・-h（--help。1 つ目の引数のときだけ）以外の引数は、「不明なオプションです」で中断します。

主な処理

  1. git と code があること・Git リポジトリの中であることを確かめ、現在のブランチを確かめる。ブランチの上にいないとき（detached HEAD）と、保護ブランチ（sf-tools/config/branches.txt に書かれたブランチ。ファイルがない・空のときは main）の上にいるときは、何も変更せずに、エラーで終了する（コミットだけが手元に残り、プッシュが通らない状態を、作らないため）
  2. origin/main を fetch して、現在のブランチにマージする（現在のブランチが main のときは行わない。早送りできないときは、マージのコミットができる）。fetch の失敗は、エラーで終了。マージの失敗（コンフリクトなど）は、失敗の理由を表示し、git merge --abort で取り消して、エラーで終了する
  3. カレントフォルダの下だけを git add --all する
  4. カレントフォルダの下に、ステージ済みの変更がなければ、未プッシュのコミットがあるときは git push だけを行って終了し、ないときは何もせずに終了する
  5. sf-check.sh で、ターゲットファイルを検証する（エラーなら終了）
  6. VS Code を別のウィンドウで開いて、コミットメッセージを入力する（閉じるまで待つ）
  7. git commit → git push

補足

  • コミットメッセージは、# で始まる行（前の空白は可）と、先頭・末尾の空行を除きます。途中の空行（件名と本文の間など）は残ります。残りが空なら、コミットもプッシュもせずに終了します。このとき、手順 2 の取り込みと、手順 3 のステージは、元に戻らず、そのまま残ります。
  • 手順 4 の「プッシュだけ」は、コミットは成功してプッシュが失敗したあとの、やり直しのためです。もう一度 sf-push.sh を実行すれば、取り残されません。手順 2 で取り込んだコミットも、未プッシュのコミットに数えます（追跡先のブランチがないときは、未プッシュ 0 件として扱います）。
  • ステージするのも、「変更なし」の判定も、カレントフォルダの下だけです。ただし、コミットでは、パスを指定しません。カレントの外で、前からステージ済みだった変更も、一緒にコミットされます。
  • コミットとプッシュのときは、インストール済みの pre-commit / pre-push フックも動きます（「プッシュだけ」のときは、pre-push だけ）。
  • sf-check.sh の出力（どの行が、なぜエラーか）は、-v がなくても画面に出ます（sf-push.sh のログには残りません）。
  • git add・git commit・git push・VS Code の起動のどれかに失敗したときも、エラーで終了します。
  • 終了コードは、正常終了（何もせず終わった場合を含む）が 0、エラーが 1 です。ログは ./sf-tools/logs/sf-push.log です（実行のたびに作り直します）。

sf-next.sh

sf-next.sh [-v]

現在の作業用のブランチが、ブランチの階層（sf-tools/config/branches.txt。例: develop / staging / main）のどこまでマージ済みかを確認し、次に出すべき PR 先のブランチを案内します。force-* フォルダの中で実行します。-v（--verbose）・-h（--help。1 つ目の引数のときだけ）以外の引数は、「不明なオプションです」で中断します。

表示されるステータス

見出し「<現在のブランチ> のマージ状況」の下に、マージの順で 1 行ずつ表示します（標準エラーに出します）。

記号表示説明
✓マージ済み現在のブランチ → 対象のブランチの PR が、マージ済み（デプロイのワークフローも実行済み）
✓マージ済み（ブランチ同期）現在のブランチのコミットが、すでに対象のブランチに含まれている（直接の PR はないが、別のブランチ経由で伝わったなど）。この PR のデプロイのワークフローは、未実行
⚠マージ済み（順序外）マージ済みだが、マージの順で前のブランチに、まだマージ済みでないもの（ブランチ同期・PR 発行中・未着手）がある。前のブランチのデプロイは、未実行
→PR発行中PR を出してあり、マージを待っている
▶次のPR先まだ PR を出していないブランチのうち、最初のもの。次に PR を出すべきブランチ
✗（文言なし）まだ PR を出していないブランチの、2 つ目以降

判定の方法

マージの順（branches.txt の順序を逆にしたもの。例: develop → staging → main）に、各ブランチを次の順で判定します。判定の前に、git fetch（branches.txt の全ブランチを、1 回のコマンドで）でリモートの最新を取得し、gh pr list で、マージ済み・オープンの PR を、それぞれ最新 50 件取得します。

  1. 現在のブランチ → 対象ブランチの直接の PR が、マージ済みにある → 「マージ済み」
  2. git merge-base --is-ancestor HEAD origin/<対象ブランチ> が真（コミットがすでに含まれている） → 「マージ済み（ブランチ同期）」
  3. 直接の PR が、オープンにある → 「PR発行中」
  4. どれにも当てはまらなければ → 「次のPR先」または「未着手」

そのあと、マージ済みのブランチより前（マージの順）に、マージ済みでないブランチがあれば、そのマージ済みを「順序外」にします。

順序外のマージの制約

develop → staging → main の順番を守らずにマージすると、飛ばしたブランチへのデプロイは、できなくなります
  • 上位のブランチ（例: main）にマージすると、コードが下位のブランチ（例: staging）に伝わります。
  • 伝わったあとは「差分なし」になり、feature → staging の直接 PR を作れなくなります。
  • デプロイのワークフローは、直接 PR のマージで起動するため、伝わっただけでは動きません。

飛ばしたブランチにデプロイしたいときは、新しいブランチを切って、順序どおりに PR を出し直します。

順序外の PR を、レビュアーが見つける仕組み（wf-sequence）

sf-next.sh を使う限り、PR の先は「次の段階」だけです。ランチャーを使わず、GitHub 上で直接 PR を作って段階を飛び越したときは、main / staging への PR を作った時点で、次のようにレビュアーに知らせます。

通知先内容
PR の会話欄「⚠️ マージ順序の確認が必要です。意図的でなければ、この PR は却下してください」というコメント（同じ PR では、既存のコメントを更新します）
Slack通知

マージは止めません（緊急の Hotfix を妨げないため。Free プランの Private リポジトリでは、GitHub がそもそも止められません）。気づいたレビュアーが、PR を却下します。

補足

  • 保護ブランチ（sf-tools/config/branches.txt に書かれたブランチ。ファイルがない・空のときは main）の上と、ブランチを取得できないとき（detached HEAD など）は、エラーで終了します。
  • 次の PR 先があるときは、「<次の PR 先> にPRを出しますか？」と確認します（Y/N/q）。Y で、<origin の URL>/compare/<次の PR 先>...<現在のブランチ>?expand=1（PR の作成画面）を、ブラウザで開き、URL も表示します（PR そのものは、作りません）。N は何もせず終了、q は中断（終了コード 1）です。
  • 開く URL は、origin の URL から作ります（URL に含まれる認証情報（//<ユーザー>:<Token>@）は除き、SSH の形は https://github.com/ に直します）。origin の URL を取得できないときは、エラーで終了します。
  • PR の状態の判定には、認証済みの gh が必要です。gh が使えないなど、取得に失敗したときは、警告を出さずに「PR なし」として判定します。
  • リモートの最新を取得できなかったときは、警告を出して続行し、手元の origin/* で判定します。
  • 次の PR 先がないときは、「PR発行中」が残っていれば「マージ完了を待ってください」、なければ「全ブランチへのマージが完了しています！」と表示して終わります。
  • 終了コードは、正常終了（N で終了した場合を含む）が 0、エラー・q での中断が 1 です。ログは ./sf-tools/logs/sf-next.log です（実行のたびに作り直します）。

sf-restart.sh

sf-restart.sh [-v]

接続先の組織を切り替えたいときに使います。force-* フォルダの中で実行します。-v（--verbose。sf-start.sh にも渡す）・-h（--help。1 つ目の引数のときだけ）以外の引数は、「不明なオプションです」で中断します。

主な処理

  1. 同じフォルダに sf-start.sh があるかを確かめる（なければ、何も削除せずに中断）
  2. 接続の設定ファイル（.sf/config.json と .sfdx/sfdx-config.json）を、一時フォルダに退避してから、確認なしで削除する（退避に失敗したら、何も削除せずに中断）
  3. 環境変数 FORCE_RELOGIN=1 を付けて、sf-start.sh を実行する（接続済みでも、組織のエイリアスの入力とログインから、やり直します）

補足

  • sf-start.sh が失敗したとき（ログインの失敗・入力の中断など）は、新しい設定ファイルが書かれていなければ、退避しておいた元の設定ファイルを戻します（戻したとき・戻せなかったときは、警告を表示します）。成功したときは、新しい設定ファイルに置き換わります。退避した一時フォルダは、終了のときに削除します。
  • 終了コードは、sf-start.sh の終了コードです。sf-start.sh を呼ぶ前に中断したとき（不明なオプション・sf-start.sh がない・一時フォルダを作れない・退避できない）は 1 です。
  • ログは ./sf-tools/logs/sf-restart.log です（実行のたびに作り直します）。

sf-hook.sh / sf-unhook.sh

sf-hook.sh
sf-unhook.sh

どちらも、force-* フォルダの、Git リポジトリのルート（.git がある場所）で実行します（.git がなければ中断します）。-v / --verbose と、1 つ目の引数の -h / --help 以外の引数は、「不明なオプションです」で中断します（何もインストール・削除しません）。ふだんは、sf-start.sh がバックグラウンドで実行する sf-install.sh が、フックを設置するため、直接実行する必要はありません。

sf-hook.sh

  1. git config --local core.hooksPath の値に husky が含まれていれば、確認なしに設定を削除する（元には戻しません）
  2. ~/sf-tools/hooks/ の pre-commit と pre-push を、.git/hooks/ にコピーして、実行権限を付ける。既存のファイルは、確認もバックアップもなしに上書きする。コピー元がなければ中断する（コピー元は ~/sf-tools/hooks/ に固定です）
  • husky 以外の値の core.hooksPath（ローカル・グローバル）が残っているときは、Git が .git/hooks/ を使わず、入れたフックが動かないため、警告を表示します（フックのコピーは行います）。
  • 入るフック: pre-commit は sf-precommit.sh を呼び、ターゲットファイルを検証して、エラーならコミットを中止します。pre-push は sf-prepush.sh を呼び、branches.txt のブランチへの直接のプッシュの禁止・ターゲットファイルの検証・origin の自分のブランチと main の取り込みを行います（取り込んだときは、そのプッシュを中止します。もう一度プッシュすると、通ります）。Salesforce の組織への検証（dry-run）は、行いません。
  • コピーされるフックは、~/sf-tools/bin/ のスクリプトを呼ぶだけのラッパーです。sf-precommit.sh・sf-prepush.sh の更新は、全プロジェクトに、すぐに届きます。ラッパー（hooks/ のファイル）自体の変更は、各プロジェクトで sf-hook.sh を実行し直すまで、届きません。
  • 終了コードは、成功が 0、中断が 1 です。ログは ./sf-tools/logs/sf-hook.log です。

sf-unhook.sh

  • .git/hooks/pre-push を削除します。pre-commit は残ります。sf-hook.sh が削除した husky の設定（core.hooksPath）も、元に戻しません。
  • pre-push がなければ、「すでに無効化されています」と表示して終了します（終了コード 0）。
  • sf-tools が置いたフック（目印の文字列がある）だけを削除します。それ以外のフックなら、警告を表示して、削除せずに終了し、最後に「状態は変わっていません」と表示します（終了コード 0）。
  • 終了コードは、成功（削除しなかった場合を含む）が 0、中断・失敗が 1 です。ログは ./sf-tools/logs/sf-unhook.log です。

フックの動きは、sf-prepush.sh と sf-precommit.sh にあります。
