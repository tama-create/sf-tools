# sf-tools 結合テスト計画（案）

> **本ドキュメントの範囲:** コマンドを連動させて動かす「結合レベル」のテストの、パターンの洗い出しと、作り方の方針。実装は、これから（案の段階）。
> 個々のコマンドの単体テストは、`tests/test_*.sh`（`doc/dev-reference.md` セクション 2）。実環境の通しの確認（e2e）は、`doc/dev-reference.md` の 9.6・9.7。

---

## 1. 目的と範囲

### 1.1 目的

- 単体テストでは見つからない、**コマンドの連動で初めて壊れる箇所**を、見つける。
- 正常系だけでなく、**異常系（失敗・中断・不整合・誤操作）**が、安全に処理されることを、確かめる。

### 1.2 範囲

- 対象: `bin/sf-*.sh`、`hooks/`、`phases/init/`、`templates/.github/workflows/`、それらの連動。
- 対象外: 結合する価値がなく、単体テストで十分なコマンド（**理由を、10 の表に書く**）、単体の分岐（単体テストで確認済み）、Linux をクライアント PC として使うこと（Linux は、GitHub Actions のサーバーとしてだけ使う）。

## 2. 現状

### 2.1 テストの層

| 層 | 何を確かめているか | 弱点 |
|---|---|---|
| 単体テスト（`tests/test_*.sh`。モック） | コマンドごとの分岐・安全ガード。エラーの分岐も多い（検証行の約 2 割が、異常・拒否に関するもの。キーワードによる大まかな集計） | `git`・`gh`・`sf` の多くは、モック。**コマンド同士の連動**は、確かめていない。実際の `git` を使うのは、一部（`test_wf-sequence.sh`・`test_project-identity.sh`・`test_common.sh` の `admin` ブランチ・`test_e2e.sh` の bare リポジトリ）。bare リポジトリと実 `git` は、**各テストが個別に作っており、共通のハーネスは無い**。「N 回だけ失敗させる」モックは、`sf org login jwt`（`test_helper.sh` の `MOCK_SF_JWT_FAIL_FIRST`）と、e2e 用の `gh`（`test_e2e.sh` の専用のモック）だけ |
| e2e（`tests/e2e/`。実際の GitHub・Salesforce） | 管理者の `sf-init` → 開発者の `sf-job` → `sf-dryrun` → `sf-push` → PR → Actions → リリースと削除 → `sf-next`。1 層・3 層。`wf-sequence` の 3 つの動き | 「うまくいく筋」が中心。異常系は、4 種類だけ（2.3） |
| 開発者の手動の確認 | `sf-init --verify` など | 記録がなく、再現できない |

### 2.2 コマンドごとの実績（e2e のログで確認）

| 区分 | コマンド |
|---|---|
| 実環境で実行（うまくいく筋） | `sf-init`（通し・`--add-tier staging`）、`sf-job`、`sf-start`、`sf-install`、`sf-hook`、`sf-dryrun`、`sf-push`、`sf-prepush`、`sf-precommit`、`sf-next` |
| 間接的に実行 | `sf-release`・`sf-check`・`sf-metasync`（`sf-dryrun` と、Actions の中で） |
| 一部のみ | `sf-sync-wf`（`--check` のみ）、`sf-deploy`（拒否のみ） |
| 単体テストのみ | `sf-unhook`、`sf-restart`、`sf-launcher`、`sf-update-secret`、`sf-upgrade`、`sf-init` の `--resume` / `--reconnect` / `--status` / `--only` |
| 別枠 | `sf-typecheck`（個人用の組織で、自身が実機確認）、`sf-init --verify`（手動） |

### 2.3 e2e で確認している異常系（4 種類）

- 秘密情報（Token・認証 URL）が、`sf-init` のログに出ない。
- `sf-deploy` が、予約名の組織への強制リリースを、拒否する。
- `wf-sequence`: 順序外の PR は警告（止めない）、環境ブランチからの PR は失敗。
- 他の段階の組織には、リリース・削除が及ばない。

**不足しているもの:** 外部サービスの失敗、中断と再開、状態の食い違い、競合、失敗後の復旧。

## 3. 合格条件（異常系は、すべて、この条件で判定する）

| # | 条件 |
|---|---|
| 3.1 | 期待する**終了コード**で終了し、安全に**止まる**（先へ進まない。半端な状態を、さらに悪くしない） |
| 3.2 | 原因が分かる**メッセージ**が出る（事実のみ。復旧案内は、`die` のメッセージに含めない） |
| 3.3 | **被害がない**（他のリポジトリ・本番・共有の組織に及ばない） |
| 3.4 | 外部の状態（GitHub・Salesforce）と、ローカルの状態（ブランチ・コミット・フック・状態ファイル・完了の印）が、**整合する**（半端な commit・ブランチ・フックが、不整合のまま残らない。残る場合は、再実行で解消できる状態である） |
| 3.5 | **再実行で、重複が生じない**（commit・ブランチ・PR・Secret・フック） |
| 3.6 | **復旧できる**（案内された復旧の手順を実行すると、成功の経路に戻れる） |
| 3.7 | **秘密が漏れない**（ログ・画面・PR・Slack・一時ファイル）。`SIGKILL` の後は、`EXIT` のトラップが動かず、一時ファイルを、その場で消せない（例: `phases/init/08_initial_commit.sh` の askpass は、`EXIT` のトラップで削除する）。そのため、次の 3 つを、**別々に**確認する: ①秘密の値そのものが、残らない／②再開に必要な、秘密でない進捗ファイル（`.sf-init-*.env` の秘密でない部分・`.progress`）だけが、残る／③認証用の一時ファイル（askpass・一時ホーム・JWT 関連）は、次回の起動時に、安全に掃除される |

> 各パターンで、確認する条件を明記する。特に、中断と再開（6.2）・状態の食い違い（6.3）は、3.4・3.5・3.6 の確認に、4.5 の不変条件を使う。

## 4. テストの層と設計方針

### 4.1 2 つの層

| 層 | 内容 | 実行 |
|---|---|---|
| **L1 ローカル結合**（新設） | 実際の `git` と、ローカルの bare リポジトリ（`origin` の代わり）で、コマンドを連動させる。`gh`・`sf` は、モック（指定した回数だけ失敗させられる） | CI（Ubuntu・macOS・Windows の Git Bash）と手元。数分。費用なし |
| **L2 実環境結合**（既存の e2e を拡張） | 今の `run.sh`（1 本の長い筋）を、シナリオ方式に分ける。モックでは表せないものだけ | 開発者（Claude）が実行。変更に関わる分だけを選ぶ |

### 4.2 L1 の設計方針

- 連動の対象は、「状態の受け渡し」: ブランチ・clone・フック・`branches.txt`・各段階のリリースファイル・`.sf-init-*.env`・完了の印・`origin` の URL からのプロジェクト判定。
- 複数の clone、remote ブランチ、フックを含める（bare リポジトリを用意するだけにしない）。
- **どのコマンドを本物にし、どれをモックにするか:**
  - 本物: `git`（PATH の本物）、`bash`・`awk`・`sed`・`openssl`・`node`（`json_get` が使う）、テスト対象の sf-tools のスクリプトとフック。
  - モック（PATH の先頭に置く）: `gh`・`sf`・`curl`（Slack）・ブラウザ（`start` / `open` / `xdg-open` / `powershell.exe`）。
- **「既存で実現済みのもの」と「L1 のために新設するもの」を分ける:**
  - 既存: 各テストが個別に作る bare リポジトリ（`test_common.sh`・`test_sf-init.sh`・`test_init-common.sh`・`test_e2e.sh`）、`test_helper.sh` のモック（`create_mock_git`・`create_mock_gh_*`・`create_mock_sf` など）、JWT の N 回失敗（`MOCK_SF_JWT_FAIL_FIRST`）、e2e 用の `gh` のモック（`test_e2e.sh`）。
  - 新設: 共通の L1 ハーネス（実 `git` ＋ bare ＋ 複数 clone の作成）、共通の故障注入つきの `gh`・`sf`・`curl` のモック（4.4）、実行順序の記録、不変条件の確認の部品（4.5）。
- **OS ごとの必須の確認項目**を定める:
  - Windows の Git Bash: パスの変換・LF（`core.autocrlf=false`）・実行権限・`/tmp` と一時フォルダの後始末。
  - macOS（Bash 3.2）: BSD の `sed` / `stat` / `base64`・`TMPDIR` の末尾の `/`。
  - Ubuntu（GitHub Actions）: 基準の環境。CI の Ubuntu は、テストの実行環境であり、Linux クライアントを想定するものではない。

### 4.3 L2 の設計方針

- **共有するのは、初期化済みの状態（fixture）まで。** 各シナリオは、専用のブランチ・PR・作業クローンを使う。
- シナリオの前後で、前提を確認する（`main` の SHA・ブランチと PR の一覧・組織のクラス・`sf` の別名・`admin` クローンのブランチ）。崩れていたら、後続のシナリオを実行しない。
- 全シナリオを毎回は動かさず、変更に関わる分だけを選ぶ。
- 失敗を起こすときは、**偽のトークン・壊したコピー**を使い、本物の鍵は壊さない（故障注入）。
- 既存の安全ガード（テスト用リポジトリの名前の形式・オーナーの一致）を通ること。ガードは、緩めない。

### 4.4 故障注入の方針と仕様

異常系は、実環境では、安全に起こせないものが多い。L1 に寄せ、L2 は、モックでは表せないものだけにする（本物の認証 URL の失効・本物の Actions の失敗通知・本物の組織のテスト失敗）。

**故障の種類（モックの指定）:**

| 指定 | 動き |
|---|---|
| N 回失敗 | 最初の N 回の呼び出しを、指定の終了コードと、指定のエラー出力で失敗させる（以後は成功） |
| N 秒遅延 | 応答を、N 秒遅らせる（タイムアウトの試験） |
| 出力後に終了 | 途中まで出力して、非ゼロで終了する |
| 子プロセスを残す | 子プロセスを残して、親が終了する（後始末の試験） |
| 部分ファイル | ファイルを、途中までだけ作って、失敗する |
| 共有ロック | 呼び出しの間、ロックのファイルを持つ（同時実行の競合の試験。実行順序を、ログに記録する） |

**止め方（中断の試験）:** `sf-init` は、Ctrl-C（`INT`）を無視する（`bin/sf-init.sh` の `trap '' INT`）。Ctrl-C は、中断の試験にならない。次の 3 つで止める。

1. `SIGTERM`（外から終了。`EXIT` のトラップは動く）
2. 子コマンドの失敗（故障注入）
3. `SIGKILL`（強制終了。`EXIT` のトラップも動かない）

### 4.4.1 fake の必須仕様（L1 の前提。**新しく作る、大きな部品**）

今の `tests/test_helper.sh` のモックは、固定の終了コードと、呼び出しの記録が中心で、状態の遷移・遅延・`SIGTERM`・子プロセス・排他を持たない。6 の異常系の多くは、次の仕様を満たす fake が無いと、L1 で再現できない。**L1 の基盤は、これを作ることが、前提になる**（最小の範囲から作り、必要になったものを足す）。

| # | 仕様 |
|---|---|
| 1 | **状態を持つ GitHub の fake**: リポジトリ・ブランチ（実体は、ローカルの bare リポジトリ）・PR・Secret・Variable・ワークフローの実行を、ファイルに保持し、呼び出しのたびに更新する。名前の衝突・権限なし・レート制限を返せる |
| 2 | **状態を持つ Salesforce の fake**: ログイン状態・クラス（デプロイ済み）・デプロイの実行・ロックを保持する。テスト失敗・ロック・認証の失効を返せる |
| 3 | **Slack（`curl`）の fake**: 成功・失敗・無効なトークンを返す |
| 4 | **呼び出し別の故障注入**: コマンド名・引数・呼び出し回数を指定して、失敗させる（4.4 の「N 回失敗」など） |
| 5 | **開始後 N 秒の遅延**・**出力後の終了**・**子プロセスの残留**・**部分ファイルの生成** |
| 6 | **ロックの取得・解放のログ**と、**実行順序のログ** |
| 7 | **プロセスの終了後に、fake の状態を検査する部品**（4.5 と連動） |

### 4.5 不変条件の確認の部品

中断・失敗のあとの「再開の前」と「再開・復旧の後」に、次を確認する部品を、共通で用意する。

- ローカル: `HEAD`・コミット数・ブランチ一覧・フックの有無・`.progress` / `.sf-init-*.env` の内容・完了の印（`setup-complete`）・一時ファイルと認証情報（askpass など）の残り。
- 外部（GitHub）: リモートのブランチ一覧・PR 一覧・Secret / Variable の一覧。**重複がない**こと（同じ commit・ブランチ・PR・Secret が、2 つできない）。
- 秘密: PAT の値が、状態ファイル・ログ・画面に残っていない。

| X1-3 | GitHub: リポジトリ名の衝突・作成権限なし・別ユーザーでログイン | L1 | ★★ |

### 6.2 X2. 中断と再開

各停止点で、止め方（4.4: `SIGTERM`・子コマンドの失敗・`SIGKILL`）を変え、再開の前後に、4.5 の不変条件を確認する。

## 10. コマンド別のカバレッジ表

実装している、すべてのコマンド・フック・ワークフローについて、「結合テストの対象か」を、明記する。**結合する価値がなく、単体テストで十分なものは、理由を書いて、対象外にする**（無理に、結合テストを作らない）。

### 10.1 完了の定義

- **結合あり**: 少なくとも、**正常系の連動を 1 つ、異常系の連動を 1 つ**（表の「パターン」に、番号がある）。
- **結合なし**: 「結合しない理由」が、**空でない**（単体テストで十分な理由を、具体的に書く）。
- **ガードのテスト**（8 の 0）: `bin/sf-*.sh`・`hooks/*`・`templates/.github/workflows/*.yml` のすべてが、この表に載っていること、各行が「結合あり（パターンの番号が 1 つ以上）」か「結合なし（理由が空でない）」のどちらかであることを、確かめる。**新しいコマンドを足して、表に載せ忘れると、テストが失敗する。**

### 10.2 コマンド
