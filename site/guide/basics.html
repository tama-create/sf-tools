基本の使い方

フォルダの考え方を押さえてから、新しい作業の始め方と、作業の再開のしかたを覚えましょう。

言葉とフォルダの構成

呼び方内容
プロジェクトforce-XXXX（リポジトリのクローン。VS Code で開く単位）。force- は固定、XXXX は管理者が決める名前です（例: acme → force-acme）
作業単位プロジェクトの直上のフォルダ（JOB-xxx・admin など）。同じ force-XXXX を、同時に複数、別々の作業として開くための入れ物です
作業フォルダ作業単位のフォルダを置く場所。どこでもよいです（sf-init.sh や sf-job.sh は、ここで実行します）
 
{作業フォルダ}\                    ← 好きな場所・好きな名前（おすすめ: C:\sf や ~/sf のような、短い名前）
├── admin\force-acme\              ← 管理者用（sf-init.sh が作る。メンテナンス用として残す）
├── admin\force-beta\              ← 別のプロジェクトも、同じ admin に置く
├── JOB-20261016\force-acme\       ← ジョブごとのクローン（sf-job.sh が作る）。同じ force-acme を、同時に複数開ける
└── JOB-20261017\force-beta\       ← 別のプロジェクトを、同じ作業フォルダに置いてもよい

どのプロジェクトか、どう決まるか

どのプロジェクトか（オーナーと XXXX）は、フォルダの名前では決まりません。開発者が使う sf-job.sh は、次の順で決めます（上にあるものが優先です）。

  1. 引数 --owner / --project
  2. 作業フォルダの下にあるクローンの git remote。クローンした時点で Git が記録した住所から、オーナーとリポジトリ名を読みます（1 種類なら自動、複数なら番号で選びます）
  3. 対話で入力
実行できない場所

sf-job.sh は、管理者用の作業フォルダ（admin）と、force-* の中では、実行できません。作業フォルダで実行してください。

ヘルプを表示する

すべての sf-*.sh スクリプトは --help / -h に対応しています。概要・オプション・処理の流れが表示されます。

sf-release.sh --help
sf-check.sh -h

新しい作業を始める（sf-job）

作業フォルダで実行します。

sf-job.sh                          # 作業フォルダの下のクローンから、プロジェクトが決まる（複数なら、番号で選ぶ）
sf-job.sh --project acme           # プロジェクトを指定する（force-acme）

ブランチ名の入力だけで、次をすべて自動で行います。

  1. ジョブ名（例: JOB-20260323）でブランチを作成

  2. 作業ディレクトリを準備（worktree または clone）

  3. sf-start.sh を自動で起動（ログイン・フック設定・VS Code の起動）

Windows のパスの長さについて

クローンは core.longpaths=true を付けて行います（Windows のパスの長さの上限、260 文字への対策）。組織に長い名前のメタデータ（例: DevOps Center の objectTranslations）があっても、チェックアウトに失敗しません。この設定はクローン先に残るので、以降の git add・commit・push にも効きます。

前日の続きなど、既存のブランチで再開するときは、force-* フォルダの中で実行します。
