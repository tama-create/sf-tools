## 1. 概要

### 1.1 目的

AI（Claude Code など）に開発を任せる、次のサイクルを回すための道具。

```
AI がコードを書く → AI がデプロイする → 人が画面で動きを確かめる
   ↑                                              ↓
   └──── AI がログの要約を読んで直す ← AI が sf-log.sh pull を実行する
```

- ログを読むのは、人ではなく AI。そのため、ログの本文に加えて、**AI が最初に読む要約**を作る（6 章）
- 取るのは、実行した人のユーザーのログだけ
- 取るのは Salesforce のデバッグログ（`ApexLog`）。名前は Apex でも、Apex だけでなく、フロー・入力規則・重複ルールなど、1 回の処理の中の動きが載る（区分ごとの詳しさは 7 章。2026-11-24 に、フロー・入力規則の行を実機で確認した: 6.3）

### 1.2 使い方の全体像

**人は、いつもどおり `sf-start` を打つだけ。** 覚えるコマンドはない。

```
sf-start（組織に接続）──→ 裏の取得役（collector）を起動 ──→ ランチャー（いつもどおり）
                           │  3 分ごと: 新しいログを手元に保存         │
                           │  期限が近づいたら: TraceFlag を延ばす     │ q で終了
                           ▼                                        ▼
                     手元に溜まる  ←── AI が質問を受けたら pull（すぐ要約を読める）
                                                  sf-start の終了時: 取得役を止め、TraceFlag を消す
```

| 誰が | すること |
|---|---|
| 人 | `sf-start` を打つ（いつもどおり）。プロジェクトで初めてのときだけ、「ログを自動で取るか」に答える（10.2） |
| 裏の取得役 | ランチャーの起動中、ログを手元に保存し続ける。TraceFlag の期限を延ばし続ける（4.3） |
| AI | 質問を受けたら `sf-log.sh pull` を実行し、`logs/apex/latest.md` を読む（4.4） |

- ランチャーを使わない人・`sf-start` を使わない場面のために、手動の `start` / `pull` / `stop` も残す（3 章）
- ランチャー（`phases/start/launcher.sh`）のメニューには、sf-log.sh を入れない（取得役の状態の 1 行だけを表示する。5.4）

### 1.3 対象の組織

- **一人用の開発組織（Developer Edition・Sandbox・スクラッチ組織）だけで使う。**
- 本番と、共有環境の組織（予約名）では取らない（10.1）。`sf-start` の自動では、「取りません」と表示して、ランチャーはそのまま起動する

## 2. 変更点

### 2.1 旧設計（sf-logwatch.sh）から

| | 旧設計 | 本設計 | 理由 |
|---|---|---|---|
| 動かし方 | 人が起動し、10 秒ごとに見張る。Ctrl+C で止める | `sf-start` が裏で取得役を起動し、ランチャーの終了で止める（2.2）。AI は `pull` を呼ぶだけ | Ctrl+C はランチャーで無効（`sf-start.sh` の `trap '' INT`）。止め忘れると TraceFlag が残る。人が覚えるコマンドを増やさない |
| 出すもの | ログの本文だけ | 本文＋**要約**（`latest.md`） | FINEST のログは 1 回の操作で数 MB になり、AI の文脈を埋める。1 回の画面操作で、ログが何本も出る。AI は要約を先に読み、必要なときだけ本文を開く |
| ログの詳しさ | `deploy-target.txt` の拡張子から自動で決める | 既定の 1 種類＋手動の `start` で切り替え（7 章） | `deploy-target.txt` は、今の作業と一致するとは限らない。15 分で 1,000MB を超えると TraceFlag が止められるため、既定で FINEST にしない |
| 新しいログの見つけ方 | `sf apex list log` の ID を、既知の ID と比べる | Tooling API の検索で、自分のユーザー・前回より後に絞る（8.3） | `sf apex list log` は、組織の全ログを返す（絞り込みのオプションがない。sf 2.157.8 の `--help` で確認） |
| DebugLevel | 起動のたびに作り、終了時に消す | 名前で探し、毎回、決まった値で上書きして使い回す（消さない） | 名前の重複を、作り直しの不要な形で解く |
| TraceFlag | 起動のたびに作り、終了時に消す | 自分が作ったもの（状態ファイルに記録した ID）だけを延ばし・消す。ほかの TraceFlag は、手動では確認して止め、自動では触らない（4.2） | 1 つのユーザーで有効な TraceFlag は、同時に 1 つだけ（公式。8.6）。Developer Console を開くと、そのユーザーに TraceFlag が作られるため、黙って書き換える・消すと、人の設定を壊す |
| 1 本のログの上限 | 2MB | 20MB（公式。8.6） | 旧設計の値は古かった |
| AI への送信 | 考慮なし | プロジェクトごとに最初の 1 回、確認する（10.2） | AI に読ませると、ログの中身（レコードの値）が AI の提供元に送られる |

### 2.2 2026-11-21 版（人が `start` を打つ方式）から

| | 2026-11-21 版 | 本設計 | 理由 |
|---|---|---|---|
| ログの取り始め | 人が作業の始めに `sf-log.sh start` | `sf-start` が、組織に接続したあとに自動で始める | 毎回コマンドを打つのは手間で、覚えることも増える（TAMAさんの指摘） |
| ログの取得 | AI の `pull` のたびに、組織から取る | 裏の取得役が一定の間隔（既定 3 分。2026-11-23 に 1 分から変更。13.3）で手元へ保存し、`pull` は直前の分を取り足して要約するだけ | 質問されたとき、すぐ答えられる。1 件の取得に数秒かかる（Windows）ため、まとめて取ると待たされる |
| TraceFlag の期限 | 2 時間。切れたら人が `start` | 2 時間。取得役が、期限が近づくたびに延ばす | 長い作業でも切れない。異常終了で延ばす役が止まれば、2 時間で自然に切れる（5.5） |
| AI への送信の確認 | `start` のたび | プロジェクトごとに最初の 1 回（答えを覚える） | 毎回聞かれるのは手間。一度は確認すべき |
| 同時実行 | 対応しない | 取得役と `pull` は同時に動く前提。手元の取得の状態を書くのは、取得役だけにする。依頼は ID つき（9.3） | 裏で常に動くため |
| 組織からの取り方 | 1 回の上限を超えたら、新しいほうを優先（古いものは飛ばし、`--since` で取り直す） | 古い順に、しおりから続きを取る（取りこぼさない。8.3）。新しいほうの優先は、要約に入れるログを選ぶときだけ | 取得役が動いている間は、`--since` で組織から取り直す経路がない（Codex の指摘）。取得役は止まらずに動くため、飛ばす必要もない |
| 確認の単位 | `start` のたび | プロジェクトごと・組織ごと・文面の版ごとに 1 回（10.2） | 別の組織（実データを写した Sandbox など）に切り替えたとき、前の答えを使わないため |
| ランチャーを 2 つ | 想定なし | 起動中の sf-start の一覧（`.owners`）を持ち、全部が閉じたときだけ止める（5.2） | 後から開いたランチャーを閉じたとき、先のランチャーの取得まで止めないため |

## 3. コマンド

### 3.1 使い方

```bash
# force-* ディレクトリで実行
bash ~/sf-tools/bin/sf-log.sh pull           # 要約を作る（AI が実行する。取得役が動いていれば、直前の分を取ってもらってから要約する）
bash ~/sf-tools/bin/sf-log.sh status         # 取得役の状態・TraceFlag の期限・前回の pull の時刻・組織のログの量を表示する
bash ~/sf-tools/bin/sf-log.sh auto on|off    # このプロジェクトで、sf-start のときに自動で取るか（10.2 の答えを変える）

# 手動（sf-start を使わない場面）
bash ~/sf-tools/bin/sf-log.sh start          # ログを取り始める（TraceFlag を作る・延ばす。取得役は起動しない）
bash ~/sf-tools/bin/sf-log.sh stop           # 取得役を止め、自分が作った TraceFlag を消す

# 内部用（sf-start.sh が呼ぶ。人は打たない）
bash ~/sf-tools/bin/sf-log.sh start --auto   # 自動の取り始め（確認で止まらない・失敗してもランチャーを止めない。4.2）
bash ~/sf-tools/bin/sf-log.sh collect        # 裏の取得役（4.3）
bash ~/sf-tools/bin/sf-log.sh leave --owner <印>   # sf-start の終了時: 持ち主の一覧から外れ、誰もいなければ止める（5.2）
```

### 3.2 オプション（案）

| オプション | 対象 | 内容 |
|---|---|---|
| `-o <エイリアス>` | 全部 | 接続先の組織。省略時は `get_target_org`（引数 > `SF_TARGET_ORG` > `sf org display` の alias） |
| `--level <standard\|detail>` | `start` | ログの詳しさ（7 章）。既定は `standard`。自動は常に `standard` |
| `--hours <N>` | `start` | TraceFlag の期限（時間）。**1〜23 の整数**（公式: 期限は開始から 24 時間未満。8.6）。既定 2。範囲外・整数でない値は `die` |
| `-y` | `start` | AI への送信の確認と、ほかの TraceFlag の置き換えの確認を省く（手動のみ） |
| `--auto` | `start` | sf-start.sh からの自動の取り始め（4.2 の自動の欄） |
| `--owner <印>` | `start --auto`・`leave` | 持ち主（sf-start）の印（5.1）。形は `PID:起動の時刻:環境の名前と乱数`（例 `1234:1795500000:wsl8f3a`。5.6。数字と英数字だけ。形が違えば失敗） |
| `--max <N>` | `pull` | 1 回に要約へ入れるログの数の上限。1 以上の整数。既定 50。超えたら、新しいほうから入れる（8.3） |
| `--since <分>` | `pull` | 前回の pull を無視して、直近 N 分のログを要約する。1 以上の整数 |

- `--help` / `-h` は、他のコマンドと同じ（冒頭コメントの第 2 ブロック）
- 取得の間隔は、環境変数 `SF_LOG_INTERVAL`（秒。30〜600。既定 180）で変えられる（4.3）。既定を 60 から 180 にしたのは、sf の 1 回の呼び出しが約 10 秒かかり（13.1）、1 回の取得に 20〜30 秒かかるため。`pull` は取得役にすぐ取らせるので、間隔を延ばしても、AI が読むログは古くならない（2026-11-23。13.3）
- `SF_LOG_MAX_SECONDS`（取得役の上限。秒。既定 43200 = 12 時間）・`SF_LOG_TEST_FAST=1`（テスト用。間隔の下限を 1 秒にし、目を覚ます間隔と待ち時間を短くする）

## 4. 処理の流れ

### 4.1 共通（全サブコマンド）

```
 1. force-* ディレクトリの確認（lib/common.sh を source した時点で確認される）
 1a. 環境の判断（5.6）: 手元のファイル（.collector・.claim）だけを読む。別の環境が扱っていれば、status 以外はその場で終える
     （begin・start --auto・leave・collect は終了コード 10 か 0、ほかは die）。status は、続けて表示する
 2. sf の確認（check_sf_cli --cache）
 3. 接続先の決定（get_target_org。-o > SF_TARGET_ORG > sf org display の alias）
 4. 予約名の確認（is_reserved_org_alias）（10.1）
 5. 本番の確認（org_local_release_check。1=本番・2=確認できない）（10.1）
 6. 自分のユーザー ID の取得（sf org display --json）
```

- 4・5 は、`bin/sf-deploy.sh` と同じ順・同じ関数で行う
- 4・5 に当たったときの扱いは、手動は `die`、自動（`--auto`）は「取りません」を表示して終了コード 10（4.2）
- `auto on|off`・`status` は、4・5 を行わず、組織に書き込まない（`status` は、TraceFlag の表示に 3・6 を使う。`auto on|off` は、組織の ID を `.consent` に書くために、3 と `sf org display` の読み取りだけを使う）

- **組織の種類を確認できないとき**（`start`・`pull`。取らないのは同じで、理由を分ける）: 認証の期限切れ・取り消し → 10（`--auto` の理由に、ログインし直し方を添える。`die` には添えない）／組織の情報を読めない（通信・sf の一時的な失敗など） → 1（裏の準備は、30 秒後に 1 回だけやり直す）／読めたが種類を判定できない → 10。読めないときは、sf の応答の `name` と `message` の先頭を `sf-log.log` に残す（セッション ID の形は伏せる）

### 4.2 start（手動と自動）

```
 0. （自動のみ）GITHUB_ACTIONS=true なら、終了コード 10（Actions の上では取らない。人の開発の場ではないため）
    （自動のみ）このプロジェクトの答え（10.2）を読む
      なし → 確認する（10.2。read_key で Y/N。q・EOF は N）。答えを保存する
      「取らない」→ 終了コード 10（取りません）
 1. （手動のみ）AI への送信の注意を表示し、ask_yn || die（-y で省く。10.2）
 2. DebugLevel「sf_tools_log_<level>」を DeveloperName で探す
      あり → 7 章の値で上書きする（差分の判定はしない）
      なし → 7 章の値で作る
 3. 自分のユーザーの TraceFlag を探す（TracedEntityId = 自分。検索では LogType で絞らず、b で種類ごとに扱いを分ける。8.2）
      a. 状態ファイルの TRACE_FLAG_ID と一致し、TracedEntityId = 自分・LogType = USER_DEBUG のものがあり、ほかに有効な USER_DEBUG がない
           → DebugLevelId・StartDate（今）・ExpirationDate（今から --hours 時間）を更新
           （ほかに有効な USER_DEBUG があれば、延ばさずに b へ。手元に期限切れの自分の ID が残ったまま、別の場所が取り始めていると、
             延ばすと期間が重なって FIELD_INTEGRITY_EXCEPTION になる。2026-11-28 に実機で発生）
           （一致する ID があっても、TracedEntityId・LogType が違えば、自分が作ったものとみなさない。b へ）
      b. a に当たらなかったときは、いま有効な TraceFlag（StartDate が空か今以前、かつ ExpirationDate が今より後）を、種類（LogType）で分ける
           （同時に有効にできないのは、同じ対象・同じ種類で期間が重なるものだけ。種類が違えば（USER_DEBUG と DEVELOPER_LOG）同時に有効にできる。2026-11-23 に実機で確認。13.1）
           ・USER_DEBUG が 2 つ以上 → 手動: die／自動: 終了コード 10（Salesforce が重なりを拒否するため、ありえない状態。推測で触らない）
           ・USER_DEBUG が 1 つ
                → そのままでは、新しいものを作れない（同じ種類で期間が重なる。8.6）
                → 手動: 表示と確認（下の ※）のあと、止める。そのあと c へ
                → 自動で、DebugLevel が sf_tools_log_standard / sf_tools_log_detail（別の場所の sf-log.sh のもの）:
                     消して引き継ぎ、c へ（開始は今）。消せなければ、終了コード 1（何も作らない）。
                     --owner の sf-start がもう終了していれば、引き継がずに 10
                → 自動で、それ以外（人が設定画面で作ったもの・別の道具のもの）: 触らない。WARNING（ID・期限と、
                     「sf-log.sh start で置き換えられます」）を出して、終了コード 10（理由に、期限と置き換え方を書く）
           ・DEVELOPER_LOG（Developer Console が作ったもの）・ほかの種類（CLASS_TRACING など）→ 触らない（USER_DEBUG の作成とぶつからない）
           ・ない → c へ
           ※ 表示と確認: ID・DebugLevel の名前・開始・期限と、「設定画面などで作られた、このユーザーのログの設定です」を表示し、
               「止めてよいか」を ask_yn || die（-y で省く）
             止める = 期限を「元の期限」と「今から 2 分後」の早いほうにする（消さない。期限を今にはできない。元の期限が 2 分以内なら、更新しない。8.2）。
               更新の失敗 → die（新しい TraceFlag は作らず、状態ファイルも変えない）
           （期限切れ・これから始まるもの（StartDate が今より後）は、対象にしない）
      c. 作る（LogType=USER_DEBUG・ExpirationDate=StartDate から --hours 時間）。StartDate は、ふだんは今。b で止めたときは、止めたものの期限（縮めた後。縮めなかったときは元の期限）の 1 秒後。
         ただし、作る直前に今の時刻と比べ、その StartDate が今より前になっていたとき（＝止めたものの期限がもう過ぎている）だけ、今にする（止めたものは、もう有効でないため重ならない）。
         止めたものの期限がまだ先なら、StartDate を今に寄せない（重なって作成に失敗するため）
         失敗 → 手動: die／自動: 終了コード 1（状態ファイルは変えない）
           b で人の TraceFlag を縮めたあとに c が失敗したときは、縮めた期限を元に戻さない（人は「止めてよい」と確認済み）。
           die のメッセージと error.log に、縮めた TraceFlag の ID・元の期限・縮めた期限を、事実として書く
 4. 状態ファイル（9.2）に、組織・ユーザー ID・TraceFlag の ID を書く
    （取得・要約の時刻は、ない、または接続先が変わったときだけ、今で初期化する）
 5. 組織のログの量を表示し、多ければ WARNING（8.6）
```

**自動（`--auto`）の終了コード**: 0 = 取り始めた／10 = 取らない（答えが「取らない」・本番・予約名・種類不明・ほかの TraceFlag がある）／1 = 失敗。**どれでも、呼び出し側（sf-start.sh）は止まらない**（5.1）。自動では `die` を使わず、`ask_yn` も使わない（`q` で `die` するため、sf-start が中断してしまう）。

- 止める候補を USER_DEBUG だけにするのは、作ろうとする種類と同じで、期間が重なると作れないのが USER_DEBUG だけだから（2026-11-23 に実機で確認。13.1）。DEVELOPER_LOG（Developer Console）は、USER_DEBUG が有効なままでも作れ、その逆も同じだったため、人の Developer Console の設定には触れない
- **自動では、人・ほかの道具の TraceFlag に一切触れない。** 自動は確認の場面を作らない方針のため（確認なしで人の設定を変えない）。取れないときは WARNING で知らせ、人が手動の `start` で置き換えられるようにする
- **別の場所の sf-log.sh の TraceFlag は、自動で引き継ぐ（後から起動した sf-start を優先する。2026-11-28）。** 「触れない」の目的は人の設定を守ることで、sf-log.sh が作るものは DebugLevel の名前で見分けられる。それまでは、同じ Salesforce のユーザーで、別のフォルダ・別の PC の設定が残っていると（PC の再起動で後始末できなかったときも）、最大 2 時間取れなかった（2026-11-28 に Windows と Mac で発生。13.3）
  - 期限を縮めずに**消す**。すぐに作れる（2 分待たない）。縮めて残すと、古い取得役の延長（ID で探すため、期限切れでも見つかる）が、新しい方の終了のあとで、生き返らせることがある
  - 引き継ぎは `start --auto` のときだけで、取得役は取り返さない（2 か所が交互に取り合わない）。古い取得役は、気づいて止まる（4.3 の c2）
  - 同じアカウントを複数の人で使うと、後から始めた人が引き継ぐ（一人用の開発組織が前提。1.3）
  - 利用者が設定画面で DebugLevel「sf_tools_log_*」を使って作った TraceFlag は、見分けられない（同じ扱いになる）
  - この変更より前の版の取得役は、引き継がれても止まらない。消された TraceFlag を作り直すことはない（延長が失敗して WARNING を書く）
  - **実際の組織で、削除の直後に作れることは、まだ確かめていない**（偽の組織のテストだけ。13.1）
- 3b で消さずに期限を縮めるのは、人が作った設定（DebugLevel の割り当てなど）を、記録として残すため。期限を「今」にすると Salesforce が拒否する（今・今から 5 秒後は拒否、今から 60 秒後は受け付けた。2026-11-23 に実機で確認）ため、時計のずれも見込んで 2 分後にする。止めたものの期限までの最大 2 分のログも、同じユーザーのログなので、取得役が取る（その間は、止めたものの詳しさで出る）
- 「元の期限」と「今から 2 分後」の早いほうにするのは、元の期限が 2 分より短いとき、人の設定を延ばしてしまわないため
- c の `StartDate` を、止めたものの期限の 1 秒後にするのは、同じ種類で期間を重ねないため（期限ちょうどを重なりとみなすかは、まだ確かめていないため、1 秒あける。13.1）。止めたものの期限から c の作成までの間（sf の呼び出しの遅れ）は、どちらの TraceFlag も有効でないため、ログが出ない（数秒〜数十秒。13.1 の確認では、sf の 1 回の呼び出しが約 10 秒）
- これから始まる TraceFlag を対象にしないのは、期限を縮めると `StartDate` より前の期限になりうるため。そのような TraceFlag と期間が重なって c の作成に失敗したら、手動は `die`、自動は終了コード 1
- 作成の失敗の理由は、sf の JSON の応答の `name` で見分ける（重なり・期限の誤りは `FIELD_INTEGRITY_EXCEPTION`。2026-11-23 に実機で確認）。文言（`message`）では判定しない（ユーザーの言語で変わる。実機では日本語で返った）

### 4.3 collect（裏の取得役）

`sf-start.sh` が、`start --auto` の成功（終了コード 0）のあとに、裏で起動する（5.1）。人は打たない。

```
 1. 取得役の印（9.2 の .collector）を確かめる
      生きている取得役がいる（同じ組織）→ 何もせずに終了（ランチャーを 2 つ起動したとき。二重に動かさない。持ち主の一覧への登録は 5.1 で済んでいる）
      生きている取得役がいる（別の組織）→ その取得役に止まるよう頼み（9.3 の停止の依頼）、止まるのを最大 30 秒待つ
      いない・死んでいる → 印を、自分の PID・起動の時刻・組織で書き直す
 2. 繰り返す（5 秒ごとに目を覚ます）:
      a. 持ち主（9.2 の .owners。起動中の sf-start の一覧）を確かめる。死んでいる持ち主は一覧から外す（5.5）。
         一覧が空になった、または起動から 12 時間たった → 後始末（4.5 の 2〜4 と同じ）をして終了
      b. 停止の依頼がある・`.owners` に CLOSING がある・`.collector` の PID と起動の時刻が自分でない（別の取得役に入れ替わった・印が消された）
         → 組織には何もせずに終了（後始末は、依頼した側・入れ替わった側が行う。4.5）
         この確かめは、各回の最初と、組織に書き込む直前（d の延長の前）に必ず行う（止められた取得役が、消された TraceFlag を延ばし直さないため）
      c. 前回の取得から SF_LOG_INTERVAL 秒たった、pull の依頼（9.3）がある、または前回の取得で取り残しがある → 取得する:
           ・取得のロック（9.3）を取る。取れなければ（取得役がいないと思った pull が取得中）、この回は飛ばす
           ・前回の続き（取得のしおり。8.3）から、古い順に最大 50 本の一覧を取り、自分のログの本文を手元に保存する
             （ふだんは sf の 1 回の呼び出しでまとめて取る。8.4・9.1。置き換えで保存する。9.3）
           ・古い順に 1 件保存するごとに、しおり（LAST_FETCH・LAST_FETCH_ID）を進める（途中で止まっても、保存した分は取り直さない）
           ・50 本を超えて残っていれば、待たずに次の回で続きを取る（取り残しの本数の目安を .status に書く）
           ・追いついたら（残りがない）、pull の依頼の ID ごとに応答（9.3）を書く
      c2. 取得の回ごとに、自分の TraceFlag がまだ自分のものかを確かめる（取得のあと。引き継がれる前のログは取り終えている）:
           ・自分のものが有効でなく、別の sf_tools_log_* の有効な USER_DEBUG がある → 引き継がれた。組織には書き込まず、
             .state の TRACE_FLAG_ID を空にし、.collector・名乗りを消し、.status を stopped（理由つき）にして終了。
             持ち主の一覧は残す（終了時の leave と、ランチャーの Start で取り戻すため）
           ・自分のものがないだけ（人が消した・相手がもう終わった） → 作り直さない。WARNING を書き、取得は続ける
           ・期限が切れただけで、相手がいない（PC のスリープなど） → d へ（延ばして、また有効にする）
           ・組織の切り替えの最中（.state の ORG が違う）・問い合わせの失敗 → 判断しない
      d. TraceFlag の残りが 60 分未満なら → 今から 2 時間に延ばす（4.2 の 3a と同じ確かめ方。自分が作ったものだけ）
           延ばせない（自分の TraceFlag が消えた・ほかの TraceFlag に置き換わった）→ .status に WARNING を書き、取得は続ける
      e. 失敗したら、次の取得までの間隔を倍にする（最大 600 秒）。成功したら元に戻す。失敗の内容は .status と sf-log.log に書く
```

- **取得役は、取りこぼさない**（古い順に、しおりから続きを取る）。取得役は止まらずに動き続けるため、新しいほうを優先して古いものを飛ばす必要がない。新しいほうを優先するのは、要約に入れるログを選ぶとき（`pull --max`）だけ（4.4・13.3）
- 起動から 12 時間で止まるのは、PID の再利用（5.5）などで、持ち主の見張りが働かなかったときの上限。止まったら `.status` に「12 時間で止まりました。sf-start をやり直すと再開します」と書く
- 取得役の出力は、画面に出さない（ランチャーの表示を乱さないため）。`sf-log.log` と `.status` にだけ書く
- 取得役は、組織への書き込みを、自分の TraceFlag を延ばすことと、持ち主がいなくなったときの後始末に限る（作る・引き継ぐは、`start` が行う）。c2 の確認のため、取得の回ごとに、sf の問い合わせが 1 回増える
- 5 秒ごとに目を覚ますのは、pull の依頼にすぐ応えるため。目を覚ますだけで、sf は呼ばない（sf を呼ぶのは、c と d のときだけ）
- `sleep` は `run` を使わない（待つだけ。その行にコメントで理由を書く。CLAUDE.md 2.1）

### 4.4 pull（AI が実行する）

```
 1. 引数（--since・--max）の形を確かめる。要約の状態（9.2 の LAST_READ_LINE・LAST_READ_ID）は、ここでは読まない
    （3 で、要約のロックを取ってから読む。ロックの前に読んだ値は使わない。同時に動く pull が、先にしおりを進めることがあるため）
 2. 取得役が生きているか（9.2 の .collector）
      生きている → 自分の ID を付けた pull の依頼を書き（9.3）、同じ ID の応答を最大 90 秒待つ
                    応えた → 3 へ
                    応えない → WARNING（「取り込みが終わっていません（残り約 N 本）」）を出して 3 へ（手元にある分で要約し、要約の先頭にも書く）
      いない → 自分で取得する（4.3 の 2c と同じ方法で、追いつくまで繰り返す。最大 200 本。超えたら、残りがあることを要約の先頭に書く）。
               取得の間は、取得のロック（9.3）を持つ（同じ時に取得役が起動しても、二者で同じログを取らないため）。失敗 → die
 3. 要約のロック（9.3。logs/apex/.read.lock。最大 90 秒）を取る。取れなければ、しおりを読まず・進めずに、目録の全行から、直近 30 分（--since があれば直近 N 分）に始まったログで要約する（WARNING。要約の先頭にも書く）。
    ロックを取ったら、要約の状態（LAST_READ_LINE・LAST_READ_ID）を読み、目録（.index）を 1 回だけ読む（最後まで書き終わった行（改行で終わる行）だけを使う）。
    LAST_READ_LINE が 0 で LAST_READ_ID が空なら「まだ何も見ていない」（目録の全行を選ぶ）。LAST_READ_LINE 行目のログの ID が LAST_READ_ID と同じなら、そのまま使う。違えば（目録を手で直した）、目録から LAST_READ_ID の行を探し、その行番号を使う。
    選び方は、次の 3 つのどれか（開始時刻ではなく、目録に足された順で選ぶ）:
      --since のとき          : しおりは使わない。目録の全行から、直近 N 分に始まったログを選ぶ
      しおりが使えないとき    : （ない・形式が正しくない・LAST_READ_ID が見つからない）WARNING を出し、目録の全行から、直近 30 分に始まったログを選ぶ
      それ以外                : LAST_READ_LINE 行目より後のすべての行のログを選ぶ
    （目録に足された順で選ぶのは、遅れて現れ、あとから拾い直したログ（8.3）は、開始時刻が、前回の要約に入れたログより前のことがあるため。2026-11-24）。
    --max を超えたら、開始時刻の新しいほうから。入れなかった本数・時間帯と、入れ方（pull --since）を要約の先頭に書く（手元にあるので、いつでも入れ直せる）。
    要約の中の並びは、開始時刻の順
 4. 要約を作る（node lib/apexlog.js。6 章）→ summaries/<時刻>.md と latest.md に書く（9.1）
 5. 4 が成功したときだけ、LAST_READ_LINE・LAST_READ_ID を、3 で読んだ目録の最後の行の番号と、その行のログの ID に進める
    （--max で入れなかったログも「見た」に含める。入れ方は要約の先頭に書いてある）。--since のときは進めない。
    3 で読んだあとに足された行は、次の pull が選ぶ（読んだ内容だけで、選ぶ行と進める番号を決めるので、間の行を飛ばさない）。
    書き込んだら（4 が失敗したときも）、要約のロックを外す
 6. 画面に、要約の 1 行目（件数・エラーの数・入れなかった本数）と、latest.md のパスを表示する
```

- `pull` は、組織には書き込まない（読み取りのみ）。AI が、確認なしで何度呼んでもよい
- **`pull` を同時に 2 つ動かしたとき**（AI のセッションを 2 つ開いているなど）: 3 の要約の状態と目録の読み取りから 5 の `LAST_READ_LINE`・`LAST_READ_ID` の書き込みまでを、**要約のロック**（`logs/apex/.read.lock`。取得のロックとは別。9.3 と同じ作り方）で 1 つずつにする。しおりは、**ロックを取ってから読む**（1 では読まない）ので、あとの `pull` は、先の `pull` が進めたしおりから読む（同じログを 2 回要約しない・しおりを戻さない。Codex の指摘で、読む位置を 3 に移した。2026-11-24）。ロックは最大 90 秒待ち、取れなければ、しおりを読まず・進めずに、直近 30 分（`--since` があれば直近 N 分）で要約する（WARNING。要約の先頭にも書く）。要約のロックの中では、組織から取らない（取るのは 2 の段階で、取得のロックの中）。2026-11-24 に、Codex の指摘で追加
- TraceFlag の期限が切れている・取得役が動いていないときは、要約の先頭に書く（AI が、人に `sf-start` のやり直しや `sf-log.sh start` を頼めるように）

### 4.5 stop

```
 1. 取得役が生きていれば、停止の依頼を書き（9.3）、止まるのを最大 30 秒待つ（止まらなければ、TERM で止め、さらに最大 10 秒、止まったことを確かめる）
      それでも生きている（kill -0 と、印の起動の時刻で確かめる。5.5）→ TraceFlag は消さない（残った取得役が延ばし直すおそれがあるため）。
      WARNING（「取得役が止まりません（PID …）。TraceFlag は残しました（最大 2 時間で切れます）」）を出して終了する（2〜4 は行わない）
 2. 状態ファイルの TRACE_FLAG_ID を読む
      ない → 「sf-log.sh が作った TraceFlag はありません」を表示して 4 へ（何も消さない）
 3. その ID の TraceFlag を消す（すでにない場合は、WARNING を出して続ける）
 4. 状態ファイルの TRACE_FLAG_ID と、取得役の印と、持ち主の一覧を消す。DebugLevel は消さない（次の start で使い回す）。手元のログは消さない（9.4）
```

- **`stop` は、状態ファイルに記録した ID 以外の TraceFlag を、検索して消すことはしない**（Developer Console などが作ったものを消さないため）
- `sf-start.sh` の終了時にも、同じ処理を行う（5.2）

### 4.6 status

取得役の状態（動いているか・組織・最後に取った時刻・取った本数・直近の WARNING）、自分のユーザーの TraceFlag の一覧（sf-log.sh が作ったものか・種類・期限）、前回の pull の時刻、自分のログの件数と合計サイズを表示する（読み取りのみ）。

### 4.7 auto on|off

このプロジェクトの答え（10.2）を書き換える。組織には触れない。`off` にしても、動いている取得役は止めない（次の `sf-start` から効く。今止めたいときは `stop`）。

## 5. sf-start.sh・ランチャーとのつなぎ

### 5.1 sf-start.sh の起動時

`sf-start.sh` の処理の流れの 5（sf-refresh.sh の裏での起動）と 7（ランチャーの起動）の間（6）に、次を足す。**sf-start の前面では、sf を呼ばない**（ランチャーを待たせないため。2026-11-23。13.3）。

```
 a. ~/sf-tools/bin/sf-log.sh がなければ、何もしない
 b. 持ち主の印を決める
      環境変数 SF_LOG_OWNER（「PID:起動の時刻:環境の名前と乱数」。5.6）があり、その PID が生きている（ランチャーの Start・SwitchOrg からの入れ子の sf-start）
        → それを使う（後始末は外側が行う）
      それ以外 → 自分の印を作り（乱数の頭に、環境の名前 RUNTIME を付ける。5.6）、export SF_LOG_OWNER=…
 c. bash sf-log.sh begin -o <エイリアス> --owner "$SF_LOG_OWNER" を実行する（前面。sf を呼ばない）
      begin: GitHub Actions 上・予約名 → 10。手元の答え（10.2）で「取らない」→ 10（初めて・エイリアスが変わったときは、ここで Y/N を聞く）。
             持ち主の一覧（.owners）に印を足す（後始末の最中は最大 60 秒待つ）。.status を starting にし、
             start --auto --collect --retry 1 を nohup で裏に起動して、0 で終わる
      裏の start --auto: 本番・種類を確認できない組織 → 10。答えの組織 ID と違う → 10（答えを消す）。DebugLevel・TraceFlag を準備して、
             .status を collecting にし、そのまま collect（取得役）になる（exec）。取らない・失敗は、.status に理由を書く。
             失敗（終了コード 1。「取らない」の 10 は除く）は、持ち主が生きていれば、.status を starting に戻して「やり直しています」を書き、
             30 秒後に 1 回だけやり直す（--retry。sf の一時的な失敗で、その日の取得が抜けないため。13.3）
    sf-start は、begin の終了コードで分ける: 0 → 自分の印なら、終了時に leave する（5.2）／10 → 何もしない（理由は sf-log.sh が表示）／
    それ以外 → WARNING「デバッグログの準備を始められませんでした」。どの場合も、ランチャーの起動に進む（ログの取得の失敗で、開発を止めない）
```

- 持ち主の印に、PID だけでなく起動の時刻と乱数を入れるのは、同じ PID の印が重ならないようにするため（生死は `kill -0` だけで見る。5.5）
- 持ち主の一覧への登録は、sf-start ではなく `begin`（と `start --auto --owner`）が行う。ロックと CLOSING の待ちを、sf-log.sh の 1 か所にまとめるため。同じ印は 2 回足さない（入れ子の sf-start）
- `begin` の確認（10.2）は、`read_key` で Y/N を聞く（`q` は「取らない」。端末でなければ聞かない。`read_key` の EOF の `die` で sf-start を止めないよう、`$( )` の中で呼ぶ）
- **裏での起動**: `nohup bash sf-log.sh start --auto --collect --retry 1 … </dev/null >/dev/null 2>>"$LOG_FILE" &` のあと `disown` する（端末の入力・出力から切り離し、端末を閉じたときの SIGHUP で一緒に止まらないようにする。止めるのは、持ち主の見張りと 5.2 の後始末）。Ctrl+C の無視（`trap '' INT`）も引き継がれる。Windows の Git Bash では効くことを確かめた（13.1）。`nohup` では `$!` と、取得役が記録した PID が違うため、取得役の生死は `.collector` の PID で見る
- `sf-start.sh` の冒頭コメント（【処理の流れ】）に、この流れを書く（CLAUDE.md 2.5）
- **sf の更新との競合**: sf-start は、`sf-refresh.sh`（24 時間ごとに、その中で `sf-update-cli.sh` が `npm install -g @salesforce/cli@latest`）と `begin` の裏の準備を、同時に動かす。sf の入れ替えの途中に sf を呼ぶと、部品が見つからずに失敗する（2026-11-24 に WSL で発生。13.3）。そこで、`sf-update-cli.sh` は動いているあいだ、ロック `~/.sf-tools-upgrade.lock`（`PID=<数字>`）を置き、`start` は最初に、その PID が生きているあいだ待つ（最大 10 分。`.status` の WARNING に「sf の更新が終わるのを待っています」。待つあいだに持ち主がいなくなれば、準備をやめる）。取得役も、更新中は取らずに次に回す。ロックができる前に準備が sf を呼んで失敗したときは、30 秒後のやり直し（`--retry`）が、ロックを待ってから動く

### 5.2 sf-start.sh の終了時（ランチャーを q で閉じたとき）

- `sf-start.sh` の `trap ... EXIT` で、**自分が持ち主の一覧に足した印があるときだけ**、`bash sf-log.sh leave --owner "$SF_LOG_OWNER"` を実行する
  - `leave`（内部用）: 一覧から自分の印を外す。一覧が空になったら、`stop` と同じ処理（取得役を止め、自分の TraceFlag を消す）を行う。ほかのランチャーがまだ起動していれば、何も止めない
  - **止めている最中に、新しい sf-start が来たとき**（後始末と登録の重なり）:
    - `leave` は、ロックの中で一覧を空にしたとき、同じロックの中で `.owners` に `CLOSING=<自分の印>` を書いてから、ロックを外して後始末をする（sf を呼ぶ間は、ロックを持たない。9.3）。後始末が終わったら、ロックの中で `CLOSING` を消す
    - 新しい sf-start（5.1 の b の登録）は、ロックの中で `CLOSING` を見つけたら、登録せずにロックを外し、`CLOSING` が消えるのを最大 60 秒待ってから、登録をやり直す。`CLOSING` の印の持ち主が死んでいれば、古いものとして消して進む
    - これで、古い後始末が、新しいランチャーの TraceFlag を消すことはない（新しい sf-start の `start --auto` は、後始末が終わってから動く）。60 秒待っても消えなければ、WARNING を出し、今回は取らない（`.status` に理由を書く）
    - 人が打つ `stop` も、同じく `CLOSING` を書いてから後始末をする
- `leave` は、自分の印を外したあと、死んだ持ち主の印を除いてから、残りを数える（4.3 の 2a と同じ確かめ方）。PC の再起動などで後始末できずに終わった印は、取得役がいないと残ったままになり、数えると、最後の sf-start を終了しても TraceFlag を消さない（2026-11-28 に再現）
- 入れ子の sf-start（sf-switch-org から。印を外側から引き継いだ）は、終了時に何もしない
- 後始末の失敗は、WARNING だけ（終了コードは、今までどおり 0）
- `leave` の出力は、`sf-start.sh` が必ず表示する（消した・ほかの sf-start がいるので残した（残りの件数）・消せなかった）。以前は出力を捨てていたため、残ったことに、画面では気づけなかった（2026-11-28）
- 人が打つ `stop` は、持ち主の一覧にかかわらず止める（人の判断のため。一覧も空にする）

### 5.3 組織の切り替え（sf-switch-org）

- `sf-switch-org.sh` は、ランチャーの中から、`FORCE_RELOGIN=1` で `sf-start.sh` を入れ子で呼ぶ（ランチャーは二重に起動しない）
- 入れ子の sf-start は、5.1 の b で外側の印を引き継ぎ、新しい組織で `start --auto` を行う
  - 0 → `collect` を裏で起動する。`collect` は、前の組織の取得役に停止を頼んで入れ替わる（4.3 の 1）
  - 0 以外 → 前の組織の取得役にも停止を頼む（つないでいない組織のログを取り続けないため）。`.status` に「取れていません（組織を切り替えたため・理由）」を書き、ランチャーに表示する（5.4）。前の組織に戻すことはしない（接続先は、もう新しい組織のため）
- 前の組織の TraceFlag は、入れ替わりのときに消す（`.state` に残る前の組織の `TRACE_FLAG_ID` を、前の組織のエイリアスで消す）。前の組織の認証がもうない（同じエイリアスで別の組織にログインし直した）などで消せなければ、WARNING（2 時間で自然に切れる）

### 5.4 ランチャーの表示

- ランチャー（`phases/start/launcher.sh`）のメニューの上の 1 行目に、`logs/apex/.status` から、ログの状態を短く表示する（例: `Log: 取得中 (15:30/23本)`／`Log: 取っていません`。WARNING は `⚠ Log: …` の 1 行。2026-11-27 に、見出しの 2 行の形に変えた。正本は `phases/start/launcher.sh` の冒頭コメント）
- ランチャーは `lib/common.sh` を読まない単独の設計のため、`.status` は `キー=値` の行にして、`while read` で読めるようにする（9.2）。ファイルがなければ、何も表示しない
- 取得中（`collecting`）のあいだも、同じく `STATE` が変わったら描き直す（本数・期限の更新では描き直さない。別の場所に引き継がれて止まっても、古い「取得中」が残るのを防ぐ。2026-11-28 に実機で発見）

- `begin` は「取得中」を書くとき、今日の本数（`COUNT_TODAY`）も数え直して書く（ランチャーは「取得中」に変わった時点で 1 回だけ描き直すため、前回の値が残ると「今日 0 本」のままになる。2026-11-24 に実機で発見）
- メニューの番号・動きは変えない

### 5.5 異常終了（ウィンドウを × で閉じた・PC が止まった）

| 起きること | 結果 |
|---|---|
| sf-start の後始末（5.2）が動かない | 取得役が、持ち主の見張り（4.3 の 2a）で、死んだ持ち主を一覧から外す。一覧が空になれば、自分で後始末をして止まる |
| 取得役も一緒に止まった | TraceFlag を延ばす役がいなくなるため、**最大 2 時間で自然に切れる**（期限を短くしている理由） |
| 取得役の印・持ち主の一覧が残った | 次の sf-start で、印の PID が死んでいれば、書き直して起動する（4.3 の 1）。死んだ持ち主は外す |
| 死んだ sf-start の PID が、別のプロセスに再利用された | `kill -0` だけでは「生きている」に見える。**生死は `kill -0` だけで見る**（`ps` での起動の時刻の比べ方は、OS ごとに違い、Windows の Git Bash で確かめる手段が乏しいため、使わない。2026-11-23。13.3）。その代わり、取得役は起動から 12 時間で必ず止まる（4.3）。そのあと TraceFlag は最大 2 時間で切れる |

- 持ち主の見張り（`kill -0`・`ps` での起動の時刻）が、Windows の Git Bash・macOS・Linux で期待どおりに動くかは、実機で確かめる（13.1）

### 5.6 環境の混在（Windows の Git Bash と WSL。2026-11-24 に追加）

- **背景**: 同じ force-* を、Windows の Git Bash と WSL（`/mnt/c/…`）の両方から開ける。`logs/apex/` のファイルは両方から見えるが、プロセスの番号（PID）の空間が別のため、`kill -0` で相手の環境のプロセスの生死が分からない（見えない PID は「死んでいる」、たまたま同じ番号があれば「生きている」に見える）。そのため、混ぜると次が起こりうる（2026-11-24 にコードを読んで見つけた。実機ではまだ起きていない）:
  - 別の環境の `pull` が、動いている取得役を「いない」とみなし、自分でも組織から取る（取得が 2 か所でぶつかる）
  - 別の環境の `begin` が、取得役を「いない」とみなし、2 つ目の取得役を立てる。持ち主の見張りが、相手の環境の sf-start を「死んだ」とみなして外し、取得役が止まって TraceFlag を消す
  - ロック（`.lock`・`.fetch.lock`・`.read.lock`）の持ち主を「死んだ」とみなし、使用中のロックを奪う
- **方針: 1 つのプロジェクトのログは、同時には 1 つの環境だけが扱う。取得役が動いている環境（扱っている環境）以外からは、`status` だけを答え、ほかは何もしない**（ファイル・ロック・組織に触れない）。別の環境からの依頼・停止・ロックの譲り合いのような「協力」はしない（最初の案では協力していたが、Codex のレビューで、合図の途切れ・ロックの古さ・停止の完了の見分けに、穴が多く見つかったため。13.3）。AI 向けの手順書（`doc/ai-dev-loop.md`）にも、「sf-start と同じ環境で実行する」と書く
- **環境の名前（`RUNTIME`）**: `lib/platform.sh` の `detect_runtime` が、次の順で決める。`$OSTYPE` が msys・mingw・cygwin で始まる → `gitbash`／darwin で始まる → `macos`／linux で始まり、`/proc/version` に microsoft を含む（大文字と小文字を区別しない）→ `wsl`／linux で始まる → `linux`／それ以外 → `unknown`。比べるときは、文字列が同じかだけを見る。ただし `unknown` は、`unknown` 同士でも同じ環境とみなさない（常に「環境不明」）。記録の `RUNTIME` が、この 5 つ以外の値・不正な形なら、「環境不明」として扱う（分からないものは、扱っているかもしれない側に倒す）。**自分の環境が `unknown` のときは、この節の判断をしない**（これまでの動き。自分の記録も「環境不明」になり、自分の取得役を自分で「別の環境」とみなしてしまうため。`unknown` は、対応していない OS だけ。記録には `unknown` と書くので、ほかの環境からは「環境不明」に見え、安全側になる）
- **記録するもの**（時刻は、ファイルの中に書いた値で比べる。ファイルの更新時刻は使わない。`/mnt/c` の更新時刻の不確かさと、OS ごとの `stat` の違いを避けるため）:
  - `.collector` に `RUNTIME` と `HEARTBEAT`（生きている合図。UTC のエポック秒）。取得役が、5 秒ごとに目を覚ますたび・sf を呼ぶ直前・ログを 1 本保存するたびに書き直す（sf を呼んでいるあいだ、合図が長く途切れないようにする。ただし、前に書いてから 30 秒より短いときは書かない。目安の 30 分より十分に短く、`/mnt/c` への書き込みを減らすため）
  - ロックのフォルダの `pid` ファイル: `<PID> <RUNTIME> <取った時刻（エポック秒）>` の 1 行。フォルダの中で、一時ファイルに書いてから置き換える（書きかけを読ませない）
  - 持ち主の印（`PID:起動の時刻:環境の名前と乱数`）。乱数の頭に、環境の名前を付ける（例 `1234:1795500000:wsl8f3a`）。sf-start が作る（印の形の検査（英数字）は、そのまま通る）
  - **扱う環境の名乗り** `.claim`（`RUNTIME=<環境>`・`OWNER=<名乗った sf-start の印>`・`AT=<名乗った時刻（エポック秒）>`）。`begin`・`start --auto` が、持ち主の登録と同じ短いロック（`.lock`）の中で書く。同じ環境の名乗りがすでにあり、その `OWNER` の持ち主が生きていれば、`OWNER` は書き換えずに `AT` だけ今にする（ランチャーからの入れ子の sf-start・同じ環境の 2 つ目の sf-start。`AT` を今にするのは、取得役が立つまでの名乗りが、途中で古くならないため。持ち主が死んでいれば、自分の印で書き直す）。取得役が、合図（`HEARTBEAT`）と一緒に `AT` を書き直す（名乗りがない・古い別の環境のものなら、自分の環境で書く）。後始末（5.2）が成功したら消す。消すのは `.owners` を消したあと（先に消すと、そのあいだに別の環境が名乗って登録した印を、`.owners` の削除が消してしまうため。2026-11-24 の実装で見つけた）。取り始めに失敗して取得役が立たないとき（`start --auto` が終了コード 1・10 で終わり、やり直しもしないとき）は、`.lock` の中で、`OWNER` が自分の印と同じで、かつ、持ち主の一覧（`.owners`）に、同じ環境のほかの印がないときだけ消す（同じ環境の別の起動が、その名乗りを使っているため）。取得役が立つ前（`begin` から取得役の起動まで。sf の更新待ち（最大 10 分）とやり直しを含む）も、扱う環境を決めておくため
- **「別の環境が扱っている」の判断**（1 つの関数にまとめる。分からないものは「扱っているかもしれない」に倒す。ただし、取得役は起動から 12 時間で必ず止まる（4.3）ので、それより古い記録は、止まったものとみなす）。上から順に見る:
  1. `.claim` がある・`RUNTIME` が自分と違う・`AT` が 30 分以内（または読めない・未来の時刻）→ 別の環境が扱っている
  2. `.collector` がない → （1 に当たらなければ）扱っている環境なし
  3. `.collector` の `STARTED` が読めない・12 時間より古い → 止まったものとみなす（扱っている環境なし）
  4. `RUNTIME` がない（この変更の前の取得役。`PID`・`STARTED`・`ORG` だけ）→ `kill -0` の結果によらず、「環境不明が扱っている」とみなす（`STARTED` から 12 時間まで）。環境の記録がないため、`kill -0` が生きていても、別の環境の同じ番号の PID かもしれない（分からないものは、扱っているかもしれない側に倒す）。同じ環境で古い取得役が動いているなら、それがログを取り続けるため、取れなくなることはない
  5. `RUNTIME` が自分と同じ → これまでどおり `kill -0`（同じ環境）
  6. `RUNTIME` が自分と違う → `HEARTBEAT` が 30 分以内、または読めない・未来の時刻 → 別の環境が扱っている。30 分より古い → 止まったものとみなす
  - 30 分にするのは、sf の 1 回の呼び出し（ふつうは 1 分以内）の途中は合図を書けないため。30 分を超えて戻らない sf は、すでに異常な状態として扱う（止まったのに気づくのが遅れても、別の環境は何もしないだけなので、危険は小さい）
- **判断する時点**: 各コマンドの最初（4.1 の 1a。sf の確認（`check_sf_cli`）・組織への問い合わせ・ロック・状態の書き込みより前。読むのは `.collector`・`.claim` だけ）と、`begin`・`start --auto` が名乗りと持ち主の登録をする短いロック（`.lock`）の中で、もう一度。ロックの中で、別の環境が扱っていなければ、`.claim` を自分の環境で書いてから、持ち主を登録する（2 つの環境で、ほぼ同時に sf-start しても、あとの環境は名乗れず、持ち主も登録しない）。取得役の起動（`collect`）も、印を書く短いロックの中で、もう一度判断する。別の環境が扱っていれば、`status` 以外は、その場で終える
- **別の環境が扱っているときの、各コマンドの動き**:
  - `begin`（sf-start）: 取り始めずに終了コード 10。「別の環境（wsl）で、デバッグログを取っています。この環境では取りません」と表示する。`.status`・`.owners`・ロックに触れない（扱っている環境の表示を、上書きしない）
  - `start --auto`: 終了コード 10（同じ表示。何も書かない）。`start`（手動）・`pull`・`stop`・`auto`: 中断する（`die`。メッセージは事実だけ: 「別の環境（wsl）で、デバッグログを取っています」）
  - `leave`: 何もせずに 0 で終わる（この環境では、印を登録していないため）
  - `collect`（取得役の起動）: 何もせずに終わる（2 つ目を立てない）
  - `status`: 「取得役: 別の環境（wsl）で動作中（最後の合図は N 秒前）」と、`.status` の内容を表示する（組織への問い合わせは、読み取りだけなので、これまでどおり行う）。`.status`・`.collector`・`.claim` が読めない・形が違う・合図の時刻が分からないとき、`.status` の `ORG` がいまの接続先と違うとき（別の組織の古い記録）は、「取得中」と言い切らず、「状態不明」（理由を添える）と表示する。名乗り（`.claim`）はあるが、取得役（`.collector`）がまだないときは、「取得役の起動待ち（環境・名乗りは N 秒前）」と表示する。組織への問い合わせ（TraceFlag の表示）に失敗したときは、その旨を表示し、手元の状態の表示は続ける
- **同じ環境どうし**: これまでどおり（`kill -0`）。ロックの古さの判断は、`pid` ファイルの `RUNTIME` が自分と同じ（または、ない）ときだけ、PID の生死で行う。`RUNTIME` が違うロック（別の環境の残り）は、取った時刻から 10 分より古いときだけ、残ったロックとして消す。`pid` ファイルがない・形が違う・時刻が未来のロックは、奪わずに待つ。待つのは、それぞれのロックのこれまでの上限まで（短いロック `.lock` は約 10 秒・取得のロックは最大 90 秒・要約のロックは最大 90 秒）。上限まで待っても取れなければ、そのコマンドの「ロックが取れない」の扱い（手動のコマンドは「ロック（<パス>）が残っています」と事実だけを表示して中断。取得役はその回を飛ばす）。残ったロックの手での片付け方（フォルダを消す）は、文書サイトのトラブルの対処に書く
- **持ち主の見張り**（4.3 の 2a）: 印の環境が自分と違えば、残りとして外す。別の環境は、名乗り（`.claim`）が取れなければ、持ち主として登録しない（同じロックの中で判断する）。そのため、取得役から見た別の環境の印は、前に別の環境で使ったときの残りだけ。外しても、動いている別の環境の sf-start に影響しない（Codex の 2・3 回目のレビューの指摘。3 回目で、名乗りがないとほぼ同時の sf-start で別の環境の印が登録される、と分かり、名乗りを足した）。環境の名前のない古い印は、これまでどおり `kill -0` で見る
- **環境の切り替え**: 扱っている環境で sf-start を終える（5.2 の後始末で、取得役が止まり、`.collector`・`.claim` が消え、TraceFlag が消える）→ 別の環境で sf-start する。後始末をせずに止まった（ウィンドウを × で閉じた・PC が止まった）ときは、合図と名乗りが 30 分以上途絶えたあと（古い形の記録なら、起動から 12 時間のあと）に、別の環境で始められる。急ぐときは、扱っていた環境で `sf-log.sh stop` を実行する
- **移行の限界**: この変更の前に起動した取得役は、`RUNTIME`・`HEARTBEAT` を書かない。上の判断で、別の環境からは「別の環境（不明）が扱っている」とみなす（安全側）。同じ環境で、古い取得役が後始末をせずに止まった場合も、同じく、起動から 12 時間は取り始めない（待てないときは、`logs/apex/.collector` を手で消す。文書サイトのトラブルの対処に書く。`die` には復旧の案内を書かない決まりのため）。sf-tools を更新したら、各環境で sf-start を終えてから起動し直すのが確実（文書サイトに書く）
- **限界**: 同じ環境どうしの PID の再利用（5.5）は、そのまま。時計のずれが 30 分を超えると、扱っている環境の取得役を「止まった」とみなすことがある（その場合も、取得役は 12 時間で止まり、TraceFlag は最大 2 時間で切れる）
- 実機で確かめること（13.1）: WSL で取得中に、Windows の Git Bash から sf-start・`pull`・`stop`・`status`／その逆／片方の取得役が止まって 30 分たったあとに、もう一方で sf-start／2 つの環境で、ほぼ同時に sf-start

### 6.1 方針

- 要約は Markdown。AI がそのまま読める形にする
- **エラーを先に、正常な情報を後に**書く。AI が最初の数十行で状況を掴めるようにする
- 本文への行番号つきの参照（`<ファイル>:<行>`）を付け、必要なら AI が本文の該当箇所だけを開けるようにする
- 要約の大きさに上限を付ける（目安 200 行。超えたら、同じ内容の繰り返しをまとめ、残りの件数だけを書く）
- **取れていないものを隠さない**: 要約に入れなかったログ（4.4 の 3）・取り込みの残り（8.3）・20MB で切られたログ・出なかった区分（6.3）・TraceFlag の期限切れ・取得役の停止とその理由は、先頭に書く

- 一覧の「操作」の括弧には、最初の CODE_UNIT に加えて、そのログの中のフロー・入力規則の名前を添える（例: `/services/data/v68.0/sobjects/Account（Validation:Account:new／フロー: Account_After_Save／入力規則: Account_Check）`）。1 回の保存が何本かのログに分かれ、最初の CODE_UNIT だけでは、フローを含むログが入力規則の処理に見えるため（6.3）
- **1 には、保存を止めたものを、すべて入れる**（例外・致命的なエラー・フローのエラーに加えて、フローのカスタムエラーと入力規則の停止。見出しのエラーの数にも数える）。AI は 1 が「なし」なら、止まった原因を探さないため（2026-11-25 の実証テストで、入力規則の停止 3 件は 4 にだけ出て、カスタムエラー 2 件はどこにも出ず、1 が「なし」・見出しが「エラー 0」になった）。4 には、入力規則ごとの評価・通過・停止の数だけを書き、停止の一覧は重ねない
  - フローのカスタムエラー（Custom Error 要素）は、レコードトリガーフロー（保存前・保存後・削除前）でだけ使え、実行すると、もとの変更を巻き戻す（公式の Custom Error Element・Default Flow Error Handling）。そのため、要素を実行したら「保存を止めた」と読む。文言はログに出ないので、フローと要素の名前を書き、定義を見るよう案内する
  - エラーは「種類と文言」でまとめるため、カスタムエラーの文言にはフローと要素の名前、入力規則の停止の文言には規則の名前を入れる（別の要素・規則を 1 つにまとめない）
- 4 のフローは、完了の行がない実行（エラーで止まった・ログの終わりで切れた）があるため、成功の数を推し量らず、開始・完了・エラーの行の数だけを書く。カスタムエラーで止めた実行にも完了の行が出るため、エラーの数に「うちカスタムエラー N」と添える
- 4 の**画面フロー**: 開始の終わり（`FLOW_START_INTERVIEW_END`）まで進み、完了もエラーもない実行を「画面待ち N」と数える。前の画面の続きの要求（開始の行がなく、要素の行だけがある）は、全部のログの実行の ID で開始したフローに結び、「続き N」と数え、その要素もフローの要素に入れる（ログ 1 本・実行 1 つにつき、続き 1）。開始したログが要約の対象にないときは、結ばない（推測しない）。画面待ち・続きは、あるときだけ書き、一覧の下に説明の行を 1 つ書く。正常に終わった画面フローが「完了 0」に見え、AI が「途中で止まった」と読み違えるのを防ぐため（2026-11-26 の実証テスト）
- 2 の所要は、一覧（8.3）の `DurationMilliseconds` をそのまま書く。ただし、ログの中の経過（行の `(<ナノ秒>)` のいちばん大きい値。処理の始まりからの経過）より **1 時間以上長い**ときは、`346530840ms（ログの中は 9835ms ※）` のように添え、表の下に「実際の所要ではない可能性」と書く。2026-11-25 に tama-dev で、操作が `N/A`（`ENTERING_MANAGED_PKG` の行だけ・Location は Monitoring）のログで、ログの中が約 10 秒なのに、ApexLog の `DurationMilliseconds` が 346530840（約 96 時間）だった（組織に問い合わせて、Salesforce の値そのものと確かめた）。普通のログは、Salesforce の値がログの中の経過の数倍（小さいログでは 100 倍）で、差は大きくても約 21 秒だったため、倍率ではなく差で見る。読めないログは比べない
- 4 の重複ルールは、**保存の中**（`DML_BEGIN`〜`DML_END` の中）と**保存の後**（保存のあとの、記録のための検出。巻き戻したあとにも出た）を分けて数える（足し合わせると、同じ保存を二重に数えるため）。一覧の「操作」の括弧には「重複: ルール名」を添える

  - イベントの行は `<時刻> (<ナノ秒>)|<種類>|<項目>|…`。**時刻は、ログのユーザーのタイムゾーン**（UTC ではない。`USER_INFO` の行にタイムゾーンが出る）
    - 要約では、行の時刻を、日付のない「その日の時刻」として表示するだけに使い、UTC に直さない。ログがいつ始まったかは、一覧（8.3）の `StartTime`（UTC）を正とする
    - `USER_INFO` の行がない・タイムゾーンを読めないときは、時刻を推測で直さず、「タイムゾーン不明」と添えてそのまま出す

- テストには、実ログをもとに手で作った小さな見本（実データを含まない）を使う。見本は、確かめたログの形に固定する
- 要約は、上の区分のうち 1 行も出なかったものを「該当する行なし（詳しさが足りずに出なかった可能性もある）」と書く（エラーが無かったのか、詳しさが足りずに出なかったのかを、AI が区別できるように）
- **読み取りの失敗は、「該当する行なし」と分けて書く**: 行の形が想定と違って読めなかった（区切りが違う・知らない種類の行）ときは、その本数と、本文のファイルへのリンクを「読み取れなかった行」として書く。読めない行があっても、要約は作る（ほかの行は読む）
- どの場合も、要約に入れたログの本文のファイルへのリンクは、必ず一覧に残す（AI が、要約で足りなければ本文を開けるように）

- 要約は `lib/apexlog.js`（Node の標準機能のみ）で作る。ログの行の解析・集計・Markdown の組み立ては、状態と分岐が多く、シェルでは重い（CLAUDE.md 2.2 の言語の方針）

## 8. Salesforce API 操作

> JSON は `json_get`（`lib/common.sh`）で読む。`grep` / `sed` で読まない（CLAUDE.md 2.2）。
> フラグは sf 2.157.8 の `--help` で確認した（`sf apex get log` の `-i`・`-n`・`-d`、`sf apex list log` は `-o` のみ）。応答の JSON のフィールド名は、2026-11-23 に実機で確かめた（8.2）。

**TraceFlag を `sf apex trace` ではなく `sf data …`（Tooling API の直接の操作）で扱う理由**

sf には `sf apex trace create` / `delete` / `list` がある（sf 2.157.8 の `--help` で確認。`create` は `-i`（対象）・`-d`（DebugLevel の名前）・`-l`（`DEVELOPER_LOG` / `USER_DEBUG`。既定は `DEVELOPER_LOG`）・`--duration`（分。既定 30・最大 1440））。それでも直接の操作にするのは:

- **延ばす（更新する）コマンドがない**。取得役は、自分の TraceFlag の期限を延ばし続ける（4.3）。作り直すと ID が変わり、「自分が作ったものだけを触る」確かめ（4.2 の 3a）が崩れる
- 期限を縮めて止める（消さずに止める。4.2 の 3b）操作がない
- 検索の条件（自分のユーザー・種類・期限）と、取る項目を、こちらで決められる
- なお、`--duration` の最大 1440 分（24 時間ちょうど）は、Tooling API の「24 時間未満」と食い違う。本書は、厳しいほう（24 時間未満）に合わせる

**sf の呼び出しの共通の扱い（8.1〜8.5 のすべて）**

| 状況 | 扱い |
|---|---|
| sf の終了コードが 0 以外 | 手動: `die`／自動・取得役: その回を失敗として扱う（4.2・4.3）。どちらも、`run` が失敗を `error.log` に記録し、状態ファイルは変えない |
| 出力を `json_get` で読めない（JSON でない・期待したキーがない） | 上と同じ（推測で進めない） |
| 検索（`sf data query`）の件数 | `result.totalSize` で判定する（2026-11-23 に実機で確認）。0 件・1 件・2 件以上を、呼び出しごとに決めた扱いに分ける（DebugLevel の 2 件以上・ほかの有効な TraceFlag の 2 件以上は、手動 `die`／自動 取らない） |
| 作成（`sf data create record`）の ID | `result.id`（2026-11-23 に実機で確認）。取れなければ失敗 |
| 検索の文に埋め込む値 | **埋め込む前に、形を検査する**。形が違えば失敗（引用符などで逃がさず、決まった形の値しか通さない）。ユーザー ID・TraceFlag の ID: 英数字 15 文字か 18 文字／DebugLevel の名前: `standard`・`detail` から作る決まった 2 つだけ／日時: `YYYY-MM-DDTHH:MM:SSZ`／件数・分・時間・PID: 1 以上の整数（`--hours` は 1〜23）／持ち主の印: `数字:数字:英数字`（3 つ目は、環境の名前と乱数。5.6）。状態ファイル・sf の応答から読んだ値も、信用せずに同じ検査をする（`LAST_FETCH`・`LAST_READ_LINE`（0 以上の整数）・`LAST_READ_ID`（`LAST_READ_LINE` が 0 なら空、それ以外は ID の形）だけは、形が違えば、直近 30 分に戻す。`LAST_FETCH_ID` は、形が違えば空にする。`LATE_FROM` は、形が違えば消す） |
| 出力の受け取り | `VAR=$(run ... --json)` で受ける（例外: 全ユーザーのログの一覧（8.3）は、他の人の見出しを記録しないため、`run` を通さない。`run` は、標準エラーも混ぜて返す。`json_get` は、全体が JSON でなければ、最初の `{` から最後の `}` までを読む。`lib/common.sh`。sf の更新のお知らせ（`»   Warning: @salesforce/cli update available …`）は標準エラーに出て、中括弧を含まないので、混ざっても読める。2026-11-23 に確認）。ログの本文だけは、この方法で受けない（8.4） |

### 8.1 DebugLevel（探す・上書きする・作る）

```bash
DL_JSON=$(run sf data query --use-tooling-api --target-org "$TARGET_ORG" --json \
  --query "SELECT Id FROM DebugLevel WHERE DeveloperName = 'sf_tools_log_${LEVEL}'") || die "DebugLevel を検索できませんでした。"
# あり → 7 章の全項目を上書き（差分の判定はしない）
run sf data update record --use-tooling-api --sobject DebugLevel --record-id "$DL_ID" --target-org "$TARGET_ORG" \
  --values "ApexCode=FINE ApexProfiling=INFO ..."
# なし → 作る
run sf data create record --use-tooling-api --sobject DebugLevel --target-org "$TARGET_ORG" --json \
  --values "DeveloperName=sf_tools_log_${LEVEL} MasterLabel=sf_tools_log_${LEVEL} ApexCode=FINE ..."
```

- 毎回上書きするのは、値を変えたとき（sf-tools の更新）に、古い値のまま使われないようにするため。差分を判定するより単純で確実
- DebugLevel は消さない。公式では、DebugLevel を消すと、それを使う TraceFlag も消える
- 検索・作成の権限がないときの応答は、実機で確かめ、メッセージに「権限が足りない」ことが分かる事実を書く（復旧の案内は書かない。CLAUDE.md 2.2）

### 8.2 TraceFlag（探す・延ばす・止める・作る）

```bash
TF_JSON=$(run sf data query --use-tooling-api --target-org "$TARGET_ORG" --json \
  --query "SELECT Id, TracedEntityId, LogType, StartDate, ExpirationDate, DebugLevel.DeveloperName FROM TraceFlag WHERE TracedEntityId = '${USER_ID}'") || die "TraceFlag を検索できませんでした。"
# 「いま有効」かは、StartDate・ExpirationDate を Node で今と比べて判定する（4.2 の 3b）
# 自分が作ったもの（状態ファイルの ID）→ 延ばす（start・collect）
run sf data update record --use-tooling-api --sobject TraceFlag --record-id "$TF_ID" --target-org "$TARGET_ORG" \
  --values "DebugLevelId=${DL_ID} StartDate=${NOW} ExpirationDate=${EXPIRY}"
# ほかの有効な USER_DEBUG（手動の確認のあと）→ 期限を「元の期限」と「今から 2 分後」の早いほうに縮める（今にはできない。元の期限が早ければ更新しない）
run sf data update record --use-tooling-api --sobject TraceFlag --record-id "$OTHER_ID" --target-org "$TARGET_ORG" \
  --values "ExpirationDate=${NEW_EXPIRY}"
# ない → 作る
run sf data create record --use-tooling-api --sobject TraceFlag --target-org "$TARGET_ORG" --json \
  --values "TracedEntityId=${USER_ID} LogType=USER_DEBUG DebugLevelId=${DL_ID} StartDate=${NOW} ExpirationDate=${EXPIRY}"
```

- 日時は、Node で `YYYY-MM-DDTHH:MM:SSZ`（UTC。ミリ秒なし）を作る（6.4）。この形で受け付けられた。読み直すと `2026-11-23T02:04:12.000+0000` の形で返る（末尾が `Z` でない。比べるときは Node で読む）（2026-11-23 に実機で確認）
- `LogType` は、作成後に変えられない（公式。更新の対象ではない）。そのため、ほかの種類の TraceFlag を USER_DEBUG に「書き換える」ことはせず、止めてから作る
- **期限を「今」にして止めることはできない**: `ExpirationDate` を今・今から 5 秒後にすると `FIELD_INTEGRITY_EXCEPTION`（「ExpirationDate は将来の日付にしてください」）で拒否され、今から 60 秒後は受け付けた（2026-11-23 に実機で確認）。そのため、止めるときは、時計のずれも見込んで 2 分後に縮める（元の期限のほうが早ければ、そのまま。4.2 の 3b）。`StartDate` より前の期限も拒否される（`MULTIPLE_API_ERRORS`）
- 応答: 作成・更新・削除は `result.id`・`result.success`（成功）／`status`=1・`name`・`message`（失敗）。検索は `result.records`・`result.totalSize`・`result.done`（2026-11-23 に実機で確認）
- 親の項目 `DebugLevel.DeveloperName` は、検索で取れる（2026-11-23 に実機で確認）
- 取得役が延ばす前にも、ID・`TracedEntityId`・`LogType` を確かめる（4.3 の 2d。人が途中で置き換えた TraceFlag を延ばさない）

### 8.3 新しいログの一覧

```bash
# run を使わない（応答に他の人のログの見出しが入るため。run は出力を sf-log.log に記録し、画面にも流す）。VAR=$(cmd) の例外（CLAUDE.md 2.1）
# 終了コードは if で受ける（set -e のもとでも、失敗の記録まで進むため）
if LIST_JSON=$(sf data query --use-tooling-api --target-org "$TARGET_ORG" --json \
  --query "SELECT Id, LogUserId, StartTime, Operation, Request, Status, LogLength, DurationMilliseconds FROM ApexLog \
           WHERE StartTime > ${LAST_FETCH} OR (StartTime = ${LAST_FETCH} AND Id > '${LAST_FETCH_ID}') \
           ORDER BY StartTime ASC, Id ASC LIMIT 51" 2>/dev/null); then
  # json_get で result.totalSize・result.records を読む。読めない（JSON でない・キーがない）→ 下の else と同じく失敗（name は「不明」）
  # result.records が配列でない・各要素の Id・LogUserId・StartTime が 8 章冒頭の表の形でない → 失敗（推測で進めない）
  # 自分のログ = LogUserId が USER_ID と一致するもの（15 文字・18 文字の違いは、先頭 15 文字で比べる）。それ以外は他の人のログ（8.4）
  # 読めたら、件数（全体・自分のログ）だけを sf-log.log に書いて、続ける
  :
else
  # json_get で name を読む（読めなければ「不明」）。name だけを sf-log.log と .status に書き、その回を失敗にする（手動: die／取得役: 4.3 の 2e）
  :
fi
```

- **この検索だけは `run` を通さない**。`run` は、出力の全文を `sf-log.log` に記録し、失敗時は `error.log` にも書き、画面にも流す（`lib/common.sh`）。この応答には他の人のログの見出し（ID・ユーザー ID・時刻・操作の名前・大きさ）が入るため、記録に残さない（10.3）
  - 代わりに、`sf-log.log` には、自分で、コマンドの種類（「ApexLog の一覧」）・終了コード・件数（全体・自分のログ）だけを書く。検索の文は、しおりの値を含むだけなので、書いてよい
  - 失敗（終了コードが 0 以外・`json_get` で読めない）のときは、応答の `name` だけを `sf-log.log` と `.status` に書く（`message` は書かない。値が入りうるため）。標準エラーは捨てる（sf の更新のお知らせなど。中身は記録しない）
  - 応答は変数にだけ持ち、ファイルに書かない。自分のログの見出しは、保存するときに 9.1 のファイル名と要約の一覧に使う

- **一覧は、全ユーザーのログの見出し（ID・ユーザー・時刻・操作の名前・大きさ）を取り、本文を保存するのは自分のログ（`LogUserId` が自分）だけ**。全ユーザーにするのは、本文をまとめて取る `sf apex get log -n`（8.4）が全ユーザーの新しい順に取るため、取りたいログより新しいログに、他の人のログが混ざっていないかを見分ける必要があるから。他の人のログは、見出しでしおりを進めるだけ（10.3）
- **古い順に、しおりから続きを取る**（取りこぼさない。4.3）。しおりは「処理済みの見出しのしおり」: 最後に処理した（自分のログなら保存した、他の人のログなら飛ばした）見出しの `StartTime`（`LAST_FETCH`）と `Id`（`LAST_FETCH_ID`）
  - 他の人のログが続くと、自分のログがなくても、しおりの処理が進むだけの回がある（1 回 50 本ずつ。一人用の開発組織（10.1）では、まれ）
  - **しおりの境目を、検索の条件そのものに入れる**（「しおりより後の時刻」か「しおりと同じ時刻で、ID がしおりより後」）。保存済みのログは、検索の結果に入らない。そのため、同じ時刻のログがいくら多くても、51 本目の有無で「残りがある」を正しく判定できる（手元で除いてから数える方式だと、保存済みのものが 51 本並んだときに、残りを見落とす）
  - しおりがまだない（初めて・初期化した）ときは、`StartTime >= <初期化した時刻>` だけで取る（`LAST_FETCH_ID` が空のため）
  - 念のため、直近に保存した ID（`SEEN_IDS`）でも重複を除く（保存したが、しおりを書く前に止まった場合）
  - 並びは `StartTime` と `Id` の 2 つで決める（同じ時刻のログの順を、毎回同じにする）。`Id` の大小の比較（`Id > '…'`）・この並び・`LIMIT`・日時 `2026-11-21T05:30:00Z` の書き方は、ApexLog で使えた（2026-11-23 に実機で確認。13.1）
- 1 回の上限は 50 本。`LIMIT 51` にして、51 本目があれば「まだ残りがある」とわかる（本数の集計の検索は使わない）。残りがあれば、取得役は待たずに次の回で続きを取る。`.status` には「残り 50 本以上」のように書く
- 1 件保存するごとに、しおりを進める（途中で失敗しても、保存した分は取り直さない。失敗したログから、次の回でやり直す）
- `Status` は、ユーザーの言語で返る（日本語のユーザーでは「成功」。失敗は例外の文言）。成功・失敗の判定に使わない（2026-11-23 に実機で確認）。`Operation` は、画面の操作や API のパス（例: `/services/data/v68.0/tooling/executeAnonymous/`）
- **新しいほうを優先する**（意図した決定）のは、組織から取るときではなく、`pull` が要約に入れるログを選ぶとき（`--max`。4.4 の 3）。取得役は止まらずに動き続けるため、組織から取る段階で古いものを飛ばす必要がない（2026-11-22 に変更。13.3）
- **遅れて現れるログの拾い直し（2026-11-24 に追加。13.1・13.3）**: ApexLog は、処理が**終わってから**一覧に現れる（`Id` と `StartTime` は、始まったときのもの）。長い処理のログは、あとから始まった短い処理のログより遅れて現れ、しおり（`StartTime`）がその先へ進んだあとでは、上の検索に二度と入らない。tama-dev で、9.5 秒の匿名 Apex（05:10:53 開始）は、05:10:54・55・57 開始の短い処理が見えている 05:10:56〜58 の時点で、一覧になかった。そこで、上の取得が追いついた回（残りがない回）に、次を足す:

```bash
# 自分のログだけ（LogUserId で絞る。他の人の見出しは入らない）。下限（「今から 30 分前」と、前の回の失敗で残した LATE_FROM の早いほう）から、しおりまでを、新しい順に 200 本まで
if LATE_JSON=$(sf data query --use-tooling-api --target-org "$TARGET_ORG" --json \
  --query "SELECT Id, StartTime, Operation, Request, Status, LogLength, DurationMilliseconds FROM ApexLog \
           WHERE LogUserId = '${USER_ID}' AND StartTime >= ${LATE_LOWER} AND StartTime <= ${LAST_FETCH} \
           ORDER BY StartTime DESC, Id DESC LIMIT 200" 2>/dev/null); then
  # 目録（.index）にない ID だけを、sf apex get log -i で 1 本ずつ取り、9.1 の名前で保存して、目録に足す（しおりは動かさない）
  :
fi
```

  - **他の人のログに触れない**: 検索は自分のログだけ。本文は `-i`（ID を指定する）だけで取り、`-n` は使わない（`-n` は全ユーザーの新しい順のため、他の人の本文が入りうる。8.4）。通常の取得の `-n` の扱い（8.4）は変えない
  - **保証の範囲**: 自分のログは、**一覧に現れたあとの最初の拾い直しが成功した時点で、始まってから 30 分以内で、範囲の自分のログが 1,000 本以内（下の「200 本に達したとき」）なら**、目録に入る（範囲の下限を「しおりより 30 分前」ではなく「今から 30 分前」にするのは、しおりの位置によって、30 分より短い処理でも範囲の外に出ることがあるため。Codex の指摘。2026-11-24）。拾い直しが失敗した回は、その下限を残して、次の回に同じところから拾い直す（下の「失敗」）。目安として、**処理にかかった時間 ＋ 一覧に現れるまでの遅れ ＋ 取得の間隔（既定 3 分）が 30 分を超えると、拾えないことがある**（限界。長いバッチなど。一人用の開発組織の、ふだんの開発のサイクルでは、まれ）
  - **動かすのは、しおりが「今から 30 分以内」のとき、または `LATE_FROM`（前の回の失敗で残した下限）があるときだけ**。しおりがそれより古く、`LATE_FROM` もないと、範囲が空になる（しおりより後に始まったログは、通常の取得が取る）。sf の呼び出し（約 5〜10 秒）を 1 回増やすのは、ログが動いているあいだだけにする
  - **動かすのは、通常の取得が追いついた回（残りがない回）に 1 回だけ**。残りがある回（取得役が長く止まっていたあと。`pull` の自分での取得が 200 本の上限で止まった回）は、拾い直しを次の回に回す。`pull` の「最大 200 本」は、通常の取得だけに数える（4.4 の 2）
  - **200 本に達したとき**（範囲に、自分のログが 200 本以上ある）は、200 本目（最も古いもの）より古いほうを、同じ範囲で続けて問い合わせる（`StartTime` と `Id` が 200 本目より前。新しい順に 200 本ずつ。**最大 5 回 = 1,000 本**）。sf の呼び出しが増えるのは、この珍しい場合だけ。1,000 本を見ても範囲の終わりに届かないときは、その古いほうを、今回も次の回も見ない（失敗ではなく、限界として扱う。拾い直しは成功とし、`LATE_FROM` があれば消す。次の回には、範囲の下限が進み、外れていく）。`sf-log.log` と `.status` に WARNING を書き、`pull` は要約の先頭に書く（拾えなかったかもしれない時間帯を書く。一人用の開発組織では、まれ）。ページの途中で失敗したときは、その回の拾い直しを打ち切り、下の「失敗」と同じく下限を残す（取れた分は目録に入っている）
  - 応答は自分のログの見出しだけだが、上の一覧と扱いをそろえ、`run` を通さず、件数（見た本数・拾い直した本数）だけを `sf-log.log` に書く
  - **失敗**（検索・本文の取得・ページの途中）しても、その回の取得は成功として扱う（しおりは、すでに進めてある）。`sf-log.log` に WARNING を書き、**その回の下限を `.state` の `LATE_FROM` に残す**（すでに `LATE_FROM` があれば、早いほうのまま）。次の回は、`LATE_FROM` と「今から 30 分前」の早いほうを下限にして、もう一度拾い直す（範囲の下限は毎回進むため、残さないと、失敗したログが次の回には範囲の外に出ていることがある。Codex の指摘。2026-11-24）。拾い直しが最後まで成功したら、`LATE_FROM` を消す。残すのは時刻だけ（ID を残さない。他の人のログの情報を記録しない）。`LATE_FROM` が 24 時間より古くなったら、消して WARNING を書く（失敗が続いているので、`pull` は要約の先頭にも書く）。拾い直しは、目録で重複を除くので、何度動かしてもよい
  - **順序**: 取得のロック（9.3）を持ったまま、通常の取得 → 拾い直しの順に行い、目録への書き込みまで終えてから、取得役は `pull` の依頼に応える（9.3）。拾い直しの検索の途中に現れた新しいログは、次の回の通常の取得が取る（その `pull` の要約には入らない。許容する）
  - 拾い直したログは、開始時刻が、すでに要約に入れたログより前のことがある。要約に入れるログは、開始時刻ではなく、**目録に足された順**で選ぶ（4.4 の 3。そうしないと、取れても要約に入らない）

### 8.4 本文の取得

```bash
# ふだん（まとめて取る）: 一覧（8.3）の中で、取りたいログより新しいログが、すべて自分のログのとき
run sf apex get log -n "$N" -d "$TMP_DIR" --target-org "$TARGET_ORG"
# それ以外（取りたいログより新しいログに、他の人のログが混ざる・一覧が 51 本で残りがある・-n で足りなかった）: 1 本ずつ
run sf apex get log -i "$LOG_ID" -d "$TMP_DIR" --target-org "$TARGET_ORG"
```

- **sf の起動が遅いため、ふだんはまとめて取る**: 1 本ずつ取ると、1 本 10〜11 秒かかった（Windows。そのほとんどが sf の起動）。`-n 2` で 2 本まとめても 12.7 秒だった（2026-11-23 に実機で確認）。一定の間隔で取る取得役では、1 本ずつでは追いつかないことがある
- **1 回の取得の対象は、一覧（8.3）を取った時点で決めて、固定する**（取りたい ID の集まり＝一覧の中の自分のログ）。取得の途中でできたログは、その回では扱わず、次の回に、しおりから取る
- **`-n` は、全ユーザーのログの新しい順に N 本を取る**。`N` は、一覧の中の、取りたい自分のログのうち最も古いものから、一覧の最後までの本数にする。この範囲に他の人のログが 1 本でもあれば、`-n` は使わず、自分のログを `-i` で 1 本ずつ取る。一覧が 51 本で残りがあるとき（取得役が長く止まっていたあと）も、`-n` の範囲が一覧の外に広がるため、`-i` で取る
- **一覧を取ったあと `-n` を呼ぶまでに新しいログができると、`-n` の N 本から、取りたいログのうち古いものが押し出され、代わりに新しいログ（他の人のものもありうる）が入る**。そのため、取れたファイルを、固定した取りたい ID と照らし合わせる:
  - 取りたい ID のファイル → 保存する
  - それ以外のファイル（押し出しの代わりに入った新しいログ）→ 中を読まずに、一時フォルダからすぐ消す（自分のログなら、次の回に取り直す）
  - 足りない ID → その回のうちに `-i` で 1 本ずつ取る（`-i` は、ID を指定するので、他の人のログは入らない）
  - **このため、`-n` を使うと、他の人のログの本文が、一時フォルダに一瞬だけ書かれることがある**（一覧と `-n` の間の数秒に、他の人のログができたとき）。保存・記録・要約には入れない（10.3）。一人用の開発組織（10.1）では、他の人のログはまれ。`-i` だけにすると、1 本 10 秒かかり、取得役が追いつかないため、この取り扱いを選ぶ（2026-11-23 決定。13.3）
- 一時フォルダ（`$TMP_DIR`）は、OS の一時フォルダではなく、決まった場所 `logs/apex/.fetch/`（9.1）にする。**取得のたびに、取得のロック（9.3）を持った状態で、まず中を空にしてから** `-d` に渡す。途中で止まった（PC が止まった・強制終了した）ときに、`-n` で混ざった他の人のログの本文が残っても、次の取得の最初に必ず消えるようにするため（OS の一時フォルダだと、どこに残ったか分からなくなる）。取得のロックは同時に 1 つしか持てないので、ほかの取得の途中のファイルを消すことはない。`logs/` は Git の管理外（9.1）。sf は、ログを `<ログの ID>.log` の名前で書く（`-n`・`-i` とも。2026-11-23 に sf 2.157.8 で確認）。`-n` では、ファイル名から ID を取るほかに対応を知る手段がない（`--json` の応答は本文の配列で、ID を含まない）ため、この名前に頼る。名前が `<ID の形（英数字 15 か 18 文字）>.log` でないファイルが 1 つでもあれば、その回を失敗として扱う（推測で対応させない）
- 取れたファイルを、9.1 の名前に変えて、日付のフォルダへ移す
- 一時フォルダの中は、取得の終わりにも `trap ... EXIT` で空にする（CLAUDE.md 2.2）。フォルダ自体は残してよい
- 本文を `$(run ...)` で受けない。`run` は、出力をすべて `LOG_FILE` に記録し、標準エラーも混ぜる（`lib/common.sh`）。本文が `sf-log.log` に丸ごと残り、sf の警告も混ざるため。`-d` で書かせ、`--json` を付けない（`-d` があり `--json` がないとき、sf が標準出力に書くのは「Log files written to <フォルダ>」の 1 行だけ。`--json` を付けると、応答に本文が入る。2026-11-23 に確認）。そのため `run` で包んでも、本文は `sf-log.log` に残らない

## 9. 保存先と、手元の状態

### 9.1 ログ本文と要約

```
force-*/logs/apex/
  latest.md                                   ← 最新の pull の要約（AI は、まずこれを読む）
  summaries/20261122_143005.md                ← pull ごとの要約（latest.md と同じ内容の控え）
  20261122/                                   ← 取得役・pull が保存したログ（ログの開始日ごと）
    143001_07LdM00000AbCdE_aura.log           ← 開始時刻_ログの ID_操作名
  .state  .status  .collector  .owners  .consent   ← 手元の状態（9.2）
  .index                                      ← 保存したログの目録（1 行に 1 本。パス・ID・開始（UTC）・操作・状態・長さ・所要。pull が要約に入れるログを選ぶ）
  requests/                                   ← 依頼と応答（9.3）
  .fetch/                                     ← 本文の取得に使う一時フォルダ（8.4。取得のたびに空にする）
```

- `templates/.gitignore` の `logs` により、Git の管理外になる
- ファイル名は、**開始時刻とログの ID で一意**にする（ID は英数字だけなので、どの OS でも安全）。同じ名前になることはない
- 操作名は、見分けやすくするための飾り。`Operation` から、英数字・`_`・`-` 以外を `_` に置き換え、先頭と末尾の `_` を除き、最大 30 文字にする（`/aura` のような値が入るため）。空になったら、付けない。元の `Operation` は、要約の一覧に、そのまま書く
- 日付・時刻は UTC ではなく、PC の現地時刻で付ける（人が見てわかるように）。並べ替え・比較には使わない（比較は `.state` の UTC の時刻で行う）
- 古いログの自動削除は、しない（9.4・13.2）

### 9.2 手元の状態のファイル

どれも `キー=値` の行（シェルで読める形。`source` はせず、`while read` で、決まったキーだけを読む）。書き換えは、一時ファイルに書いてから `mv` で置き換える（途中で止まっても、壊れた状態を残さない）。

| ファイル | キー | 書く人 |
|---|---|---|
| `.state` | `ORG`・`USER_ID`・`TRACE_FLAG_ID`（**sf-log.sh が作った** TraceFlag の ID）| `start`・`stop` |
| | `LAST_FETCH`・`LAST_FETCH_ID`（取得のしおり: 最後に保存したログの開始時刻（UTC）と ID）・`SEEN_IDS`（直近に保存した ID）・`LATE_FROM`（拾い直しが失敗した回の範囲の下限。UTC。次の回は、ここから拾い直す。成功したら消す。24 時間より古ければ消す。8.3。2026-11-24） | 取得役（取得役がいないときだけ `pull`） |
| | `LAST_READ_LINE`（前回の要約で読んだ、目録（`.index`）の最後の行の番号。目録は足すだけなので、これより後の行が「まだ要約に入れていないログ」）・`LAST_READ_ID`（その行のログの ID。目録を手で直して行番号がずれたときに、行を探し直すため。4.4 の 3）。2026-11-24 に `LAST_READ`・`LAST_READ_IDS`（開始時刻で選ぶ方式）から変更（遅れて拾い直したログを落とさないため。8.3・4.4）。**古い `.state` からの移行**: `LAST_READ_LINE` がなく `LAST_READ` があるときは、目録のうち、開始時刻が `LAST_READ` より前の行と、`LAST_READ` と同じ秒で `LAST_READ_IDS` に入っている行を「見た」とみなし、それ以外の最初の行の 1 つ前の行番号と、その行のログの ID を `LAST_READ_LINE`・`LAST_READ_ID` にする（最初の行がそれ以外なら、`LAST_READ_LINE=0`・`LAST_READ_ID` は空。全部の行を「見た」なら、最後の行の番号と ID。同じ秒で要約に入れていないログを「見た」にしない。Codex の指摘。2026-11-24）。`LAST_READ_LINE` は 0 以上の整数（0 = まだ何も見ていない。そのとき `LAST_READ_ID` は空） | `pull` |

| `.claim` | `RUNTIME`（扱う環境）・`OWNER`（名乗った sf-start の印）・`AT`（名乗った時刻。エポック秒）。5.6 | `begin`・`start --auto`（`.lock` の中で書く）・取得役（`AT` を書き直す）・後始末（消す） |
| `.collector` | `PID`・`STARTED`（起動の時刻）・`ORG`・`RUNTIME`（動いている環境。5.6）・`HEARTBEAT`（生きている合図。UTC のエポック秒。目を覚ますたび・sf を呼ぶ直前・ログを 1 本保存するたびに書き直す。5.6） | 取得役 |
| `.owners` | 1 行に 1 つ、持ち主（起動中の sf-start）の印（`PID:起動の時刻:環境の名前と乱数`。5.6。環境の名前のない古い印も読む）。後始末の最中は `CLOSING=<印>` の行（5.2） | sf-start（足す）・`leave`（外す・`CLOSING` を書いて消す）・取得役（死んだものを外す）・`stop`（空にする・`CLOSING` を書いて消す） |

- 接続先・ユーザー ID が変わったら、`.state` の取得・要約の時刻を初期化する（別の組織の時刻・ID を使わない）
- `.state` のキーは、書く人ごとに分けてある。書くときは、ファイル全体を読み直し、自分のキーだけを差し替えて書く（9.3）

### 9.3 取得役と pull の同時実行

取得役は裏で常に動き、AI の `pull` はいつでも呼ばれる。同時に動いても壊れないように、次のようにする。

- **組織から取って手元の取得のしおりを書くのは、取得役だけ。** 取得役が生きているときの `pull` は、自分で取らず、取得役に頼む
- **依頼と応答は、ID つきのファイルにする**（複数の `pull` が同時に頼んでも、混ざらない）:
  - `pull` は、ID（`<PID>_<時刻>_<乱数>`）を作り、`requests/pull.<ID>` を、一時ファイルに書いてから `mv` で置く（読みかけのファイルを見せない）
  - 取得役は、追いついたとき（4.3 の 2c）、**拾い直し（8.3）と目録への書き込みまで終えてから**、その時点の `requests/pull.*` のそれぞれに、`requests/done.<ID>` を同じ方法で置き、依頼のファイルを消す（応えたあとに `pull` が目録を読めば、その回に取れたログは、すべて目録にある。2026-11-24）
  - `pull` は、自分の ID の `done.<ID>` だけを待ち、読んだら消す
  - 5 分より古い依頼・応答は、取得役が消す（`pull` が待つのをやめたあとの残り）
  - 停止の依頼は `requests/stop`（中身は問わない。何度置いても同じ）。取得役は 5 秒以内に気づいて止まり、消す（4.3 の 2b）
- **取得のロック**（`logs/apex/.fetch.lock`）: 組織からログを取って手元に保存する人（取得役・取得役がいないときの `pull`）は、1 回の取得の間、このロックを持つ。取得は sf を呼ぶので長い（数秒〜数十秒）が、このロックは取得だけに使うので、ほかの処理は待たせない
  - 取得役は、取れなければ、その回を飛ばして次の回にする。`pull` は、取れなければ最大 90 秒待ち、取得役が起動していればそちらに頼む（4.4 の 2）
- **要約のロック**（`logs/apex/.read.lock`。2026-11-24 に追加）: `pull` が、目録を読んで要約に入れるログを決め、`LAST_READ_LINE`・`LAST_READ_ID` を書くまでの間、このロックを持つ（`pull` を同時に 2 つ動かしても、同じログを 2 回要約せず、しおりを戻さない。4.4）。取得のロックとは別（要約のロックの中では、組織から取らない）。取得役は持たない（目録に足すだけで、しおりを読まないため）
  - 作り方・古いロックの扱いは、下の短いロックと同じ（`mkdir`・中に PID と起動の時刻）
- **本文の保存は、置き換えで行う**: 一時ファイル（日付のフォルダの中の `.tmp.<ID>.<PID>`）に書いてから `mv` で本来の名前にする。本来の名前のファイルがすでにあれば（別の人が先に保存した）、一時ファイルを消して、成功として扱う（同じ ID のログは同じ中身）
- `.state`・`.owners`・`.consent` を書き換えるときは、短いロックを取る: `mkdir logs/apex/.lock`（`mkdir` はどの OS でも「作れたら自分のもの」が確実。`flock` は macOS にないため使わない）。取れなければ 0.2 秒待って、最大 10 秒やり直す。ロックの中に PID を書き、その PID が死んでいれば、古いロックとして消す
- ロックを持つのは、ファイルを読み直して書き換える間だけ（sf を呼んでいる間は持たない）
- ランチャーを 2 つ起動しても、取得役は 1 つだけ（4.3 の 1）。取得役は、持ち主の一覧（`.owners`）が空になるまで動く（5.2）

### 9.4 手元に保存したログの扱い

- 手元の `logs/apex/` には、組織のログの本文がそのまま残る（レコードの値などを含む）。Git の管理外だが、PC のバックアップ・同期（OneDrive など）の対象にはなりうる
- sf-log.sh は、手元のログをどこにも送らない。送られるのは、AI がファイルを読んだときだけ（10.2）
- 取得役は、ランチャーの起動中、自分の操作のログをすべて手元に保存する。量の目安は、実機で測る（13.1）
- `stop` は、手元のログを消さない（直したあとで読み返すことがあるため）。消すときは、`logs/apex/` の日付のフォルダを手で消す。これを `--help` の【補足】と手順書（11 章）に書く
- 自動で消すか（日数で消すなど）は、未決（13.2）

### 9.5 このツール自身のログ

- 他のコマンドと同じく `./sf-tools/logs/sf-log.log`。`run` の失敗は `error.log` にも追記される（`lib/common.sh`）
- 取得役は長く動くため、`sf-log.log` が大きくなりすぎないようにする（取得役は、成功した回を 1 行にまとめ、sf の応答の全文は失敗したときだけ残す。具体的な方法は実装時に決める）

## 10. 安全

### 10.1 取らない組織

| 組織 | 判定 | 手動 | 自動 | 理由 |
|---|---|---|---|---|
| 共有環境の組織（予約名 `prod` / `staging` / `develop` / `main`） | `is_reserved_org_alias` | `die` | 取らない（終了コード 10） | 共有の組織は、Actions がリリースする先で、ふだんの開発の場ではない。TraceFlag の延長・停止で、他の人の調査を邪魔しうる。`sf-deploy.sh` と同じ保護にそろえる。必要になったら、あとで緩める |
| 本番 | `org_local_release_check` が 1 | `die` | 取らない | 本番のユーザーの操作のログには、実データが載る。AI に読ませる用途に合わない。TraceFlag を本番に作ること自体の影響（性能・ログの量）も避ける |
| 種類を確認できない | `org_local_release_check` が 2 | `die` | 取らない | 本番でないと確かめられないため（推測しない） |

- 予約名以外の名前を付けた共有の組織は、名前では止められない。その場合も、本番なら 2 行目で止まる。Sandbox の共有の組織を止める手段はないため、10.2 の確認で守る

### 10.2 AI への送信の確認

- ログには、レコードの値・SOQL の条件・コールアウトの内容が載る。AI に読ませると、それが AI の提供元に送られる
- **自動**: 次のどれかのとき、`begin`（sf-start の前面）が次の注意を表示して、`read_key` で Y/N を聞く（`q` は N。端末でなければ聞かずに「取らない」とし、答えを保存しない）。答えを `.consent`（`AUTO`・`ORG` = エイリアス・`ORG_ID`・`VERSION`）に保存し、同じエイリアス・同じ文面の版のあいだは、もう聞かない（sf を呼ばずに判定する。ランチャーを待たせないため。2026-11-23。13.3）
  - `.consent` がない（プロジェクトで初めて）
  - つないだ組織のエイリアスが、`.consent` の `ORG` と違う（別の組織に切り替えた）
  - **同じエイリアスで、別の組織に入り直した**: `begin` では分からない（sf を呼ばないため）。裏の `start --auto` が、つないだ組織の ID を `.consent` の `ORG_ID` と照らし合わせ、違えば取らずに（10）答えを消す。ランチャーには「取っていません（同じエイリアスで、別の組織に入り直したため…）」と出て、次の sf-start で聞き直す。`ORG_ID` が空（答えた直後）なら、そのときの組織 ID を書く。同意のない組織のログは、手元に保存しない
  - 注意の文面の版（`VERSION`）が変わった（sf-tools の更新で、送るものや注意が変わったとき）
  - 「ランチャーの起動中、この組織のデバッグログを、裏で自動で手元に保存します。ログは AI に読ませる前提です。ダミーデータの組織で使ってください。本番のデータを写した Sandbox（Full・Partial）では、N を選んでください。あとから `sf-log.sh auto on|off` で変えられます」
- **手動**: `start` のたびに、同じ注意を表示し、`ask_yn || die` で確認する（`-y` で省く）
- `.consent` は、プロジェクト（force-* のフォルダ）ごとに 1 つ。答えは、最後に答えた組織の分だけを持つ（組織を行き来すると、そのたびに聞く。手間より、データの扱いの確認を優先する）。`logs/apex/` を消すと、次の `sf-start` で、もう一度聞く
- `auto on|off` で変えたときは、その時点でつないでいる組織のエイリアスを `ORG` に、ID を `ORG_ID` に書く
- 開発者向けの道具のため、CLAUDE.md 2.4 の管理者向けの警告ボックスの対象外（`print_admin_warning` は使わない）

### 10.3 組織への書き込み

- 書き込むのは、次だけ:
  - `sf_tools_log_*` の DebugLevel（作る・上書きする）
  - 自分のユーザーの TraceFlag（sf-log.sh が作ったものを、作る・延ばす・消す）
  - 自分のユーザーの、ほかの有効な USER_DEBUG の TraceFlag（**手動の**確認のあと、期限を 2 分後に縮めて止める。消さない。自動では触らない）
- 他の人の TraceFlag には触れない（検索の条件を、自分のユーザー ID に限る）
- 他の人のログは、**本文を保存・記録・要約しない**。新しいログの一覧（8.3）だけは、全ユーザーの見出し（ID・ユーザー・時刻・操作の名前・大きさ）を読む（本文をまとめて取れるかを見分けるため。8.4）。見出しは、しおりを進めるのに使うだけで、手元に保存しない（一覧の検索は `run` を通さず、応答を `sf-log.log`・`error.log` に記録しない。8.3）。しおり（`.state` の `LAST_FETCH`・`LAST_FETCH_ID`）には、他の人のログの時刻と ID が入りうるが、次の検索の起点に使うだけ
- ただし、本文をまとめて取る `-n`（8.4）では、一覧を取った直後に他の人のログができると、その本文が一時フォルダ（`logs/apex/.fetch/`）に書かれることがある。中を読まずに、すぐ消す。途中で止まって残っても、次の取得の最初に消す（8.4）。「本文を取らない」とは言い切れないため、この形で書く
- この取り扱いを許すのは、sf-log.sh が、ダミーデータの一人用の開発組織で使う前提だから（10.1 で本番・共有の組織を止め、10.2 の確認で、本番のデータを写した Sandbox では使わないよう求める）。他の人のログの本文が一時的にでも PC に書かれては困る組織では、そもそも sf-log.sh を使わない

## 11. AI 向けの開発サイクルの手順書

### 11.1 置き場所（推奨）

- `~/sf-tools/doc/ai-dev-loop.md`（sf-tools のリポジトリ内）に置く
  - force-* の `CLAUDE.md` などには、「開発のサイクルは `~/sf-tools/doc/ai-dev-loop.md` に従う」の 1 行だけを書く
  - 理由: 手順を直したとき、各利用者の `git pull` で届く（`templates/` に置くと、`sf-project` を実行した時点の写しのまま古くなる）
- force-* の AI の指示ファイルへの入れ方（2026-11-24 に決定。13.2）: `templates/` に `CLAUDE.md`（`@~/sf-tools/doc/ai-dev-loop.md` の 1 行。Claude Code が手順書を読み込む）と `AGENTS.md`（Codex など向けに、同じことを文で書いた 1 行）を置く。新しく作る force-* には、`sf-project` の Phase 3 が写す（force-* のリポジトリにコミットされ、チーム全員の AI に届く）。すでにある force-* は、その 2 つのファイルを手でコピーしてコミットする（文書サイトの commands-dev に書いた）。雛形には「この行は消さないでください」の注意を入れ、プロジェクト独自の決まりは、その下に自由に書き足せる。`sf-start.sh` は、起動のたびに、その行があるかを確かめ、なければ WARNING で知らせる（書き換えない）。手順書は、デバッグログのサイクルに加え、sf-tools のコマンドの使い分け（AI が実行してよいもの・人に頼むもの・実行しないもの）も書く（2026-11-24。TAMAさんの依頼）

### 11.2 中身（`doc/ai-dev-loop.md` に書いた。2026-11-24）

1. 人は `sf-start` で作業を始める（ログは自動で取られる）。AI は、最初に `sf-log.sh status` で、取得役が動いているかを確かめる。動いていなければ、理由（取らない組織・答えが「取らない」・ほかの TraceFlag）を人に伝える
2. コードを書き、`sf-deploy.sh` でデプロイする
3. 人に、確かめる操作を具体的に伝え、終わったら知らせてもらう
4. `sf-log.sh pull` を実行し、`logs/apex/latest.md` を読む。必要なら、要約に書かれた本文の行だけを開く。要約の先頭に「入れなかった古いログ」があれば、必要なときだけ `--since` で入れ直す
5. 直して 2 に戻る。直らない原因が分からないときは、人に `sf-log.sh start --level detail` を頼む（詳しいログに切り替える）
   - AI が自分で Apex を試しに動かすときは、`sf apex run` ではなく、Tooling API の `executeAnonymous` を直接呼ぶ（`sf api request rest "/services/data/v68.0/tooling/executeAnonymous/?anonymousBody=<URL エンコードしたコード>"`）。`sf apex run` は、sf が自分の詳しさでログを出すため、SOQL・DML などの行が出ない（6.3）
   - **動かす前に、毎回、人の了承を取る**（読み取りだけのコードも）。了承を求めるときは、接続先の組織（エイリアス・組織 ID）と、動かす Apex の全文を見せる。組織でコードを動かすことは、データの書き換え（DML）・非同期の処理の登録・外部への通信になりうるため
   - `executeAnonymous` は、コードを URL の引数（GET）でしか受け取らない。長いコード（URL エンコード後に約 16KB を超えるもの）は、URL の長さの上限で失敗しうる。長いコードは、クラスにしてデプロイしてから呼ぶ
   - Windows の Git Bash では、`/` で始まる引数が、Windows のパスに書き換えられることがある（2026-11-24。`?` のない `/services/data/…` が `NOT_FOUND` になった。`?` のある `executeAnonymous` の URL は通った）。`sf api request rest` は、`MSYS_NO_PATHCONV=1` を付けて呼ぶ
6. AI は、`start`・`stop`・`auto` を実行しない（組織への書き込みと、取るかどうかの判断は、人に残す）

### 11.3 取れないもの（手順書に書く）

- **LWC・Aura の画面側のエラー**（ブラウザのコンソール）は、デバッグログに残らない。人に、ブラウザの開発者ツールのコンソールの内容を貼ってもらう
- **別のユーザーで動く処理**: プラットフォームイベントのトリガー（Automated Process ユーザー）・スケジュールで動くフロー・プラットフォームイベントで動くフロー・他の人がスケジュールしたジョブは、自分のユーザーの TraceFlag では取れない
- 非同期の処理（Queueable・Batch・future）は、実行の時刻がずれる。`pull` を少し待ってから呼ぶ
- 取得中に人が Developer Console を開くと、別の種類（DEVELOPER_LOG）の TraceFlag が作られる。USER_DEBUG とはぶつからないが、ログの詳しさがどうなるかは未確認（8.6）。ログの行が足りないと感じたら、`status` で確かめる

## 12. 実装時に守る規約

- **冒頭コメント（仕様の正本）**: 書式は `doc/doc-style.md` 3.2（【使い方】【オプション】【処理の流れ】【前提条件】【補足】）。`--help` / `-h` で第 2 ブロックを表示する（CLAUDE.md 2.5）。`tests/test_cli_args.sh` が【オプション】を確かめる。`sf-start.sh`・ランチャー（`phases/start/launcher.sh`）の冒頭コメントも、5 章に合わせて直す
- **ログ**: `lib/common.sh` を source する前に `LOG_FILE`（`./sf-tools/logs/sf-log.log`）・`SCRIPT_NAME`・`LOG_MODE` を定義する。`die` のメッセージに復旧の案内を含めない
- **`run` ラッパー**: sf コマンドは `run` で実行する。例外（`sleep`・`kill -0`・裏での起動 `&` など）には、その行に理由のコメントを付ける（CLAUDE.md 2.1）
- **Bash 3.2 / BSD 互換**: `declare -A`・`mapfile`・`timeout`・`date -d`・`sed -i`・`flock` を使わない（CLAUDE.md 2.2）
- **入力**: `ask_yn`・`read_key` など `lib/input.sh` の関数を使う（CLAUDE.md 2.3）。自動（`--auto`）では、`ask_yn`（`q` で `die`）を使わない
- **sf-start を止めない**: `sf-start.sh` の中の sf-log.sh の呼び出しは、失敗しても先へ進む（`|| true` ではなく、終了コードで INFO / WARNING を分ける。5.1）
- **テスト**: `tests/test_helper.sh` の `create_mock_sf` で sf をモックにする。要約（`lib/apexlog.js`）は、実ログをもとに手で作った小さな見本（実データを含まない）で確かめる（6.3）。少なくとも次を確かめる:
  - 予約名・本番・種類不明で、手動は止まり、自動は「取らない」で終わる
  - `stop` が、状態ファイルにない TraceFlag を消さない
  - 手動: ほかの USER_DEBUG があるとき、確認なしでは止めない。止めるときは、期限を「元の期限」と「今から 2 分後」の早いほうにし（延ばさない）、新しい TraceFlag をその期限から始める（その期限が過ぎていれば今から）。縮めたあとに作成が失敗しても、元に戻さず、ID・元の期限・縮めた期限を書く。USER_DEBUG が 2 つ以上なら止まる（die）。DEVELOPER_LOG・ほかの種類には触れない
  - 取得: 全ユーザーの一覧の応答（他の人のログの ID・ユーザー ID）が、`sf-log.log`・`error.log`・画面に出ない（成功・失敗とも）
  - 取得: 取りたい ID は一覧の時点で固定する。取りたいログより新しいログがすべて自分のものなら `-n` で 1 回で取り、他の人のログが混ざる・一覧に残りがあるときは `-i` で取る。`-n` で押し出されて足りない ID は、その回に `-i` で取る。取りたい ID 以外のファイルは、中を読まずに消し、保存・記録しない。`<ID>.log` の形でないファイルがあれば、その回を失敗にする
  - 要約: 複数行にまたがるイベント（`FATAL_ERROR`・`LIMIT_USAGE_FOR_NS`）・後ろに `|` が付かない行を読める。行の時刻を、ログのユーザーのタイムゾーンとして表示する。`USER_INFO` の行がないときは「タイムゾーン不明」と添える
  - 自動: ほかの TraceFlag に触れない（更新も削除もしない）
  - 自動: 確認で `q` を押しても、sf-start が中断しない
  - 検索の文に埋め込む値（ID・日時・件数・PID）の形が違えば、失敗として扱う（状態ファイルを書き換えた場合を含む）
  - `--hours` の範囲外・整数でない値で止まる
  - 取得・要約に失敗したとき、状態ファイルが変わらない
  - 取得役: 持ち主が全部死んだら、後始末をして止まる／一部だけ死んだら、止まらない／停止の依頼で止まる／2 つ目は起動しない／前の組織の取得役と入れ替わる／12 時間で止まる
  - `leave`: ほかの持ち主がいれば、何も止めない。最後の 1 つなら止める。後始末の最中（`CLOSING`）に来た sf-start は、後始末が終わるまで待ってから登録する
  - 取得: 同じ時刻のログが 51 本以上あっても、しおりの境目の条件で、取りこぼさない
  - `stop`・`leave`: TERM のあとも取得役が生きていれば、TraceFlag を消さない
  - 取得役: 停止の依頼・CLOSING・印の入れ替わりに気づいたら、組織に何もせずに止まる（延長の直前にも確かめる）
  - 取得のロック: 取得役と `pull` が同時に取ろうとしても、片方だけが取る。同じログの本文がすでにあれば、成功として扱う
  - 要約: 読めない行があっても要約を作り、「読み取れなかった行」と「該当する行なし」を分けて書く
  - 持ち主の印の起動の時刻が違う（PID の再利用）とき、死んだとみなす
  - 取得役が生きているときの `pull` は、自分で組織から取らない（依頼する）。2 つの `pull` が同時に頼んでも、それぞれ自分の応答を受け取る
  - `.lock` が古い（PID が死んでいる）とき、消して進む
  - 取得: 51 本以上あるとき、古い順に 50 本を取り、次の回で続きを取る（取りこぼさない）。途中で失敗したとき、保存した分は取り直さない
  - `pull --max` を超えたとき、入れなかった本数と時間帯が要約に出る
  - `.consent`: 組織の ID・文面の版が変わったら、もう一度聞く
  - sf-switch-org で、新しい組織の `start --auto` が失敗したとき、前の組織の取得役も止まり、`.status` に理由が出る
  - `sf-start.sh`: sf-log.sh の終了コード（0・10・1）ごとの表示と、どれでもランチャーが起動すること。入れ子（sf-switch-org）の終了時に、取得役を止めないこと（`tests/test_sf-start.sh`）
  - ランチャー（`phases/start/launcher.sh`）: `.status` があれば 1 行を表示し、なければ何も表示しないこと（`tests/test_launcher.sh`）
