## 1. 目的と判断基準

### 1.1 目的

**指示のとおりに操作すれば、迷わず、最後まで設定が完了する**こと。利用者がポチポチと選んでいくだけで終わる、ウィザード形式にする。

### 1.2 合否の基準（これが満たせなければ不合格）

利用者が、使っている最中に、次のどれかを思ったら、それは**設計の不具合**である。

| 利用者の疑問 | 設計が満たすべきこと |
|---|---|
| 「いま、どこ？」 | すべての画面に、現在地（全体のうち、いくつ目か）を出す |
| 「これは、何？」 | 画面の先頭に、このステップが何のためかを、1 文で出す |
| 「次は、何をすればいい？」 | 利用者の操作を、1 画面に 1 つだけ、はっきり書く |
| 「このあと、どうなる？」 | 操作のあとに起きることを、先に書く |
| 「どれを選べばいい？」 | 推奨を先頭に示し、迷う選択肢は、そもそも出さない |
| 「固まった？」 | 待ち時間は、「何を待っているか・最大どのくらいか」を出す |
| 「失敗した。どうすれば？」 | 何が起きたか／どう直すか／どこから再開されるか、を出す |
| 「終わった？次は？」 | 完了画面に、できたことと、次にやることを出す |

## 3. 設計原則

| # | 原則 | 具体的なルール |
|---|---|---|
| R1 | **全体像を最初に** | ステップの一覧・所要時間の目安・事前に用意するもの（必要な権限・組織の数も）を、最初に出す。準備ができてから、始める |
| R2 | **現在地を常に** | すべての画面の先頭に `ステップ 3 / 9: ○○` と、完了済みを出す |
| R3 | **1 画面に 1 つの操作** | 利用者の操作は、1 画面に 1 つ。「やること」と「そのあと起きること」を、書く。複数の操作が要るときは、画面を分ける |
| R4 | **利用者に判断させない** | 検出できるもの・既定が決まるものは、聞かない。判断が必要なときは、推奨を先頭にして、Enter で推奨を選べるようにする |
| R5 | **言葉を平易に** | 専門用語は、はじめに 1 度だけ説明する。内部の呼び名（Phase・ECA・JWT）は、画面に出さない |
| R6 | **操作の語彙を統一** | `Enter` = 次へ／`番号` = 選択／`q` = 中断。画面の下に、毎回、操作のヒントを出す |
| R7 | **待ち状態を明示** | ブラウザで作業するときは、「何の画面が出ていれば合っているか」「何をするか」「終わったら何を押すか」を書く。**時間制限があれば、先に書く**（P15） |
| R8 | **待ち時間を明示** | 数十秒以上かかる処理は、「何を待っているか・最大どのくらいか・いま何回目か」を出す（P16） |
| R9 | **失敗の三点セット** | 何が起きたか／どう直すか／**どこから再開されるか（再開の単位を、正確に）**。（`die` は、既存規約どおり事実のみ。案内は、直前の `log` で出す） |
| R10 | **完了画面** | できたこと／次にやること（具体的なコマンド・URL）を出す。実際に設定できたものだけを書く |
| R11 | **やり直せる** | 中断しても、再実行で、続きから再開できる。各ステップは、冪等にする |
| R12 | **機密を見せない** | Token 等は、画面・ログに出さない（既存規約） |

### 4.2 開始画面（R1）

```
══════════════════════════════════════════════
  新しい Salesforce プロジェクトを作ります
══════════════════════════════════════════════

  作るもの   : tamashimon-org/force-yamada（GitHub のリポジトリ）
  かかる時間 : 30〜60 分ほどが目安です（ブラウザでの作業・Salesforce の反映待ちを含みます）

  （管理者向けの警告ボックス。sf-tools が古ければ、ここで更新の確認）

  【先に、用意してください】
    □ GitHub : tamashimon-org の管理者としてログインしたブラウザ
    □ Slack  : 通知用の「共有チャンネル」（全員が参加するもの）
               まだなければ、いま Slack で作ってください
    □ Salesforce : 接続する組織の、システム管理者のアカウント
               ブランチの構成で選ぶ数（1〜3 組織）だけ、必要です

  【これから行うこと】
    1. 準備の確認
    2. プロジェクトの確認
    …（1 行に 1 つ）
    8. Salesforce の接続
    9. 動作の確認

  ▶ 用意ができたら Enter を押してください（q で中断）:
```

- 管理者向けの警告（既存の赤いボックス）と、「続行しますか？」は、**この画面に統合**する（P13）。**実装済み**: 警告ボックスは、所要時間の下に出し、確認は、最後の `wizard_confirm` の 1 回（Enter / Y で進む。N / q / EOF は中断）。`--resume N`（2 以上）/ `--only N` のときは、全体像を出さず、警告ボックスのあと「続行しますか？」（`ask_yn`）。
- 前回の途中までの状態が残っている場合の「続きをやる／最初からやり直す」（実装済み）は、**この画面のあと**（確認・`check_gh_owner`・ロックのあと）に出す。完了済みのときの選択（接続を見る／動作を確認／最初から）も、同じ位置。
- sf-tools が古い場合は、管理者向けの警告のあと、確認の前に、**確認のうえ更新し、自動で、もう一度、はじめから実行する**（P14。実装済み）。実行しなおしたあとも、警告と確認は、毎回出す（確認を飛ばさない）。詳細は `doc/dev-reference.md` 4.13。

### 4.3 各ステップの共通の見た目（R2・R3・R6）

```
──────────────────────────────────────────────
  ステップ 5 / 9: GitHub の Token を作ります
  （完了: 準備の確認・プロジェクト・リポジトリ・ブランチ）
──────────────────────────────────────────────

  ○○のために、必要です。（1 文）

  ▶ あなたがやること
      1. …
      2. …

  ▶ そのあと
      この画面に戻って、貼り付けて、Enter を押してください

  [Enter] 次へ   [q] 中断
```

- 自動のステップは、「ステップ n / 9: ○○ ... ✔ 完了」の 1 行に集約する（画面を埋めない）。
- ブラウザを使うステップは、R7 に従い、「ブラウザに、○○の画面が出ます。**そこで、やること**」を、箇条書きにする。
- **実装の状況**: 見出し（区切り線・`ステップ n / 9: タイトル`・「（完了: …）」・目的の 1 文）は、実装済み（S1。フェーズループが、新しいステップに入るときに `wizard_step` を出す。同じステップの 2 つ目の Phase では、出さない）。完了済みの名前は、ステップのタイトルの全文（例: 「準備の確認・プロジェクトの確認・リポジトリの作成・ブランチの構成」）。「▶ あなたがやること」「▶ そのあと」・画面の下のヒント・自動のステップの 1 行表示は、未実装（S2。部品の `wizard_do` / `wizard_next` / `wizard_hint` / `wizard_auto` はあるが、どの Phase も使っていない）。

### 4.4 主要な画面の設計

**(1) ステップ 2（プロジェクトの確認）**: Y/N を聞かず、内容を見せて Enter のみ。誤りの原因は、指定した（入力した）オーナー・プロジェクト名であることを書く。（**未実装**: Phase 2 は、リポジトリとクローン先を表示して、`ask_yn "▶ よろしいですか？"` で聞く。続けて、sf-tools の版を選ばせる: (2)）

```
  次の内容で、作ります。
    GitHub のリポジトリ : tamashimon-org/force-yamada
    作る場所             : ~/sf/admin/force-yamada

  指定した（入力した）オーナーとプロジェクト名（XXXX）から決めています。違う場合は q で中断して、
  正しい値を指定してから、もう一度、実行してください。

  [Enter] この内容で進む   [q] 中断
```

**(2) 環境種別（本番／検証）（P4）**: 一般の利用者には**聞かない**。既定は「本番環境」。sf-tools の開発者が検証環境を使うときだけ、環境変数 `SF_TOOLS_BRANCH=development` で指定する（既存の仕組み）。検証環境のときだけ、開始画面に「検証環境（開発者用）で実行します」と表示する。（**未実装**: Phase 2 は、今も「sf-tools の版」を `[1/2/q]` で聞く（1 = 配布版 `main` / 2 = 開発版 `development`。2 は、警告と確認のあと）。開始画面の検証環境の表示もない。Q1）

### 4.5 失敗の画面（R9・R11）


実装（S1）:

```
     原因     : 「GitHub の Token」で、中断しました（上の表示を、確認してください）
```

### 4.6 `--legacy-connected-app` の仕様

S3 で実装済み（正本は、`bin/sf-init.sh` と `phases/init/10_sf_auth.sh` の冒頭コメント）。

| 項目 | 内容 |
|---|---|
| 指定方法 | `sf-init.sh --legacy-connected-app`（新規実行・`--resume N` のどちらでも指定できる）。実体は環境変数 `SF_INIT_LEGACY_CONNECTED_APP=1` で、`--add-tier` / `--reconnect`（`add_tier.sh`・`reconnect.sh`）も、これを見る |
| 動作 | Phase 10 のアプリ種別を、「接続アプリケーション（1）」にする。従来の手動手順（Connected App の作成案内・コンシューマー鍵とユーザー名の入力）に、そのまま入る。ログイン先は、既定と同じ 3 択。JWT 接続テストと組織の種類の読み取りを、同じ一時的なホームの中で行い、Secrets を登録する前に、本番は main のみのガードを通す（`org_jwt_test`・10.4 の 2） |
| 保存 | 選んだ種別は、`APP_TYPE` として `.sf-init-XXXX.env` に保存する（既存の仕組み）。続きから再開するときは、保存した種別を使い、オプションの再指定は要らない |
| 既定 | 指定がなければ、外部クライアントアプリ（2）。`APP_TYPE` が保存されていれば、その値（`APP_TYPE=1` が保存済みなら、指定がなくても 1 のまま） |
| 無効な組み合わせ | `--legacy-connected-app` と、保存済みの `APP_TYPE=2` が食い違うとき（途中まで ECA で進めたあと）は、中断して、事実を表示する |
| ヘルプ | `--help` と、不明なオプションのメッセージに、追記する |
| テスト | 既定の経路（ECA）と、`--legacy-connected-app` の経路を、別々のシナリオにする |

### 4.7 段階と、組織の種類の独立（柔軟性の設計）

> 利用者（設計者・導入する人）は、**開発の時期・テストの時期・本番への代行**など、さまざまな場面で使う。導入する側も、**お試しで Sandbox に入れる → 本番に入れる**と、**段階的に**進める。どの段階（main / staging / develop）にも、**どの種類の Salesforce 組織（本番・Sandbox・Developer Edition）が来るかは、不定**である。この前提で、設計する。

#### 4.7.1 独立した 3 つの軸

| 軸 | 内容 | 制約 | あとから変えられるか |
|---|---|---|---|
| A. 段階の数 | main / staging / develop（何段階か） | なし | 増やせる（`--add-tier`・実装済み） |
| B. 各段階の接続先 | 段階ごとに、**ログイン先の URL**（本番・Developer Edition 等 / Sandbox / 組織の URL）と、接続するユーザー | **Salesforce の本番組織は、main にしか、つなげない**（staging・develop には、つなげない。4.7.2 の F8）。Sandbox・Developer Edition などは、**どの段階にも、つなげる**（main にも） | **付け替えられる（`--reconnect`・実装済み）** |
| C. sf-tools の版 | 配布版（main）・検証版（development） | 開発者向け | 環境変数 `SF_TOOLS_BRANCH` |

#### 4.7.2 ルール

| # | ルール |
|---|---|
| F1 | **段階の名前（main / staging / develop）と、組織の種類は、基本的に、結びつけない。** 「main = 本番」「staging = Sandbox」を、前提にしない（画面・文言・既定値・判定）。**唯一の制約は F8（本番は main のみ）** |
| F2 | ログイン先は、**URL で決める**（`login.salesforce.com` / `test.salesforce.com` / 組織の URL）。「種類」を聞いて、URL に変換することは、しない |
| F3 | 組織の種類は、**ログイン後に、組織自身から読み取る**（`IsSandbox`・`OrganizationType`）。表示と保存（状況の確認用）に使う。ログイン先の決定には、使わない（ログイン前に決める必要があるため） |
| F4 | 画面の呼び名は、**段階の名前**と、**実際の組織名・種類**にする。「本番」「検証」を、段階に当てはめない |
| F5 | 接続先は、**あとから付け替えられる**。段階ごとに、1 つずつ、同じ画面の流れで、やり直せる |
| F6 | 日々のコマンド（sf-start 等）も、**エイリアスの名前**で、ログイン先を決めない（P17）。認証済みの組織の一覧から選ぶ。新しくつなぐときは、F2 の 3 択（**一部実装**: sf-start は、エイリアスの名前で決めるのをやめ、F2 の 3 択にした（環境変数 `SF_INIT_LOGIN_URL_START` でも指定できる）。一覧から選ぶのは未実装で、エイリアスは入力する） |
| F7 | 安全のための既定（Sandbox）は、**段階に依存しない**。どの段階でも、同じ。本番に接続するときだけ、利用者が、明示的に選ぶ |
| F8 | **Salesforce の本番組織は、main にしか、つなげない**（ソースの流れは、develop → staging → main で、本番に出るのは、main のみ。staging・develop が本番に接続されると、意図しない本番への反映になるため）。**ガード**: ① staging・develop のログイン先の選択肢 [1] には、「本番は、main のみ」と添える。② **ログイン後**、組織から種類を読み取り（F3）、**本番と判定されたら、staging・develop には、接続しない**（中断して、事実を表示する）。③ **判定できないとき（種類を読み取れない・矛盾する）は、main 以外には、つなげない**（利用者の確認では、通さない。本番かどうか、確かめられないため。外部レビューの指摘で、確認で通す案から変更）。main は、どの種類でも可（判定できなくても、続行する）。④ `--reconnect` でも、同じガードを通す |

#### 4.7.3 段階的な導入の流れ

| 場面 | やること | 使うもの |
|---|---|---|
| お試し（Sandbox 1 つ） | 1 段階（main）にして、ログイン先に Sandbox を選ぶ | `sf-init.sh` |
| 本番にも入れる | main の接続先を、本番に付け替える。または、段階を増やして、本番を後ろに置く | `sf-init.sh --reconnect main` / `--add-tier` |
| 開発用・検証用の組織を増やす | 段階を増やす | `sf-init.sh --add-tier staging` / `--add-tier develop` |
| 本番作業の代行 | 利用者の管理者として、ブラウザでログインして、接続する | `sf-init.sh`（F2 の [1]） |
| いまの接続を見る | 段階ごとの、ログイン先・組織名・種類・ユーザーを、一覧にする（実装では、その前に、セットアップの診断も出す） | `sf-init.sh --status`（実装済み） |

#### 4.7.6 接続情報のモデル（共通）

`sf-init.sh`・`--reconnect`・`--status`・`sf-start.sh`・`sf-update-secret.sh` が、**同じ接続情報モデル**を使う（実装を、共通の関数に集約する）。段階ごとに、次を持つ。

| 項目 | 内容 | 保存先 |
|---|---|---|
| ログイン入口 | `login.salesforce.com` / `test.salesforce.com` / 組織固有の URL | GitHub Variables `SF_INSTANCE_URL_*`（既存） |
| 接続ユーザー | 管理者権限のユーザー名 | GitHub Variables `SF_USERNAME_*`（既存） |
| コンシューマー鍵 | 外部クライアントアプリのキー | GitHub Secrets `SF_CONSUMER_KEY_*`（既存） |
| 組織 ID・組織名 | ログイン後に、組織から読み取る | GitHub Variables `SF_ORG_ID_*`・`SF_ORG_NAME_*`（実装済み。機密ではない） |
| 組織の種類 | `IsSandbox`・`OrganizationType`・（Trial の場合）期限 | `SF_ORG_KIND_*`（実装済み。表示用。保存するのは、判定した種類 production / sandbox / developer / trial / unknown だけで、元の項目と Trial の期限は、保存しない） |
| 最終確認日時 | 実際にログインして、確認した日時 | `SF_ORG_CHECKED_*`（実装済み） |

- 保存は `org_save`（`lib/org.sh`）。組織の情報を読み取れたとき（組織 ID があるとき）だけ保存する。共通の関数は、`lib/org.sh`（ログイン先の選択・種類の読み取り・ガード・保存）にまとめた。`sf-init.sh`・`--reconnect`・`--add-tier` は、`phases/init/init-common.sh` の `register_jwt_secret` / `register_jwt_secret_eca` を通して使う。`sf-update-secret.sh` は、`lib/org.sh` を直接使う（ログイン先の選択・`org_jwt_test`・`org_guard`・`org_save`）。`sf-start.sh` は、ログイン先の選択だけを使う。`--status` は、Variables を読むだけ。

- **用語**: 「ログイン入口」（`login.salesforce.com` など。組織そのものの URL ではない）と、「組織固有の URL」（My Domain）を、区別して書く。
- **種類の読み取り**: ログイン後に、`sf data query` で、`Organization`（`Id`・`Name`・`IsSandbox`・`OrganizationType`・`TrialExpirationDate`）を取得する。**取得できない・矛盾する場合は、「判定不能」と表示し、推測しない。main 以外には、接続しない**（main は、続行する）。項目名・値は、実機の応答を記録してから、仕様にする（Q10）。（実装済み: `org_read_info` → `org_kind`。判定の順は `lib/org.sh` の冒頭コメント・`doc/jwt-auth-spec.md`）
- **取り違えの防止**: 段階ごとに、**組織 ID を必須の状態**として保存する。`--status` と `--reconnect` は、組織 ID・組織名・ユーザー・ログイン入口・最終確認日時を表示する。（**一部実装**: 組織 ID は、読み取れたときだけ保存し、必須にはしていない（main は、判定不能でも接続する）。`--status` は、上の項目をすべて表示する。`--reconnect` の「いまの接続」は、最終確認日時を出さない）
- **同じ組織を、複数の段階に使う**: 禁止はしない。**強い警告**を出す（デプロイが、同じ組織の中で、循環するため）。`--status` で、重複を明示する。（**一部実装**: `--status` の警告だけ。接続するときの警告は、未実装）
- **スクラッチ組織**: 対象外（寿命のある、別の仕組みのため）。Trial は、期限が近い・切れたとき、`--status` で警告する。（Trial の期限の警告は、**未実装**。期限を保存していない）

#### 4.7.7 `--reconnect` の安全設計

1 つの段階の接続先を、付け替えるときの手順と、守ること。実装は `phases/init/reconnect.sh`（S3。手順の正本は、その冒頭コメント）。各項目の末尾に、実装の状態を書く。

1. **現在の接続を表示**する（段階・組織 ID・組織名・種類・ユーザー・ログイン入口）。（実装済み。続けて、管理者向けの警告・`check_gh_owner`・「付け替えますか？」（`ask_yn`）。確認は、ログインの**前**）
2. ログイン先を選ぶ（4.4 (6)）。ログインしたあと、**新しい組織の ID・名前・種類を表示**し、「この段階（main など）に、この組織をつなぎます」と、**明示的に確認**する。（**一部実装**: ログイン先の選択と、ログインした組織の表示（`org_guard`）はある。ログインのあとの明示的な確認は、ない）
3. F8 のガード（本番は main のみ）を通す。（実装済み。外部クライアントアプリを作る前に判定する）
4. **一括で更新する**: `SF_USERNAME_*`・`SF_INSTANCE_URL_*`・`SF_CONSUMER_KEY_*`・組織情報。途中で失敗したときは、**どこまで更新されたかを、表示する**（古い接続と、新しい接続が、混ざったままにしない）。（**未実装**: 1 つずつ登録し、失敗したところで中断する。新旧の値が混ざりうることは、`reconnect.sh` の冒頭コメントに書き、もう一度 `--reconnect` でそろえる運用）
5. **古い組織に残るもの**（外部クライアントアプリなど）は、自動では削除しない。**残っていることと、片付け方を、表示する**。削除は、明示の確認つきの、別の操作にする。（実装済み: 組織 ID が変わったとき、外部クライアントアプリ・接続アプリケーションの両方の名前と、削除の場所を表示する。削除の操作は、作っていない）
6. `--add-tier` と、`sf-update-secret.sh` との**役割**: `--add-tier` = 段階（ブランチ・ワークフロー）の追加。接続は、共通の接続の流れを使う。`sf-update-secret.sh` = 鍵・ユーザー名の部分的な更新（鍵の入れ替えなど）。付け替えは、`--reconnect`。いずれも、4.7.6 の共通の関数を使う。（実装済み）

### 10.3 利用者（設計者）からの制約

- **Salesforce の本番組織は、必ず main**（staging・develop には、つなげない）。それ以外の種類（Sandbox・Developer Edition など）は、どの段階にも、つなげる。→ F8（4.7.2）。ガードは、ログイン後の種類の読み取りで行い、判定できないときは、利用者に確認する（Q10）。（のちに、10.4 の 1 で改訂: 判定できないときは、確認では通さず、main 以外にはつなげない。F8 ③）
