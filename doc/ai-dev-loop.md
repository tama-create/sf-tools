# AI 向けの開発サイクルの手順（デバッグログを読みながら直す）

> この手順書は、force-* のプロジェクトで Salesforce の開発を手伝う AI（Claude Code・Codex など）が読む。
> force-* の `CLAUDE.md`・`AGENTS.md` は、この文書を指す 1 行だけを持つ（sf-tools の `templates/` から入る）。
> 手順を直すと、各利用者の `~/sf-tools` の `git pull` で届く。設計の正本は `~/sf-tools/doc/sf-log-design.md`（11 章）。

## 1. 前提

- 作業の場所は force-* のプロジェクトのルート（`sfdx-project.json` があるフォルダ）。コマンドは `bash ~/sf-tools/bin/<名前>.sh` で呼ぶ
- 人は `sf-start.sh` で作業を始める。sf-start は、ランチャーを開く前に、デバッグログ（`ApexLog`。Apex だけでなく、フロー・入力規則・重複ルールなど、1 回の処理の動きの記録）を、裏で自動で取り始める。ランチャーの見出しの下に、状態の 1 行（取得中・準備中・取っていません など）が出る
- 取るのは、接続中の組織の、**自分のユーザー**のログだけ。一人用の開発組織（Developer Edition・Sandbox・スクラッチ組織）で、ダミーデータで使う
- **sf-start と同じ環境で実行する**（sf-start を WSL で起動したなら、AI のコマンドも WSL で。Windows の Git Bash と WSL を、同じプロジェクトで混ぜない。取得役が別の環境で動いていると、正しく見分けられない）

## 2. 開発のサイクル

### 2.1 始める前に

- `bash ~/sf-tools/bin/sf-log.sh status` で、取得役が動いているか・TraceFlag の期限を確かめる
- 動いていなければ、理由を人に伝える（取らない組織・答えが「取らない」・ほかの TraceFlag と重なっている など。`status` とランチャーの 1 行に出る）。取り始めるのは人（`sf-start.sh` のやり直しか `sf-log.sh start`）

### 2.2 直して、デプロイする

- コードを直し、`bash ~/sf-tools/bin/sf-deploy.sh` でデプロイする（デプロイの前の確認は、そのコマンドの案内に従う）

### 2.3 人に、確かめる操作を頼む

- 画面での操作を、具体的に伝える（どの画面で、どのレコードに、何をするか）。終わったら知らせてもらう
- デバッグログには、画面のクリックそのものは残らない（サーバーで動いた処理だけ）。人に、操作の内容を一言添えてもらうと、ログと結び付けやすい

### 2.4 ログを読む

- `bash ~/sf-tools/bin/sf-log.sh pull` を実行し、`logs/apex/latest.md` を読む（組織には書き込まない。何度呼んでもよい）
  - 取得役が動いていれば、取得役に「今すぐ取って」と頼んでから要約する。動いていなければ、自分で組織から取る
  - 要約には、前回の `pull` のあとに手元に保存したログが入る（開始時刻ではなく、保存した順。遅れて取れた長い処理のログも漏れない）
- 要約の節（上から順）:
  1. エラー（例外・致命的なエラー・フローのエラー。場所 `[ファイル:行]` つき）
  2. ログの一覧（操作・状態・長さ・所要・SOQL・DML。操作の括弧に、最初の処理と、フロー・入力規則・重複ルールの名前）
  3. `System.debug` の出力（新しい順）
  4. フロー・入力規則・重複ルール（どのフローが動き、どの要素を実行したか・入力規則の評価と停止・重複ルールの保存の中と後の回数・見つかった重複・動作）
  5. 制限の使用量（上限の 50% を超えたものだけ）
  6. 切り詰め・出なかった区分・読み取れなかった行
- 詳しく見たいときだけ、要約に書かれた `[ファイル:行]` の本文を開く（本文の全部を読まない。長い）
- 要約の先頭の注意（「入れなかった古いログ」「拾い直しに失敗」「要約のロックを取れませんでした」など）を、必ず読む。古い分は `pull --since <分>`（必要なら `--max <本数>`）で入れ直せる

### 2.5 直して、2.2 に戻る

- 原因が分からないときは、人に `sf-log.sh start --level detail` を頼む（詳しいログに切り替える。項目の値・条件の結果・制限の使用量などが出る。ログが大きくなる）

## 3. Apex を試しに動かすとき

- **動かす前に、毎回、人の了承を取る**（読み取りだけのコードも）。了承を求めるときは、接続先の組織（エイリアス・組織 ID）と、動かす Apex の全文を見せる。組織でコードを動かすことは、データの書き換え（DML）・非同期の処理の登録・外部への通信になりうるため
- `sf apex run` ではなく、Tooling API の `executeAnonymous` を直接呼ぶ（`sf apex run` は、sf が自分の詳しさでログを出すため、SOQL・DML などの行が出ない）:
  `MSYS_NO_PATHCONV=1 sf api request rest "/services/data/v68.0/tooling/executeAnonymous/?anonymousBody=<URL エンコードしたコード>" --target-org <エイリアス>`
  - Windows の Git Bash では、`/` で始まる引数が Windows のパスに書き換えられることがあるため、`MSYS_NO_PATHCONV=1` を付ける
  - コードは URL の引数（GET）でしか渡せない。長いコード（URL エンコード後に約 16KB を超えるもの）は失敗しうる。長いコードは、クラスにしてデプロイしてから呼ぶ
- データを残さずに試すときは、セーブポイントで巻き戻す（`Savepoint sp = Database.setSavepoint(); … Database.rollback(sp);`）

## 4. AI がしないこと

- `sf-log.sh start`・`stop`・`auto` を実行しない（組織への書き込みと、取るかどうかの判断は、人に残す）
- 組織のログや、手元のログ（`logs/apex/`）を消さない
- 了承なしに、組織のデータを書き換えない（3 章）

## 5. ログで取れないもの・注意

- **長い処理のログ**: ログは、処理が終わってから組織の一覧に現れる。取得役と `pull` は、直近 30 分に始まった自分のログを確かめ直して拾う。目安として、処理の時間と取得の間隔（既定 3 分）を足して 30 分を超えるログは、取れないことがある
- **LWC・Aura の画面側のエラー**（ブラウザのコンソール）は、デバッグログに残らない。人に、ブラウザの開発者ツールのコンソールの内容を貼ってもらう
- **別のユーザーで動く処理**: プラットフォームイベントのトリガー（Automated Process ユーザー）・スケジュールで動くフロー・プラットフォームイベントで動くフロー・他の人がスケジュールしたジョブは、自分のユーザーの TraceFlag では取れない
- **非同期の処理**（Queueable・Batch・future）は、実行の時刻がずれる。`pull` を少し待ってから呼ぶ
- **重複ルール**: 動作が「許可（警告）」のルールでも、Apex・API の保存は、`DuplicateRuleHeader.allowSave` がなければ止められる（`DUPLICATES_DETECTED`）。部分保存（`Database.insert(…, false)`）は、ログに失敗の行が出ない。要約の 4 の「重複あり」で見る
- 取得中に人が Developer Console を開くと、別の種類（DEVELOPER_LOG）の TraceFlag が作られる。ログの詳しさがどうなるかは未確認。ログの行が足りないと感じたら、`status` で確かめる
