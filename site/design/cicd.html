🧭 CI/CD の仕組み（設計の考え方）

sf-tools は、変更を 1 段ずつ確かめながら、本番に届ける仕組みを、自動で動かします。このページでは、その全体像と、なぜこの作りなのかを説明します。コマンドの使い方は、コマンド一覧にあります。

ひとことで言うと

変更は、開発用 → 検証用 → 本番の順に、1 段ずつ進みます。各段で、自動のチェックが入るので、確かめないまま、本番に出ることを防げます。本番の組織で直接加えられた変更は、定期的に（平日の 3 時間おきに）Git に取り込まれ、ほかの段にも広がります。

（CI/CD は、変更の確認と反映を自動で行う仕組みのことです。）

sf-tools の位置づけ

Salesforce の組織は、そのままでは、Git で管理されていません。変更の履歴が残らず、誰が、いつ、何を変えたかを、あとから追いにくい状態です。

sf-tools は、ソースコードを Git で管理する、普通の開発の流れ（手元で開発 → commit・push → PR → マージ）の中で、検証から本番へのリリースまでを、自動でつなげる道具です。共有の環境へのリリースは、組織に向けて直接コマンドを打つのではなく、Git への変更の取り込み（マージ）の結果として起きます。自分用の組織には、手元から試せます（手元での検証と、共有の環境の保護）。

Salesforce には、変更セットや DevOps Center など、リリースのための仕組みが、標準で用意されています。sf-tools は、それらとは別のアプローチで、Git（と GitHub）を中心に置き、開発の流れと、自動の仕組み（GitHub Actions）を、一続きにつなぎます。どちらが正しい、ということではなく、Git を中心にして開発したいチームのための選択肢です。

内部では、Salesforce CLI（sf）を使っています。CLI は強力ですが、使いこなすのが難しいため、sf-tools が包んで、日々の作業を「番号を選ぶだけ」にしました。コマンドの寄せ集めではなく、開発の流れと、自動の仕組みが、一続きでつながる仕組みです。このページでは、その仕組みの中身を説明します。

設計の 3 つの柱

Salesforce のメタデータは、変更した部分だけを、差分として扱えます。この特性を活かして、Git（変更の履歴）と各組織（本番・ステージング・開発）の内容を、いつもそろえます。

  1. 本番が正（原本） — 本番の組織を、いつも「原本」として扱います。本番で起きた変更は、平日の 3 時間おきに、自動で見つけて Git に取り込み、Git 上のほかの段階のブランチへも広げます。人が何もしなくても、ずれを、自動でそろえ直す仕組みです（取り込むのは、sf-tools/config/metadata.txt に書いた種類だけです）。

  2. 作業用のブランチから、各環境へ、1 本ずつ届ける（スター型のプロモート） — 作業用のブランチから、各環境へ向けて、それぞれ別に PR（取り込みの依頼）を出します。環境のブランチどうしを、直接つなぐことは、禁止です。

  3. 自己完結型のワークフロー — 自動で動く処理（ワークフロー）の定義（いつ・何を動かすか）を、各プロジェクト（force-*）の中に含めます。雛形は sf-tools が持っていて、プロジェクトを作るときに、コピーします。処理の中身のスクリプト（sf-release.sh・sf-metasync.sh）は、ワークフローが動くたびに、公開されている sf-tools から取ってきて使います（ワークフローの全体像）。

環境とブランチ

ブランチの階層は、sf-tools/config/branches.txt で、プロジェクトごとに決めます。管理者が、セットアップ（sf-init.sh）のときに、3 つのパターンから選びます。

パターンブランチ使いどころ
3 階層main / staging / develop標準の構成（開発 → 検証 → 本番）
2 階層main / staging開発用の組織を使わない場合
1 階層main小さなプロジェクト・1 人での開発

main は必ず使います。develop を使うときは、staging も必要です。3 階層の場合の対応は、次のとおりです。

層組織ブランチエイリアス役割
本番層Productionmainprod正（Source of Truth）。本番の最新の状態
検証層Staging / UATstagingstaging結合テスト・顧客の確認用
開発層Development / QAdevelopdevelop最初の検証用。開発のベースライン
作業層各自の Sandbox など（自分用の組織）作業用のブランチ（ジョブ名。例: JOB-20260323）自由（sf-start.sh で入力）作業項目ごとの、変更の源

作業用のブランチは、開発者が sf-job.sh で、GitHub 上の main の最新から、ジョブ名と同じ名前で作ります。エイリアス（組織に付ける短い呼び名）の prod / staging / develop / main は、共有の環境のための予約名です。手元のパソコンからは、この名前の組織へ、検証もリリースもできません（手元での検証と、共有の環境の保護）。

段階は、あとから足せます（構成の変更と診断）。

プロジェクトの作成（管理者が先）

プロジェクト（force-XXXX）は、管理者が先に sf-init.sh で作ります。リポジトリ・ワークフロー・ブランチ・ブランチ保護・GitHub に登録する情報（Secrets / Variables）・組織への接続・最初のメタデータの同期まで、まとめて用意します（最初のセットアップ）。

開発者は、管理者から「できました」の連絡を受けてから、sf-job.sh で作業を始めます。リポジトリがまだないと、sf-job.sh は止まります。そのため、管理者と開発者の作業は、並行して進められません。

リリースの流れ（スター型のプロモート）

すべてのリリースは、作業用のブランチを起点にして、各ターゲットのブランチへ、個別に PR を出して行います。

リリースする対象は、作業用のブランチにコミットした、sf-tools/release/<ブランチ名>/ のターゲットファイルに書いたものだけです。deploy-target.txt に追加・更新するもの、remove-target.txt に削除するものを書きます（ターゲットファイルの書き方）。同じターゲットファイルが、各環境への PR で使われます。

なぜ、環境ブランチどうしを、直接マージしないのか

環境ブランチの間でマージすると、意図しない変更が混ざるおそれがあります。必ず作業用のブランチを経由させることで、「各環境に、何がデプロイされたか」を、はっきり追えます。

マージの順序

おすすめの順序は、branches.txt の逆順（下位 → 上位）です。3 階層なら develop → staging → main の順です。

  • 開発者が sf-next.sh を使う限り、順序は守られます（sf-next の説明）。
  • GitHub 上で直接 PR を作り、順序を飛ばしたときは、wf-sequence が警告します（main / staging への PR のとき）。PR の会話欄にコメントを書いて、Slack にも通知します。マージは止めません（緊急のリリースを妨げないため）。気づいたレビュアーが、却下します。
  • 環境ブランチからの直接の PR（例: develop → staging、staging → main）は、エラーにします（必須チェック「順序チェック」が失敗し、PR へのコメントと Slack の通知も行います）。

実際にマージを止めるのは、ブランチ保護（GitHub の Ruleset。main と staging に設定）の必須チェックです。「これが成功しないと、PR をマージできない」チェックのことで、対象ファイル確認・デプロイ検証・順序チェック の 3 つを登録します。無料プランの非公開リポジトリなどで、ブランチ保護を設定できなかったときは、失敗が表示されるだけで、マージは止まりません（レビュアーが却下します）。リポジトリの管理者は、ブランチ保護を越えられます。

順序を飛ばすと、飛ばしたブランチへは、デプロイできなくなります

上位のブランチ（例: main）にマージすると、コードが下位のブランチ（例: staging）に伝わります（wf-propagate）。伝わったあとは「差分なし」になり、直接の PR を作れません。デプロイのワークフローは、直接の PR のマージで動くため、伝わっただけでは動きません。

飛ばしたブランチにデプロイしたいときは、新しいブランチを切って、順序どおりに PR を出し直します。

手元での、プッシュの前のチェック

git push のとき、pre-push フック（プッシュの直前に、自動で動くチェック）が、次のことを行います。

  1. 環境ブランチ（branches.txt のブランチ。保護ブランチとも呼びます）の上からのプッシュと、環境ブランチへのプッシュ（git push origin feature:main や、削除も）を止めます。ブランチの上にいないとき（detached HEAD）も止めます。
  2. ターゲットファイルの書き方を確かめます（エラーなら止めます）。
  3. リモートの最新の作業用のブランチと main（自動で更新された、本番の状態）に、まだ取り込んでいない変更があれば、自動でマージして取り込みます。取り込んだときは、そのプッシュは中止します（取り込んだ変更が、そのプッシュに含まれないためです）。もう一度プッシュすると、通ります。

フックは、sf-start.sh が裏で動かす sf-install.sh が、自動で入れます。sf-push.sh・sf-next.sh も、環境ブランチの上では動きません。

手元での検証と、共有の環境の保護

  • ランチャーの 1 Check（sf-check.sh）: ターゲットファイルの書き方・パス・メタデータの種類（リリース・削除できるか）を確かめます。
  • ランチャーの 4 Dryrun（sf-dryrun.sh）: 接続中の組織で、「反映できるか」だけを確かめます（組織には反映しません）。
  • ランチャーの 5 Deploy（sf-deploy.sh）: 自分用の組織（個人の Sandbox・Developer Edition など）に、実際に反映します（確認の Y/N があります）。
手元からは、共有の環境と本番の組織に、検証も反映もできません

エイリアスが予約名（prod / staging / develop / main）の組織と、本番の組織（名前に関係なく。組織の種類を読み取って確かめます。種類を確かめられない組織も止まります）には、dry-run も含めて、手元のパソコンからは実行できません。共有の環境への反映は、GitHub にコミットし、PR のレビューを通して、GitHub 上のワークフロー（wf-release）だけで行います。誤操作を防ぐためです（共有の環境の接続の情報は、GitHub にあり、手元にはありません）。

ワークフローの全体像

ワークフローの定義は、各プロジェクトの .github/workflows/ に含まれます。雛形は sf-tools/templates/.github/workflows/ にあり、sf-init がコピーします。

sf-tools（雛形の正本）                       force-* リポジトリ（完全内包版）
templates/.github/workflows/  ─ sf-init →   .github/workflows/
├── wf-validate.yml                          ├── wf-validate.yml
├── wf-sequence.yml                          ├── wf-sequence.yml
├── wf-release.yml                           ├── wf-release.yml
├── wf-propagate.yml                         ├── wf-propagate.yml
└── wf-metasync.yml                          └── wf-metasync.yml

なぜ自己完結にするのか: ワークフローの定義が、ほかのリポジトリ（sf-tools）の定義を呼び出さずに、各プロジェクトの中だけで動くようにするためです。ワークフローを直すときは、まず雛形を更新します。そのあと、管理者が sf-sync-wf.sh で、各プロジェクトに反映します。自動では書き換わりません（管理者が、作業用のブランチで実行し、PR で取り込みます）。

ただし、wf-validate・wf-release・wf-metasync は、動くたびに、公開されている sf-tools を取ってきて（Variable SF_TOOLS_BRANCH のブランチ。設定がなければ main）、その中の sf-release.sh・sf-metasync.sh を使います。そのため、スクリプトの修正は、sf-tools の main に入ると、すべてのプロジェクトに、すぐ届きます。作成済みのプロジェクトに自動で届かないのは、ワークフローの定義そのものの変更だけです。

ワークフロー目的ブロックするか
wf-validatePR の作成・更新のたびに、dry-run で検証し、結果を PR にコメントするmain / staging への PR で、失敗したらブロック（必須チェック）。それ以外への PR は、表示だけ
wf-sequencemain / staging への PR で、マージの順序を確認する環境ブランチからの PR だけ、ブロック（必須チェック）
wf-releasePR のマージで、対応する組織へリリースし、Slack に通知する—
wf-propagatemain への PR のマージで、main の変更を、staging・develop へ伝える—
wf-metasync本番の組織のメタデータを、main へ、定期的に同期する—

ターゲットファイルに、反映も削除も 1 つも書いていない PR は、検証・順序の確認・リリースの本体を飛ばします（必須チェックとしては、成功として扱います。ただし、環境ブランチからの PR の順序の確認は、飛ばしません）。

いつ動くかの一覧は、ワークフローの更新にあります。

Slack の通知

できごと通知の内容
リリースの成功・失敗（wf-release）リリース先・PR の情報・Actions のログへのリンク（リリースの対象がなく、飛ばしたときは、通知しません）
マージ順序の未確認・環境ブランチからの PR（wf-sequence）未マージのブランチ・PR の情報
下流への伝播のコンフリクト（wf-propagate）コンフリクトしたブランチ・PR の情報・Actions のログへのリンク

wf-validate の結果は、Slack ではなく、PR のコメントで知らせます。wf-metasync は、失敗しても Slack には通知しません（Actions の画面で、失敗として表示されます）。

各ワークフローの動き

wf-validate（PR の検証）

PR を作る・更新するたびに（マージ先は問いません）、sf-release.sh を検証モード（dry-run）で実行します。

  1. ターゲットファイルに、反映も削除も書いていなければ、検証を飛ばす（ジョブ「対象ファイル確認」）
  2. マージ先のブランチに応じて、接続する Salesforce 組織を選び、JWT 認証でログインする
  3. 検証モードでリリースを実行する（ジョブ「デプロイ検証」）
  4. 結果（成否・ログ）を、PR にコメントとして書く（毎回、新しいコメントを足す）
  5. 失敗したら、ジョブが失敗する。main / staging への PR では、必須チェックのため、マージできない（それ以外への PR は、表示だけ）
マージ先認証の情報接続する組織
mainSF_CONSUMER_KEY_PROD / SF_USERNAME_PROD / SF_INSTANCE_URL_PROD本番
staging*_STGステージング
develop / その他*_DEV開発

全組織で共通の SF_PRIVATE_KEY（JWT 用の秘密鍵）を使います（認証情報）。開発用の組織を登録していない構成（main だけ・main と staging）で、main / staging 以外へ PR を出すと、ログインで失敗します。

wf-sequence（マージ順序の確認）

main / staging への PR のときに、順序を確かめます（develop への PR では動きません）。branches.txt は、いつも origin/main から読みます（PR のマージコミットには、含まれないことがあるため）。ターゲットファイルに、反映も削除も書いていなければ、確認を飛ばします（マージ元が環境ブランチのときは、飛ばしません）。

  • マージ元が環境ブランチ → エラーでブロック（PR へのコメントと、Slack の通知も行う）
  • 順序外（例: staging にマージしないまま main へ PR）→ PR に警告のコメント（同じ PR では、既存のコメントを更新）と、Slack の通知。ブロックはしません。
  • 順序が正しい → 正常に終了（以前の警告があれば「✅ 問題ありません」に更新）
  • branches.txt が見つからない → 確認を省略

wf-release（リリース）

PR を main / staging / develop にマージしたあとに、マージ先に対応する組織へ、リリースします（手動でも実行できます）。

  1. ターゲットファイルに、反映も削除も書いていなければ、リリースを飛ばす（ジョブ「リリース対象確認」。Slack にも通知しない）
  2. リリース先を、Actions の Summary に記録する
  3. マージ先に応じた組織だけに、JWT 認証でログインする（main → 本番、staging → ステージング、develop → 開発）
  4. sf-release.sh --release を実行する
  5. 成功でも失敗でも、Slack に結果を通知する

同じマージ先へのリリースは、1 つずつ順に動きます。

wf-propagate（下位ブランチへの伝播）

main への PR をマージすると、その変更を、下位のブランチへ自動で伝えます（main → staging、main → develop。git の merge と push。PR は通しません）。ブランチがない構成では、そのブランチへの伝播を飛ばします。

  • Git の上の同期だけです。Sandbox の組織への自動デプロイは、行いません（伝播は PR のマージではないので、wf-release は動きません）。
  • メタデータの同期（wf-metasync）のボットの push では、このワークフローは動きません。同期のあとの下位への伝播は、同期のコマンド（sf-metasync.sh）自身が担います。
  • 送るときは PAT_TOKEN（管理者の GitHub の Token）を使います（staging のブランチ保護を越えるためと、ワークフローのファイルの変更を含むマージを送るためです）。
  • コンフリクトしたときは、マージを中止して Slack に通知し、ジョブを失敗させて、手動の対応を求めます。自動では解決しません（人間が判断すべき状況のためです）。

wf-metasync（本番の自動同期）

平日の日本時間 9:00 / 12:00 / 15:00 / 18:00 に、本番の組織の最新の状態を、main に反映します。手動でも実行できます（セットアップの最後と、sf-init.sh --verify が、手動の実行で動かします）。同時には 1 つずつしか動きません。

  1. main を、全履歴つきでチェックアウトする（差分の計算に、全履歴が必要なため）
  2. Node.js・Java・Salesforce CLI と、差分を計算する sf のプラグイン（sfdx-git-delta）を入れる
  3. 本番の組織に、JWT 認証でログインする
  4. sf-tools を取ってきて、sf-metasync.sh を実行する
  5. 差分を求め、sf-tools/config/metadata.txt に書かれた種類のメタデータを取得する（取得する種類）
  6. 変更があれば、コミットして、main へ直接 push し、branches.txt のほかのブランチ（staging・develop）へ伝える（伝えられなかったブランチは、警告を出して飛ばす）。変更がなければ、何もせず、正常に終わる

設計上の判断

判断理由
本番の同期を、PR なしの直接 push にした数時間おき（平日の日本時間 9・12・15・18 時）の同期に、承認は要らないため。ボットのコミットで、手動のコミットと区別できる。管理者の負担を減らす。ブランチ保護（必須チェック）は、PAT_TOKEN で越える（Token の持ち主が、リポジトリの管理者のとき）
同期のボットの push では、wf-propagate を動かさないPR のマージのときだけ動くため。同期のあとの伝播は、同期のコマンド自身が担う
手元から、共有の環境（予約名の組織・本番の組織）へは、dry-run も含めて実行させない共有の環境への反映は、GitHub にコミットし、PR のレビューを通して、ワークフローだけで行うため。名前を付け替えた本番の組織も、組織の種類の確認で止める（誤操作の防止。共有の環境の接続の情報は GitHub にあり、手元にはない）
マージ順序の確認を、警告だけにした緊急の Hotfix を妨げないため。Slack の通知で、気づけるようにする
環境ブランチどうしの直接マージは、ブロックする意図しない変更の混入を防ぐ。作業用のブランチ経由を強制して、各環境のデプロイ内容を追えるようにする
ターゲットファイル（deploy-target.txt と remove-target.txt）が両方とも空なら、正常に終わるCI で、リリースの定義だけ、先に準備する運用を許すため
自己完結のワークフローと、雛形の一元管理ワークフローの定義が、sf-tools の定義を呼び出さずに、各プロジェクトの中だけで動くようにするため。処理の中身（sf-release.sh・sf-metasync.sh）は、動くたびに sf-tools から取ってくるので、スクリプトの修正は、すぐ全プロジェクトに届く。ワークフローの定義の変更は、sf-sync-wf.sh で、管理者が反映する
ツールの更新は、24 時間に 1 回毎回 sf-start.sh で更新すると、起動が遅くなるため（sf-install.sh が、前回から 24 時間以上たっていれば、sf-upgrade.sh を裏で動かす）
下流への伝播のコンフリクトは、自動で解決しない本番と開発で、同じ箇所が変わった状況は、人間が判断すべきため。Slack の通知で気づき、手動で対応する
本番の変更を、定期的に（平日の 3 時間おきに）全環境へ伝える古いコードをもとにした開発による、デグレを避けやすくするため（重なった変更は、main の取り込みや PR の時点で、見つかる）
ブランチ保護の必須チェックは、ジョブ名だけで登録するGitHub の必須チェックの名前は、ワークフロー名を含まない、ジョブ名だけのため（ワークフロー名つきで登録すると、条件が満たされず、PR をマージできない）。実際の GitHub で確かめた
branches.txt で、ブランチ構成を変えられるようにしたプロジェクトの規模に応じて、1〜3 階層を選べるようにするため
sf-next.sh で、次の PR 先を自動で判定するマージ順序の間違いを防ぐ。ブラウザで PR の作成画面を、直接開ける
