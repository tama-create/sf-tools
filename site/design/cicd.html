🧭 CI/CD の仕組み（設計の考え方）

sf-tools は、変更を 1 段ずつ確かめながら、本番に届ける仕組みを、自動で動かします。このページでは、その全体像と、なぜこの作りなのかを説明します。コマンドの使い方は、コマンド一覧にあります。

ひとことで言うと

変更は、開発用 → 検証用 → 本番の順に、1 段ずつ進みます。各段で、自動のチェックが入るので、確かめないまま、本番に出ることはありません。本番で起きた変更は、自動で、ほかの段にも広がります。

（CI/CD は、変更の確認と反映を自動で行う仕組みのことです。）

設計の 3 つの柱

Salesforce のメタデータは、変更した部分だけを、差分として扱えます。この特性を活かして、Git（変更の履歴）と各組織（本番・ステージング・開発）の内容を、いつもそろえます。

  1. 本番が正（原本） — 本番の組織を、いつも「原本」として扱います。本番で起きた変更は、自動で見つけて、Git 上のすべてのブランチへ、すばやく広げます。ずれたら、自動でそろい直す仕組みです。

  2. 作業ブランチから、各環境へ、1 本ずつ届ける（スター型のプロモート） — 作業用のブランチ（feature）から、各環境へ向けて、それぞれ別に PR（取り込みの依頼）を出します。環境のブランチどうしを、直接つなぐことは、禁止です。

  3. 自己完結型のワークフロー — 自動で動く処理（ワークフロー）を、各プロジェクト（force-*）の中に、すべて含めます。雛形は sf-tools が持っていて、プロジェクトを作るときに、コピーします。

環境とブランチ

ブランチの階層は、sf-tools/config/branches.txt で、プロジェクトごとに決めます。

パターンブランチ使いどころ

2 階層main / staging開発用の組織を使わない場合
1 階層main小さなプロジェクト・1 人での開発

3 階層の場合の対応は、次のとおりです。

層組織ブランチエイリアス役割
本番層Productionmainprod正（Source of Truth）。本番の最新の状態
検証層Staging / UATstagingstaging結合テスト・顧客の確認用

段階は、あとから足せます（構成の変更と診断）。

リリースの流れ（スター型のプロモート）

すべてのリリースは、feature/* のブランチを起点にして、各ターゲットのブランチへ、個別に PR を出して行います。

デプロイする対象は、sf-tools/release/<ブランチ名>/deploy-target.txt に書いたものだけです（ターゲットファイルの書き方）。

なぜ、環境ブランチどうしを、直接マージしないのか

環境ブランチの間でマージすると、意図しない変更が混ざるおそれがあります。必ず feature ブランチを経由させることで、「各環境に、何がデプロイされたか」を、はっきり追えます。

マージの順序

おすすめの順序は、branches.txt の逆順（下位 → 上位）です。3 階層なら develop → staging → main の順です。

  • 開発者が sf-next.sh を使う限り、順序は守られます（sf-next の説明）。
  • GitHub 上で直接 PR を作り、順序を飛ばしたときは、wf-sequence が警告します。PR の会話欄にコメントを書いて、Slack にも通知します。マージは止めません（緊急のリリースを妨げないため）。気づいたレビュアーが、却下します。
  • 環境ブランチどうしの直接の PR（例: develop → staging）は、エラーでブロックします。
順序を飛ばすと、飛ばしたブランチへは、デプロイできなくなります

上位のブランチ（例: main）にマージすると、コードが下位のブランチ（例: staging）に伝わります（wf-propagate）。伝わったあとは「差分なし」になり、直接の PR を作れません。デプロイのワークフローは、直接の PR のマージで動くため、伝わっただけでは動きません。

飛ばしたブランチにデプロイしたいときは、新しいブランチを切って、順序どおりに PR を出し直します。

手元での main の同期

git push の前に、リモートの最新の main（自動で更新された、本番の状態）を取り込んでいるかを、確認します。未取り込みなら、main を自動でマージして、最新にします（pre-push フック）。

ワークフローの全体像

CI/CD の処理は、各プロジェクトの .github/workflows/ に、すべて含まれます。雛形は sf-tools/templates/.github/workflows/ にあり、sf-init がコピーします。

sf-tools（雛形の正本）                       force-* リポジトリ（完全内包版）
templates/.github/workflows/  ─ sf-init →   .github/workflows/
├── wf-validate.yml                          ├── wf-validate.yml
├── wf-sequence.yml                          ├── wf-sequence.yml
├── wf-release.yml                           ├── wf-release.yml
├── wf-propagate.yml                         ├── wf-propagate.yml
└── wf-metasync.yml                          └── wf-metasync.yml

なぜ自己完結にするのか: 各プロジェクトが、sf-tools の状態に左右されず、独立して動くようにするためです。ワークフローを直すときは、まず雛形を更新します。そのあと、管理者が sf-sync-wf.sh で、各プロジェクトに反映します（自動では書き換わりません）。

ワークフロー目的ブロックするか
wf-validatedry-run で検証し、結果を PR にコメントする失敗したら、マージをブロック
wf-sequenceマージの順序を確認する環境ブランチどうしの PR だけ、ブロック
wf-release対応する組織へリリースし、Slack に通知する—
wf-propagatemain の変更を、staging・develop へ、順に伝える—
wf-metasync本番の組織のメタデータを、main へ、自動で同期する—

いつ動くかの一覧は、ワークフローの更新にあります。

各ワークフローの動き

wf-validate（PR の検証）

PR を作る・更新するたびに、sf-release.sh を検証モード（dry-run）で実行します。

  1. マージ先のブランチに応じて、接続する Salesforce 組織を選ぶ
  2. 検証モードでリリースを実行する
  3. 結果（成否・ログ）を、PR にコメントとして書く
  4. 失敗したら、終了コード 1 で、マージをブロックする
マージ先認証の情報接続する組織
mainSF_CONSUMER_KEY_PROD / SF_USERNAME_PROD / SF_INSTANCE_URL_PROD本番
staging*_STGステージング
develop / その他*_DEV開発

全組織で共通の SF_PRIVATE_KEY（JWT 用の秘密鍵）を使います（認証情報）。

wf-sequence（マージ順序の確認）

branches.txt に書かれたブランチへの PR のときに、順序を確かめます。branches.txt は、いつも origin/main から読みます（PR のマージコミットには、含まれないことがあるため）。

  • マージ元が環境ブランチ → エラーでブロック
  • 順序外（例: staging にマージしないまま main へ PR）→ PR に警告のコメント（同じ PR では、既存のコメントを更新）と、Slack の通知。ブロックはしません。
  • 順序が正しい → 正常に終了（以前の警告があれば「✅ 問題ありません」に更新）
  • branches.txt が見つからない → 確認を省略

wf-release（リリース）

PR をマージしたあとに、マージ先に対応する組織へ、リリースします。

  1. リリース先を、Actions の Summary に記録する
  2. マージ先に応じた組織に、認証する
  3. sf-release.sh --release を実行する
  4. 成功でも失敗でも、Slack に結果を通知する

wf-propagate（下位ブランチへの伝播）

main への PR をマージすると、その変更を、下位のブランチへ自動で伝えます（main → staging、main → develop。git の merge と push）。

  • Git の上の同期だけです。Sandbox の組織への自動デプロイは、行いません。
  • メタデータの同期（wf-metasync）のボットの push では、このワークフローは動きません。同期のあとの下位への伝播は、同期のコマンド自身が担います。
  • コンフリクトしたときは、マージを中止して Slack に通知し、手動の対応を求めます。自動では解決しません（人間が判断すべき状況のためです）。

wf-metasync（本番の自動同期）

平日の日本時間 9:00 / 12:00 / 15:00 / 18:00 に、本番の組織の最新の状態を、main に反映します。

  1. main を、全履歴つきでチェックアウトする（差分の計算に、全履歴が必要なため）
  2. Node.js と Salesforce CLI を入れる
  3. 本番の組織に、JWT で認証する
  4. 前回の同期からの差分を求め、sf-tools/config/metadata.txt に書かれた種類のメタデータを取得する（取得する種類）
  5. 変更があれば、コミットして、main へ直接 push し、staging・develop へ伝える。変更がなければ、何もせず、正常に終わる

設計上の判断

判断理由
本番の同期を、PR なしの直接 push にした数時間おきの同期に、承認は要らないため。ボットのコミットで、手動のコミットと区別できる。管理者の負担を減らす。ブランチ保護は、PAT_TOKEN で通る
同期のボットの push では、wf-propagate を動かさないPR のマージのときだけ動くため。同期のあとの伝播は、同期のコマンド自身が担う
マージ順序の確認を、警告だけにした緊急の Hotfix を妨げないため。Slack の通知で、気づけるようにする
環境ブランチどうしの直接マージは、ブロックする意図しない変更の混入を防ぐ。feature 経由を強制して、各環境のデプロイ内容を追えるようにする
deploy-target.txt が空なら、正常に終わるCI で、リリースの定義だけ、先に準備する運用を許すため
自己完結のワークフローと、雛形の一元管理sf-tools への実行時の依存をなくし、各プロジェクトが独立して動くため。変更は sf-sync-wf.sh で、管理者が反映する
ツールの更新は、24 時間に 1 回毎回 sf-start.sh で更新すると、起動が遅くなるため
下流への伝播のコンフリクトは、自動で解決しない本番と開発で、同じ箇所が変わった状況は、人間が判断すべきため。Slack の通知で気づき、手動で対応する
本番の変更を、すばやく全環境へ伝える古いコードをもとにした開発による、デグレを防ぐため
ブランチ保護の必須チェックは、ジョブ名だけで登録するGitHub の必須チェックの名前は、ワークフロー名を含まない、ジョブ名だけのため（ワークフロー名つきで登録すると、条件が満たされず、PR をマージできない）。実際の GitHub で確かめた
branches.txt で、ブランチ構成を変えられるようにしたプロジェクトの規模に応じて、1〜3 階層を選べるようにするため
sf-next.sh で、次の PR 先を自動で判定するマージ順序の間違いを防ぐ。ブラウザで PR の作成画面を、直接開ける
