# sf-tools 文書の書き方（3 階層の決まり）

> **本書の位置づけ:** sf-tools の文書を、誰が読むかに合わせて、3 つの階層に分け、それぞれの書き方を決める。**AI（Claude）も人も、文書を書く・直すときは、本書に沿う。**
> 実装の判断は `CLAUDE.md`、詳細な実装は `doc/dev-reference.md`、文書サイトの作り方は `doc/dev-reference.md` 9.8 を参照。

---

## 1. 3 つの階層

文書は、難しさで、3 つの階層に分ける。

| 階層 | 読む人 | 難しさ | 置き場所 | 書く人 |
|---|---|---|---|---|
| **1. コードの冒頭コメント** | 開発者 | いちばん難しい。技術的で、**正確** | `bin/` `lib/` `phases/` `hooks/` のスクリプトの冒頭、`templates/` のワークフローの冒頭 | 開発者（と AI） |
| **2. 技術者向けの文書** | 技術者 | 1 よりかみ砕く。技術者が分かる程度 | `site/reference/`、`doc/` の設計書・リファレンス | 1 を読み取って、AI が書く |
| **3. 一般の利用者向けの文書** | IT に詳しくない方（Salesforce の管理者・業務担当を含む） | いちばんやさしい | `README.md`、`site/` の `index.html`・`guide/`・`admin/`・`design/`・用語集 | 2 を元に、AI が書く |

- **管理者向けのコマンド（`sf-init.sh` など）**の階層 2 は、`doc/dev-reference.md` 4 章と、コードの冒頭コメント（`--help`）です。`site/admin/` は、管理者向けの階層 3 で、手順を詳しく、やさしく書きます。`site/reference/commands.html` は、管理者向けコマンドについては、`site/admin/` へ案内します。
- **階層 1 が正本**です。間違いがあってはいけません。ここが間違っていると、2 と 3 も、すべて間違いになります。
- 階層 2・3 は、**同じ内容を、読み手に合わせて、言い換えたもの**です。階層が下がるほど、表現はやさしくなり、細かい仕様は省かれます。

---

## 2. 情報の流れ

### 2.1 上から下へだけ流す

```text
階層 1（コードの冒頭コメント）  →  階層 2（技術者向け）  →  階層 3（一般向け）
```

- 新しい事実（コマンドの動き・オプション・ファイル名・数字）は、**必ず階層 1 から**始める。
- 階層 2・3 に、階層 1 にない事実を、足さない。足したいときは、先に階層 1 を直す。
- 階層 3 は、階層 2 を言い換えたもの。階層 1 を、直接かみ砕いて書くこともあるが、階層 2 と食い違わないこと。

### 2.2 変えたときの手順

1. 階層 1（冒頭コメント）を直す。**コードを変えたら、冒頭コメントも、必ず、同じ変更の中で直す**（`CLAUDE.md` 2.5）。
2. 階層 2 のうち、元の冒頭コメントが変わったものを、書き直す。
3. 階層 3 のうち、その階層 2 を言い換えたものを、書き直す。
4. `mm` の前に、人が、書き直した文書を読んで確かめる。
5. 読み直したら、印を付け直す: `bash tests/docs-stamp.sh --update <文書> [<コード>]`（変わったコードが複数あるときは、1 本ずつ読んで、`<コード>` を付けて付け直す。付けないと、その文書のすべての印が、まとめて付け直される）。冒頭コメントを変えて、印が合わなくなった文書は、`bash tests/docs-stamp.sh --check` で分かる。変更の中身は `--diff <文書>` で見られる。

CI は、文書を、**自動で書き換えない**。食い違いを、知らせる（見つける）だけにする。

## 3. 階層 1: コードの冒頭コメントの書き方

### 3.1 方針

- **技術的で、正確に書く。** やさしさより、正確さを優先する。曖昧な表現を避ける。
- コードの動きと、**1 つも食い違わない**こと。動きを変えたら、同じ変更の中で、コメントも直す。
- `--help` の表示になる（2 つ目の `# ====` から 3 つ目の `# ====` までの部分）。

### 3.2 書式

```bash
# ==============================================================================
# sf-xxx.sh - コマンドの一行説明
# ==============================================================================
# 概要（1〜3 文）。何をするコマンドか。
#
# 【使い方】
#   sf-xxx.sh [オプション]
#
# 【オプション】
#   -x, --xxx  : 説明
#
# 【処理の流れ】
#   1. ...
#   2. ...
#
# 【前提条件】
#   - 実行する場所・必要な権限・事前の準備
#
# 【補足】
#   - 注意点・例外・終了コードなど
# ==============================================================================
```

- 見出し（【使い方】【オプション】【処理の流れ】【前提条件】【補足】）の名前と順序を、そろえる。
- 該当する項目がないときは、見出しごと省いてよい。ただし、オプションがあるのに【オプション】がない、などはしない。

## 4. 階層 2: 技術者向けの文書の書き方

- 読む人は、Git・シェル・Salesforce の開発を知っている技術者。技術用語（PR・ブランチ・dry-run・JWT など）は、説明なしで使ってよい。
- 冒頭コメントを、**そのまま写さない。** 読み取って、次のように整理する。
  - 何をするか（目的）。いつ使うか。
  - 使い方とオプション（表にする）。
  - 処理の流れ（番号つきの手順）。
  - 前提と、注意点（失敗するとき・やってはいけないこと）。
- 内部の実装の言葉（関数名・変数名・Phase の番号など）は、読み手に必要なものだけにする。
- 階層 1 にないことを、書かない。推測で書かない。

---

## 5. 階層 3: 一般向けの文書の書き方

### 5.1 方針

- 読む人は、Git やコマンドに詳しくない方でもある。**内容は、階層 2 と同じで、表現をやさしくする。**
- 「親しみやすく」書く。ただし、業務で使う文書なので、軽くしすぎない。**「です・ます」は保つ。** 親しみやすさは、言い回しとアイコンで出す。
- 読み手が、**迷わず・つまずかず・不安にならずに、次の一歩を踏み出せる**ことを、いちばん大事にする。

### 5.2 書き方の決まり

| 決まり | 内容 |
|---|---|
| 用語 | 初めて出る専門用語には、短い説明を添える。できれば、具体例も。用語は、**用語集**（`site/guide/glossary.html`）にそろえる（管理者 = プロジェクト管理者、リリース = デプロイ、段階 = 環境） |
| 文 | 1 文を短く。**読点（、）は 1 文に 1〜2 個まで**（列挙は除く）。主語を省かない。二重否定を避ける |
| 手順 | 手順ごとに、「結果の見方」「失敗したとき」「元に戻せるか」を、1 行ずつ添える |
| 禁止形 | 「〜してはいけません」を連発しない。「〜する仕組みです。代わりに〜してください」と、理由と代わりの方法を示す |
| 不安への配慮 | 「途中で止まっても大丈夫です」「何も変更しません」など、安心できる事実を、先に伝える |
| 冒頭 | 各ページの最初に、「何のページか」「誰が・いつ読むか」を、短く書く |

### 5.3 アイコン

囲み（`<div class="box 種類">`）の種類ごとに、決まったアイコンが、自動で付く（`site/assets/style.css`）。本文に、手で打ち込まない。

| 種類 | アイコン | 使いどころ |
|---|---|---|
| 通常 | 💡 | ヒント・補足 |
| `warn` | ⚠️ | 注意（失敗しやすい点・影響がある点） |
| `danger` | 🛑 | してはいけないこと・元に戻せないこと |
| `ok` | ✅ | できたこと・うまくいった状態 |
| `next` | 👉 | 次に進むページの案内 |
| `admin` | 🔑 | 管理者専用 |

- ページの見出しや、カードには、内容を表すアイコンを 1 つ付けてよい。
- **コードブロック・画面の出力例・記号の表には、アイコンを足さない**（実際の表示と食い違うため）。
- 箇条書きの各行や、すべての見出しに付けると、うるさくなる。使いすぎない。

## 6. 確認

| 確認 | 方法 |
|---|---|
| 見出しの番号（Markdown） | `tests/test_docs.sh` |
| 文書サイトの形式・リンク・番号・囲み | `tests/test_site.sh` |
| 文書に書かれた事実（コマンド名・オプション名・パス・環境変数）が、コードにあるか | `tests/test_docs_facts.sh`。コード片の中の「コマンドとオプションの組」も確かめる（別のコマンドのオプションを取り違えていないか）。外部コマンドのオプションなど、コードにないが書いてよいものは、`tests/docs-facts-allow.txt` に理由つきで書く |
| 元の冒頭コメントが変わったのに、対応する文書が見直されていないか | `tests/test_docs_stamps.sh`。`doc/doc-stamps.txt` に、「文書 ↔ 基になるコード」と、見直した時点の冒頭コメントのチェックサムを記録し、変わると失敗する（検出だけ。文書は自動で書き換えない）。使い方は、`tests/docs-stamp.sh` の冒頭コメント |
| 分かりやすさ | 人が読んで確かめる。必要に応じて、別の AI にレビューを依頼する |
