🔁 日々の開発の流れ

変更を書いて、確かめて、送る。毎日くり返す一連の操作です。すべて、force-* フォルダの中で実行します。ふだんは、ランチャー（メニュー）の番号を押すだけで進められます。コマンドを直接打つことも、もちろんできます。

全体の流れ

自分専用の組織で、実際に試したいときだけ、②のあとに「自分の組織に反映」を使います（自分の組織で、実際に反映する）。共有の環境（本番など）への検証と反映は、手元のパソコンからはできません。PR を作ると GitHub 上で自動で検証され、PR をマージすると、自動で反映されます（GitHub Actions という、GitHub 上で自動で動く仕組みが行います）。

手元から検証・反映できるのは、自分用の組織だけです

次の組織には、手元のパソコンから、dry-run（検証）も、反映もできません。実行すると、確認の画面の前に止まります。

  • 共有の環境の組織: エイリアス（組織に付けた短い呼び名）が prod / staging / develop / main の組織です。この 4 つの名前は、共有の環境のための予約名で、管理者のセットアップが、この名前で登録します。
  • 本番の組織: 名前に関係なく止まります（sf-tools が、組織の種類を読み取って確かめます）。種類を確かめられなかった組織も、念のため止まります。

ただし、staging・develop の組織（本番ではない組織）を、予約名ではない別の名前で接続すると、名前でしか見分けられないため、止まりません。共有の環境の組織に、自分で接続しないでください。

ランチャーで進める（おすすめ）

毎日の操作は、ランチャーのメニューから、番号を 1 つ押すだけで実行できます。コマンドの名前を覚える必要は、ありません。コマンドを直接打つこともできます（慣れている方は、そちらでも構いません）。便利なので、ランチャーをおすすめしています。

ランチャーは、自動で開きます

sf-job.sh や sf-start.sh を実行すると、最後に、ターミナルでランチャーが自動で開きます。閉じてしまったときや、VS Code のターミナルで使いたいときは、force-* フォルダの中で、次のように打ちます（PATH を設定していれば、sf-l まで打って Tab キーを押すと、補完されます）。

sf-launcher.sh

やりたいことから、押す番号を引けます。

やりたいこと押す番号コマンドで打つなら
ターゲットファイルの書き方を確かめる1 Checksf-check.sh
変更を GitHub に送る2 Pushsf-push.sh
次の PR の出し先を知る3 Nextsf-next.sh
自分専用の組織に、反映できるか確かめる（dry-run）4 Dryrunsf-dryrun.sh
自分専用の組織に、実際に反映する5 Deploysf-deploy.sh
前日の続きなど、作業を再開する6 Startsf-start.sh
接続先の組織を切り替える7 Restartsf-restart.sh
  • 終わると、メニューに戻ります。q で終了します。コマンドが失敗しても、ランチャーは終わりません（エラーを読んで、直して、もう一度押せます）。メニューにない数字や文字を押しても、何も起きません。
  • ランチャーから実行するコマンドには、オプションは付きません。オプションを付けたいときは、コマンドを直接打ちます。
  • sf-job.sh / sf-start.sh から自動で開いたランチャーでは、Ctrl+C は効きません。終了は q です（基本の使い方）。
  • VS Code のターミナルでは、6 と 7 は表示されません（VS Code が、二重に開かないようにするためです）。1〜5 を使います。
  • sf-job.sh（新しい作業を始める）は、メニューにありません。force-* フォルダの外の、作業フォルダで実行するためです（基本の使い方）。始めたあとは、ランチャーが自動で開きます。
  • ランチャーは、force-* フォルダの中でだけ使えます。
  • 番号を指定して、1 回だけ実行することもできます（例: sf-launcher.sh 4）。検索して選びたいときは、sf-launcher.sh --fzf（fzf が必要です）。

ターゲットファイルを書く

ターゲットファイルは、「何を反映するか」「何を削除するか」を書いておくファイルです。release/<ブランチ名>/ の下にあります（force-XXXX フォルダの中の sf-tools フォルダです。パソコンに置いた ~/sf-tools とは、別のものです）。

ファイル役割
deploy-target.txt反映するメタデータを、並べて書く
remove-target.txt削除するメタデータを、並べて書く

書き方は、ターゲットファイルの書き方を見てください。

反映できるか確かめる（dry-run）

🎛️ ランチャーの [4] Dryrun コマンドで打つなら:

sf-dryrun.sh

実際には反映せずに、接続中の自分用の組織で「反映できるか」だけを確かめます。組織の中身は変わらないので、安心して試せます。共有の環境の組織と本番の組織では、dry-run も、手元からはできません（上の囲み）。共有の環境への検証は、PR を作ったときに、GitHub 上で自動で行われます。

  • 流れ: まず、ターゲットファイルの書き方を確かめます（ランチャーの 1 Check と同じ確認）。そのあと、組織の「デプロイ状況」の画面をブラウザで開き、dry-run を実行します。Apex のテストクラス（@isTest が付いたクラス）をターゲットファイルに書いていれば、そのテストも、自動で実行されます。
  • 結果の見方: 成功か失敗かが、ターミナルに表示されます。ブラウザの「デプロイ状況」の画面でも、確かめられます。
  • 失敗したとき: エラーの内容が表示されます。ターゲットファイルや、変更の内容を直して、もう一度実行してください。ログは、force-* フォルダの中の sf-tools/logs/（sf-dryrun.log と sf-release.log）にも残ります。
  • ターゲットファイルに、反映も削除も 1 つも書いていないときは、「デプロイ対象なし」と表示して、何もせずに終わります。

sf-release.sh を、オプションなしで実行しても、同じ dry-run になります。sf-dryrun.sh -r のように -r を付けると、検証ではなく実際の反映になる（確認が出ます）ので、検証だけなら付けないでください。

自分の組織で、実際に反映する（sf-deploy）

🎛️ ランチャーの [5] Deploy コマンドで打つなら:

sf-deploy.sh

接続中の、自分専用の組織（個人用の Sandbox・Developer Edition・Scratch Org）に、変更を実際に反映します。自分の環境で動きを確かめたいときや、Sandbox を乗り換えたときに、今の開発物をまとめて入れ直すときに使います。

  • 組織の側の変更を、上書きします。組織で直接変えた内容とぶつかっても、止めずに上書きします（ぶつかりの確認をしない設定で反映します）。実行する前に、上書きの警告と、確認（Y / N / q）が出ます。Y を押したときだけ、反映します。
  • 作業用のブランチの上で実行します。main などの保護ブランチ（sf-tools/config/branches.txt に書かれた、共有の環境のブランチ）の上では、止まります。
  • 流れは、dry-run と同じです（ターゲットファイルの確認 → 「デプロイ状況」の画面を開く → 反映）。テストクラスも、同じく自動で実行されます。
共有の環境・本番には、反映できません

共有の環境の組織（予約名 prod / staging / develop / main）と、本番の組織（名前は問わない。種類を確かめられない組織も）には、パソコンから反映できない仕組みです（実行すると、確認の前に止まります。上の囲み）。共有の環境へは、GitHub に変更を送り、PR を作って、レビューを通し、マージします。そうすると、GitHub Actions が、自動で反映します。

変更を送る（sf-push）

🎛️ ランチャーの [2] Push コマンドで打つなら:

sf-push.sh

カレントフォルダ（ランチャーから実行したときは、force-* フォルダ全体）の下の変更を、まとめてコミットして、GitHub に送ります。次の順に進みます。

  1. 今いるブランチを確かめます（下の「コミットする前に止まる場合」）。

  2. GitHub の main の最新を取ってきて、今のブランチに取り込みます（マージ）。ほかの人の変更が、先に main に入っていても、ここで合わせられます。取り込みでぶつかり（コンフリクト）が起きたときは、理由を表示し、取り込みを取り消して止まります。

  3. カレントフォルダの下の変更を、コミットの対象にします（git add）。変更がなく、まだ送っていないコミットだけがあるときは、それを送って終わります。何もなければ、何もせずに終わります。

  4. ターゲットファイルの書き方を確かめます（ランチャーの 1 Check と同じ）。エラーがあれば、どの行がなぜ悪いかを表示して止まります。

  5. VS Code が、新しいウィンドウで開きます。コミットメッセージ（何を変えたかの説明）を書いて、保存して、そのタブ（ウィンドウ）を閉じます。閉じるまで、先に進みません。# で始まる行は、メッセージに入りません。何も書かずに閉じると、コミットもプッシュもせずに終わります。

  6. コミットして、GitHub に送ります（プッシュ）。このとき、Git のフックも自動で動きます。

  • 送るのだけが失敗したときは、もう一度実行してください。まだ送れていないコミットが、送られます。
  • 前もって、自分で git add していた、カレントフォルダの外の変更も、一緒にコミットされます。
  • ログは、sf-tools/logs/sf-push.log に残ります。
コミットする前に止まる場合

次の 2 つのときは、コミットする前に、エラーで止まります。コミットだけが手元に残って、送れない状態を作らないための仕組みです。

  • ブランチの上にいないとき（detached HEAD）
  • 保護ブランチ（branches.txt のブランチ。main など）の上にいるとき

そのときは、sf-job.sh で作った、作業用のブランチに移ってから、もう一度実行してください。

PR の状況を確認する（sf-next）

🎛️ ランチャーの [3] Next コマンドで打つなら:

sf-next.sh

いまの作業用のブランチが、develop → staging → main のどこまで取り込まれたかを、一覧で表示します（段階は、プロジェクトの branches.txt の設定によります。main だけのプロジェクトもあります）。次に PR（取り込みの依頼）を出す先も、案内します。

JOB-20261024 のマージ状況
  ✓ develop   マージ済み
  → staging   PR発行中
  ▶ main      次のPR先
記号意味
✓ マージ済みその段階への PR が、マージ済みです（「ブランチ同期」と付くときは、別のブランチ経由で、変更がすでに入っています。この PR による反映は、行われていません）
⚠ マージ済み（順序外）前の段階を飛ばして、マージされています。飛ばした段階には、反映されていません
→ PR発行中PR を出してあり、マージを待っています
▶ 次のPR先次に PR を出す先です
  • 次の PR 先があるときは、「〜にPRを出しますか？」と聞かれます。Y を押すと、GitHub の PR の作成画面がブラウザで開きます。PR そのものは、まだ作られていません。画面で内容を確かめて、作成のボタンを押してください。N は何もせず終了、q は中断です。
  • PR は、段階の順番どおり（develop → staging → main）に出します。順番を飛ばしてマージすると、飛ばした段階には、あとから反映できなくなります（詳しくは、リファレンス）。sf-next.sh の案内に従えば、順番どおりになります。
  • main などの保護ブランチの上では、使えません（作業用のブランチの上で実行します）。

自動で動くチェック（git フック）

コミットとプッシュのときに、次のチェックが、自動で動きます（フックは、sf-start.sh が裏で設置します）。何もしなくて大丈夫です。sf-push.sh を使っても、git のコマンドを直接打っても、同じように動きます。

フックいつ内容
pre-commitgit commit のときターゲットファイルの書き方を確認します。エラーがあれば、コミットを止めます
pre-pushgit push のとき
  1. 保護ブランチへの直接のプッシュを止めます。保護ブランチは、branches.txt に書かれた、共有の環境のブランチ（main / staging / develop など）です。その上からのプッシュも、作業用のブランチから保護ブランチへ送ることも（削除も）、できません。保護ブランチへは、PR を通します。
  2. ターゲットファイルの書き方を確認します。エラーがあれば、プッシュを止めます。
  3. GitHub 上の自分のブランチと main に、まだ取り込んでいない変更があれば、取り込みます（マージ）。取り込んだときは、そのプッシュは止まります（取り込みを含めずに送ってしまわないためです）。もう一度プッシュすると、通ります。取り込みでぶつかったときは、取り込みを取り消して止まります。

pre-push は、Salesforce の組織への検証（dry-run）は、行いません。組織で反映できるかは、ランチャーの 4 Dryrun（自分用の組織）と、PR を作ったときの自動の検証で確かめます。

困ったときは

うまく動かないときは、トラブルシューティングの「開発者の方へ」を見てください。コマンドの詳しい説明は、開発者向けコマンドにあります。
