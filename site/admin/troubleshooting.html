🩺 トラブルシューティング

うまく動かないときの、原因と直し方です。落ち着いて、当てはまるものを探してください。ほとんどは、原因を直して、もう一度実行すれば元に戻ります。前半は管理者の方（セットアップ・ワークフロー）、後半は開発者の方（毎日の作業）向けです。

最初に試すこと
  • エラーの文章を、最後まで読んでみてください。直し方が、書いてあることが多いです。
  • ログは、force-* フォルダの中の sf-tools/logs/<コマンド名>.log に残っています（sf-init.sh・sf-job.sh・sf-typecheck.sh と、動作の確認の verify.log は、~/sf-tools/logs/ の下です。くわしくはログとリポジトリ構成）。
  • 管理者は、sf-init.sh --status で、足りないものを調べられます（何も変更しません）。
  • GitHub のワークフローの失敗は、リポジトリの Actions の画面で、失敗したステップ（手順）の名前とログを見ます。下の見出しは、そのステップの名前でも探せます。

管理者の方へ（セットアップや自動処理で困ったとき）

sf-init.sh が途中で止まった・中断したい

まず、ログを見ます。

cat ~/sf-tools/logs/sf-init.log

「どこで間違えたか分からない」ときは、管理者用の admin フォルダの中の force-* で、sf-init.sh --status を実行します。リポジトリ・ブランチ・ワークフロー・Secrets・Variables・ブランチ保護が、そろっているかを、✓（できている）と ✗（足りない。直し方も表示）で教えてくれます（何も変更しません。診断の説明）。

原因を直したら、前と同じ作業フォルダで、もう一度 sf-init.sh を実行してください（同じオーナー・XXXX を選びます）。途中まで進んでいたときは、開始画面の確認のあとに、「続きをやる」「最初からやり直す」の選択肢が出ます（途中で止まったとき）。

  • 中断したいとき: セットアップの間は、Ctrl+C が効きません（途中の半端な状態を作らないためです）。質問の画面で q を入力するか、ターミナルを閉じてください。閉じたあとも、もう一度実行すれば、続きから再開できます。
  • 「すでに実行中です」と出て止まる: 同じ作業フォルダ・同じ XXXX の sf-init.sh が、ほかのターミナルで動いています。そちらを終えてから実行してください。前の実行が、もう動いていない（ターミナルを閉じたなど）ときは、自動で引き継ぐので、このメッセージは出ません。
  • 完了済みのプロジェクトで、--resume / --only が断られる: 完了済みのプロジェクトでは、使えません。オプションなしで sf-init.sh を実行して、メニューから選ぶか、--reconnect / --add-tier を使います。
  • 実行の場所が違う: 最初のセットアップは、作業フォルダ（admin や force-* の外）で実行します。--status などの保守のモードは、反対に、force-* の中で実行します。

main / staging への PR が、マージできない（必須のチェックが「待機中」のまま）

PR の画面で、「Expected — Waiting for status to be reported」のような表示のまま、マージのボタンが押せないときの原因です。ブランチ保護（Ruleset）の必須チェックの名前が、ワークフローの実際のチェック名と合っていないためです。名前が合わないと、条件は、永久に満たされません。

以前のバージョンの sf-init.sh は、必須チェックの名前を validate / 対象ファイル確認 のように、ワークフロー名つきで登録していました。正しい名前は、ジョブ名だけの 対象ファイル確認・デプロイ検証・順序チェック です（いまの sf-init.sh は、この 3 つで登録します）。この問題は、ブランチ保護が実際に効くリポジトリ（有料プラン、または公開リポジトリ）で起こります。管理者（リポジトリの Admin ロール）は、ブランチ保護を迂回できるので、マージできます。

確かめ方と直し方は、次のとおりです。

  1. 管理者用のフォルダ（admin/force-XXXX）で、sf-init.sh --status を実行します。「Ruleset protect-main: 必須チェックの名前が、ワークフローのジョブ名と合っていません」と出たら、これが原因です（余分な名前と、足りない名前も表示されます。何も変更しません）。

  2. GitHub のリポジトリの Settings → Rules → Rulesets で、protect-main と protect-staging を開きます。

  3. 「Require status checks to pass」の一覧を、対象ファイル確認・デプロイ検証・順序チェック の 3 つだけにします（ワークフロー名は付けません）。保存します。

新しく作るプロジェクトは、最初から、正しい名前で登録されます。sf-sync-wf.sh はワークフローのファイルだけを書き換え、ブランチ保護は変えないので、この直し方は、手で行う必要があります。必須チェックの仕組みは、ワークフローのページにあります。

wf-metasync / wf-propagate が失敗する（PAT_TOKEN）

wf-metasync（[metasync] メタ同期）と wf-propagate（[propagate] ブランチ伝播）は、Secret PAT_TOKEN（GitHub の Token）を使って、リポジトリを取得し、main / staging / develop へプッシュします。失敗したステップで、原因を見分けます。

失敗したところ主な原因
最初のステップ「ソースコードを取得」PAT_TOKEN が登録されていない・有効期限が切れた・無効にした
プッシュのところで「push declined due to repository rule violations」Token の持ち主が、リポジトリの Admin ではない（ブランチ保護を迂回できない）
伝播のプッシュ（ワークフローのファイルの変更を含むとき）Token に workflow の権限がない

どの場合も、リポジトリのオーナー（組織の場合は、その組織の管理者）のアカウントで、新しい Token（Classic。repo・workflow）を発行し、リポジトリの Secrets の PAT_TOKEN を登録し直してください（手順はそのほかの情報の登録し直し）。sf-init.sh は、登録のときに、Token の有効性・権限・持ち主が Admin であることを確かめますが、そのあとで Token を無効にしたり、期限が切れたり、持ち主の権限が変わったりすると、この状態になります。sf-update-secret.sh では、PAT_TOKEN は更新できません。

この失敗は、Slack に通知されません

wf-metasync は、成功も失敗も通知しません。wf-propagate が通知するのは、コンフリクトのときだけです。Actions の画面か、sf-init.sh --status の「直近の実行」で、ときどき確かめてください。

手元で sf-metasync.sh を実行した時刻と重なって、wf-metasync のプッシュが拒まれることもあります。このときは、Actions の画面から、もう一度実行してください。

wf-propagate が、コンフリクトで失敗する

main へのマージのあと、main を staging / develop へ伝えるときに、同じ場所が別々に変更されていると、コンフリクト（衝突）します。このときは、そのブランチへのマージを取り消して（ブランチは変わりません）、Slack に、コンフリクトしたブランチ・PR・ログの URL を通知し、失敗で終わります。

コンフリクトしたブランチは、手で解消します（main を、そのブランチにマージします）。解消するまで、そのブランチは main から遅れたままです。

wf-validate / wf-sequence が動かない・失敗する

動かないときは、次を確かめてください。

  • ワークフローのファイルが、.github/workflows/ の中にあるか。ないときは、sf-sync-wf.sh で、最新の雛形から作り直せます。
  • PR に、コンフリクトがないか。コンフリクトのある PR では、どちらも動きません。解消すると動きます。
  • wf-sequence は、main / staging への PR でだけ動きます。
  • PR のタイトル・本文の編集では、動きません（PR の作成・ソースブランチへのプッシュ・再オープンで動きます）。

失敗するときは、次を確かめてください。

  • wf-validate が「Salesforce 組織にログイン」で失敗する: main / staging 以外への PR は、develop の組織で検証します。develop の組織を登録していない構成（main のみ・main + staging）では、このステップで失敗します。PR の出し先を確かめてください。
  • PR のコメントが「⚠️ 検証が実行されませんでした」: 検証の前のステップ（ログイン・sf-tools の取得など）で止まったか、取り消し・時間切れです。Actions の画面で、失敗したステップを見ます。
  • 「❌ 検証失敗」: dry-run の検証そのものが失敗しています。コメントのログに、原因（どのファイルの、どの問題か）が出ます。開発者が、ターゲットファイルか変更の内容を直して、プッシュし直します。
  • 順序チェック が失敗する: 環境ブランチ（main / staging / develop など）から、直接 PR を出しています。作業用のブランチから出し直してください。

マージしたのに、組織にリリースされない

  • ターゲットファイル（deploy-target.txt・remove-target.txt）に中身がないと、wf-release の「リリース実行」はスキップされます。Slack にも通知されません。
  • wf-propagate や wf-metasync が staging / develop へ伝えた変更は、PR のマージではないので、リリースされません。その段階にリリースするには、その段階への PR を出して、マージします。順序を飛ばしてマージしたときの注意は、sf-next.sh の説明にあります。
  • main / staging / develop 以外のブランチへのマージでは、リリースは行われません。

sf-sync-wf.sh が止まる

表示原因と直し方
「force-* ディレクトリの中ではありません」force-* のフォルダに移ってから実行します
「… ブランチでは実行できません（環境ブランチです）」「現在のブランチを取得できません」main などの環境ブランチの上、またはブランチの上にいない（detached HEAD）ためです。sf-job.sh で作業用のブランチ（system-日付）を作って、そこで実行します（更新の手順）
「origin に接続できないため、sf-tools が最新かどうかを確認できません」ネットワークの不調などで、GitHub につながりません。つながる状態で、もう一度実行します
「sf-tools に未コミットの変更または未 push のコミットがあるため、自動では更新できません」~/sf-tools を手で変更しています。git -C ~/sf-tools status で確かめて、変更を片付けてから実行します
「sf-tools が最新ではないため、続行できません」sf-tools の更新の確認で、N / q を答えました。古い雛形でワークフローを書き換えないため、更新しないと実行できません
「sf-tools の更新に失敗しました」「sf-tools を更新しても、最新になりませんでした」更新の途中で失敗したか、更新の直後に、さらに新しい版が出ました。もう一度実行します
「sf-tools が最新ではありません」（--check のとき）--check は sf-tools を更新しません。--check なしで実行するか、sf-tools を更新してから調べます
--remove の「ファイル名として正しくありません」「削除対象が見つかりません」「雛形にあるため、削除できません」フォルダを含まないファイル名（wf-old.yml など）で、.github/workflows/ にあり、雛形から廃止されたものだけを指定できます

更新したワークフローのプッシュが拒まれるときは、GitHub の認証に workflow の権限（スコープ）があるかを確かめてください。ワークフローのファイルをプッシュするには、この権限が必要です。

wf-metasync / wf-validate / wf-release が「自動化ツール（sf-tools）を取得」で失敗する

sf-tools は公開リポジトリなので、新しいワークフローは、Token なしで取得します。このエラーは、以前のバージョンの雛形で作ったプロジェクトで起こります。ワークフローが SF_TOOLS_TOKEN 付きで取得していて、その Token が使えないときに起こります（登録されていない・期限が切れた・無効になった、のどれかです）。

sf-sync-wf.sh で、ワークフローを最新の雛形に合わせると、Token なしの取得に変わります。新しい雛形の取得の行は、次の形です。

git clone -b ${{ vars.SF_TOOLS_BRANCH || 'main' }} https://github.com/tama-create/sf-tools.git ...

Variable SF_TOOLS_BRANCH が、存在しないブランチを指しているときも、このステップで失敗します（ふつうは登録しません。未登録なら main を使います）。

「差分抽出ツール（Salesforce Git Delta）をインストール」で TypeError が出て失敗する

エラーの例: TypeError: webidl.util.markAsUncloneable is not a function

以前のバージョンの雛形で作ったプロジェクトで、ワークフローの Node.js のバージョン（node-version）が古いときに起こります。いまの雛形は、Node.js 22 を使います。sf-sync-wf.sh で、ワークフローを最新の雛形に合わせてください（雛形の変更は、作成済みのプロジェクトには、自動では届きません）。

開発者の方へ（毎日の作業で困ったとき）

毎日の作業は、ランチャー（sf-launcher.sh。sf-job.sh や sf-start.sh のあとに開くメニュー）から行うのがおすすめです。メニューの番号は、1 Check・2 Push・3 Next・4 Dryrun・5 Deploy です（VS Code のターミナル以外では、6 Start・7 Restart も出ます）。

sf-job.sh が動かない

  • 実行する場所: sf-job.sh は、管理者用のフォルダ（admin）や、force-* フォルダの中では、動きません。作業フォルダ（作業用のフォルダを、まとめて置いている場所）に移動して、もう一度実行してください。
  • リポジトリが見つからない: プロジェクトのリポジトリ（force-XXXX）は、管理者が先に作ります。まだ作られていない・オーナーや XXXX の名前が違う・自分のアカウントに読み書きの権限がない、のどれかです。管理者に確かめてください（リポジトリができるまでは、始められません）。
  • 途中で失敗した: それまでに作ったブランチ・フォルダは、残ります。ブランチを作ったあとでクローンに失敗したときは、同じジョブ名で、もう一度実行し、「既存のブランチを使う」に Y を答えると、続きから進めます。
  • 中断したい: Ctrl+C は効きません。入力の画面で q を入力してください。

sf-push.sh（ランチャーの 2 Push）が止まる

次のときに、コミットする前に止まります。変更が、手元に半端に残らないようにするための仕組みです。

  • ブランチの上にいない（detached HEAD）・保護ブランチ（main など）の上にいる: sf-job.sh で作った、作業用のブランチに移ってから、もう一度実行してください。
  • 「origin/main とのマージに失敗しました」: sf-push.sh は、コミットの前に、最新の main を取り込みます。同じファイルの同じ場所を、ほかの人が先に変えて main に入っていると、コンフリクトで失敗します（取り込みは取り消され、手元は元のままです）。画面に、失敗の理由が出ます。解消の仕方が分からないときは、管理者かレビュアーに相談してください。
  • 「git fetch に失敗しました」: GitHub につながりません。ネットワークを確かめて、もう一度実行します。
  • ターゲットファイルのエラー: どの行が、なぜエラーかが、画面に出ます。直して、もう一度実行します（書き方はターゲットファイルの書き方）。

コミットメッセージを空のまま閉じると、コミットもプッシュもせずに終わります。コミットのあとでプッシュだけ失敗したときは、もう一度 sf-push.sh を実行すると、プッシュだけを行います。

git push が止められる

プッシュのときに、自動のチェック（pre-push フック）が動きます。次のときは、プッシュを止めます。

  • main / staging / develop（保護ブランチ）の上にいるとき、ブランチの上にいないとき、保護ブランチへプッシュしようとしたとき（git push origin feature:main など）。作業用のブランチに移って、PR（取り込みの依頼）を出して、反映してください（sf-next.sh、ランチャーの 3 Next が、出し先を案内します）。
  • ターゲットファイルの書き方にエラーがあるとき（画面に、エラーの行が出ます）。
  • GitHub の最新の取得に失敗したとき（「リモート情報の取得に失敗しました」）・取り込みがコンフリクトしたとき（「… の自動取り込み（git merge）に失敗しました」。取り込みは取り消されます）。

「リモートの変更を、現在のブランチに取り込みました（早送りを含む）。このプッシュには、取り込みが含まれないため、中止しました。」と表示されたときは、故障ではありません。main などの新しい変更を取り込んだので、もう一度プッシュしてください（sf-push.sh をもう一度実行するか、git push）。今度は通ります。

この仕組みを、避けて通る方法は、案内していません。どうしても必要なときは、管理者に相談してください。

dry-run（sf-dryrun.sh。ランチャーの 4 Dryrun）が失敗する

画面に、エラーの内容が出ています。多くは、ターゲットファイルの書き方や、変更の内容が原因です。直して、もう一度実行してください。書き方は、ターゲットファイルの書き方にあります。実行の前に断られるときは、次の見出しを見てください。

Dryrun・Deploy が、実行の前に断られる（手元から実行できない組織）

sf-dryrun.sh（4 Dryrun）・sf-deploy.sh（5 Deploy）・sf-release.sh は、手元のパソコンからは、自分専用の組織（個人用の Sandbox・Developer Edition・Scratch Org）にだけ使えます。次の組織には、検証（dry-run）も含めて、実行できません。

表示理由
「… は共有環境（予約名）のため、ローカルから実行できません」接続先のエイリアス（組織の呼び名）が、prod / staging / develop / main です。これは、チームで共有する段階の組織の名前です
「… は本番組織のため、ローカルから実行できません」組織の種類を調べたら、本番でした（名前を変えて接続した本番も、止めます）
「… の組織の種類を確認できないため、ローカルから実行できません」組織の情報を読み取れず、本番でないことを確かめられません（ログインが切れている・組織につながらない など）

（sf-deploy.sh では、「実行できません」が「強制リリースできません」になります。）共有の段階の組織へは、変更を GitHub に送り、PR を作って、レビューを通し、マージします。そうすると、ワークフローが反映します。自分用の組織に切り替えるには、sf-restart.sh（VS Code のターミナル以外で開いたランチャーでは、7 Restart）を使います。

sf-deploy.sh は、このほか、保護ブランチ（main など）の上や、ブランチの上にいないときも、断ります。作業用のブランチで実行してください。

sf は成功しているのに、失敗と表示される

Salesforce CLI が、公式インストーラー版のときに起こります。npm 版に入れ替えると、直ります（Salesforce CLI は npm 版を使う）。

CRLF の警告が出る

Windows と、ほかの環境の、改行コード（行の終わりの印）の違いを知らせる、Git の警告です。動作には影響しないので、そのままで大丈夫です。
