📖 用語集

この文書に出てくる言葉を、やさしく説明します。「これは何だろう？」と思ったら、ここを見てください。すべてを覚える必要はありません。

この文書での言葉の使い方
  • 管理者は、「プロジェクト管理者」のことです（次の節）。Salesforce のシステム管理者と同じ人のこともありますが、役割は別です。
  • リリースとデプロイは、同じ意味です（変更を Salesforce の組織に反映すること）。コマンドの名前に合わせて、どちらも出てきます。

人と役割

言葉意味
プロジェクト管理者（管理者）新しいプロジェクトを作り、接続や設定を整える担当の方です。最初に 1 回の準備をして、そのあとは、ときどき見直します。Salesforce のシステム管理者と同じ人のこともありますが、GitHub の設定など、別の作業も受け持ちます
開発者Apex や LWC、項目、画面などを作って、変更を出す方です。日々の作業で、sf-tools のコマンドをいちばん使います
レビュアーPR（変更を取り込む依頼）の内容を見て、取り込んでよいかを決める方です

プロジェクトとフォルダ

言葉意味
プロジェクト（force-XXXX）1 つの Salesforce 開発の単位です。GitHub 上のリポジトリ 1 つに対応します。名前は force- で始まり、XXXX の部分は管理者が決めます（例: force-acme）。管理者が、sf-tools の雛形で先に作ります。開発者は、それができてから使い始めます
ランチャー（sf-launcher.sh）sf-tools の毎日のコマンド（Check・Push・Next・Dryrun・Deploy など）を、メニューの番号で選んで実行する画面です。番号を 1 文字押すだけで（Enter は不要）実行し、終わるとメニューに戻ります。sf-start.sh の最後に、自動で開きます（sf-job.sh も、最後に sf-start.sh を動かすので、同じく開きます）。コマンドの名前を覚えなくても使えるので、開発者の方には、ランチャーをおすすめします
リポジトリファイルと、その変更の履歴を、しまっておく場所です（GitHub 上にあります）
クローン（clone）リポジトリを、自分のパソコンにコピーすることです。コピーしたものも、クローンと呼びます
作業フォルダ作業用のフォルダを、まとめて置く場所です。どこでも構いません（おすすめは ~/sf のような短い名前）
作業単位1 つの作業のためのフォルダです（JOB-日付 など）。同じプロジェクトを、別々の作業として、同時に開くための入れ物です

Git と GitHub

言葉意味
ブランチ変更を、本線から分けて進めるための「枝」です。作業ごとに 1 本作ります。本線を汚さずに、安心して試せます
コミット変更を、履歴に 1 つ記録することです
プッシュ（push）手元の変更を、GitHub に送ることです
PR（プルリクエスト）「この変更を取り込んでください」という依頼です。取り込む前に、自動の検証と、レビュアーの確認が入ります
マージPR の変更を、取り込み先のブランチに合わせることです
ワークフロー（GitHub Actions）GitHub の上で、自動で動く処理です。この文書では、検証・リリース・同期などを行う仕組みを、ワークフローと呼びます。人が操作しなくても、PR を作ると動き出します
フックコミットやプッシュの直前に、自動で動くチェックです。まちがった内容を、送る前に止めてくれます
作業用のブランチ開発者が、1 つの作業のために作るブランチです。sf-job.sh が、main の最新から、ジョブ名と同じ名前で作ります。変更は、ここで行い、PR で共有の環境のブランチへ取り込みます
環境ブランチ（保護ブランチ）共有の段階に対応するブランチ（main / staging / develop）のことです。プロジェクトの sf-tools/config/branches.txt に書かれています。この上では、直接、作業しません。sf-push.sh・sf-next.sh・sf-deploy.sh などは、この上では止まります。フック（pre-push）も、このブランチへの直接のプッシュを止めます。変更は、作業用のブランチから PR を出して、取り込みます。文書によって「環境ブランチ」「保護ブランチ」と呼びますが、同じものです
ブランチ保護（Ruleset）大切なブランチを守るための、GitHub の設定です（Ruleset は、GitHub でのこの設定の名前です）。sf-init.sh が、main と staging に、protect-main・protect-staging という名前で設定します。ブランチの削除と、強制プッシュ（履歴の書き換え）を禁止し、PR をマージする前に、必須チェックが通ることを求めます。リポジトリの管理者は、このルールを越えられます（自動のワークフローが、管理者の Token で main に送るためです）。無料プランの非公開リポジトリなどでは、設定できないことがあります（セットアップ）
必須チェック「これが成功しないと、PR をマージできない」と、ブランチ保護に登録したチェックです。sf-tools では、対象ファイル確認・デプロイ検証・順序チェック の 3 つです。名前が、ワークフローのジョブの名前と合っていないと、いつまでも満たされず、PR をマージできなくなります（ワークフロー）

段階（環境）と組織

言葉意味
組織（org）Salesforce の環境 1 つのことです。本番・Sandbox・Developer Edition などがあります
段階変更を、順番に確かめながら本番へ進めるための、段のことです。develop（開発）→ staging（検証）→ main（本番）の 3 段が標準です。段ごとに、ブランチと Salesforce の組織が、1 つずつ対応します。小さなプロジェクトは、main だけの 1 段でも使えます
Phase（フェーズ）sf-init.sh の内部の処理の単位です（1〜10）。画面に出る「ステップ n / 9」とは、番号がずれています。--resume / --only を使うときだけ、意識します（ステップとの対応）
環境段階と同じ意味で使います（本番環境・検証環境・開発環境）
エイリアス接続する組織に付ける、短い呼び名です（例: myorg）。Salesforce CLI（sf）でログインするときに付け、コマンドは、この名前で組織を選びます
共有の環境（共有環境）チームで共有する段階（main / staging / develop）の組織のことです。変更は、PR をマージしたときに、GitHub 上のワークフローが反映します。手元のパソコンからは、dry-run も反映もできません
予約名共有の環境の組織のために取ってある、エイリアスの名前です（prod / staging / develop / main）。この名前の組織には、手元から dry-run も反映もできません。自分用の組織に、この名前を付けないでください
自分用の組織開発者が、1 人で試すために使う組織です（個人の Sandbox・Developer Edition など）。手元から dry-run や反映ができるのは、この組織だけです。本番の組織は、名前に関係なく、手元からは使えません（種類を確かめられない組織も、念のため止まります。日々の作業）

リリースの言葉

言葉意味
リリース（デプロイ）変更を、Salesforce の組織に反映することです
dry-run（検証）実際には反映せずに、「反映できるか」だけを確かめることです。組織の中身は変わらないので、安心して試せます。sf-tools のリリースは、まず dry-run が基本です。手元のパソコンから dry-run できるのは、自分用の組織だけです（ランチャーの 4 Dryrun）。共有の環境と本番の組織への dry-run は、PR を作ったときに、GitHub 上のワークフローが自動で行います
メタデータApex クラス・項目・画面レイアウトなど、Salesforce の設定や部品のことです
ターゲットファイル「何を反映するか」「何を削除するか」を書いておくファイルです（deploy-target.txt と remove-target.txt）。作業用のブランチごとに、プロジェクトの中の sf-tools/release/<ブランチ名>/ に置きます。どちらにも何も書いていないときは、「デプロイ対象なし」として、何も反映しません（日々の作業）
メタデータの同期組織の最新の状態を、Git に取り込む処理です。手元の変更とは関係なく、組織で直接加えられた変更も、Git に残せます

認証と秘密の情報

言葉意味
SecretGitHub に登録して、人にも見えないように隠しておく情報です（秘密鍵や Token など）
VariableGitHub に登録する情報のうち、見えても問題のないものです（ユーザー名や URL など）
Token（トークン）長い英数字の文字列で、「合言葉」のように使います。パスワードの代わりに、ツールどうしが、おたがいを確かめます
PATGitHub の Personal Access Token のことで、GitHub の「合鍵」のようなものです。ワークフローが、リポジトリを更新するために使います。管理者が、セットアップのときに、force-XXXX のリポジトリのオーナー（組織のリポジトリなら、その組織の管理者）のアカウントで作り、Secret PAT_TOKEN に登録します（セットアップ）
JWT 認証パスワードの入力なしで、秘密鍵を使って、Salesforce にログインする方法です。GitHub 上のワークフローが、自動でログインするために使います
外部クライアントアプリSalesforce の側に作る、「このツールからのログインを許可する」という登録です（Salesforce が推奨する方式です）。JWT 認証で、ワークフローがログインするために使います。既定の方式では、セットアップのときに、sf-init.sh が、段階の組織ごとに自動で作ります（名前は SF_TOOLS_ で始まります。セットアップ）
