## 1. 目標・非目標・要件

### 1.1 目標

| # | 目標 |
|---|---|
| G1 | `main` を、prod の組織の内容（`metadata.txt` の種類）と一致させる。**追加・変更だけでなく、削除も反映する** |
| G2 | 一致させた `main` を、現行と同じ方法で、下流のブランチ（`branches.txt` の `main` 以外）へ伝播する |
| G3 | 取得の失敗・部分的な取得で、`main` から大量のファイルを消さない（安全が、速さより優先） |
| G4 | 速さ: **まず、現行より遅くしない。** 速くする手段（並列化・差分取得）は、測定で効果を確かめてから入れる |
| G5 | 公式サポート外の依存をなくす（sfdx-git-delta（SGD）を廃止する）。追加の npm パッケージは使わない |

### 1.2 非目標

- 組織への書き込み（同期は、読み取りだけ）
- `metadata.txt` にない種類・管理パッケージの部品の同期（現行のワイルドカードの取得と同じく、対象外）
- 「組織の差分だけを返す仕組み」の自作（Salesforce に、そのような API はない。【事実（依頼の調査）】）
- sfdx-hardis・Gearset などの導入
- 伝播の方式の変更（現行の `phase_propagate_downstream` のまま）
- 大きな組織での「1 回の取得の上限（10,000 ファイル・400 MB）」の完全な解決（測定してから決める。11.2 の U9）

### 1.3 要件

| ID | 要件 | 優先 | 満たし方 |
|---|---|---|---|
| R1 | 完全同期（削除を含む） | 必須 | 鏡像（ミラー）方式（3.1・4.5） |
| R2 | 安全: 失敗・部分的な取得で、大量に削除しない | 必須 | 削除の守り S1〜S8（4.5.2） |
| R3 | 高速 | 高 | フェーズ 0 で測定 → 効果があれば、フェーズ 2b（並列）・3（差分）（10.1） |
| R4 | 公式サポート外の依存を増やさない | 必須 | SGD の廃止。組織への接続は sf の公開コマンドだけ（フェーズ 3 だけ、Metadata API を Node 標準の `https` で直接呼ぶ。5 章） |
| R5 | Windows の Git Bash・macOS（Bash 3.2）・Linux・GitHub Actions で同じに動く | 必須 | シェルは Bash 3.2 の範囲。重い処理は Node（標準ライブラリだけ）の 1 ファイルに集める（3.4） |
| R6 | 既存の運用を壊さない | 必須 | 同じコマンド名・同じワークフローのまま動く（**今の `wf-metasync.yml` を配り直さなくても動く**）。警告 + 確認・伝播・未プッシュの push は、そのまま（7 章） |
| R7 | 中断・再実行に強い | 高 | フェーズ 1・2 は、状態を持たない（3.5）。中断時は、作業ツリーを戻す（6 章） |
| R8 | 移行のときに、結果を確かめられる | 高 | `--dry-run`（計画だけ表示）と、旧方式との並走（10.2） |

### 1.4 「完全同期」の範囲（定義）

- **対象:** `metadata.txt` の各種類を `sf project retrieve start --metadata <種類>` で取得したときに、返ってくるもの全部。
- **一致させる場所:** 「管理対象のフォルダ」（3.6）の中だけ。その中で、取得で返らなかったファイルは、削除する（例外: `.gitkeep`・`.forceignore` に当たるファイル）。
- **範囲外（現行と同じ）:**
  - 管理パッケージの部品（ワイルドカードの取得は含まない。【事実（依頼）】）
  - 標準オブジェクト（`Account` など）の `.object-meta.xml`（`CustomObject` のワイルドカードは、標準オブジェクトを含まない。【仕様・要確認】）
  - プロファイルの中身は、「同じ取得に含まれる部品」についての権限だけになる（【仕様】。現行の 1 回の取得と同じ中身。4.4 の制約の元）

## 3. アーキテクチャ

### 3.1 方針

1. **フェーズ 1 は「状態を持たない鏡像（ミラー）方式」**: 毎回、空の一時プロジェクトへ、**現行と同じ 1 回の取得**を行い、管理対象のフォルダを、その結果と同じにする。
   - 利用者の旧実装（全削除 → 全取得 → Git の差分で追加・変更・削除を認識）と、同じ考え方。違いは 2 つ。
     (a) 一時フォルダに取るため、取得が失敗しても、作業ツリーは変わらない。
     (b) 削除を反映する前に、守り（4.5.2）を通す。
   - 取得の命令は、現行と同じ（種類・1 回）。そのため、**ファイルの中身（特にプロファイル）は、現行と変わらない**。変わるのは「削除が反映される」ことだけ。
   - 時間は、現行の「全種類の取得」とほぼ同じ（現行も、毎回、全種類を取得している。【事実】手順 7）。SGD の分だけ減る。
2. **重い処理は、Node の 1 ファイル `lib/metasync.js` に集める**（境界は、この 1 ファイルだけ。`lib/typecheck.js` と同じ形）。シェルは、順序・Git・確認・ログ・sf の起動を受け持つ。
3. **組織への接続は、フェーズ 1・2 では、sf の公開コマンドだけ**。Node から組織へ直接つなぐのは、フェーズ 3（更新日時の一覧）が初めて。
4. **差分取得（フェーズ 3）は、条件付き**。プロファイルの制約（4.3）で、差分にできる種類が限られるため、効果は組織によって大きく違う【推測】。フェーズ 0 の測定で、効果を確かめてから決める（10.1）。

### 3.2 構成要素と責務

| 要素 | 責務 | 言語 | フェーズ |
|---|---|---|---|
| `bin/sf-metasync.sh` | 全体の順序・Git の操作・警告と確認・ログ・終了コード・sf の起動（`run`） | シェル | 1〜 |
| `lib/metasync.js` | `plan`（手元と取得結果の比較・削除の守りの判定・計画の出力）、`apply`（計画の反映） | Node | 1 |
| 同上 | `crosscheck`（削除する部品と、組織の一覧の突き合わせ） | Node | 2 |
| 同上 | `inventory`（Metadata API の `listMetadata`。更新日時つきの一覧）、差分の計画 | Node | 3 |
| `config/metadata-dirs.txt`（sf-tools 側・新規） | 種類 → フォルダ名の表（付録 A） | 設定 | 1 |
| `config/metasync-diff-types.txt`（sf-tools 側・新規） | 差分取得を許す種類の一覧（検証を通ったものだけ） | 設定 | 3 |
| force-* の `sf-tools/config/metadata.txt` | 同期する種類（現行のまま） | 設定 | 1〜 |
| force-* の `.forceignore` | 鏡像で「残すファイル」の判定と、取得の除外（一時プロジェクトへ写す） | 設定 | 1〜 |
| force-* の `sf-tools/metasync/inventory.tsv`（新規） | 前回の一覧（部品ごとの更新日時） | 状態 | 3 |
| `templates/.github/workflows/wf-metasync.yml` | 起動・ログイン・sf-tools の取得（SGD・Java のステップを外す） | YAML | 1（配布は任意） |

### 3.3 データの流れ（フェーズ 1）

```text
 prod の組織
     │  sf project retrieve start --metadata <metadata.txt の全種類>（1 回。現行と同じ）
     ▼
 一時プロジェクト ${TMPDIR}/sf-metasync-XXXXXX/force-app/main/default/...   ← 取得結果（B）
     │
     │  node lib/metasync.js plan  ── 手元の main の作業ツリー（A）と、B を、管理対象のフォルダごとに比べる
     ▼
 計画（plan.tsv: A=追加 / M=変更 / D=削除 / H=削除の保留 と理由）
     │  シェル: 要約を表示 → 確認（手元）。--dry-run はここで終了
     │  node lib/metasync.js apply
     ▼
 main の作業ツリー  ── git add -A -- force-app → コミット → push --no-verify → 伝播（現行のまま）
```

### 3.4 シェルと Node の境界

```text
node lib/metasync.js plan  --repo DIR --fetched DIR --types-file F --dirs-table F
                           [--recent-files F] [--allow-mass-delete] --out PLAN
node lib/metasync.js apply --plan PLAN --repo DIR --fetched DIR
（フェーズ 2）node lib/metasync.js crosscheck --plan PLAN --deleted-manifest F --org-manifest F --out PLAN
（フェーズ 3）node lib/metasync.js inventory --types-file F --api 66.0 --parallel 5 --out INV
              （標準入力に、sf org display --json の出力を受ける。5.4）
```

- **計画の形式（TSV）:** `操作<TAB>パス<TAB>理由`。操作は `A`（追加）・`M`（変更）・`D`（削除）・`H`（削除の保留）。パスは、リポジトリの根からの相対（区切りは `/`）。
- **標準出力:** 人が読む要約（件数・保留の理由）。シェルは、そのまま表示し、ログにも記録する。
- **終了コード:** `0` = 計画できた（保留なし）／ `3` = 計画できた（保留あり。S2〜S4・S6）／ `1` = 中断（引数の誤り・読めない・安全の条件）。
- **判断の分担:** 「保留にするか」は Node（データの量が多いため）。「Actions か手元か」「確認するか」「終了コードをどうするか」は、シェル。
- **テスト用の差し替え:** `SF_METASYNC_NODE`（起動する node）など、`typecheck.js` の `SF_TYPECHECK_CMD` と同じ考え方で用意する。
- Bash 3.2 の制約（連想配列なし・`mapfile` なし）のため、集合の比較は、すべて Node で行う。シェルは、ファイルを渡すだけにする。

### 3.5 状態の持ち方

#### 3.5.1 フェーズ 1・2: 状態を持たない

- 毎回の結果は、「組織の今の内容」と「`main` の `HEAD`」だけで決まる。Actions のランナーが毎回新しくても、手元で実行しても、同じ結果になる。壊れる状態がない（再実行で、必ず直る）。
- 「最近のマージ」の保留（4.5.2 の S5）は、Git の履歴から、その場で求める（状態ファイルは使わない）。

#### 3.5.2 フェーズ 3: 部品ごとの更新日時を持つ

- 持つもの: 前回の同期で見た一覧（種類・名前・更新日時）。**前回の同期の時刻は持たない**（更新日時が「前回と違うか」だけで比べる。時計のずれ・時刻の境界で取りこぼす問題を避ける。毎回変わる値を持たないため、変更がないときに、状態だけのコミットも生まれない）。

| 置き場所 | 長所 | 短所 | 判定 |
|---|---|---|---|
| **`main` の中のファイル**（`sf-tools/metasync/inventory.tsv`。同期のコミットに同梱） | 中身と状態が、同じコミットで必ずそろう（片方だけ進むことがない）。Actions・手元で共通。履歴が残り、人が読める。失われても、全件で作り直せる | 下流のブランチにも伝播する（`force-app` の外のため、リリースの対象にはならない【推測: `deploy-target.txt` 方式のため】）。大きな組織では、数 MB になりうる【推測】 | **推奨** |
| 専用のブランチ（例: `metasync-state`） | `main`・下流を汚さない | push が 2 回になり、片方だけ成功しうる（ただし、古い状態は「余分に取得する」側にずれるので、危険は小さい【推測】）。Ruleset・PAT の扱いが 1 つ増える | 次点 |
| Git notes | `main` を汚さない | `actions/checkout` は notes を取得しない。push の設定が特殊。運用者に見えにくい | 不採用 |
| Actions の cache | 速い | 手元と共有できない。7 日使わないと消える。ブランチごとに分かれる | 不採用 |
| 手元のファイル（`.gitignore` の対象） | 単純 | Actions では毎回消える | 不採用 |

#### 3.5.3 状態がない・壊れた・食い違うとき

- 読めない・形式の版が違う・`metadata.txt` の種類と合わない → その回は**全件**（フェーズ 1 と同じ）で行い、状態を作り直す。状態は「速くするための手がかり」で、正しさの根拠にはしない。

### 3.6 管理対象のフォルダと、残すファイル

- **根:** `sfdx-project.json` の `packageDirectories` の `path` に `/main/default` を付けたもの（雛形では `force-app/main/default`。【事実】`templates/sfdx-project.json`）。**`packageDirectories` が 1 つでなければ、中断する**（S8。新しい部品の置き場所が、一時プロジェクトと手元で食い違うため）。
- **管理対象のフォルダ** = 「付録 A の表で、`metadata.txt` の種類に当たるフォルダ」と「取得結果にあるフォルダ」の和集合。
  - 表にない種類（利用者が `metadata.txt` に足した種類）は、取得結果に現れたフォルダで分かる。取得結果が 0 件で、表にもない種類は、削除を判定できないため、WARNING を出し、そのフォルダは触らない。
- **フォルダを共有する種類**（`objects/` に `CustomObject`・`CustomField`・リストビューなど。`workflows/` に `Workflow`・`WorkflowRule` など）は、**フォルダ単位で鏡像にする**。
  - そのため、`metadata.txt` から `CustomObject` だけを外すと、`objects/*/*.object-meta.xml` は削除になる（現行は残る）。`--dry-run` で見える（11.2 の U11）。
- **管理対象の外は、触らない**: 根の外（`force-app` の他の場所・`sf-tools/` など）と、`metadata.txt` にない種類のフォルダ（例: 雛形にある `staticresources/`。`StaticResource` は標準セットにない【事実】`templates/sf-tools/config/metadata.txt`）。
- **残すファイル（削除の対象にしない）:**
  - `.gitkeep`（雛形の各フォルダにある【事実】）
  - `.forceignore` に当たるファイル（雛形では `**/jsconfig.json`・`**/.eslintrc.json`・`**/__tests__/**`【事実】）。LWC の Jest のテスト（`lwc/<名前>/__tests__/`）は、組織にないため、これがないと消える。
  - `.forceignore` の解釈は、`*`・`**`・末尾の `/`・先頭の `/` だけに対応する（Node で自作。追加パッケージなし）。否定（`!`）の行は、WARNING を出し、無視する（= 残すファイルが増える側に倒れるので、安全側）。

## 4. 同期のアルゴリズム

### 4.1 フェーズ 1 の手順

1. 〜5. 現行の手順 1〜5 と同じ（sf の確認・事前の確認・警告と確認・`main` への切り替え・pull）。
6. **一時プロジェクトを作る**: `mktemp -d "${TMPDIR:-/tmp}/sf-metasync-XXXXXX"`。手元の `sfdx-project.json` と `.forceignore` を写す（取得の分解の設定・除外を、手元と同じにするため）。`packageDirectories` が 1 つでなければ中断（S8）。
7. **取得**: 一時プロジェクトで、`sf project retrieve start --target-org prod --metadata <各種類> --wait <分> --json`（種類と回数は現行と同じ）。
   - 失敗（終了コードが 0 以外）で、応答が一時的なエラー（`MetadataTransferError`・`UNKNOWN_EXCEPTION`・接続の切断・503 など）なら、60 秒待って **1 回だけ**やり直す（読み取りだけのため、やり直しても安全）。成否は、終了コードで判定する（文言は「やり直すか」の判断にだけ使う）。
   - それでも失敗なら、中断する（作業ツリーは変わっていない）。
8. **計画**: `node lib/metasync.js plan`。管理対象のフォルダごとに、手元（A）と取得結果（B）を比べる。
   - B にあり A にない → `A`（追加）。両方にあり中身が違う → `M`（変更）。A にあり B にない（残すファイルを除く）→ `D`（削除）。
   - 中身の比較は、バイト単位。改行コード（CRLF / LF）だけの違いは「同じ」とみなす（`.gitattributes` で LF にそろえる設定のため【事実】`templates/.gitattributes`。違いを `M` に数えると、要約の件数が実際の Git の差分より多く見えるため）。
9. **削除の守り**（4.5.2 の S2〜S5・S7）を通し、当たった削除を `H`（保留）にする。
10. **表示と確認**: 要約（追加・変更・削除・保留の件数、削除の一覧の先頭 30 件、保留の理由）を表示する。手元では `ask_yn`（N・q は中断）。Actions 上では、表示だけ。`--dry-run` は、ここで終了する（作業ツリー・コミット・push・伝播は行わない）。
11. **反映**: `node lib/metasync.js apply`（`A`・`M` は写す、`D` は消す、`H` は何もしない）。
12. **Git**: `git add -A -- <根のパッケージのフォルダ>` → `HEAD` との差分で分岐（現行の手順 8 と同じ。差分なしで未プッシュのコミットがあれば push だけ）。コミットの 1 行目は現行と同じ（「定期更新: Salesforce変更の自動反映 (YYYY-MM-DD)」）。本文に、件数と保留の件数を書く。
13. **伝播**: push したときだけ（現行の手順 9 と同じ）。
14. **終了**: 保留（S2〜S4）があれば、終了コード 3。終了時は、一時フォルダを消す。手順 11 のあと、コミットの前に中断したときは、管理対象のフォルダを `HEAD` に戻してから（6 章）、元のブランチへ戻る（現行の手順 10）。

### 4.2 一覧の取得

#### 4.2.1 存在の一覧（フェーズ 2）

- `sf project generate manifest --from-org prod --metadata <種類>... --name org --output-dir <一時>` を **1 回**（sf の公開コマンド。1 つのプロセスの中で一覧を取るため、種類ごとに sf を起動する方式（【測定】70 回で 828 秒）にならない）。
- 管理パッケージの部品は、`--include-packages` を付けない限り含まない、と理解している【仕様・要確認】。フォルダ型（Report など）の中身まで一覧に入るかは【要確認】（フェーズ 0 の M4）。
- 削除するときだけ実行する（削除がない回は、時間を使わない）。

#### 4.2.2 更新日時つきの一覧（フェーズ 3）

- 1 つの Node プロセスから、Metadata API の `listMetadata` を直接呼ぶ（接続は 5 章）。【測定】3 種類/回で 24 回、5 並列で 2.4 秒（4023 件）。
- **3 種類/回**（`listMetadata` の上限）。並列は 5（測定した値）。
- **フォルダ型**（Report・Dashboard・Document・EmailTemplate）: まず、フォルダの種類（`ReportFolder`・`DashboardFolder`・`DocumentFolder`・`EmailFolder`）を一覧し、フォルダごとに `{type, folder}` を問い合わせる（3 つ/回）。Report・EmailTemplate は、`unfiled$public` を足す【仕様・要確認】。フォルダの多い組織では、回数が増える（フォルダ数 ÷ 3 回。【未測定】）。
- **管理パッケージの除外**: `namespacePrefix` が空でなく、`manageableState` が `installed`・`installedEditable`・`deprecated`・`deprecatedEditable` のものを除く（`unmanaged`・値なしは残す）。ワイルドカードの取得の範囲と合うかは【要確認】。
- **やり直し**: 通信エラー・HTTP 5xx・SOAP の一時的なエラーは、最大 3 回（2・4・8 秒待つ）。`INVALID_SESSION_ID` は、終了コード 4 で返し、シェルがトークンを新しくして（5.4）、全体を 1 回だけやり直す。
- **失敗の扱い**: ある種類の問い合わせが、やり直しても失敗したら、その種類は「一覧なし」とする（差分に使わず、その回は全件。削除の判定にも使わない）。
- API の呼び出し回数: 1 回の同期で「種類の数 ÷ 3 + フォルダの数 ÷ 3」回。日次の API 上限に数えられるかは【未確認】（数えられても、数十回 × 1 日 4 回で、上限に比べて小さいと見込む【推測】）。

### 4.3 種類ごとの方式の判定（フェーズ 3）

上から順に当てはめ、最初に当たったものに決める。`full` = 全件（その種類はワイルドカードで取得し、フォルダを鏡像にする）、`diff` = 差分。

| 順 | 条件 | 方式 | 理由 |
|---|---|---|---|
| 1 | 状態がない・`--full`・定期の全件の回（4.6） | 全種類 `full` | 取りこぼしの修復 |
| 2 | **文脈に依存する種類**（Profile。PermissionSet・CustomObjectTranslation は【要確認】）と、**それが参照する種類**（ApexClass・ApexPage・CustomObject・CustomField・CustomTab・CustomApplication・Layout・CustomPermission・ExternalDataSource・Flow・CustomMetadata・ExternalCredential など）= グループ P | `full`（P は 1 回の取得にまとめる） | プロファイルの中身は、同じ取得に含まれる部品の権限だけになる【仕様】。P を分ける・一部だけ取ると、プロファイルの中身が変わる |
| 3 | `config/metasync-diff-types.txt`（許可リスト）にない | `full` | 正確さ（変更で日時が動くか）を検証した種類だけを差分にする |
| 4 | 今回の一覧に、2000-01-01 より前（1970-01-01 を含む）・空の更新日時がある | その回は `full` | 【測定】14 種類で 1970 のまま。実行時に自動で検出する |
| 5 | 一覧が失敗した・前回より件数が半分以下になった | `full` | 一覧が不完全なおそれ（削除の守りに回す） |
| 6 | 変更のある部品が、その種類の 30% を超える | `full` | 分けて取るより、全件のほうが速いと見込む【推測】 |
| — | それ以外 | `diff` | |

- **許可リストの候補**（すべて検証待ち。P に入らず、【測定】で日時が付く種類、またはフォルダ型）: ApexTrigger・ApexComponent・LightningComponentBundle・AuraDefinitionBundle・FlexiPage・QuickAction・EmailTemplate・Report・Dashboard・Document・ContentAsset。FlexiPage・QuickAction がプロファイル・アプリから参照されるか（P に入れるべきか）は【要確認】。
- **差分の判定**: 前回の一覧にない、または更新日時が前回と違う部品 → 取得する。前回にあって今回にない部品 → 削除（4.5.1）。
- **「正確さ（変更したときに日時が動くか）」は未検証**のため、次の 3 つで扱う。
  1. 許可リストに入れる前に、書き込みありの検証（9.6）で、「変更で日時が進む」「削除で一覧から消える」を確かめる。
  2. 本番で、影の比較（`--verify-diff`。10.2）を行い、差分の結果と全件の結果が、10 回続けて一致した種類だけを、許可リストに入れる。
  3. 運用中も、定期の全件（4.6）で、取りこぼしを直す（取りこぼしの最大の期間は、全件の間隔）。

### 4.4 取得

#### 4.4.1 フェーズ 1: 現行と同じ 1 回

- 種類・回数を変えない（プロファイルの中身を変えないため）。`--wait` を明示する（値は、フェーズ 0 の測定で決める。仮に 120 分）。
- 並列化は、**フェーズ 1 に入れない**。理由: (a) 種類を分けると、プロファイルの中身が変わる（4.3 の 2）。(b) 同じ組織への同時の取得を、Salesforce がどれだけ並べて処理するか【未測定】。

#### 4.4.2 分割・並列（フェーズ 2b。測定で効果があったときだけ）

- グループ P は、分けない（1 本）。P 以外の種類を、種類の単位で 2〜3 組に分け、P と並べて取得する。全体の時間は、いちばん遅い組の時間になる。P が大半を占める組織では、ほぼ速くならない【推測】。
- 明示の一覧で取るときは、1 回あたり部品 2,000 件以下に分ける（10,000 ファイルの目安。【推測】Apex は 1 部品 2 ファイルなど）。
- 1 回の取得が上限を超えたら、失敗として中断する（その回の同期は行わない）。P だけで上限を超える組織の扱いは、未決（11.2 の U9）。

#### 4.4.3 差分の取得（フェーズ 3）

- 変更のある部品（`diff` の種類）の明示の一覧と、`full` の種類のワイルドカードを、1 つの `package.xml` にまとめ、取得は 1 回にする（sf の起動・認証で約 10 秒/回。【測定】）。
- `diff` の種類の反映: 取得した部品のファイルを写す（バンドル（LWC・Aura）は、バンドルのフォルダ単位で鏡像にする。バンドルの中で消えたファイルを消すため）。

### 4.5 削除の認識と守り

#### 4.5.1 削除の認識

- **フェーズ 1・2、`full` の種類:** 管理対象のフォルダの中で、取得結果にないファイル（残すファイルを除く）。
- **フェーズ 3、`diff` の種類:** 手元のファイルから、種類ごとの単純な規則で部品の名前を求め（例: `triggers/<名前>.trigger` と `-meta.xml`、`lwc/<名前>/`、`reports/<フォルダ>/<名前>.report-meta.xml`）、今回の一覧にない部品のファイルを削除する。規則は、許可リストの種類だけに持つ（規則のない種類は、差分にしない）。

#### 4.5.2 守りの一覧

| ID | 条件 | 振る舞い | `--allow-mass-delete` で解けるか |
|---|---|---|---|
| S1 | 取得の失敗（終了コードが 0 以外。JSON の `status` が 0 以外） | 中断。何も変えない | 解けない |
| S2 | 取得は成功したが、応答に問題の報告がある | 「その組織で使えない種類」の報告 → その種類のフォルダは触らない（WARNING）。それ以外の報告 → **その回の削除を、すべて保留** | 解けない |
| S3 | 消えたフォルダ: 手元に 1 件以上あったフォルダが、取得結果で 0 件 | そのフォルダの削除を保留 | 解ける（手元のみ） |
| S4 | 削除の件数が多い: 削除 > max(100 件, 管理対象のファイルの 10%)（値は仮。11.2 の U1） | 削除を、すべて保留（追加・変更は反映する） | 解ける（手元のみ） |
| S5 | 最近のマージ: 直近 24 時間に、同期以外のコミット（PR のマージ）で変わったファイル | その削除を保留（リリースの実行中・リリースの失敗の可能性。下記） | 対象外（時間がたてば解ける） |
| S6 | （フェーズ 2）削除するファイルの部品が、組織の一覧に「ある」 | その削除を保留（取得の取りこぼし） | 解けない |
| S7 | 同じファイル名の削除と追加（既定の位置以外に置いたファイルの移動） | 一覧で示す（保留にはしない） | — |
| S8 | `packageDirectories` が 1 つでない | 中断 | 解けない |

- **S5 の理由:** `main` に PR がマージされてから、`wf-release` が組織へのリリースを終えるまでの間に同期が動くと、その部品は「組織にない」ため削除され、その削除が下流（staging など）にも伝播して、作業中のブランチから消える。リリースが失敗したときも同じ。現行（削除しない）では起きなかった、**鏡像方式で新しく生まれる危険**。
  - 求め方（案）: `git log --first-parent -m --since="24 hours ago" --invert-grep --grep='^定期更新: Salesforce変更の自動反映' --name-only --format= HEAD -- <根>`（マージのコミットは、1 つ目の親との差分を見る。【要テスト】）
- **S2 の補足:** 部分的に成功したときに、`sf project retrieve start` が終了コード 0 を返すか 1 を返すかは【未確認】（フェーズ 0 の M5）。どちらでも安全になるように、S1・S2 の両方を置く。
- **保留の扱い:** 保留した削除は、ファイルを残す（= 現行と同じ状態）。次の回に、条件が解ければ削除される。
- **Actions 上:** 保留（S2〜S4・S6）があれば、追加・変更のコミット・push・伝播まで行ったうえで、終了コード 3（ジョブを失敗として表示し、気づけるようにする。11.2 の U2）。S5 だけのときは、終了コード 0（想定どおりの一時的な保留のため）。
- **手元:** 手順 10 で、要約と削除の一覧を表示して、確認を取る。`--allow-mass-delete` は、S3・S4 を解く（**Actions 上では、指定すると中断**）。S1・S2・S6・S8 は、オプションでは解けない（原因を直す）。

### 4.6 定期的な全件（フェーズ 3）

- **Actions:** その日の最初の定期実行（UTC 0 時台。cron の 1 本目）は全件。判定は、シェルで `GITHUB_EVENT_NAME=schedule` かつ `date -u +%H` が 03 未満。**ワークフローを変えずに動く**（配り直しが要らない）。
- **`workflow_dispatch`（手動・sf-init の最初の同期・`--verify`）:** 全件。
- **手元:** 既定は全件（管理者が手で動かすのは、確かめたいときのため。11.2 の U7）。`--diff` で差分。
- **状態がない・読めない・版が違う:** 全件（3.5.3）。
- 取りこぼしが残る最大の期間は、平日で約 1 日（週末をまたぐと、金曜の最初の回から月曜の最初の回まで）。

### 4.7 コミット・push・伝播

- 現行の手順 8・9 を、そのまま使う。変更点は 3 つ。
  1. `git add` の範囲を、根のパッケージのフォルダ（とフェーズ 3 の状態ファイル）に絞る（取得は一時プロジェクトに行うため、それ以外が変わる理由がない。無関係なファイルが、同期のコミットに入るのを防ぐ）。
  2. 手元の確認は、手順 10 の 1 回にする（現行の「`git status --short` を表示して確認」に代わる。二重の確認を避ける）。未プッシュのコミットだけを push するときの確認は、現行のまま。
  3. コミットの本文に、件数（追加・変更・削除・保留）を書く。1 行目は変えない（e2e の確認・履歴の検索・S5 の判定が、1 行目を使うため）。

## 5. 接続方法（Node から組織へ。フェーズ 3 で必要）

### 5.1 選択肢の比較

| 案 | 内容 | 長所 | 短所 | 判定 |
|---|---|---|---|---|
| A | `sf org display --json` の `accessToken`・`instanceUrl` を、Node 標準の `https` で Metadata API（SOAP）に渡す | 公開コマンドの出力と、公開の API だけ。手元・Actions で同じ。秘密鍵を Node で扱わない | 【事実（依頼）】今は `INVALID_SESSION_ID`（原因は未特定）。将来、`sf org display` がトークンを表示しなくなるおそれ【推測】 | **推奨**（5.3 の切り分けで動くことが前提） |
| B | Node 標準の `crypto` で、JWT ベアラーフローを自作する | sf に依存しない | 秘密鍵・コンシューマー鍵が要る。Actions にはあるが、手元の管理者にあるとは限らない（2 つの経路になる）。秘密鍵を扱うコードが増える | 予備（Actions だけ。A が動かないとき） |
| C | sf の内部の `@salesforce/core` を、絶対パスで `require` する | 動くことは確認済み【事実（依頼）】 | sf の内部の構造に依存する（OS・npm の場所・sf の更新で壊れる） | 不採用（調査のときだけ使う） |
| D | `sf org list metadata` を種類ごとに | 公開コマンドだけ | 【測定】70 回で 828 秒、8 並列で 338 秒 | 不採用 |
| E | `sf data query`（Tooling API を含む）で `LastModifiedDate` を読む（Report・Dashboard・EmailTemplate・Document は通常のオブジェクト。ApexTrigger・LightningComponentBundle などは Tooling API） | 公開コマンドだけ。レコードの `LastModifiedDate` は、意味がはっきりしている【仕様】 | 1 回の問い合わせが sf の 1 回の起動（約 10 秒。【測定】）。対応しない種類がある。バンドルの中のファイルの変更で、バンドルの日時が動くかは【未検証】 | A が使えないときの代わり（許可リストの種類だけ） |
| F | `sf project generate manifest --from-org` | 公開コマンド・1 回 | 更新日時が出ない | 存在の確認（フェーズ 2）にだけ使う |

### 5.2 推奨

- **フェーズ 1・2 では、Node から組織に接続しない**（sf の公開コマンドだけ。接続の問題が、最初の改善を止めない）。
- **フェーズ 3 は、案 A。** 前提として、フェーズ 0 で 5.3 の切り分けを行い、A が手元（Windows・macOS）と Actions の両方で動くことを確かめる。動かなければ、案 E を許可リストの種類だけに使う（遅くなるが、公開コマンドだけで済む）。

### 5.3 `INVALID_SESSION_ID` の切り分け（読み取りだけ・テスト用の組織で）

1. 同じトークンで、REST の `GET {instanceUrl}/services/data/v66.0/limits` を Node から呼ぶ → 200 なら、トークン自体は有効。
2. SOAP の宛先が `{instanceUrl}/services/Soap/m/66.0` であること（Partner API の `/u/` などではないこと）。
3. `SessionHeader` が、名前空間 `http://soap.sforce.com/2006/04/metadata` の中の `<sessionId>` であること。**名前空間を誤っても、`INVALID_SESSION_ID` になる可能性が高い**【推測】。`@salesforce/core`（案 C）が動くことは、同じ認証でトークンが通ることを示しており、要求の形の違いが原因である可能性が高い【推測】。
4. 調査のときだけ、`@salesforce/core` が送る SOAP の本文を記録して、自作の本文と比べる（製品のコードでは使わない）。
5. 判断: 1 が NG → 案 A は使えない（案 E へ）。1 が OK で SOAP が NG → 2〜4 で直す。

### 5.4 トークンの扱い

- `sf org display --target-org prod --json` の出力は、シェルの変数にもログにも入れず、パイプで Node の標準入力に渡す（`sf org display ... 2>/dev/null | node lib/metasync.js inventory ...`。`run` を使わない理由を、行にコメントする。現行の手順 2 も、同じ理由で出力を捨てている【事実】）。
- Node は、トークンを、出力・例外のメッセージ・一時ファイルに書かない。エラーは、`faultcode` と本文の先頭 200 文字だけを出し、トークンの形の文字列（`00D` で始まる長い文字列）は伏せる。
- トークンの更新: Node が `INVALID_SESSION_ID`（終了コード 4）を返したら、シェルが `sf data query --query "SELECT Id FROM Organization" --target-org prod`（sf が必要ならトークンを更新する【仕様の理解・要確認】）を 1 回実行し、`sf org display` から取り直して、1 回だけやり直す。

## 6. 失敗モードと、安全な振る舞い

| 失敗 | 検知 | 振る舞い | 再実行で直るか |
|---|---|---|---|
| sf がない・npm 版でない | `check_sf_cli` | 中断（現行） | 環境を直せば |

| 同時実行（Actions どうし） | ワークフローの `concurrency: metasync`（現行） | 1 つずつ動く | — |

## 7. インターフェース

### 7.1 既存のコマンドを拡張するか、新しいコマンドにするか

| 観点 | 既存の `sf-metasync.sh` を拡張 | 新しいコマンド（例: `sf-metasync2.sh`） |
|---|---|---|
| 配布 | sf-tools の `main` へのマージだけで、全 force-* に届く（ワークフローは、毎回 sf-tools を clone して `sf-metasync.sh` を呼ぶ。【事実】`wf-metasync.yml` Step 8・9） | 各 force-* の `wf-metasync.yml` を書き換え、`sf-sync-wf.sh` で配り直す必要がある |
| 既存の利用者 | sf-init の最初の同期・`sf-init.sh --verify`・e2e・文書の印が、そのまま使える | すべて書き換え |
| 並走（新旧の比較） | `--dry-run` で代わりができる（10.2） | しやすい |
| 切り戻し | revert → rr | ワークフローを戻す（配り直し） |

**推奨: 既存の `sf-metasync.sh` を拡張する。** 新しいコマンドの利点（並走のしやすさ）は、`--dry-run` で足りる。

### 7.2 オプション

| オプション | フェーズ | 内容 |
|---|---|---|
| `-n`, `--dry-run` | 1 | 手順 10 の表示までで終了する（作業ツリー・コミット・push・伝播は行わない）。警告と確認は出す（読み取りのみのモードも、警告と確認をセットにする決まり。`CLAUDE.md` 2.4） |
| `-y`, `--yes` | 1 | `--dry-run` のときだけ、開始の確認を省く。`--dry-run` なしで指定したら中断（push の確認を省く手段にしないため） |
| `--allow-mass-delete` | 1 | S3・S4 の保留を解く。手元のみ（Actions 上では中断）。手順 10 の確認は省かない |
| `-j`, `--json` | 1 | 意味が変わる（取得は内部で常に `--json`）。案: 取得の JSON の応答の要約を、画面にも出す（11.2 の U10） |
| `-v`, `--verbose` | 1 | 現行のまま |
| `--full` / `--diff` | 3 | 全件・差分を、明示する（既定は 4.6） |
| `--verify-diff` | 3 | 影の比較: 差分の計画と全件の計画を両方作り、食い違いを種類ごとに表示する。コミットは全件の結果で行う（10.2） |

### 7.3 終了コード

| コード | 意味 |
|---|---|
| 0 | 同期した・変更がなかった（S5 の保留だけのときも 0） |
| 1 | 中断した（何も push していない、または未プッシュのコミットが残る） |
| 3 | 同期した（追加・変更の push・伝播まで行った）が、削除の保留（S2〜S4・S6）がある |

### 7.4 冒頭コメントの案（フェーズ 1。【処理の流れ】の 1〜5 は現行と同じため、要点だけ）

```bash
# ==============================================================================
# sf-metasync.sh - Salesforce メタデータ Git 自動同期スクリプト
# ==============================================================================
# sf-init で登録した prod エイリアスの組織（本番・Sandbox どちらでもよい）から、metadata.txt の種類のメタデータを取得し、
# main ブランチの管理対象のフォルダ（【補足】）を、取得した内容と同じにする（追加・変更・削除）。差分があればコミットして
# push し、push したときは、branches.txt の main 以外のブランチへ、main をマージして push する。
# どのブランチから実行しても、main に切り替えて処理し、終了時に元のブランチへ戻る。
#
# 【使い方】
#   bash ~/sf-tools/bin/sf-metasync.sh [オプション]     # force-* ディレクトリで実行する（管理者向け）
#
# 【オプション】
#   -n, --dry-run           : 手順 10 の計画の表示までで終了する（作業ツリー・コミット・push・伝播は行わない）
#   -y, --yes               : --dry-run のときだけ、手順 3 の確認を省く（--dry-run なしで指定すると、中断する）
#       --allow-mass-delete : 手順 9 の保留のうち、S3（消えたフォルダ）・S4（削除の件数）を解く。手元でのみ
#                             （GitHub Actions 上で指定すると、中断する）。手順 10 の確認は省かない
#   -j, --json              : 手順 7 の取得の応答（JSON）の要約を、画面にも表示する
#   -v, --verbose           : コマンドの応答（出力）をコンソールにも表示する
#   -h, --help              : このヘルプを表示して終了する
#   ※ 上記以外のオプション・引数を指定すると、中断する（終了コード 1）
#
# 【処理の流れ】
#   1.〜5. （現行と同じ: sf の確認・事前の確認・警告と確認・main への切り替え・リモートの最新の取り込み）
#   6. 一時フォルダ（${TMPDIR:-/tmp}/sf-metasync-XXXXXX）に、sfdx-project.json と .forceignore を写した空のプロジェクトを作る。
#      sfdx-project.json の packageDirectories が 1 つでなければ、中断する
#   7. 一時フォルダで sf project retrieve start --target-org prod --metadata <metadata.txt の各種類> --wait <分> --json を
#      実行する。終了コードが 0 以外で、応答が一時的なエラー（MetadataTransferError など）なら、60 秒後に 1 回だけやり直す。
#      失敗したら、中断する（作業ツリーは変わらない）
#   8. node lib/metasync.js plan で、管理対象のフォルダごとに、手元と取得結果を比べ、追加・変更・削除の計画を作る
#   9. 削除の守り: 次に当たる削除を、保留にする（ファイルを残す）
#      S2 取得の応答に問題の報告がある（「その組織で使えない種類」は、その種類のフォルダだけ。それ以外は、すべての削除）
#      S3 手元に 1 件以上あったフォルダが、取得結果で 0 件 ／ S4 削除が max(100 件, 管理対象のファイルの 10%) を超える
#      S5 直近 24 時間に、同期以外のコミットで変わったファイル
#   10. 計画の要約（件数・削除の一覧の先頭 30 件・保留とその理由）を表示し、確認（Y/N）を取る。N・q なら中断する
#       （GitHub Actions 上では、表示のみ）。--dry-run は、ここで終了する
#   11. node lib/metasync.js apply で、計画を作業ツリーに反映する
#   12. git add -A -- <パッケージのフォルダ> でステージし、HEAD との差分で分岐する（現行の手順 8。確認は手順 10 で済み）。
#       コミットの本文に、件数を書く
#   13. （手順 12 で push したときのみ）branches.txt の main 以外の各ブランチへ、main を伝播する（現行の手順 9）
#   14. 終了時: 一時フォルダを削除する。手順 11 のあと、コミットの前に中断したときは、管理対象のフォルダを HEAD に戻す
#       （git checkout HEAD -- <フォルダ>・git clean -fdq -- <フォルダ>）。そのあと、元のブランチへ戻る（現行の手順 10）
#
# 【前提条件】
#   - （現行の 1〜3 と同じ）。sf のプラグインは不要（sfdx-git-delta は使わない）。node（npm 版の sf の前提のため、ある）
#
# 【補足】
#   - 終了コード: 0（同期した・変更がなかった）／ 1（中断した）／ 3（同期したが、削除の保留（S2〜S4）がある）
#   - 管理対象のフォルダ: <パッケージのフォルダ>/main/default の下の、config/metadata-dirs.txt で metadata.txt の種類に
#     当たるフォルダと、取得結果にあるフォルダ。それ以外は触らない
#   - 残すファイル: .gitkeep と、.forceignore の行に当たるファイル（否定の行 ! は無視する）
#   - （現行の補足: 未コミット・未追跡のファイル、--no-verify、branches.txt、伝播の WARNING、ログ）
# ==============================================================================
```

### 7.5 ワークフローの変更と、配布との関係

- フェーズ 1 のスクリプトは、**今の `wf-metasync.yml`（SGD・Java を入れる）のままでも動く**（`sf sgd` を呼ばなくなるだけ）。そのため、rr だけで全 force-* に届き、各プロジェクトの作業は要らない。
- 雛形からは、Step 3（Java）・Step 5（SGD）を外す。各 force-* への反映は、管理者が `sf-sync-wf.sh` で行う（任意。時間の節約だけ）。
- 雛形に `timeout-minutes` を明示するかは、フェーズ 0 の測定で決める（GitHub の既定は 360 分【仕様】）。

### 8.2 フェーズごとの見積もり

| フェーズ | 1 回の時間（見積もり） | 根拠・仮定 |
|---|---|---|
| 現行 | T_full + SGD（Actions はプラグインと Java のインストール） | SGD の差分は空（P1） |
| 1 | **T_full + 計画・反映（数秒）**。Actions は SGD・Java の分だけ短い（ワークフローを配り直した場合） | 取得は現行と同じ 1 回。計画・反映は、ファイルの読み比べだけ（DE の 1289 ファイルなら 1 秒未満【推測】。400 MB でも十数秒【推測】）。SGD・Java のインストールの時間は【未測定】（Actions のログで分かる） |
| 2 | フェーズ 1 + 削除があるときだけ 約 20〜30 秒 | sf の起動 2 回（`generate manifest` を 2 回）+ 一覧の時間【推測】 |
| 2b | max(T_P, T_他の組) + 数秒 | 並列の効果は【未測定】。T_P（グループ P）が大半なら、ほぼ同じ【推測】 |
| 3（差分の回） | 約 10 秒（`sf org display`）+ T_list + 約 10 秒（sf の起動）+ T_取得（P ∪ 日時が使えない種類 ∪ 変更分） | DE では P と日時が使えない種類（CustomObject を含む）が大半と見込まれ、95 秒から大きくは減らない【推測】 |

- **差分取得で減らせるのは、「P に入らず、日時が使える種類のうち、変更がなかった分」の取得の時間だけ。** Report・Dashboard・EmailTemplate・Document・LWC などが多い組織では効く可能性があり、Apex・オブジェクト・レイアウトが大半の組織では、ほとんど効かない【推測】。

### 8.3 大きな組織での見積もりの仮定

- 取得の時間は、部品の数・容量にほぼ比例すると仮定する【未確認】。DE は約 85 秒（起動を除く）で 1289 ファイル（約 15 ファイル/秒）。
- 利用者の旧実装の「1 時間以上（並列でも 20 分を切らない）」は、対象の種類・範囲が今の 70 種類と同じかが分からないため、そのまま比べられない【推測】。
- 一覧（Node）の時間は、部品の数とフォルダの数で増える。大きな組織では【未測定】。

## 9. テスト計画

### 9.6 更新日時の正確さの検証（書き込みあり）

- **対象の組織:** e2e 専用の使い捨ての Developer Edition だけ。予約名（`prod`・`staging`・`develop`・`main`）は拒否、組織の種類が本番なら拒否、GitHub Actions 上では拒否（いずれも `sf-typecheck.sh` の既存の守りを、そのまま使う。**緩めない**）。
- **方法:** `lib/typecheck.js` に `--mode datecheck` を足す（サンプルの定義と、名前に `SfToolsE2eMin` を含むものだけを書く・消す守りを、そのまま使う）。実行してよい sf のコマンドの一覧には、`org list metadata` だけを足す（読み取り）。
- **手順（種類ごと）:** リリース → 一覧で更新日時 D1 を記録 → 70 秒待つ → 中身を少し変えてリリース（バンドルは、メタ以外のファイルだけを変える）→ 一覧で D2 を記録（D2 > D1 か）→ 削除 → 一覧から消えたか → 結果を TSV に出す。後始末は、既存の削除の段階（null 区切り）で必ず行う。
- **分からないまま残ること:** 画面（Lightning のレポートビルダー・フロービルダーなど）での編集で日時が動くか。これは、本番での影の比較（10.2）で補う（差分が取りこぼせば、全件との食い違いとして見える）。
- 結果は、許可リスト（`config/metasync-diff-types.txt`）の候補にする。

> 利用者の想定の「最初に SGD 廃止 + 削除の認識 + 並列化」から、**並列化をフェーズ 2b に後ろ倒しにした**。理由: 種類を分けて並べると、プロファイルの中身が変わる（4.3 の 2）。効果も【未測定】のため。

### 10.2 旧方式との並走（結果の一致の確認）

- **フェーズ 1:** 旧方式（今の `main` の sf-tools）で同期した直後に、新方式で `--dry-run` を実行する。期待: 追加・変更が 0 件（改行コードの違いは数えない）、削除は「これまで残っていた古いファイル」だけ。削除の一覧から何件かを選び、組織の画面で「本当にない」ことを確かめる。
- **フェーズ 3:** `--verify-diff`（影の比較）。1 回の実行で、差分の計画と全件の計画を作り、種類ごとに食い違いを表示する。コミットは全件の結果で行うため、本番の `main` に危険はない（時間は 2 倍近くかかる）。

### 10.3 切り戻し

- スクリプトの切り戻しは、revert → rr（ワークフローは、新旧どちらのスクリプトでも動く）。フェーズ 3 の状態ファイルは、古いスクリプトでは使われないだけ（害はない）。

### 10.4 各プロジェクトでの移行時の作業

- 初めて新方式で動くとき、これまでに溜まった「組織にない古いファイル」が、一度に削除の対象になる。件数が多いと、Actions では S4 で保留になり、終了コード 3（失敗の表示）になる。
- 対処: 各 force-* の管理者が、手元で 1 回 `--dry-run` で確かめ、問題がなければ `--allow-mass-delete` で実行する。**rr の前に、利用者（各プロジェクトの管理者）への告知が要る。**

## 13. この設計の弱点（自信のない前提）

1. **文脈に依存する種類の範囲**（Profile は確かだが、PermissionSet・CustomObjectTranslation・Translations は記憶に基づく理解で、未確認）。分割・差分の設計（フェーズ 2b・3）の土台のため、M6 で外れると、作り直しになる。
2. **sf の応答の細部を、実機で見ていない**: 部分的に成功したときの終了コードと `messages` の形（S1・S2）、`generate manifest --from-org` のフォルダ型・管理パッケージの扱い（S6）、ワイルドカードが標準オブジェクトを含まないこと。
3. **大きな組織での時間の内訳を知らない**: グループ P が大半なら、フェーズ 2b・3 の価値は小さい。フェーズ 0 の結果しだいで、「フェーズ 1（+2）で十分」という結論になりうる。
4. **`INVALID_SESSION_ID` の原因**（`SessionHeader` の名前空間・宛先の誤り）は推測。外れると、フェーズ 3 は遅い案 E になる。
5. **実際の force-* のリポジトリの多様性を見ていない**: 雛形の構成（パッケージのフォルダ 1 つ・既定の位置・`.forceignore` の 3 行）を前提にしている。既定の位置以外のファイル・独自の `.forceignore`・改行コードの混在が多いと、移行時の削除・移動が想定より大きくなる。

## 15. 実測の結果と、変更の検知の設計（2026-11-01 追記）

> **位置づけ:** 4 章のフェーズ 3（差分取得）より先に作る、**「変更がなければ、取得そのものを省く」**仕組みの設計。実装は、まだ行わない。利用者の要望（組織の変更を、速く `main` に反映したい。大きな組織を使えない環境で、確かめられる範囲の測定を行った）に基づく。

### 15.1 実測の結果（Developer Edition の `develop` 組織。管理パッケージを除く）

#### 15.1.1 測定 1: 設定変更の履歴（`SetupAuditTrail`）に、変更が記録されるか

- 52 種類（`metadata.txt` の種類のうち、`sf-typecheck` にサンプルがあるもの）を、作成 → 削除した。リリース ok 52・削除 ok 52。
- 履歴に記録されたのは 112 件。**作成・削除の両方が記録された種類は 31**。**作成も削除も記録されない種類が 12**: `Report`・`ReportType`・`Document`・`EmailTemplate`・`EmailFolder`・`HomePageComponent`・`HomePageLayout`・`Letterhead`・`CustomNotificationType`・`CustomHelpMenuSection`・`CspTrustedSite`・`CorsWhitelistOrigin`。作成だけ記録された種類が 4（`LightningMessageChannel`・`DashboardFolder`・`ContentAsset`・`ExternalServiceRegistration`）。
- 履歴と時間の窓の対応は、時刻による割り当てのため、種類ごとの細かい数には誤差がある。確かなのは「12 種類は、まったく記録されない」点。
- **意味:** レポート・ドキュメント・メールテンプレートは、利用者が画面から日常的に編集する種類だが、履歴に残らない。**履歴だけで「変更なし」と判定すると、これらの変更を見逃す。**

#### 15.1.2 測定 1b: 履歴に出ない種類で、更新日時の一覧が使えるか

- `EmailTemplate`・`Report`・`ReportType`・`Document`・`Letterhead`・`HomePageComponent` の 6 種類を、作成 → 変更 → 削除した。**6 種類とも、「一覧に出る」「変更で更新日時が進む（デプロイとの差は 6〜11 秒）」「削除で一覧から消える」を満たした。**
- 未測定: `CspTrustedSite`・`CorsWhitelistOrigin`・`HomePageLayout`・`CustomNotificationType`・`CustomHelpMenuSection`。`EmailFolder` は、履歴にも出ず、更新日時も 1970 のため、どちらでも判定できない。

#### 15.1.3 既出の測定（再掲）

- 一覧の取得: `sf` を種類ごとに呼ぶと 1 回約 10 秒（70 種類で 338〜828 秒）。1 つの Node プロセスから API で呼ぶと、70 種類が 14 秒（順に）／ 2.4 秒（5 並列）。
- 全件取得: 1289 ファイルで 53〜95 秒（`sf` の起動・認証の約 10 秒を含む）。
- 更新日時が 1970 のまま使えない種類: 管理パッケージを除く 31 種類のうち 14 種類（`CustomObject`・`Settings`・`SharingRules`・`CustomObjectTranslation` など）。ただし、このうち `CustomObject`・`SharingRules`・`Workflow` などは、履歴には記録される（15.1.1）。

### 15.2 方式: 種類ごとに、検知の方法を決める

| 区分 | 検知の方法 | 該当する種類 |
|---|---|---|
| **A 履歴** | `SetupAuditTrail` に、前回の同期より後の記録があるか（1 回の問い合わせ） | 15.1.1 で記録が確認できた 31 種類 |
| **B 更新日時の一覧** | 種類ごとの `listMetadata`。前回の一覧より、更新日時が進んだ・件数や名前が変わった | 履歴に出ず、更新日時が使える種類（`Report`・`ReportType`・`Document`・`EmailTemplate`・`Letterhead`・`HomePageComponent` など） |
| **C 検知できない** | 毎日 1 回の全件取得でだけ反映する | 両方で確認できない種類（`EmailFolder`・未測定の種類・履歴の確認がない `Settings` など） |

- 区分は、**種類ごとの表（`config/metasync-detect.txt` の案）**に持ち、**確認が済んだ種類だけ**を A・B に入れる。表にない種類は C。
- 履歴の `Section`（分類名）は、**組織の言語で表示が変わる**（例: 「Apex クラス」）。そのため、`Section` の文字列で種類を絞らない。**A は「前回の同期より後に、記録が 1 件でもあるか」だけ**で判定する（種類の区別をしない）。

### 15.3 アルゴリズム（変更の検知。`sf-metasync.sh` の取得の前に行う）

1. **前提:** 状態ファイル（15.4）が読める・版が合う・「その日の最初の定期実行」でない・`--full` でない・`--dry-run` でない。満たさなければ、検知を飛ばして、通常どおり全件取得（フェーズ 1 の動き）。
2. **A:** `SELECT COUNT() FROM SetupAuditTrail WHERE CreatedDate > <前回の同期の時刻 − 10 分>` （余裕の 10 分は、時計のずれと、記録の遅れの分）。1 件以上 → **変更あり**。
3. **B:** 区分 B の種類の一覧を取り、状態ファイルの前回の記録（種類ごとの「最新の更新日時」「件数」「名前の一覧のハッシュ」）と比べる。最新の更新日時が進んだ・件数または名前が変わった → **変更あり**。
4. 2・3 のどちらかが「変更あり」→ **全件取得**（フェーズ 1 と同じ）。どちらも「変更なし」→ **取得を省き**、「変更はありませんでした（検知）」で終了する（コミット・push・伝播はしない）。
5. 検知の途中で、**問い合わせが失敗・不完全**（履歴の問い合わせの失敗、一覧の失敗、認証切れ）→ **全件取得に切り替える**（検知の失敗が、取りこぼしの原因にならないようにする）。
6. 全件取得に進んだとき、成功したら、状態ファイルを更新する（15.4）。

- **全件取得を省くだけ**で、一部だけを取る（部分取得）ことは、この段階では行わない。**変更があれば、必ず全件**（正確さは、フェーズ 1 と同じ）。部分取得は、4.3 の許可リストの検証が済んだあとの、別の段階。
- **取りこぼしの最大の期間:** 区分 C の種類の変更だけが、翌日の全件取得まで反映されない（最大約 1 日）。A・B の種類は、次の定期実行（最大 3 時間後）で反映される。

### 15.4 状態

- **置き場所:** `main` の中のファイル `sf-tools/metasync/state.json`（3.5.2 の推奨どおり）。同期のコミットに同梱する。ただし、**変更を検知しなかった回は、コミットしない**（状態だけのコミットを作らない）。そのため、状態の時刻は「最後に全件取得した時刻」になる。検知の基準もこの時刻を使う。
- **内容:** `version`・`lastFullSyncAt`（最後に全件取得して成功した時刻。UTC）・区分 B の種類ごとの `newest`・`count`・`hash`。
- **壊れたとき・食い違うとき:** 読めない・`version` が違う・`metadata.txt` の種類と合わない → その回は全件取得（状態は、速くするための手がかりで、正しさの根拠にはしない）。

### 15.5 見込みの時間と、条件

- 変更がない回: 認証の確認（`sf org display`。Linux の Actions で数秒）＋ 履歴の問い合わせ ＋ 区分 B の一覧（数種類。Node から 1 秒前後）。**全体で数秒〜10 秒の見込み**【推測。履歴の問い合わせの時間は未測定】。
- 変更がある回: 検知の時間（上）＋ 全件取得（フェーズ 1 と同じ）。
- Actions の準備（チェックアウト・Node・sf の導入。約 1〜2 分）は、検知で省けない。変更がない回の短縮は、**全件取得の時間（規模に比例）**が上限。

### 15.9 測定 2: 規模を増やしたときの時間（2026-11-01・`develop` の組織）

測定用の Apex クラス（名前は `SfToolsE2eMinScale<番号>`。1 件あたり約 0.7 KB）を、一時的に作成し、`metadata.txt` の 70 種類で測った。測定のあとは、すべて削除した（残り 0 件を確認）。

|---|---|---|---|---|
| 基準（追加なし） | 1404 | 60〜112 秒（3 回: 112.7・59.8・106.1） | 3.0〜3.8 秒 | — |

|---|---|
| 履歴の件数の問い合わせ（`SELECT COUNT() FROM SetupAuditTrail WHERE CreatedDate > …`） | 0.2〜0.3 秒（記録 1400 件の中から、20 件の変更を検知: 件数 20） |
| `ApexClass` の一覧で、変更の検知（20 件が新しい更新日時で出る） | 一覧の取得は 3〜15 秒（実行ごとのばらつきが大きい）。変更 20 件を検知 |

#### 15.9.1 分かったこと

- **全件取得の時間は、ファイル数に素直に比例しなかった。** 1404 → 8404 ファイルで、60〜112 秒 → 114〜123 秒。同じ条件の実行ごとに ±50% ばらつく（基準だけで 60〜112 秒）。`ApexClass` は 1 件あたりが軽いため、この規模では、**実行ごとの固定的な時間（組織側の処理の待ち）が大きい**と見られる。重い種類（`Profile`・`CustomObject`・Flow など）が多い組織の時間は、**この測定からは分からない**。
- **検知は十分に速い。** 履歴の問い合わせ 0.2〜0.3 秒、一覧（70 種類）3〜5 秒。変更がない回は、検知だけで終わり、全件取得（約 60〜120 秒）の**十数分の一**になる見込み（認証の確認の時間は別）。
- **履歴は、デプロイで部品ごとに 1 件ずつ記録される**（1400 件のデプロイ → 1400 件。20 件の変更 → 20 件）。件数が多くても `COUNT()` は速い。
- **部分取得は速い。** 20 件の変更だけなら 10 秒（全件の 1/6〜1/12）。ただし、`Profile` などの文脈依存の種類（4.3）は、この測定に含まれていない。
- **取得のファイル数の上限（10,000）に近づく。** 8404 ファイルでも取得できた。これより大きい組織では、1 回の取得が上限を超えるため、種類を分けて取る必要がある（11.2 の U9）。
- **削除のデプロイは遅い**（1000 件で約 3.5 分）。テスト用の大量のコンポーネントの後始末には、時間を見込む。

#### 15.9.2 設計への影響

- 15.3 の「変更がなければ取得を省く」は、**検知の時間が小さい**ことが確かめられた。実装する価値がある。
- 規模が大きいほど効果が増えるかは、**重い種類が多い組織で測るまで分からない**。この測定の範囲（8404 ファイル）では、全件取得が 2 分前後で収まっており、**「変更がない回は数秒」**が主な利点になる。
- 部分取得（15.3 の最後の段落で見送った段階）は、**20 件の変更なら 10 秒**で済むことが確かめられた。許可リストの検証（4.3）を済ませたあとの段階として、有望。
- 全件取得の時間が、実行ごとに ±50% ばらつくため、**速度の評価は、複数回の平均で行う**（1 回の比較では、判断を誤る）。

### 15.11 実装（フェーズ 2。2026-11-01）

- **場所:** `lib/metasync.js` の `detect`（読み取りのみ。sf の呼び出しは同時に 4 つまで）、`bin/sf-metasync.sh` の検知フェーズ（手順 5 の中）、`config/metasync-detect.txt`（区分の表）、`templates/.github/workflows/wf-metasync.yml`（cron と `--full`）。
- **接続方法:** 15.6 の案 a（`sf data query` と `sf org list metadata`）。`@salesforce/core` は使わない。
- **モード（環境変数 `SF_METASYNC_DETECT`。Actions では Variable）:** `off`（既定。従来どおり、毎回、全件取得）／ `shadow`（検知はするが、取得は常に行う。検知が「変更なし」なのに実際は変更があれば、WARNING で一覧を出す）／ `on`（「変更なし」なら取得を省く）。段階 3（影の比較）で問題がなければ、既定を `on` にする。
- **`--full`:** 検知が「変更なし」でも、取得する。毎日 1 回の cron（UTC 0:00）と、手動の実行に付ける。区分 C の種類の変更を、毎日 1 回は反映するため（最大約 1 日の遅れ）。
- **状態ファイルの更新の規則（15.4 の見直し）:** 状態を書くのは、**検知が「変更あり」または「不明」だったときだけ**（全件取得と反映が成功したあと）。変更なしの回は書かない。これで、毎日の `--full` が「変更なし」なら、状態だけのコミットを作らない。検知が変更ありなのにファイルが変わらなかったとき（組織の管理の操作の記録など）は、基準の時刻を進めるために、状態だけのコミットになる。このコミットは、下流のブランチへ伝播しない。
- **基準の時刻:** `lastFullSyncAt` = 検知の開始時刻（取得の前）。取得の最中の変更は、次の回に検知される。履歴の問い合わせは、この時刻の 10 分前を基準にする。
- **失敗の扱い:** 一覧・履歴の失敗、状態の破損や設定（種類の一覧・区分の表）の不一致は、すべて「不明」→ 全件取得。検知は、取得を省くための手がかりで、正しさの根拠にしない。削除の判定には使わない（削除は、これまでどおり、全件取得の結果と S1〜S8 で決める）。
- **未プッシュのコミットがあるとき・`--dry-run`・`--full`:** 検知が「変更なし」でも、取得する。
