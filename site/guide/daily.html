🔁 日々の開発の流れ

変更を書いて、確かめて、送る。毎日くり返す一連の操作です。すべて、force-* フォルダの中で実行します。ふだんは、ランチャー（メニュー）の番号を押すだけで進められます。コマンドを直接打つことも、もちろんできます。

全体の流れ

自分専用の組織で、実際に試したいときだけ、②のあとに「自分の組織に反映」を使います（自分の組織で、実際に反映する）。共有の環境（本番など）への反映は、PR をマージすると、自動で行われます。

ランチャーで進める（おすすめ）

毎日の操作は、ランチャーのメニューから、番号を 1 つ押すだけで実行できます。コマンドの名前を覚える必要は、ありません。コマンドを直接打つこともできます（慣れている方は、そちらでも構いません）。便利なので、ランチャーをおすすめしています。

ランチャーは、自動で開きます

sf-job.sh や sf-start.sh を実行すると、最後に、ターミナルでランチャーが自動で開きます。閉じてしまったときや、VS Code のターミナルで使いたいときは、force-* フォルダの中で、次のように打ちます（sf-l まで打って Tab キーを押すと、補完されます）。

sf-launcher.sh

やりたいことから、押す番号を引けます。

やりたいこと押す番号コマンドで打つなら
ターゲットファイルの書き方を確かめる1 Checksf-check.sh
変更を GitHub に送る2 Pushsf-push.sh
次の PR の出し先を知る3 Nextsf-next.sh
反映できるか確かめる（dry-run）4 Dryrunsf-dryrun.sh
自分専用の組織に、実際に反映する5 Deploysf-deploy.sh
前日の続きなど、作業を再開する6 Startsf-start.sh
接続先の組織を切り替える7 Restartsf-restart.sh
  • 終わると、メニューに戻ります。q で終了します。コマンドが失敗しても、ランチャーは終わりません（エラーを読んで、直して、もう一度押せます）。
  • VS Code のターミナルでは、6 と 7 は表示されません（VS Code が、二重に開かないようにするためです）。1〜5 を使います。
  • sf-job.sh（新しい作業を始める）は、メニューにありません。force-* フォルダの外の、作業フォルダで実行するためです（基本の使い方）。始めたあとは、ランチャーが自動で開きます。
  • ランチャーは、force-* フォルダの中でだけ使えます。
  • 番号を指定して、1 回だけ実行することもできます（例: sf-launcher.sh 4）。検索して選びたいときは、sf-launcher.sh --fzf（fzf が必要です）。

ターゲットファイルを書く

ターゲットファイルは、「何を反映するか」「何を削除するか」を書いておくファイルです。release/<ブランチ名>/ の下にあります（force-XXXX フォルダの中の sf-tools フォルダです。パソコンに置いた ~/sf-tools とは、別のものです）。

ファイル役割
deploy-target.txt反映するメタデータを、並べて書く
remove-target.txt削除するメタデータを、並べて書く

書き方は、ターゲットファイルの書き方を見てください。

反映できるか確かめる（dry-run）

🎛️ ランチャーの [4] Dryrun コマンドで打つなら:

sf-dryrun.sh

実際には反映せずに、接続中の組織で「反映できるか」だけを確かめます。本番を変えずに、安心して試せます。

  • 結果の見方: 成功か失敗かが、ターミナルに表示されます。
  • 失敗したとき: エラーの内容が表示されます。ターゲットファイルや、変更の内容を直して、もう一度実行してください。ログは、force-* フォルダの中の sf-tools/logs/ にも残ります。

sf-release.sh を、オプションなしで実行しても、同じ dry-run になります。

自分の組織で、実際に反映する（sf-deploy）

🎛️ ランチャーの [5] Deploy コマンドで打つなら:

sf-deploy.sh

接続中の、自分専用の組織（Sandbox・Developer Edition・Scratch Org）に、変更を実際に反映します。自分の環境で動きを確かめたいときに使います。

共有の環境には、反映できません

本番・staging・develop といった共有の環境には、パソコンから反映できない仕組みです（実行すると、確認の前に止まります）。共有の環境へは、GitHub に変更を送り、レビューを通して、PR をマージします。そうすると、自動で反映されます。

変更を送る（sf-push）

🎛️ ランチャーの [2] Push コマンドで打つなら:

sf-push.sh

カレントフォルダの下の変更を、まとめてコミットして、GitHub に送ります。

  • コミットメッセージは、VS Code で入力します。
  • main に新しく入った変更も、自動で取り込みます。
  • 送るのだけが失敗したときは、もう一度実行してください。まだ送れていないコミットが、送られます。
コミットする前に止まる場合

次の 2 つのときは、コミットする前に、エラーで止まります。コミットだけが手元に残って、送れない状態を作らないための仕組みです。

  • ブランチの上にいないとき（detached HEAD）
  • 保護ブランチ（branches.txt のブランチ。main など）の上にいるとき

そのときは、sf-job.sh で作った、作業用のブランチに移ってから、もう一度実行してください。

PR の状況を確認する（sf-next）

🎛️ ランチャーの [3] Next コマンドで打つなら:

sf-next.sh

いまのブランチが、develop / staging / main のどこまで取り込まれたかを、一覧で表示します。次に PR（取り込みの依頼）を出す先も、案内します。

自動で動くチェック（git フック）

コミットとプッシュのときに、次のチェックが、自動で動きます。何もしなくて大丈夫です。

フックいつ内容
pre-commitgit commit のときターゲットファイルの書き方を確認します。エラーがあれば、コミットを止めます
pre-pushgit push のときターゲットファイルの書き方を確認し、main などの新しい変更を取り込みます。main / staging / develop の上からも、これらへも、直接は送れません（PR を通します）。新しい変更を取り込んだときは、そのプッシュは止まります（もう一度プッシュすると、通ります）
困ったときは

うまく動かないときは、トラブルシューティングの「開発者の方へ」を見てください。コマンドの詳しい説明は、開発者向けコマンドにあります。
