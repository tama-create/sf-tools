✅ 動作の確認（--verify）

sf-init.sh で作ったプロジェクトが、実際に動くことを確かめます。本物のリポジトリと、本物の Salesforce 組織を使って、リリースと削除までを、通しで試します。

安心して使うための、3 つのポイント
  • 入るのは、誰も使わない Apex クラス 2 つだけです（SfToolsE2eHello と、そのテスト SfToolsE2eHelloTest）。ほかのものには、触れません。
  • 最後に、自動で削除します。本番の組織（main）にも、同じ手順で入れて、削除します。
  • 途中で止まって残ったときも、--cleanup で消せます（使い方）。
管理者専用です

実際のリポジトリに、PR とコミットが残ります。実際の組織にも、リリースします。始める前に、実行する内容が表示されます。Enter を 1 回押すと、始まります。q で中断すれば、何も変更しません。本番（または、種類を判定できない）組織があるときは、質問の文面で、本番を含むことを明示します。

使い方

force-* フォルダの中で実行します。

sf-init.sh --verify               # 診断 → 実行内容の表示 → 確認 → リリース → 削除 → 結果
sf-init.sh --verify --plan        # 診断と、実行内容の表示だけ（何も変更しない）
sf-init.sh --verify --no-metasync # wf-metasync（Salesforce → Git の同期）の実行を、省略する
sf-init.sh --verify --cleanup     # 削除のみ（リリースの途中で止まって、組織に Hello World が残ったとき）

セットアップの最後（ステップ 9）でも、「動作を確認しますか？ [Enter = 確認する / s = あとで]」と聞かれます。Enter なら、環境全体の確認から、リリースと削除までを、続けて実行します（⏱️ 約 20 分。3 層の場合）。確認で失敗があっても、セットアップは、完了扱いです（結果と直し方が表示されます）。

流れ

  1. 診断: --status と同じ診断です。不足があれば、ここで中断します（直し方が表示されます）。

  2. 実行内容の表示: リポジトリ・段階ごとの組織の名前と種類（本番は、赤く表示）・PR の数・目安の時間。

  3. 確認: Enter を 1 回押すだけです（sf-init と同じ Git Bash で、続けて実行する想定のため、入力は最小です。sf-init.sh から呼ばれたときは、sf-init が確認済みのため、聞きません）。

  4. 環境の確認（リリースの前。NG があれば、リリースへ進まず、組織には、何も変更しません）。

    • SF_TOOLS_BRANCH が、main または development である。
    • ローカルのログ（~/sf-tools/logs）に、Token・認証 URL が残っていない。
    • wf-metasync（Salesforce → Git の同期）を、手動で 1 回実行し、成功する（JWT ログイン・sf-tools の取得を含む）。main の組織の変更が、main にコミットされることがあります。手前の 2 つが NG のときは、実行しません。--no-metasync で、省略できます。

  5. リリース: 同じブランチから、段階ごとに PR を出します。順番は、develop → staging → main です（ない段階は飛ばします）。各段階で、wf-validate（検証）→ マージ → wf-release と進みます。main へのマージのあとは、wf-propagate も確認します。

  6. 削除: 削除用のブランチ（remove-target.txt と、リポジトリのクラスのファイルの削除）から、同じ順に、各段階へ。組織のクラスと、リポジトリのファイルの両方が、消えます。

  7. 結果: 段階ごとの成功・失敗を表示します。

段階ごとに確認すること

  • その段階の組織への JWT ログインが、成功した。
  • ほかの段階のログインのステップが、実行されていない（別の組織に入っていない）。
  • 接続ユーザー（SF_USERNAME_*）が登録されていて、ログに、そのユーザーが出ている。
  • ログに、Hello World のクラス名が出ている。

組織へのログインは、不要です（ワークフローの実行結果で確認します）。

注意

  • リポジトリに、PR とコミット（追加と削除）の履歴が残ります。作業用ブランチ verify-hello-* は、検証の最後に、自動で削除します（PR の履歴は、PR の番号で残ります。途中で止まったときは、調査のために、ブランチを残します）。Slack に、段階ごとに、数通の通知が届きます。
  • リリースの間、組織が、短時間、占有されます。作業の少ない時間帯に、実行してください。
  • ブランチ保護で、PR のマージが拒否されると、その段階で止まり、PR が残ります。
  • 検証用と同じ名前のクラス（SfToolsE2eHello / SfToolsE2eHelloTest）のファイルが、すでにリポジトリにあるときは、実行しません。上書きして、削除してしまうからです（前回の検証の残りなら、--cleanup で消せます）。組織だけにある同名のクラスは、検出できません。--cleanup は、この固定名のクラスだけを削除します。
  • 失敗したとき: リリースのあとで止まった場合は、組織に Hello World が残ることがあります。残った段階と、sf-init.sh --verify --cleanup（削除のみ）を、表示します。
  • gh のアカウントは、リポジトリのオーナー（組織の管理者）にしてください。
  • GitHub Actions の上では、実行できません。
  • 対象にする段階は、リモートにあるブランチから決まります。main は必須です。staging があれば staging も、develop と staging の両方があれば develop も対象です。
  • 終了コードは、すべての確認が成功したとき（--plan を含む）が 0、失敗した確認がある・途中で止めたときが 1 です。ログは ~/sf-tools/logs/verify.log に、実行のたびに新しく書かれます。

パターン別のサンプルの確認（--components）

sf-init.sh --verify --components                  # パターン別のサンプルを、develop の組織だけに、リリースして、削除する
sf-init.sh --verify --components --validate-only  # 検証（dry-run）だけ。マージせず、組織には、何も反映しない（オブジェクト系も含む）
sf-init.sh --verify --components --with-objects   # オブジェクト系（トリガー・Layout・オブジェクト・項目）も、リリースして、削除する

Hello World（Apex だけ）の代わりに、書き方のパターンが違うコンポーネントを、小さく 1 つずつ試します。develop の組織にリリースして、削除します。全種類を試すものではなく、「種類ごとに、ターゲットファイルの書式（[files] / [members]）・パス・名前の書き方が違っても、リリースの仕組みが動く」ことの確認です。

パターンサンプル
1 ファイル + -meta.xmlApexClass（本体・テスト・トリガーのテスト）／ ApexTrigger
バンドル（フォルダ単位）LWC（[files] に .js を指定）／ Aura（[members] で指定）
単独の XMLFlow（Draft。検証のみ）／ PermissionSet
名前に空白・ハイフンLayout（SfToolsE2eHello__c-SfToolsE2eHello Layout）
フォルダ付き・名前に $EmailTemplate（unfiled$public/SfToolsE2eHello）
1 ファイルに複数メンバーCustomLabels（リポジトリに、すでに labels のファイルがあるときは、上書きを避けるため、含めません）
親子（オブジェクト系）CustomObject（SfToolsE2eHello__c）／ CustomField（Note__c）／ ApexTrigger ／ Layout
オブジェクト系について

オブジェクト系（ApexTrigger とそのテスト・Layout・CustomObject・CustomField）は、--validate-only（何も作らない）では、常に検証します。リリースと削除の通しには、既定では含めません（--with-objects で含めます）。カスタムオブジェクトは、削除しても、15 日間は、削除済みの状態で名前が予約されます。ごみ箱から消すまで、同じ API 名では作り直せません。そのため、通しをくり返すと、2 回目から失敗します。

  • 対象は develop の組織だけです（develop・staging・main の 3 層の構成のみ。それ以外は、拒否します）。staging・本番の組織には、入れません。
  • 流れ: サンプルと deploy-target.txt を載せた PR を develop 向けに出す → wf-validate（dry-run）→ マージ → wf-release。続けて、削除を行います（既定は 1 段階。--with-objects のときは 2 段階: 段階 1 はトリガー・テストクラス・LWC・Aura・Flow・権限セット・メールテンプレート・labels、段階 2 は項目・オブジェクト。参照するものを先に消すためです）。
  • --validate-only: サンプルの PR を出して、wf-validate（dry-run）の成功を確認し、PR はマージせずに閉じます。組織には、何も反映しません（目安 4 分）。
  • 目安の時間: リリースと削除の通しで、約 7 分（--with-objects: 約 10 分）。
  • Flow は、検証のみ（--validate-only）で検証し、リリースと削除の通しには含めません。接続ユーザーに、API で Flow を削除する権限がない組織があり（insufficient access rights on cross-reference id。Flow 型・FlowDefinition 型のどちらでも拒否されます）、削除できずに組織に残ってしまうためです。--cleanup は、リポジトリの Flow のファイルを削除します。組織に残った Flow は、画面（設定 → フロー）で、手動で削除してください。
  • Layout は、オブジェクトの最後の 1 つにできないため、削除対象にせず、オブジェクトの削除に任せます。
  • 名前は、すべて SfToolsE2eHello 系で、誰も使いません。ほかのファイルを、上書きしません（検証用と同名のファイルが、develop にすでにあるときは、実行しません）。
  • 途中で止まって、組織に残ったときは、sf-init.sh --verify --components --cleanup（削除のみ。--with-objects でリリースしたときは、--with-objects も付けます）で消します。失敗したときの案内にも、付けるべきコマンドが表示されます。--cleanup は、何度実行しても通ります（組織にすでにないものがあっても、エラーにしません）。前回の検証が残した labels のファイル（サンプルのラベルだけのもの）も、サンプルのものとして、削除します。

メタデータの種類ごとの可否の確認（sf-typecheck.sh）

管理者専用（個人用の組織）

実行の前に、警告と確認が表示されます（-y で省略できます）。GitHub Actions 上では実行できません。

個人用の組織で、メタデータの種類ごとに、リリースと削除ができるかを確かめ、可否の表（config/metadata-capability.txt）を作ります。この表は、sf-check.sh が、ターゲットファイルの確認に使います。

sf-typecheck.sh --org ALIAS                        # リリースして、削除する
sf-typecheck.sh --org ALIAS --validate-only        # 検証だけ（組織には、何も反映しない）
sf-typecheck.sh --org ALIAS --only ApexPage,Queue  # 種類を絞る
sf-typecheck.sh --list                             # 確認する種類の一覧だけ（組織には接続しない）
sf-typecheck.sh --coverage                         # 確認の進み具合だけ（組織には接続しない）
オプション内容
--org ALIAS接続先の組織のエイリアス（--list と --coverage 以外では必須）
--validate-only検証だけを行います。削除の列は「unknown」（実行していない）のままです
--only A,B指定した種類だけを確認します（--list に出る名前と完全に一致するもの。一致しない名前は無視され、1 つも一致しなければ 0 種類で正常終了します）
--out FILE結果の表の出力先（既定: カレントフォルダの sf-typecheck-result.txt）。すべての種類を処理し終えたときだけ書きます
--list確認する種類の一覧を表示して終了します
--coverage変更セットで扱える種類のうち、確認済み・未確認の数を、区分ごとに表示します（リリースも削除も ok / リリースのみ ok / ng または limited を含む / 判定できない / 表にない）。種類の一覧は、ok 以外の 4 区分だけ出ます
-y, --yes冒頭の確認（Y/N）を省略します（警告ボックスは表示されます）

安全のための拒否

次のどれかに当たると、何も実行せずに中断します。

  • GitHub Actions の上（--list と --coverage は、実行できます）
  • 接続先が、予約名（prod / staging / develop / main）
  • 組織の情報を読み取れない、または、組織の種類が本番、あるいは判定できない
  • Sandbox が「個人用」か「共有」かは、判定しません。個人用の組織を指定していることを、確認してから実行してください。
  • 作成・削除するのは、名前に SfToolsE2eMin を含むものだけです。LWC は、名前が小文字で始まる決まりがあるため、sfToolsE2eMin の綴りも認めます。それ以外は、認めません。名前の条件に当たらないものがあると、その時点で全体を中断します。それまでに処理した種類は、実行済みのまま残り、結果の表も書かれません。
  • リリース・削除に失敗した種類（ng）があっても、終了コードは 0 です（警告が表示されます）。結果の表で判断してください。
