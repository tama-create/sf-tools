⚙️ ワークフローの更新（sf-update-workflows）

ワークフローは、GitHub の上で自動で動く処理です（検証・リリース・同期など。GitHub Actions という仕組みで動きます）。このページでは、sf-project が作る 4 つのワークフローが、いつ・何をするのかと、作成済みのプロジェクトのワークフローを、sf-tools の最新の雛形に合わせて更新する sf-update-workflows.sh の使い方を説明します。

このページの要点
  • ワークフローは、sf-project.sh が作る 4 つ（validate・sequence・release・metasync）です。
  • リリースは一方通行です。develop → staging → main の順に、同じコミットのまま上げます。前の段階に出していないコミットは、次の段階へ出せません（一方通行の決まり）。
  • main / staging への PR は、3 つのチェック（対象ファイル確認・デプロイ検証・順序チェック）が通らないと、マージできません（ブランチ保護が効いているとき）。
  • リリースや同期の処理の中身は、ワークフローが動くたびに、sf-tools から取ってきます。sf-tools の更新は、すぐに届きます。
  • ただし、ワークフローのファイル自体の修正は、自動では届きません。sf-update-workflows.sh（管理者専用）で、作成済みのプロジェクトに反映します。
  • sf-update-workflows.sh --check は、差分があるかを調べるだけです（何も変更しません）。

自動で作られるワークフロー

sf-project.sh は、プロジェクトの .github/workflows/ に、次の 4 つを作ります（雛形は sf-tools/templates/.github/workflows/）。GitHub の Actions の画面には、2 列目の名前で表示されます。

ファイル画面での名前いつ動くか手動の実行
wf-validate.yml[validate] デプロイ前検証PR の作成・更新（ソースブランチへのプッシュ）・再オープンのとき。マージ先のブランチは問いませんできない
wf-sequence.yml[sequence] マージ順序チェックmain / staging への PR の作成・更新・再オープンのときできない
wf-release.yml[release] デプロイmain / staging / develop への PR をマージしたあとできない（PR を通らずに組織へ出す道をなくすため。失敗したリリースのやり直しは、その実行の「Re-run jobs」）
wf-metasync.yml[metasync] メタ同期平日（月〜金）の日本時間 9:00 / 12:00 / 15:00 / 18:00（3 時間おき）に自動で。9:00 の回は、毎日 1 回の全件取得（--full）です。GitHub の混雑で、開始が遅れることがあります。変更の検知を使うときは、Variable SF_METASYNC_DETECT（off / shadow / on。未設定は off）を設定します。一覧の指紋を使うときは、Variable SF_METASYNC_FINGERPRINT（off / shadow / on。未設定は off。shadow は検証用で取得を省かない。on は「変更なし」の回の取得を省く）を設定します。秘密情報の検査は、Variable SF_METASYNC_SECRET_SCAN（off / shadow / on。未設定は shadow = 警告だけ。on は疑いで止めて Slack に通知）で切り替えます。追加の取得（レポート・ダッシュボード・メールテンプレート・標準オブジェクト上の項目などを、名前を指定してもう 1 回取る）は、Variable SF_METASYNC_EXTRA（off / on。未設定は off）で切り替えます。公開リポジトリでは、常に取得せずに止まりますできる（どのブランチで実行しても、main を同期する）
  • 「手動の実行」は、GitHub の Actions の画面の「Run workflow」ボタン（workflow_dispatch）のことです。手動で実行できるのは、wf-metasync だけです。sf-project のセットアップの最後と、sf-project.sh --verify は、wf-metasync を、この方法で起動します。
  • どのワークフローも、ブランチへの直接のプッシュでは動きません。PR のタイトル・本文の編集でも動きません。
  • 以前の wf-propagate.yml（main の変更を、staging・develop のブランチへ自動で伝える）は、2026-11-26 に廃止しました（下りの伝播はしない）。作成済みのプロジェクトに残っていれば、sf-update-workflows.sh --remove wf-propagate.yml で消します。
  • コンフリクト（同じ場所を、別々に変更した衝突）のある PR では、wf-validate と wf-sequence は動きません（GitHub が、マージした結果を作れないためです）。コンフリクトを解消すると、動きます。

マージの前の必須チェック

必須チェックとは、「これが成功しないと、PR をマージできない」と、ブランチ保護（GitHub の Ruleset）に登録したチェックです。sf-project は、main と staging のブランチ保護（protect-main / protect-staging）に、次の 3 つを登録します。

必須チェックの名前どのワークフローのジョブか失敗するとき
対象ファイル確認wf-validate と wf-sequence の両方にあります（PR の画面には、同じ名前で 2 つ並びます）ふつうは失敗しません（デプロイの対象があるかを調べるだけです）
デプロイ検証wf-validate同じブランチから前に同じ段階へ出した部品が、今回のターゲットファイルから抜けているとき（一方通行の決まり）・dry-run の検証が失敗したとき
順序チェックwf-sequencePR の先端のコミットが、前の段階にまだ出ていないとき（一方通行の決まり）・環境ブランチ（main / staging / develop など）から、直接 PR を出したとき
  • 必須チェックは、ジョブの名前だけで照合されます。ワークフローの名前を付けた形（以前の sf-project が登録していた「validate / 対象ファイル確認」など）は、永久に満たされず、PR をマージできなくなります。以前のバージョンで作ったプロジェクトは、トラブルシューティングを見てください（sf-project.sh --status が、食い違いを見つけます）。
  • デプロイの対象がない PR（ターゲットファイルが空）では、デプロイ検証 と 順序チェック は、スキップされます。スキップされたチェックは、GitHub の仕様で、成功として扱われるので、マージは止まりません。
  • develop などへの PR には、ブランチ保護がないため、検証が失敗しても、マージは止まりません（結果の表示だけです）。
  • ブランチ保護が作れなかったプロジェクト（無料プランの非公開リポジトリなど）では、どのチェックが失敗しても、マージは止まりません。また、リポジトリの Admin（管理者の権限を持つ人）は、ブランチ保護を迂回できます。その場合でも、一方通行の決まりを破った PR は、マージのあとの wf-release が、組織へ出しません（最後の守り）。
ジョブの名前を、変えないでください

ワークフローのジョブの名前（name:）を手で変えると、必須チェックが永久に満たされず、PR をマージできなくなります。wf-release の「リリース対象確認」は、必須チェックの「対象ファイル確認」と、わざと別の名前にしてあります（同じ名前だと、先の段階の PR で付いた成功が、次の段階の PR の必須チェックを、満たしてしまう恐れがあるためです）。

wf-validate（デプロイ前検証）

PR を作るたび・更新するたびに、sf-release.sh を、検証のモード（dry-run。組織には反映しない）で実行し、結果を PR にコメントします。

  • 検証の前に、一方通行の決まりの「積み重ね」（R2）を確かめます（sf-promote-check.sh --pr <番号> --only stack）。破っていれば、dry-run をせずに失敗し、抜けた部品を、ログと PR のコメントに出します。
  • ジョブは 2 つです。対象ファイル確認 が、ターゲットファイル（sf-tools/release/<ソースブランチ名>/ の deploy-target.txt・remove-target.txt）に中身があるかを調べ、あれば デプロイ検証 が動きます。
  • 検証に使う組織は、マージ先で決まります。main への PR は main の組織、staging への PR は staging の組織、それ以外（develop や、作業用のブランチへの PR）は develop の組織です。develop の組織を登録していない構成（main のみ・main + staging）で、main / staging 以外への PR を出すと、ログインで失敗します。
  • PR へのコメントは、毎回、新しく追加します。見出しは「✅ 検証成功」「❌ 検証失敗（終了コード）」、途中の手順で止まった・取り消された・時間切れになったときは「⚠️ 検証が実行されませんでした」です。長いログは、末尾の 3000 文字だけを載せます。
  • Slack には通知しません。

wf-sequence（マージ順序チェック）

main / staging への PR で、一方通行の決まりの「順序」（R1）と「環境ブランチ」（R3）を確かめます（sf-promote-check.sh --pr <番号> --only sequence）。段階の並びは、main ブランチの sf-tools/config/branches.txt で決まります（PR の中身ではなく、常に main から読みます）。

PR の状態チェック知らせ方
順序どおり（PR の先端のコミットに、前の段階のリリースの印がある）成功何もしません（以前に ⛔ のコメントがあれば、「✅ 問題ありません」に書き換えます）
順序外（前の段階に、まだ出していないコミット。前の段階に出したあとに変更したときも）失敗（マージできない）PR へのコメント「⛔ 一方通行の決まりにより、この PR はマージできません」（理由つき）と、Slack
環境ブランチから直接出した PR失敗（マージできない）PR へのコメント「⛔ 環境ブランチからの PR は、許可されていません」と、Slack
  • 緊急の修正（Hotfix）も、例外にしません。develop → staging → main の順に上げます（2026-11-26 に、以前の「順序外でも止めない」をやめました）。
  • 開発者が sf-pr.sh（ランチャーの「次の PR」）を使う限り、順序は守られます。このチェックは、GitHub の画面で直接 PR を作ったときの備えです。仕組みの詳細は、sf-pr.sh の説明にあります。
  • Salesforce の組織には、接続しません。

wf-release（デプロイ）

PR を main / staging / develop にマージすると、マージ先に対応する組織へ、sf-release.sh --release でリリースし（組織に反映し）、結果を Slack に通知します。

  • ジョブは 2 つです。リリース対象確認 がターゲットファイルに中身があるかを調べ、あれば リリース実行 が動きます。中身がない・マージせずに閉じた PR では、リリースせず、Slack にも通知しません。
  • 最後の守り: リリースの前に、一方通行の決まり（R0〜R3 のすべて）を、もう一度確かめます（sf-promote-check.sh --pr <番号>）。破っていれば、組織へ出さずに失敗し、Slack に「リリースを止めました」と通知します。ブランチ保護が効かない組織で、止められた PR をマージしても、組織は変わりません。
  • リリースの印: リリースが成功したら、PR の先端のコミットに、コミットの状態（commit status）sf-tools/released-<段階> を付けます。次の段階への PR の順序の確認は、この印を見ます。
  • ログインするのは、マージ先の組織だけです（main → main の組織、staging → staging の組織、develop → develop の組織）。
  • Slack には、成功なら「リリース成功」、失敗・取り消しなら「リリース失敗」を、リリース先・ブランチ・PR・日時・ログの URL と一緒に送ります。
  • 続けてマージしても、同じマージ先へのリリースは、1 つずつ順に動きます（待っている実行は、取り消されません。ただし、待ちが 100 を超えると、GitHub の仕様で、それ以降は取り消されます）。マージ先が違うリリースは、並行して動きます。
  • wf-metasync のプッシュ（PR を通さないプッシュ）では、動きません。staging / develop の組織にリリースするのは、その段階への PR をマージしたときだけです。
  • 手動の実行（Run workflow）は、できません（workflow_dispatch を外しました）。失敗したリリースは、その実行の画面の「Re-run jobs」でやり直します（同じ PR・同じコミットなので、一方通行の決まりも同じく確かめます）。

一方通行の決まり（develop → staging → main）

開発したものは、develop → staging → main の順に、同じコミットのまま上げます。staging で問題が出たら、staging では直さず、開発の環境で直して、develop から出し直します。この決まりは、ワークフローが仕組みとして強制します（判定の本体は、sf-tools の sf-promote-check.sh の 1 か所です。設計: doc/one-way-promotion-design.md）。

決まり内容確かめる場所
R0 前提main の branches.txt が読める・段階の並びが正しい・フォークからの PR でない（判断できないときは、止めます）すべて
R1 順序PR の先端のコミットに、1 つ前の段階の「リリースの印」があるwf-sequence・wf-release
R2 積み重ね同じブランチから、前に同じ段階へ出したリリース（まだ main まで届いていないもの）の部品が、すべて、今回のターゲットファイル（反映か削除）に入っているwf-validate・wf-release
R3 環境ブランチ環境ブランチ（branches.txt のブランチ）から、直接 PR を出していないwf-sequence・wf-release
  • ターゲットファイルが空の PR は、どの決まりも確かめず、リリースもせず、印も付けません（組織に何も出ないためです）。
  • リリースの印（sf-tools/released-<段階>）は、wf-release が付けたもの（github-actions[bot]・このリポジトリの wf-release.yml の成功した実行・同じコミット）だけを信じます。人が付けた印・ほかのワークフローの印は、無視します。
  • develop に出したあとで変更して push すると、先端のコミットが変わるので、develop から出し直しになります（sf-pr.sh が、次の出し先を develop と案内します）。

下りの伝播はしない

main の変更を、staging・develop のブランチへ、サーバーで自動で伝えることは、しません（以前の wf-propagate と、sf-metasync.sh の伝播を、2026-11-26 にやめました）。

  • main の最新は、開発者のパソコンで、sf-push.sh が、push のたびに、開発のブランチへ取り込みます。サーバーで全員のブランチへ一斉にマージしないのは、作業中の手元と食い違い、コンフリクトを解けないためです。
  • 環境のブランチ（develop・staging）は、PR で上がってくる開発のブランチだけで更新されます。main とずれてかまいません（組織と中身の一致は、上りの PR の一方通行の決まりで守ります）。

wf-metasync（メタ同期）

main の組織（prod の名前で接続した組織。本番とは限りません）から、最新のメタデータを取得し、main の「同期の対象のフォルダ」を、取得した内容と同じにして（追加・変更・削除）、変更があれば、コミットしてプッシュします（Salesforce の組織の内容を正とします）。処理の中身は sf-metasync.sh です。

  • 取り込むのは main だけです。staging / develop のブランチへは、伝えません（下りの伝播はしない。開発のブランチが、sf-push.sh で main を取り込みます）。
  • このプッシュは PR ではないので、wf-release は動かず、組織へのリリースは行われません。
  • 変更がなければ、何もせずに成功します。
  • 削除の安全の守り: 組織で削除されたものは、main からも消えます。ただし、削除が多すぎるとき・フォルダごと消えたとき・取得に問題の報告があったときは、削除だけを保留（ファイルを残す）にして、追加・変更だけを反映し、ジョブを失敗として表示します（対処）。
  • Slack には、成功・失敗のどちらも通知しません。失敗に気づくには、Actions の画面か、sf-project.sh --status の「直近の実行」を見ます。
  • 定期の実行と手動の実行が重なっても、1 つずつ動きます（待っている実行は、新しい実行に置き換えられます）。手元で実行した sf-metasync.sh と重なってプッシュが拒まれたときは、失敗するので、もう一度実行してください。

Secrets と Variables

ワークフローは、GitHub に登録した Secret（隠しておく値）と Variable（見えてもよい値）を使います。登録は sf-project が行い、あとからの登録し直しは、秘密の情報の管理のページで説明しています。

使うもの使うワークフロー用途
SF_PRIVATE_KEY・SF_CONSUMER_KEY_*・SF_USERNAME_*・SF_INSTANCE_URL_*validate・release・metasyncSalesforce の組織に、JWT 認証でログインする
PAT_TOKENmetasync だけリポジトリの取得と、main へのプッシュ（ブランチ保護を迂回し、ワークフローのファイルの変更を含むプッシュもできるようにするため。PAT の持ち主が Admin であることが前提）
SLACK_BOT_TOKEN・SLACK_CHANNEL_IDrelease・sequenceSlack への通知（release はリリースのたび（止めたときも）、sequence は順序外・環境ブランチのとき）
SF_TOOLS_BRANCH（任意）validate・release・metasync取ってくる sf-tools のブランチ。ふつうは登録しません（未登録なら main）

PR へのコメント（validate・sequence）・一方通行の確認（PR・コミットの状態・Actions の実行を読む）・リリースの印を付けること（release）には、GitHub が自動で用意する Token を使うので、登録は要りません。

雛形に合わせて更新する（sf-update-workflows.sh）

sf-update-workflows.sh            # 雛形との差分を表示し、確認のうえ、上書きする
sf-update-workflows.sh --check    # 差分があるかだけを調べる（何も変更しない）
sf-update-workflows.sh --remove wf-old.yml   # 雛形から廃止されたワークフローを削除する

sf-project.sh で作成済みの force-* に、あとから、ワークフローの修正（不具合の修正・安全対策など）を反映するコマンドです。sf-tools の雛形と、プロジェクトのワークフローを比べて、違いを表示します。確認のうえで、雛形の内容に上書きします。

いつ必要になるか

validate・release・metasync は、動くたびに、公開されている sf-tools（ふつうは main ブランチ）を取ってきて、その中の sf-release.sh や sf-metasync.sh を使います。そのため、リリースや同期の処理の中身の修正は、sf-tools が更新されれば、すべてのプロジェクトに、すぐ届きます（sf-update-workflows.sh は要りません）。

sf-update-workflows.sh が必要なのは、ワークフローのファイル自体（起動の条件・ジョブの構成・使う Secret など）が、雛形で直ったときです。これは、作成済みのプロジェクトには、自動では届きません。届いていないかは、sf-update-workflows.sh --check で調べられます。

管理者専用

CI/CD（リリース・検証）の動作が変わるため、実行の冒頭に、赤い警告ボックスと確認（Y/N/q）が表示されます（--check を除く）。sf-refresh.sh などから、自動では実行されません（利用者の意思なく、ワークフローが書き換わるのを防ぐためです）。

更新の手順（おすすめ）

  1. sf-job.sh で、ジョブ名 system-日付（例: system-20261006）の作業用ブランチを作ります。ブランチは、GitHub の最新の main から作られます。ワークフローの更新の PR だと、名前で分かります。

  2. そのフォルダで sf-update-workflows.sh を実行し、差分を確認して Y を答えます。

  3. git diff .github/workflows/ で、内容を確認します。

  4. sf-push.sh で、コミットしてプッシュします（ワークフローのファイルをプッシュするには、workflow の権限（スコープ）のある GitHub の認証が必要です）。

  5. PR を出して、マージします。develop / staging がある構成では、通常の変更と同じ順序（develop → staging → main）で、PR を出します（次の PR 先は、sf-pr.sh が案内します）。ワークフローのファイルだけの変更は、ターゲットファイルが空なので、一方通行の決まりの確認とリリースは、スキップされます。

動作

  • force-* フォルダの中で、作業用のブランチの上でしか、実行できません。環境ブランチ（sf-tools/config/branches.txt のブランチ。main / staging / develop など）の上や、ブランチの上にいないとき（detached HEAD）は、中断します。sf-tools に雛形のフォルダがないときも、中断します。
  • sf-tools（~/sf-tools）が最新であることが必須です。実行すると、まず、sf-tools が GitHub（origin）の同じブランチより遅れていないかを確かめます。遅れていれば、確認（Y/N/q）のうえで sf-tools を更新し、更新した sf-tools で、同じオプションのまま、もう一度、自動で実行します（古い雛形で、プロジェクトのワークフローを書き換えないためです）。
    • origin に接続できない・更新を断った（N / q）・更新に失敗した・sf-tools に未コミットの変更や未プッシュのコミットがある場合は、中断します。
    • もう一度実行したあとも、まだ遅れているときは、確認と更新は行いますが、3 回目の実行はせずに、中断します。
    • 最新かどうかを確かめられないとき（sf-tools が Git のリポジトリでない・ブランチの上にいない・origin に同じブランチがない）は、警告を出して、続行します。
    • --check は、何も変更しない（読み取り専用の）ため、sf-tools を更新せず、遅れていれば中断します。
  • 比べるとき、改行コード（CRLF / LF）だけの違いは、差分とみなしません。雛形にあってプロジェクトにないファイルは「新規」、内容が違うファイルは差分（diff -u）を表示します。
  • 差分を表示したあと、もう一度「雛形の内容で、上記のワークフローを上書きします。よろしいですか？」（Y/N/q）と聞かれます。N / q なら、何も変更しません。
  • 自動でコミット・プッシュはしません。
  • 雛形にないワークフローは、変更せず、名前を表示するだけです。--remove で、雛形から廃止されたものだけを削除できます（雛形にあるものは、削除できません）。
  • --remove が受け付けるのは、wf-old.yml のような、フォルダを含まないワークフローのファイル名（英数字で始まり、.yml / .yaml で終わるもの）だけです。.github/workflows/ にないファイルを指定したときは、中断します。確認は、冒頭の警告のあとと、削除の直前の、2 回あります。--remove のときは、比較・上書きはしません。
  • --check は、差分なしで終了コード 0、あれば 1 を返します。複数のリポジトリを見回るときに使えます。ただし、1 は「中断」（sf-tools が遅れている・環境ブランチの上、など）のときにも返るので、「差分あり」とは区別できません。
  • --check と --remove は、同時に指定できません（エラーで終了し、何も変更しません）。
  • -v（--verbose）は、コマンドの応答をコンソールにも表示します。ほかの引数は、「不明なオプションです」で中断します。
  • GITHUB_ACTIONS=true の環境でも、警告と確認は省略しません。
  • ログは ./sf-tools/logs/sf-update-workflows.log です（実行のたびに作り直します）。
ブランチ保護（Ruleset）は、変更しません

sf-update-workflows.sh が書き換えるのは、.github/workflows/ のファイルだけです。雛形で、必須チェックになっているジョブの名前が変わったときは、ブランチ保護の必須チェックも、合わせて直す必要があります。食い違いは、sf-project.sh --status が見つけます（直し方は、トラブルシューティング）。
